# To-dos, cards and the task board

**The board.** The user has one task board: every to-do, wherever it was made, in `<data>/todos.json` (`{v, rev, items, seen}`, 0600, written by `ChatStore.updateBoard` on the store's one queue). An item's creator is `addedBy` (`user` or an agent) and `from.chatId`, the chat it was made in (null: added on the board itself), with `from.turn`, `from.itemId` (the reply it came from) and `from.label` (its group in a chat's panel, kept so it outlives the reply). `done`/`removed` are `{at, by}` or null, `last` the latest action, `rev` the file's rev when the item last changed. A removed item stays as a tombstone, never pruned, because sync never deletes and a pruned one would come back from the other machine. `seen` maps `seenKey(chat, agent)` (`<chat id>/<agent>`: a session is a chat's, a room member's in a room) to the rev that session last read. Caps: 300 characters a title, 50 per `add`, 500 open on the board; an `add` skips text equal to an open item's anywhere on the board. Pure rules are `shared/src/todos.ts`; `TodoService` (`core/todos/todoService.ts`) does every change through `updateBoard` and broadcasts `todos:changed {rev}` on every change, also at an unchanged rev (a turn's `settle`, a task's own change), so clients refetch on every event and never dedupe by rev. A read of a missing file is an empty board and makes no file; a corrupt one is set aside as `todos.json.bak-<time>` (`parseTodoFile`, which also reads an item from before the board, with no `from.chatId`, as made on the board). **Migration.** Before the board each chat had `chats/<id>.todos.json`, and My to-dos was `todos.json`. At every start, before the hub serves a call, `migrateToBoard` (`core/todos/boardMigration.ts`, wired in `app.ts`) reads every per-chat list that parses (`ChatStore.legacyTodoLists`; one that does not stays, logged by chat id only), copies its cards' files into `attachments/todos`, folds the items in with that chat as their `from.chatId` (`mergeLegacyTodos`: ids kept, an id already there keeps the later `updatedAt`, so a list a sync brings back folds in again safely; one new rev for all of it, and each folded chat's sessions marked as having seen it, so no agent is told the move as news), moves My to-dos' old card files from `attachments/my-todos`, and removes the old files (`dropLegacyTodos`). A failure leaves the old files for the next start and logs only its code.

**Agent tools.** `zumibot_todos` is a stdio MCP server built like `zumibot_browser`: `todoBridge.mjs` (its own `input` in `backend/vite.config.ts`) talks over a Unix socket in a 0700 `/tmp/cb-t-*` dir (`todoIpc.ts`, the browser's framing, a 1 MiB request limit so 50 items with their notes fit one add) with a capability token issued per CLI attempt, bound to `{chatId, agent, turn}` and revoked when the attempt ends; the bridge names no chat or item of its own. The server entry sets `alwaysLoad: true`: an agent with many MCP tools gets MCP tools deferred behind the CLI's tool search, and without it such an agent never found the to-do tools. Its tools are `list` (every open item on the board with its creator, assignee and status, each card's notes cut at 300 characters, and what others changed since this session last saw the board), `add` (into New with nobody assigned, the agent as creator and the calling chat as `from.chatId`; an optional `description` of up to 4 000 characters), `check` and `remove` (any item on the board), the card tools `ask_user` and `ready_for_review` (see Cards and tasks), and `comment {id, text}` (any card on the board; see Comments). It goes in a second `--mcp-config` of every run of every agent, and into every `/btw` side run (`ChatService.sideBrowser`), so the tool definitions and the prompt-cache prefix never change; the side run's deny hook still blocks the calls. The bridge's parsed call is the wire form the server parses again (`parseTodoWire`), so a field keeps its tool name until the IPC hands it to the service. `ChatService` answers `mcp__zumibot_todos__*` permission requests itself in both permission modes: no card, no stored rule, no Jev hint. Every text an agent writes (titles, groups, notes, questions, options, review summaries) is scrubbed with its vault values before it is stored (`scrubbedTodos`). The calls show no tool rows; the turn's last item gets a `todos` touch (added count; ticked, unticked and removed texts; `asked` questions; `review`) instead, shown as a chip and one line per change (`state/todoLine.ts`). Every tool answer ends with the open board, cut at 4 000 characters with a pointer to `list`.

**What the agent reads.** The appended system prompt always holds the fixed `TODO_SYSTEM` paragraph (`todoPrompt.ts`): the board, its columns (New, To do, Blocked, In progress, In review, Done), that a card has a creator and an assignee and an agent starts on one when the user moves it to To do, every agent sees the whole board, add only when asked, one actionable line each, everything needed to act on an item in its description (the card may go to an agent that never sees the chat), the reply's headings as groups, skip what is already open, tick when done, remove only when asked, ids for the tools only. Before each turn the message may end with a note (`TodoService.note`, keyed by the chat the turn runs in and its agent): a new or seeded session (`force`; Edit, Resend and version switches resume from before the hidden turns' notes), a `/todo` turn, or a session that never saw the board while something on it is not its own work, get the open items (what others changed first, then the open list, cut at 4 000 characters); otherwise only what others changed since the session's `seen`, with "Call list to see the whole board.", so a busy board does not cost every turn its whole list. An empty board adds nothing unless the turn is a `/todo` one. The note is never a chat item. The turn records the rev the note read, and `markSeen` stores it (never moving back) when the turn ends, so a change made while the reply ran is still news next turn; an empty board gets no file from it. A task chat's message also ends with its card note (see Cards and tasks). A failure of the touch, `settle`, `markSeen` or `endTurn` is logged by its code only and never fails the turn. Changing `TODO_SYSTEM` or the tool list misses every chat's prompt cache once, when it ships.

**`/todo`.** A message starting with `/todo` (reserved name, like `btw`; `splitTodo`) asks for a list (never for an agent without the `bridges` cap, ACP and remote: the `/` menu hides `/todo` and the commands that make to-dos then, `offersTodo`; `ChatService.runTurn` and `GroupService` refuse them with their own sentence, `todoRefusal` (not the cards' `bridgeRefusal`), before any run, so Resend, routine runs and workflow steps are covered, a room while any member lacks the cap; `chats:send` and `chats:edit` refuse up front too), alone or before a command (`/todo /check-inbox`). The handlers strip it, resolve the command from the rest, and store `todo: true` on the user item with `text` as typed. A command with `todos: true` sets the flag by itself, a routine run of it too (`RoutineRunner` passes the resolved command's flag to the queue); a leading `/todo` in a routine prompt stays plain text, since a routine's command must lead its saved prompt. At read time `readAs`/`withCommands` drop the `/todo` and append `TODO_REQUEST` ("Put the action items of your reply on the user's task board…, each with a description that holds everything needed to act on it") for every agent that reads the message, in a room too; only the moderator, which reads `text`, does not see it. So Edit and Resend keep it (an edit's flag comes from its new text, Resend keeps the old one). `TaskQueue` and `GroupService` pass the flag through (`todoAsked` in a room when an unseen message has it). Zumi Bot sets `todos: true` on list-style commands and adds the to-do tool names to any `tools:` list it writes; `AgentStore.save` adds every `TODO_TOOLS` name to every non-empty `tools:` list (`withTodoTools`), since with `--agent` a `tools:` list limits the agent to what it names.

**A chat's panel.** The side panel's **Open To-dos** view (`TodosPanel.tsx` over `state/todosPanel.ts` and `useTodos.ts`, `todos:list(chatId)`) lists the board's items made in that chat: open ones grouped by the reply that made them, newest group first, under the agent's headings; ticked ones in one folded **Done** list (open state kept per device, newest 100 then Show more). No row has a checkbox, nor a status field: a row starts with its column's dot (`todo-row-dot`), which is also its status menu (`StatusDot`: a click lists every status with its dot, the current one checked; arrows move, Esc or a click elsewhere closes it, and the side panel leaves Esc to an open `[role="menu"]`). A pick moves the card right there as a drop on the board does (Done ticks it), so the title keeps the row's width; Needs approval or Chat deleted shows beside the title when it applies; To do or In progress on a card nobody has opens the card under the row with the assignee picker up, and the move follows the pick; remove with a 6 second **Undo** toast; "by agent" or the member's name on an agent tick. The input row adds an item made in this chat by the user (`todos:add(text, chatId)`), grouped under "Added by you" without Show in chat; the agent's next note tells it ("added by the user"). **Show in chat** is offered for a reply that is loaded, or while older pages are unloaded, and hidden once the whole history is loaded without it. Each row opens as a card (below). An add from the panel fires the workflow `todo` event with the chat (`onAdded`); one made on the board has no chat to name and fires none.

**The board page** (`TodoBoard.tsx`, `state/todoBoard.ts`, `useBoard.ts`; Grid: `TodoGrid.tsx`, `state/todoGrid.ts`). Two views, switched in the head: **Kanban** (the columns below) and **Grid**. Kanban is the default each time the app starts; the choice is App state, so it lasts while the page is left and opened again, and a reload starts on Kanban. Grid is one table of every card the board holds, open and the done ones it loaded (`gridRows`), with Status first (the same picker as the drawer, beside the agent's chat state and open questions), then Title (notes and files hints), Assignee, Creator, Created and Updated; a click on a column's head sorts by it (`nextSort`: again flips it, dates start newest first; the default is status in board order, oldest first), Nobody sorts last either way, the head and the Title column stay in view while it scrolls (Status slides under Title), the filters apply, and **Show completed** (a switch, off by default, kept per device in `localStorage` as `zumibot.grid.showDone`) adds the done cards: while it is off a footer says how many the filters would show (every done card, the older ones not loaded included, when no filter is set), with Show. A row (but not its own controls) opens the card's drawer, and its Status moves the card as a drop does, asking who first when nobody has it. **Bulk delete.** Each row starts with a box to pick it, and the head's box picks every shown row (a dash while only some are); the picks stick to the left edge with Title. While any picked row is shown, a bar over the table says how many with **Clear** and **Delete N**, which removes them all through `todos:remove` (in batches of `REMOVE_BATCH` 200, the handler's cap; `useTodoActions.removeIds`) with the page's one Undo toast, and closes the drawer when its card was among them. Only picked rows still shown count (`selectedRows`), so a filter or another tab's removal never deletes a card the user cannot see; Esc clears the picks while no drawer is open. Picks are the grid's own state and drop when it unmounts (`toggleSelected`, `toggleAll`, `selectionState` in `state/todoGrid.ts`). The rail's To-dos opens it at `/todos`, with no column beside it (as the Inbox); `/todos/<task id>` opens that card in the drawer (`todosFromPath`; `/todos/mine` from before the board reads as `/todos`, and a link from then that named a chat names no card, so the board just opens). `useBoard` fetches `todos:board` (`boardOf`: every open item, the newest `BOARD_DONE_MAX` 200 done ones and how many are done in all) when the socket connects and after every `todos:changed` (300 ms trailing debounce, an older answer never replaces a newer one, a failed fetch keeps the last board); the app holds it always, since it also feeds the rail badge and the Inbox. A column per status (`TODO_STATUSES`; `boardColumn` reads the stored status with the task chat's `inFlight`, approval count and existence the app already holds): **New** (the default, also for a card assigned to an agent: nothing starts; oldest first), **To do** (its agent should start), **Blocked** (a question waits on the card, or approval cards wait in its chat), **In progress**, **In review** (the agent finished; the user checks), **Done** (newest tick first; the count is every done item). A task chat deleted mid-work shows its card in New. A card shows its title (inline markdown, so its links open; it is a `div role="button"`, not a button, since a link cannot sit in one, and a click on a link does not open the card; the Grid's Title is drawn the same way) with the notes and files hints, and a ⋯ menu with **Open** (the drawer), **Copy link** (`/todos/<id>` on this origin) and **Remove** (with the page's Undo toast), then labelled rows with an icon each: Status (a tag tinted with its column's `--status-*` colour), Created by, and, when they apply, Agent (Working…, Needs approval, Chat deleted) and Questions; its foot holds the assignee's avatar (`avatarInitials`: "You", or an agent's two letters on its own colour (its ink, `agentInk`, so the initials keep 4.5:1); dashed when nobody has it; on an open card it is the assignee menu) and how long ago it was made (amber past 3 days). **The assignee changes in place**: on an open card, the Kanban card's footer avatar and the Grid's Assignee cell are a menu (`AssigneeMenu`, `TodoAssignee.tsx`: Nobody, You, every givable agent) that assigns without the drawer; an agent gets the folder the drawer's picker would start at (`quickFolder`: the card's own while its agent stays, else the creator chat's, else `app.newChatFolder`), and one given a card in To do or In progress starts at once, as from the drawer. No checkbox ticks a card (the Grid's boxes only pick rows to delete): Done (or the drawer's Status) ticks a card, another column unticks it. A card is dragged (HTML5 drag and drop) to any other column (the drawer's Status moves it without a drag): `todos:move(id, status)` (see Cards and tasks); a card nobody is assigned to, moved to To do or In progress, opens its drawer with the assignee picker up instead, and the move follows the pick (`dropAction`, `assignThen`). A column's ‹ button collapses it to a slim strip (its dot, count and name read top to bottom; a click opens it again) that still takes a drop; which columns are collapsed is kept per device in `localStorage` (`zumibot.board.collapsed`, read with `parseCollapsed`, so a bad value reads as none) and never synced. The header adds a card made on the board (yours, New, unassigned). **Filters** (`TodoFilters.tsx`, `BoardFilter`, `matchesFilter`) apply to both views: a search (every word, any case, in the title or notes; Esc clears it), the assignee (anyone, you, unassigned, or an agent from `boardAssignees`) and the creator (anyone, you, or an agent from `boardCreators`), with **Clear filters** while any is set. On a phone (below 800 px) the board keeps the screen: the head drops its title (the bar above names the page) and holds the views, the open count (hidden below 380 px) and a **Filters** button (`board-tools-toggle`) that folds the filters away and shows how many are set (`filterCount`); they start open while one is set. Wider, the add box and the filters share one row (`board-bar`): the add box takes what the filters leave, and the filters drop under it as one block when both do not fit (the search has a set width, not a flex basis, so the row measures them right). They are App state with the view, so they hold across Kanban and Grid and while the page is left, and a reload clears them. While a filter is set, Done counts its matches only and an empty column reads "No matches.". The drawer floats over the board, which dims under it (`board-scrim`: a click there, Esc or ✕ closes it, so a drag needs it closed; on a phone it fills the page and nothing dims); focus moves into it. Its head holds the previous/next stepper ("2 of 22"), the card's column ("in New"), and **Expand**/**Shrink** and ✕; its foot holds **Remove card** (with the page's Undo toast) and the keys (← → to move · Esc to close, hidden on a touch screen). The title sits in the body, at the top of the card's hero (see Cards and tasks). Expanded, the drawer becomes a dialog centered on the board, wide (up to 1 180 px), with the card on the left and its comments on the right, each column scrolling on its own and the comment box stuck to the comments column's foot (`.todo-card-main` and `.todo-card-side`, which are `display: contents` elsewhere, so the comments follow the card as one column); the choice is kept per device in `localStorage` (`zumibot.board.drawerExpanded`, `DRAWER_EXPANDED_KEY`) and applies to every card, and below 900 px the button hides and the card stays one column. In one column the body scrolls and the comment box sits under it, always in view (`todo-card-foot-box`; `TodoCard`'s `drawer.wide` says which layout, read from the expand choice and the 900 px query). **Previous / next**: the head's ‹ and › (with where the card sits, "3 of 12", hidden on a phone) and the keys ← and K, → and J (not while typing, nor with Ctrl, Alt or Cmd: `cardStepKey`) open the card before or after in the order the view shows them, filters applied (`cardNeighbors`): Kanban reads column by column, left to right, each top to bottom, collapsed ones included (`kanbanOrder`); Grid reads its rows as sorted, done ones only while Show completed is on (`gridRows`, so its sort is the board page's state, not the table's). An end stops, it never wraps; a card the view does not show (a link to a filtered-out or done one) gets no buttons. A step drops a pending assignee pick, as a click on another card does. Each column head has its status's dot (the same one sits beside the drawer's Status), and the card open in the drawer is outlined. The look takes the app's tokens only (`--accent`, `--sel-*`, and the status dots' `--status-*` tokens: New a gray, To do the accent blue, Blocked the error red, In progress orange, In review yellow, Done green, all made from the theme's own colors), so dark mode follows. The rail badge is the open cards on the user's side: every one but those an agent has in To do or In progress (`boardBadge`, `99+` past 99). The board looks at no chat (presence reports none).

**Cards and tasks** (`TodoCard.tsx`, `state/todoCard.ts`, `core/todos/taskCards.ts`, `core/todos/taskPrompt.ts`). Every item opens as a card: from a panel row (its chevron, or a click on the title that is not on a link; only inside a `TodoListContext`, with the app's `TodoCardEnvContext`, so elsewhere a row stays plain) or a board card (its drawer). The card starts with its hero: a line naming the creator (face, who, its chat as a link, the date and age), the title (in the drawer only; a panel row already shows it), then pills: **Status** (a picker that moves the card as a drop does), **Assignee** (the pill opens the assignee menu: Nobody and You apply at once, an agent opens the assign form under the pills with it chosen, to confirm the folder) and the agent's state. Then, in order: the agent's work or the attempts (**Run attempts…** in a tinted box while nobody works on it), **Notes** (an empty one is a dashed "Add notes the agent should read first" that opens the editor, which also edits the title; with notes, Edit sits on the section head), **Images** (empty: a dashed drop zone, click or drop images; with images: tiles and a dashed Add tile; under either, while room is left, a paste box: a text field that takes only pasted images, named as the composer names a pasted one, and drops pasted text) and **Comments** (with a count; empty: "No comments yet"). **Item fields**, all optional so older files and the other machine's sync read as before: `status` (`new`, `todo`, `blocked`, `progress`, `review`; absent is New, and a ticked item is Done whatever it holds: `statusOf`), `assignee` (`'user'` or an agent's name; absent is nobody), `folder` (where an assigned agent's chat runs), `description` (markdown notes, at most 10 000 characters), `files` (at most 10 attachments, under `attachments/todos/`, a folder no chat id can name), `task` (`{agent, chatId, at, review}`: the chat the assigned agent works in) and `questions` (`{id, text, options, by, at, answer}`). An older file's `mine` reads as assignee `user`, and a task without an assignee as its agent. The pure rules are `editTodo`, `assignTodo`, `setStatus`, `startTask`, `askTodo`, `answerTodo`, `reviewTodo`, `reopenTodo`, `taskTurnStarted`, `taskTurnEnded`, `askingOf`, `taskState` and `boardColumn`. An edit of the title, notes or files moves the rev with `last.action` `edited`, so agents hear of it like a tick, as do a tick and untick a move makes; assigning, other moves and a task's own changes (questions, answers, review) only restamp the item and broadcast at the same rev, so agents are not told about another chat's work. **Editing.** `todos:edit(id, {text?, description?, addFiles?, removeFiles?})` (`TodoService.userEdit`): staged ids are committed into `attachments/todos` only after the cap is checked (a failed edit takes them back), and a removed file is deleted once the edit is stored. **Assigning** (`todos:assign(id, assignee | null, folder | null)`, `TaskCards.assign`) starts nothing by itself. An agent needs a folder and refuses when unknown, broken or Zumi Bot; the folder must exist, and is remembered as the agent's last one. A new assignee drops the old agent's `task` and questions (its chat stays; a Blocked or In review card goes back to New; its card tools refuse with "The user took this task card over" when the user took it), and the old agent's running turn is stopped. An agent given a card already in To do or In progress starts at once. The picker's folder starts at the card's own folder while its agent stays, else the creator chat's folder (a worktree's checkout), else `app.newChatFolder`; **Change…** is the folder picker. **Moving** (`todos:move(id, status)`, `TaskCards.move`). To do and In progress refuse a card nobody has ("Assign it to you or an agent first."); the user's card just moves. An agent's card starts (`start`, a done card unticked first): with no live chat of that agent for the card, the card goes to To do at once (adding a worktree on a big repo is slow, and the card must not wait in its old column; a failed placement puts it back), then the chat is placed as `chats:create` does (a built-in's own folder, the folder's worktree when its toggle is on), made titled by the card with `ChatMeta.task {todoId}`, its meta pushed, the item linked (`startTask`: To do, earlier questions dropped), copies of the card's files staged, and `Task: <title>` plus the notes and the card's comments in full (`taskMessage`: author and quoted text, oldest first, the oldest left out past 8 000 characters with a pointer to `list`) submitted through the `TaskQueue` without waiting for the turn; with its chat still there, the card goes to To do and the chat is sent `CONTINUE_MESSAGE` with the comments others wrote or edited since the chat's last reply (`continueMessage`, from `replyAt`, else the task's start) (or, while its turn still runs, it just shows In progress). New and Done stop a running turn (`chatService.stop`; the chat stays); Blocked and In review only move the card. Nothing but the card is passed: never the creator chat. **The chat moves the card** (`TodoService.chatPush` and `turnEnded`, wired into the app's push and `onTurnEnd`): a task chat's meta going `inFlight` moves its card to In progress; the turn's end moves it to Blocked when a question still waits, else to In review when it ended well (also with no `ready_for_review`), else (stopped, failed) to New. Done is never moved, nor a card whose assignee is no longer the chat's agent. **The task chat.** Every turn's message ends with `taskNote` (after the board note): the card's title, how to ask (`ask_user`, then end the turn) and finish (`ready_for_review`), how many questions still wait, or that the card was removed. `AskUserQuestion` is denied there with `TASK_QUESTIONS_DENIED`, so questions reach the card, where nobody has to watch the chat. `ask_user {questions: [{question, options?}]}` (1 to 10, 1 000 characters each, up to 6 options of 120; the card goes to Blocked) and `ready_for_review {summary}` (4 000; In review) find the card through the calling chat's `task` link and refuse with a sentence for a plain chat, a removed card, one given to another chat, one the user took over, or a ticked one. A question ends a review. **Answering and writing back.** `todos:answer(id, [{id, text}])` (`TaskCards.answer`) refuses before storing when the task chat is gone, stores the answers (an answered question is never replaced), then sends them as one user message (`answersMessage`: each question quoted, its answer under it); `todos:reply(id, text)` ends a review and sends the text. Both go through the queue, so a running chat holds them. **The agent's work** section shows while the assignee is the task's agent: Open chat →, the review summary, the questions and, at its foot, a line to write to the agent (`CardReply`); a row in a chat's panel changes the card's status without opening it (see A chat's panel). **Inbox and push.** The Inbox lists one `todo` entry per open card with an open question (`askingOf` over the board the app holds), answered in place, with **Open to-do →** to its drawer (see [Inbox](inbox.md)). The task chat's turn end carries `cardQuestions` when its touch has `asked`, and its notification is a `waiting` one with `inbox: true` instead of `replied`, cleared when the chat's next turn starts (see [Notifications](notifications.md)).

**Comments.** A card holds `comments` (`TodoComment`: `{id, text, by, at, editedAt?, deletedAt?}`, markdown, at most 4 000 characters each and 200 live ones a card), by the user or any agent, on any card. The drawer's **Comments** section lists them oldest first with the author's face, age and "edited", and a box at its foot (Ctrl/Cmd+Enter posts); the user edits or deletes only their own (`todos:comment`, `todos:editComment`, `todos:deleteComment`; `commentTodo`, `editComment`, `deleteComment` refuse another author's). A board card and a grid title show a comment count hint (`cardHints`). A new or edited comment moves the rev with `last.action` `commented`, so every agent's next note says "commented by …: <title> — "<text>"" (the newest comment by that author, cut at 300 characters): that is how the user's comment reaches the card's task chat on its next turn, which `taskNote` also points out. A delete only restamps the item and leaves a tombstone (text emptied, `deletedAt`), so sync, which joins a card's comments by id in `mergeTodos` (`mergeComments`: the later edit wins, a tombstone always), never brings it back. `list` shows each card's newest 5 comments, cut at 300 characters. An agent's `comment` is scrubbed with its vault values (`scrubbedTodos`), and the turn's touch carries `commented` (the cards' titles), shown as "💬 Commented on: …". An agent rename moves each comment's `by` and `asked`.

**Threads and `@agent` in comments.** A comment may answer another (`replyTo`, always a top-level comment: a reply to a reply joins its thread, `threadRoot`); the drawer draws each top-level comment as a thread row (face, name and age, the text under them; a chat panel's card keeps bubbles, the user's tinted) with its replies under a rail (`commentThreads`; a deleted one stays as "This comment was deleted." while it has live replies, its tombstone keeping `replyTo`), and Reply, Edit and Delete under each (Delete asks in the app's `ConfirmDialog`, never a browser dialog). The comment boxes (`TodoCommentBox.tsx`) are a plain-lines Tiptap field (one paragraph per line, `promptToDoc`/`docToPrompt`, pasted text stays text, capped at `TODO_COMMENT_MAX`) with the composer's `@` list of the agents a card can go to (`givableAgents`: loadable, not Zumi Bot, with the `bridges` cap, so no ACP or remote agent) and its `MentionHighlight`: away from the caret a handle reads as the agent's display name in its color, the raw handle staying the text. The `@` and `/` lists float in a body portal (`todo-comment-pop`, fixed, placed by `popPlace` in `state/commentBox.ts`: under the box, or over it when there is more room there), so they never push the comments down nor get clipped by the drawer. Comments draw handles as chips (`MentionScope`). **Commands in comments.** A `/word` typed anywhere in the box (at the start or after whitespace, `commentSlashQuery`) opens the `/` list of the commands of every agent the comment mentions, in mention order (`commentCommandOptions`, no built-ins; grouped by agent when it mentions several); a pick inserts `/name ` (`insertCommentCommand`). On the server each asked agent reads its own commands fresh (`commandsOf`), and every `/name` in the comment that agent owns (`commentCommands` in `shared/src/commentCommands.ts`: at the start or after whitespace, then whitespace or the end, code aside; each once, in order) is filled with the comment minus every handle and named command as `$ARGUMENTS`, then added to `commentAskMessage` as "The comment runs your command /name" with the filled prompt. So `@a @b /card` runs each agent's own `/card`; an agent without it just reads the comment. A `/name` that runs (`commentCommandMarks`: owned by an agent the comment mentions) is tinted in the comment box (`CommentCommandHighlight`) and shows as the chat's command chip in a posted user comment (`remarkCommands`), in its one owner's color, neutral when several own it; any other `/word` stays text. `todos:comment(id, text, replyTo?)` goes through `CommentAsks` (`core/todos/commentAsks.ts`): the loadable agents the user's comment mentions (`findMentions`, Zumi Bot and broken files aside, at most `TODO_COMMENT_ASKS_MAX` 3) are stored on it as `asked` (a reply that mentions none goes to the agents already in its thread, `threadAgents`: those its top comment asked and those who answered, the latest first, so answering an agent needs no second `@`; a reply that names an agent asks only that one; a mention of an agent without `bridges`, an ACP or remote one, refuses the whole comment before it is stored, with `commentAskRefusal`: its chat would lack the to-do tools the message points at, and a remote one would take the card off this machine; a thread agent that has lost the cap since is left out, never asked), the comment is stored first, then each agent runs in the background in its chat for that card, `ChatMeta.cardComments {todoId}` (one per card and agent, found by that and `agentName`, kept for later mentions so it remembers the thread; concurrent mentions share one `making` promise). A new one is placed as a task's chat is (`placeAgent` in `rpc/handlers.ts`, a worktree when the folder's toggle is on) in the card's folder, else the folder of the chat the card was made in, else the agent's last folder, else home, titled `Comments · <card title>`, and is a plain chat the user can open and write in. The agent is sent `commentAskMessage` (the card's title and id for the to-do tools, its notes, the earlier comments and the comment quoted), with copies of the card's images that chat was not sent yet (`stageUnsent`, matched by name and size, so each image goes once and one added later goes with the next mention), through the `TaskQueue` under a known message id; when that turn ends, its last message before the next user message (`finalReply`, cut to fit a comment with "…(the rest is in the chat)") is posted under the comment as that agent's reply (`TodoService.agentReply`). A turn with no message (stopped, failed) posts nothing. Under the comment, a chip per asked agent reads Starting…, Working…, Answered or No answer yet with **Open chat →** (`commentAsks` in `state/todoCard.ts`, from the chat list). Edits never ask again, and an agent's own comments never ask anyone, so agents cannot loop. A server restart mid-turn loses the post (the chat keeps the answer).

**Parallel attempts.** A card nobody is working on offers **Run attempts…**: 2 to 5 agents (the same one twice is fine, engines may differ) each get the card in their own chat and their own git worktree, all made from one base commit, so their diffs compare. The set lives on the card (`TodoItem.attempts`, a `TodoAttempts`: its id, when it started, the base commit, the folder, the card text every attempt was given, a row per attempt and, once decided, the `winner`'s chat id; `failed` names picks that could not start). Each attempt's chat carries `ChatMeta.attempt` (`{todoId, setId, n, outcome?}`). The card's own `task` stays **unset** while a set runs, so the card tools refuse in an attempt chat exactly as in a plain one and nothing but the user moves the card, which sits In progress. **Keep this one** gives the card to that attempt's agent, links its chat as the card's `task`, moves the card to In review and archives every other attempt's chat through the ordinary archive path, so a worktree release that refuses a dirty folder says so and nothing is forced; a refusal is reported per attempt and that chat is left. **Cancel set** drops the set (back to New) and stops what runs, leaving the chats and their worktrees for the user to archive. Spend caps are unchanged: each attempt's turns are its agent's own, so an agent's `dailySpendCap:` applies as anywhere else, the row reads "Paused at a spend cap", and the dialog says N attempts cost about N× one plus a line for each capped agent. The pure rules are `shared/src/attempts.ts` (states, labels, picks, the lines) and `startAttempts` / `keepAttempt` / `dropAttempts` in `shared/src/todos.ts`; the service is `core/attempts/attemptSets.ts`, the UI `TodoAttempts.tsx`, `AttemptCompare.tsx` and `state/attempts.ts`. Full detail: [Review loop](review-loop.md).

**Pull requests.** A task card's "<agent>'s work" section ends with that chat's pull request, or **Open PR…** while it has none: the same box the chat's own Changes panel shows, with **Refresh** and **Send to agent** on a failing check. `TodoItem.pr` (`{number, url, state, chatId}`, optional) is the board's display copy, written only by the card's own task chat; the chat's `ChatMeta.pr` is what counts, and the checks are never copied, being volatile. Writing it restamps the item without a rev bump, like the task's other changes. See [Review loop](review-loop.md).

**Elsewhere.** Edit, Resend and version switches leave the board alone. Fork and Clone room copy no to-dos: an item lives once on the board, under the chat it was made in. Deleting a chat leaves its items on the board (the card reads "Created by … in a deleted chat", a task whose chat was deleted shows in New as Chat deleted, and To do starts a new chat) and drops only its sessions' `seen` keys. An agent rename moves its name in `addedBy`, `assignee`, ticks and removals, `last`, `task.agent`, each question's `by` and the `seen` keys (`ChatStore.renameAgent`). `sync.mjs` joins `todos.json` by item id (`mergeTodos`): the later `updatedAt` wins per item, tombstones included; the merged `rev` is the larger plus one, `seen` the smaller per key, and every item the sides disagree about is restamped to the merged rev so `changesSince` does not skip it; a `chats/<id>.todos.json` from a peer still on an older version is joined as before and moved onto the board at the next start. Design: `docs/superpowers/specs/2026-11-04-chat-todos-design.md`, `docs/superpowers/specs/2026-11-15-todo-cards-design.md` (the cards, then the board).

**Engines without `bridges` (ACP).** A task chat relies on the to-do bridge's `ask_user` and `ready_for_review`, so `givableAgents` leaves such agents out of every assignee menu and `TaskCards.assign` (and its start, for an agent that changed engine after it was assigned) refuses them with `bridgeRefusal`.
