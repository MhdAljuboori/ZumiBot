# Dispatched agents

**Dispatched agents (`core/dispatch/`, `shared/src/dispatch.ts`).** **Open Dispatched agents** in the side panel (badge "N running" while any runs, else the total) lists every subagent the chat's agents started with the CLI's `Agent`/`Task` tool, grouped by reply (newest first, "This reply" on top), a nested one indented under its parent; a row opens that agent's conversation: once it ended its final report first (markdown, small headings), then the prompt it got and its steps: its text (current models write almost none in a subagent, so the steps are mostly tool calls), its tool calls (`ToolCallRow`, Input and Result), nested dispatches as rows that open them, and "working…" while it runs. The steps fold under "N steps" (`stepsShown`) for a finished agent with a report, and stay open while it runs, when it has no report, or once the reader watched it end. The chat's Agent rows get **Watch ›** (running) or **View ›** (ended) through `DispatchLinkContext`. `streamParser` keeps a subagent's text (`subText`), every tool (`subToolUse`, `subToolResult` with `detail`) and the CLI's `task_started`/`task_progress`/`task_updated` lines (`taskStarted`/`taskProgress`/`taskUpdated`; `task_updated` names only the task, mapped through `task_started`); the subagent's prompt line and deltas stay dropped. Each `agentTurn` (not `/compact`) gets a `DispatchRecorder` from `DispatchService.begin`: an entry per dispatch keyed by its tool use id, ended by its tool result (totals and report from `tool_use_result`) or a final `task_updated`, whichever comes first. Newer CLIs hand the report back with the subagent's last call, `SubagentHandback` (`message`, `handbackMessage`), and the dispatch's result only points at it: the recorder takes that message as the report from the raw input (so up to 50 000 characters, past the 20 000 input cap) and keeps no step for it, and `agentBody` does the same at read time for entries stored before; at turn end, after the items are saved, what still runs becomes `stopped` or `interrupted` and `finish` writes it. Entries live in `chats/<id>.dispatch.json` (0600, `ChatStore.loadDispatch`/`updateDispatch`), never in chat items, so no prompt, seed or meter holds them. While a turn runs its entries stay in memory, where every read finds them, and `dispatch:changed {chatId}` goes out about once a second (never dedupe); the file is written once, at `finish` (a restart mid-turn loses that turn's entries). The service holds the stored entries and the visible Agent row ids (fed by `ChatStore`'s items listener) of the 20 chats used last, so a refetch reads nothing from disk. Caps: text, results and input JSON 20 000 characters, prompt and report 50 000, 1 000 steps (first 50, newest 950, one `gap` step), and per chat the newest 200 entries within 10 000 000 characters of JSON (`pruneEntries`; the newest always stays). Browser tools are stored with input `{}`, browser and desktop results as the fixed "… command completed./failed." lines. `dispatch:list` returns summaries of entries whose top-level Agent row is a visible item or that are live (a hidden message version hides its agents), a stored `running` entry no turn records reads `interrupted`; `dispatch:get {chatId, id, from?}` returns one entry, only the steps from `from` on unless its indexes moved (then whole, `from` 0), so `useDispatchEntry` appends. Pure UI rules are `state/dispatchPanel.ts`. Rename moves `member`; delete removes the file; fork and Clone room start without it; `sync.mjs` joins it by entry id (later `updatedAt` wins, then the same caps). A failed save logs only its code and never fails a turn. A Codex agent's subagents are recorded the same way from its `subAgentActivity` items and child threads (named by their path, with no prompt, since the spawn's message is sealed; ended `stopped` by the recorder when Stop ends the process; see [Codex agents](codex.md)).
