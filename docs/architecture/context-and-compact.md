# Context meter, Compact and keep warm

**Context meter and Compact.** `streamParser` turns the `usage` of each of the agent's own requests into a `context` event (input + cache read + cache write + output), `result.modelUsage[model].contextWindow` into the window, and `status: compacting` / `compact_boundary` into `compacting` / `compacted`. `agentTurn` saves the latest as a `ContextUse` (`ChatMeta.context`, per member in `GroupInfo.context`), coalesced like the item saves. After a compaction `used` is null until the next request, because the CLI's `post_tokens` counts only the summary, not the system prompt and tools. Edit, Resend and version switches clear the meter, and a fork starts without one. Compact (`chats:compact`, through `TaskQueue` like an edit, so sends meanwhile queue) runs `/compact <note>` as a turn on the agent's session (in a room, on one member, shown as working; a Codex agent's thread gets `thread/compact/start` and no note, see [Codex agents](codex.md)). It adds no items and never reseeds a missing session. `ChatMeta.compacting` and `ActiveTurn.compacting` show "Compacting…". The ring and its popover are `ContextMeter.tsx` over `state/contextMeter.ts`. The ring counts as full at the agent's Compact at size when it is inside the window (`meterLimit`, `compactAtOf`; per member in a room), since that is where the session compacts: "300K / 400K before compacting", amber from 75% of it, and the popover names the size and the window. Each `ContextUse` also keeps `at`, the time of its last request: the prompt cache lives an hour from it, and after that the next message writes the whole context to the cache again at full price (in the logs this was the biggest single cost). `ColdNotice.tsx` (pure rules `coldContexts`/`coldNotice` in `state/contextMeter.ts`) shows over the composer when a context of at least 200K is idle past that hour, compactable, not running, and not one the CLI compacts first anyway (its agent's `autoCompactWindow` is below its size): **Compact first** (per member in a room) runs the normal Compact, **Dismiss** hides it until that context runs again. Contexts saved before `at` existed fall back to `replyAt`. **Keep warm** (`core/btw/keepWarm.ts`, settings in `shared/src/keepWarm.ts`) stops that reload from happening at all: `ChatService` hands every saved context of a real request to `KeepWarm.note` (`onContext`), and for a context of at least 100K it pings 55 minutes after the last request, and every 55 minutes after that, until the window ends (**Settings › General › Tokens**: rooms Off/4/8/12 h, default 12; single chats Off/2/4 h, default 2; `AppSettings.keepWarm`, `app:getKeepWarm`/`app:setKeepWarm`). A ping is `SideQuestions.warm`: a side run from the agent's clean point with the side guard, `--no-session-persistence` and the fixed `KEEP_WARM_MESSAGE`, so its request reads the session's cached prefix (same base, tools and browser as a side question) and resets the cache's hour while the session stays as it was; no entry, no broadcast, no unread or notification, and its cost is recorded as `#keepwarm` ("Keep warm" in Usage). It skips a running chat (its own requests read the cache), an archived or A→B chat, and one with no session to resume; a failed ping, a compaction, a context under 100K or the end of the window stops the pings until the next real request. At most two run at once. A good ping moves the context's `at` in place (`patchInPlace`), so the cold notice and the ring follow the cache. The schedule lives in memory, for sessions this server ran: a session synced from the other machine runs there. `ZUMIBOT_TEST_KEEPWARM_MS` (via `devEnv()`) shortens the interval for `e2e:usage`. In the logs a 12 h window for rooms saved about three times what its pings cost (cache reads are a fortieth of a rewrite on Opus); single chats come back sooner or not at all, so their window is short.
