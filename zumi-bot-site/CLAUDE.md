# zumi-bot-site

Before changing code here, read `docs/architecture/updates.md` (repo-root path; it covers the release flow this site shows).

Quick rules for this folder:

- Public, read-only showcase for `https://zumibot.run`. It offers the latest desktop installers and the server's install steps, all served from this site; it never links to a file or release in the repo or anything that needs a token. Its only GitHub link is the repo's home page, as an icon button after the header's theme button; the footer has `contact@zumibot.run`.
- It also hosts the update channel: the prebuild re-publishes the latest GitHub release under `public/releases/` (`latest.json` manifest, `<x.y.z>/zumibot-server.tar.gz`, `releases/<x.y.z>/zumibot-docker.tar.gz(.sig)` (the Docker bundle, optional), and `latest/` with the package, `SHA256SUMS`, `install.sh` and `releases/latest/docker/install.sh`). Servers and `install.sh` update from there with no token. The files are public but unlisted. The manifest shape (`publishRelease.ts`) is the contract `parseManifest` in `zumi-bot-server/shared/src/update.ts` reads: change both together.
- `releaseInfo.ts` keeps only version, date and notes from the release API. `scripts/fetchRelease.mjs` (npm `prebuild`, request logic in `latestRelease.ts`) writes `src/release.json` from it, downloads the release's package and `SHA256SUMS`, checks the hash, and publishes them. With no `GITHUB_TOKEN` it writes `null` and exits 0, so local builds work; with a token, any failure (non-200 other than 404, network, bad JSON, a missing asset, a checksum mismatch) exits 1 so Vercel keeps the previous good deploy. `release.json` is git-ignored.
- **Node**: `engines.node` is `22.x`, which Vercel reads to pin the build's Node major (the prebuild script runs `.ts` through node's type stripping, which needs 22.6+).
- **Vercel**: the project's Root Directory is `zumi-bot-site`, so this folder's `vercel.json` applies and its commands step up to the repo root (`cd ..`) for the workspace install and build. Set `GITHUB_TOKEN` (read access to the repo's releases) as a build env var; it is only read by the prebuild script and never reaches the bundle. Redeploy (deploy hook) after each release so the page shows it. Fine-grained tokens expire: pick a long expiry; an expired one fails the build (Vercel keeps the old deploy). Keep the Vercel setting "Include source files outside of the Root Directory" on. Builds that change nothing are skipped (`scripts/shouldBuild.mjs`, the `ignoreCommand`), and `prune-site-deployments.yml` deletes all but the production deploy and its rollback target: see "Keeping deploys few" in the updates doc.
- Desktop installers: `electron-build.yml` attaches them to the tag's release with `SHA256SUMS-desktop`, and the prebuild publishes each listed one under `public/releases/<x.y.z>/` after checking its hash (names and sizes go into `release.json`; `src/downloads.ts` reads them). They are optional: a missing list or file never fails the build, a hash mismatch does.
- The page is thirteen scenes (`src/scenes/`), plus the unnumbered "Built on Claude Code" band after the hero (`BuiltOn.tsx`, no `data-scene`): eleven of drawn app windows, not screenshots, then Download (the visitor's own system featured, `useVisitor.ts`) and On a server (`serverInstall.ts`, which mirrors the install doc's Phase 3 commands). Icons come from the app's `frontend/src/botShapes.ts` (the Zumi Z is the logo) and colors from its `tokens.css`; keep them in step when the app's look changes. Demo data only (`showcase.ts`). Details: the page section of the showcase part of `docs/architecture/updates.md`.
