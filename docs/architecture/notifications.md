# Notifications

**Notifications (`core/notify/`).** Tells the user when an agent needs them or finishes, on devices that have no tab open. Four kinds, each a per-device toggle: `waiting` (the `approvals` push in `ChatService`, so rooms and routine chats are covered; fires on each rise of pending, not on falls), `replied` and `error` (`ChatService.onTurnEnd`; a stopped turn, `/compact` and the moderator are silent; a to-do task chat's turn that put questions on its card, `cardQuestions`, is a `waiting` one instead, with `inbox: true` on its payload: its text reads "<agent> has a question for you" and a click opens `/inbox`, from the service worker's `clickUrl` and the shell's `open`; the chat stays in `asking` until its next turn starts, seen as its `inFlight` meta push, which clears it, and `state()` counts it as pending so a page load does not close it) and `routine-failed` (`RoutineRunner.onFailed`; a user stop or a restart is silent, a run failed by its turn's error gets `routine-failed` or else `error`, never both). `paused`, `test`, `workflow` (a Notify step's, see [Workflows](workflows.md)) and `spend-cap` (see [Spend caps](spend-caps.md)) are extra payload kinds. The payload is `{v,kind,tag,chatId,title,agent?,at}` (plus a workflow's `run?`, `body?` and `message?` (the Inbox message id) for a Notify step only, and `inbox?` for a to-do card's question) and carries the chat title only, never prompt text, tool input, answers, commands or paths. `tag` is the slot: `chat:<id>:waiting` is separate from `chat:<id>` (room members run side by side, so a reply must not replace a pending card), and routines that open a new chat each run are keyed by routine. Each device caps non-`waiting` at 10 a minute. Presence (`presence.ts`) is kept per RPC connection (the hub passes the connection to connection-aware handlers) and in memory only: *looking* = page visible + focused + on that chat + input within 3 min, and the page flushes a last looking report when the chat changes. If anyone looks at the chat, no device is notified; the event is held and released when nobody looks, dropped when input followed it or the card was answered, with a 10 s drop grace. A device has a random id in `localStorage` and a channel: `push` (browser or home-screen app on the VPS) or `desktop` (the shell, over its live socket). Push devices are bound to the sign-in session: logout and logout-all (`createGate`'s `sessionEnded`) pause them with one data-free `paused` push, expiry pauses at the next event, and the page-load `notify:refresh` rebinds but never creates a device, so a removed one stays removed. Web Push is hand-rolled on `node:crypto` in `webPush.ts` (RFC 8291 `aes128gcm`, RFC 8292 VAPID, tested against the RFC Appendix A vector); `pushSender.ts` drops a subscription on 404/410, retries once on 429/5xx and times out after 10 s, and a failure is logged with the device label, never the endpoint. VAPID keys are made on the first subscribe, so Local mode (no push) makes none. `/sw.js` and `/manifest.webmanifest` sit behind `createGate` like every route but the three app icons, so the manifest link needs `crossorigin="use-credentials"`; the CSP is unchanged. The service worker always shows a notification (browsers revoke a push that shows none), merges names only for consecutive `replied`, and has no `fetch` handler. Its text names agents as the UI does (`displayName`, `shared/src/agentName.ts`, a file with no imports so the worker never bundles `yaml`), while the payload keeps the handle; its badge is `badge-96.png`, white on transparent, since Android draws a badge from its alpha alone and the full-colour icon came out as a white square. `icon-192.png`, `icon-512.png` and `badge-96.png` are the only files served before the gate (`PUBLIC_FILES` in `http/static.ts`, never falling back to the app page): when Chrome installs the app, Google's WebAPK server fetches the manifest's icons with no cookie, got the login redirect, and the splash fell back to the small launcher icon, blurred. The manifest has no `maskable` icon on purpose: Chrome drew one unmasked on the splash, a square tile instead of the rounded one. The two app icons store every pixel's colour already blended onto white, alpha kept (their clear corners are white, not black): the WebAPK splash drops the alpha, and black corners turned the rounded tile into a square. `npm run icons` (`design/zumibot-icon/make-icons.mjs`) renders them that way (`onWhite`), with every other app icon, from Zumi Bot's Z. Clearing reaches live pages by `notify:clear`; a device with none asks `notify:state` on the next page load. The shell takes the optional `DesktopBridge.notify?/closeNotifications?/onNotificationClick?` (Electron `Notification`; shells up to 3.5.0 refuse the HTML5 permission, so they get no notifications and Settings say to update). A notification never answers anything: a click only opens the chat. Every entry point is fire-and-forget, so a failure never reaches a chat. **Settings › Notifications** (`NotificationsSettings.tsx`) sets this device, its toggles and other devices. Dev hook: `ZUMIBOT_TEST_PUSH_ORIGIN` (via `devEnv()`) allows one `http://127.0.0.1` push origin for the e2e. Design: `docs/superpowers/specs/2026-10-31-notifications-design.md`. **Channels as targets.** A paired Telegram or Slack chat is a `NotifyTarget` beside the devices (`targets()` in the deps; see [Channels](channels.md), Notifications).
- It has its own toggles, push's four plus `workflow`, all off by default, in `channels.json`. A Notify step obeys that toggle there.
- It gets the same events through the same path: `deliver` (presence holds, input drops, the release when nobody looks), `toRun` and `spendCap`.
- `kindFor` decides by its toggles, and the rate cap is keyed `channel:<platform>`.
- A chat whose turn already talks to that channel (`drives`) is skipped for it, never for the devices.
- A target that can't take one (not paired, the bot not running here) answers null, and one that throws is logged by its name only.
- Its text is `channelNotifyText`: push's title and line, a Notify step reduced to its title.
