# `/btw` side questions

**`/btw` side questions.** `core/btw/` starts a separate answer from the agent's latest clean entry with `--resume`, `--resume-session-at`, `--fork-session` and `--no-session-persistence` (a Codex agent's from an ephemeral `thread/fork`, see [Codex agents](codex.md)); without a session it seeds from visible items. The main run continues. The side run reuses the main run's exact agent, model and effort, system prompt, tool definitions, environment and browser/MCP arguments to preserve its prompt-cache prefix, and runs in the server's permission mode (a chat's own mode stays with its main run, see [Chat mode and effort](chat-mode-and-effort.md)). A `PreToolUse` deny hook passed with `--settings` blocks every tool (`No tools in a side answer`; a Codex side run's is `CODEX_SIDE_DENY_HOOK` on its argv, see [Codex agents](codex.md)), and unexpected permission requests are denied without a card. A fork reporting the main session id fails visibly; it is never retried as plain resume. Questions and streamed answers live separately in `chats/<id>.btw.json`, so chat items, later agent prompts and context meters never contain them. Entries form threads: a follow-up (`btw:follow`) is an entry whose `thread` names its root, with the root's agent, mention and `after`, so the open limit, Stop, restart, rename, fork and sync handle it like any entry. A root keeps a server-only `snapshot` (`point`, `upTo`, `context`; `btw:list` and `btw:changed` strip it), written once its preparation settles, and every follow-up forks from that point (or seeds from the items up to `upTo`) with the root's room or A→B context, so it never answers from where the main run has moved since; its message replays the thread's earlier questions and answers (`followMessage`, at most 40 000 characters, the root's pair always kept). A root made before snapshots answers follow-ups from the chat's current point. A follow-up is refused while any entry of its thread is open (`Wait for this answer to finish`), on a root an agent asked, on one that never got an agent, or on an unfinished one that never saved its snapshot (`Ask this side question again first`); one whose A→B source chat is gone ends with `sourceGoneText`, as `btw:ask` does. The composer routes `/btw` through the `btw:*` RPCs; the chips on messages (one per thread, with the whole thread's spinner or warning) and **Open Side questions** (which counts threads) open `SidePanel.tsx` as its Side questions view (no chip under the composer). That view has its own question box at the top (Enter asks, Shift+Enter a new line, cleared only when every ask succeeded, an error kept under it; one ask opens its new thread, Both stays on the list) and lists one row per thread in the Dispatched agents style (status dot, root question, `N questions`, a live or last-answer line), grouped by the reply they were asked after, newest first (`groupThreads`). A row, a chip or a focus request opens the thread chat style (`SideThreadView.tsx`: questions as right-hand bubbles, each answer under its question, Show in chat, followed at the bottom) with a follow-up box whose Ask waits while an answer runs. The pure rules (`sideThreads`, `threadOf`, `threadLine`, `canFollow`, `canAskAgain`) are in `state/sideQuestions.ts`. The list's **Answer from** chips (`pickChips`, pure in `state/sideQuestions.ts`) are none in a single chat, Auto plus each loadable member in a room, and B, A and Both in an A→B chat (A greyed once the source chat is gone, Both unless 2 of the 3 slots are free), and need no RPC of their own: `sideTexts` turns a chip into a leading `@handle` (none for Auto or the chat's own agent; Both is two `btw:ask` calls, B's then A's), and a typed leading `@handle` wins. Rooms pick an answering member through the moderator, or use an explicit mention. Stop keeps partial text, Ask again reruns in place and is offered only on a thread's last entry (a follow-up reruns from the same snapshot), and restart marks unfinished entries interrupted. A stop ends an answer at once, but shutdown (`stopAll`) also waits for the preparation calls it cut off and for every keep-warm ping (one still preparing ends without starting its run), so a late one (a fresh base making the chat's `claude-tmp` folder, a browser turn being disposed) never writes into the data dir after the server stops. At most three run per chat, with a three-minute timeout; no side answer sets unread or sends a notification. An answer waiting on a `side_question` call (see [Agent asks](agent-asks.md)) pauses its clock (`SideDeadline`, which the run's own timeout follows), so the asked agent gets its full three minutes, and is capped at `SIDE_ASKING_CAP_MS` (6 minutes) overall.
