# Agents, memory and remembered approvals

**Remembered approvals.** "Allow always for this agent" on an approval card writes a rule to `approvals.json` (`core/store/approvalStore.ts`). Rules match by tool name; `Bash` matches the exact command only, and a rule for a sandboxed run never allows the same command with `dangerouslyDisableSandbox`; a background process start (`mcp__zumibot_processes__start`) matches its exact command and folder as written, never a Bash rule (see [Background processes](processes.md)). `ChatService` answers a matching request itself, and the card shows `auto-allowed-agent`. Rules of an agent whose file disappears are dropped: by the agents-folder watcher while the server runs, and at start for agents deleted while it was off (unless some agent file fails to load; Zumi Bot's are kept). They are listed and removable in the agent editor. A rule can also be a CLI rule (`cli: "Bash(git branch -D:*)"`, key `["cli", rule]`), made only from a blocked row's Allow… with "Always for this agent" or from the editor's own Add (`approvals:addCli`, a prefix or a folder rule): it never answers a `can_use_tool` request but goes into the agent's runs as a Claude Code allow rule, and the editor shows it as `Bash: commands starting with <prefix>`, or a folder rule (`cli: "Read(//<folder>/**)"`, `toolName: 'Read'`) as `Read: files in <folder>` (see [Allow a refused call](chat-mode-and-effort.md#allow-a-refused-call)). A routine or workflow delete (`confirmOnly` in `shared/src/automations.ts`) is never remembered or auto-allowed, by chat or by agent: its card offers only Allow once and Deny, and any answer but Deny is stored as allow-once. A claude.ai connector write (see [Connectors](connectors.md)) is remembered only while that service's Remember switch is on: with it off, its card offers no remembering, any allow-* is kept as allow-once, and chat keys and agent rules made earlier are inert (still stored, not applied) until the switch is back on. A connector read asks nothing, and a connector write in a run the user did not type (`spec.auto`) is refused before any card.

**Agents.** `AgentStore` reads and watches the agents dir (`ZUMIBOT_AGENTS_DIR`, default `~/.claude/agents`) and parses frontmatter with `shared/src/frontmatter.ts` (`memory` and `memoryLimit` are known keys; see Agent memory; `serversOff`, `skillsOff`, `plugins`, `mcpServers` and `hooks` are the extension keys, see [Servers, plugins, skills and hooks](extensions.md): Zumi Bot never writes them). Agent Studio's Engine select picks the engine, written as `provider:` (none for Claude, `codex`, `acp`, labelled **ACP agent**, or `ag-ui`, labelled **Remote agent (AG-UI)**); the cards it shows follow that engine's caps (`studioCards` in `state/acpCard.ts`: the model choices, Compact at, the daily cap, the loadout and browser, memory and the desktop), and picking **ACP agent** shows the ACP card at once: Command, Arguments and Sign-in keys, the launch confirmed on this machine beside the form's, and Test. Its Save also confirms that launch (see [Codex agents](codex.md) and [Protocol engines](protocol-engines.md)). Picking **Remote agent (AG-UI)** shows the remote card the same way: Endpoint, Auth key (a Vault API key granted to the agent, by env name) and Auth header, the remote notice naming the host, the endpoint confirmed on this machine beside the form's, and Test (it checks the address and connects, sending no request); the instructions card says the body is not sent, and once a saved agent is switched onto it, the card says its older chats do not continue. The row's tag reads **Remote**. `autoCompactWindow` (100000–1000000 tokens, the CLI's own key) is shown in Agent Studio as **Compact at** (Default, 200K, 300K, 400K, 600K; Default removes the key, leaving the CLI's own point near the window's end; it is not called Auto because nothing picks a size). The CLI applies the frontmatter key only when the agent runs as a subagent, so `ChatService` passes it to the agent's own runs as `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (read per attempt through `compactWindow`; env changes no prompt, so the cache prefix holds, and side runs never get it, so a side answer never compacts). The CLI then compacts before a request once the context nears that size. Zumi Bot (`zumiBot.ts`, "Keeping an agent's context small") gives a new agent a "Keeping your context small" section (read in parts; more than 3 images, bulk reads and broad searches go to a subagent that keeps the agent's model for judging; confirm a subagent's finding before failing on it; `Agent` added to any `tools:` list that needs it) only when its job reads heavy output (images, browser pages, big diffs or files, logs, bulk API data), since extra rules lengthen every request; every new agent gets `autoCompactWindow` (400000 by default, 600000 for one that ships to production in one long run, 300000 for an assistant of many small jobs), which adds nothing to its prompt. Deleting an agent moves it to the freedesktop trash (`core/trash.ts`), never a hard delete. Zumi Bot (`core/agents/zumiBot.ts`, name `zumi-bot`) is a built-in agent the server writes itself. Its working folder is fixed to the agents dir, and it gets deny rules. Besides agents it creates, edits and deletes routines and workflows through its own tools (see [Zumi Bot automations](zumi-bot-automations.md)). Its `/make-friendly [agents]` command (none named = every agent but itself) brings agents written before ZumiBot up to what it gives a new one: commands, `autoCompactWindow`, the asking and answer-format sections, context rules for heavy jobs, color and icon, and the ZumiBot tools in an existing `tools:` list. It adds only what is missing, without asking per agent, skips a file that does not parse, and never changes the agent's own instructions, `name`, `description`, `model`, `memory` or `computerUse`, nor adds, changes or removes `serversOff`, `skillsOff`, `plugins`, `mcpServers` or `hooks`; it never adds or removes `provider`, and gives a Codex agent (`provider: codex`) no tools, `AskUserQuestion` or subagent context lines. Zumi Bot writes a Codex agent only when asked (see [Codex agents](codex.md)). It writes `provider: acp` or `provider: ag-ui` only when asked too, and never writes or changes an agent's `acp:` launch or `agui:` endpoint, which only Agent Studio sets (see [Protocol engines](protocol-engines.md)). Its name was `bot-father-agent` before: at every start `migrateOldBuiltIn` (`core/agents/oldBuiltIn.ts`, before `sync.start()`, whose removal pass would drop the old approvals) runs the agent-rename pipeline from the old name to `zumi-bot` and then trashes the old file, but only while that file or a chat, approval or routine still names it, since the full rename reads every chat; a sync with a machine on an older version brings both back. Usage records load only in `usage.start()`, so they move right after it. An ACP agent's confirmed launch (`protocol-launch.json`, see [Protocol engines](protocol-engines.md), Launch trust) moves with the rename pipeline right after the approvals, and the agents-folder watcher's removal pass and `agents:trash` drop it.

**Icon and color (`BotIcon.tsx`, `botShapes.ts`, `state/bot.ts`).** Agent Studio's Icon & color card picks a shape (`icon:`, ZumiBot-only, one of `ICON_OPTIONS` in `shared/src/frontmatter.ts`, `robot` the default) and a color (`color:`, the CLI's own key). `COLOR_OPTIONS` stays exactly the CLI's eight names, since the CLI drops any other value; `--agent-<name>` in `styles/tokens.css` is the icon set's own shade, used for the icon and other fills; text in an agent's color takes `--agent-<name>-ink` (`agentInk`, see Palette and contrast in [App shell UI](ui.md)), since several fills are too pale to read on white. Each shape is an even-odd path in a 100 box, kept as its `body` and its `eyes` (`botShapes.ts`, from `design/zumibot-icon/zumibot-svg/`; `frontend/tests/botShapes.test.ts` fails when they drift): the eyes are holes, so they show whatever is behind the icon (the robot's are `filledEyes`, inside its hollow visor), and an agent with no color is drawn in `--bot-fg`. An idle icon is one path. A working one bobs and tilts as a whole while its eyes glance left and right (`bot-look`, `EYE_SHIFT` units, off under reduced motion): hole eyes become a mask over the body whose eye cut-out moves, since a shape drawn in the background's color would not match every row, hover and theme; filled eyes are drawn on top. The test also checks every shape's eyes stay on its face at that shift. The faces from before 0.1.0 (`LEGACY_ICONS`: `triangles`, `wink`, `circles`) are shown and selected as `robot`, `cat` and `chat`, the nearest shapes, while the file keeps its value until the user picks another; nothing rewrites agent files for it. Any other value is a custom icon: drawn as `robot`, shown as "Custom: <value>" with no shape selected. Zumi Bot is always drawn as `zumi-z` in `--bot-zumi` (`builtIn`), whatever its file says; `zumi-z` is in neither list, so no other agent can pick it, and one that writes it by hand gets a custom icon. Zumi Bot's prompt lists the shapes and colors from those two lists. The app's own icons are the same Z: the rail logo is `BotIcon`, and `npm run icons` (`design/zumibot-icon/make-icons.mjs`, pure Node) renders every PNG from `zumi-z.svg` (the three `favicon.png` copies for the app, login pages and site, `icon-192.png` and `icon-512.png`, the white `badge-96.png`, and the desktop's `build/icon.png`, which the tray also uses); rerun it after changing the Z.

**Agent memory (`core/memory/`, `shared/src/memory.ts`).** An agent file with `memory: user` turns on Claude Code's own agent memory, so ZumiBot has no store of its own: the files are `<CLAUDE_CONFIG_DIR or ~/.claude>/agent-memory/<agent>/` (one `.md` per memory with `name`, `description`, `metadata.type`, plus the `MEMORY.md` index), and `claude --agent` in a terminal reads the same ones. The agent saves on its own and the CLI asks no approval for it. `MemoryStore` lists, saves and deletes by hand (delete goes to the Trash), checks every file name, and rejects a stale save by `modified` (`MEMORY_CHANGED`). Index repair only adds missing lines, never rewrites the user's or agent's own; it runs on list, on creating a memory and at the start of each reply, not on save or delete. A watcher on the folder broadcasts `memory:changed`, so an open Memory section follows what the agent writes. The cap (`memoryLimit`, 25/50/100/150, default 100) is told to the agent by the appended prompt (counts only, never memory text) and enforced in the UI by hiding New memory; the CLI cannot be stopped from writing past it, and nothing is evicted. `chatService` counts a `Write`/`Edit`/`MultiEdit` whose `file_path` is a direct child `.md` (not `MEMORY.md`) of the agent's folder, with a non-error result, and stores `memory: {saved, updated}` on the reply item; the chat shows "Memory: 1 saved" with a View link to Agent Studio. `memory: project` and `local` depend on each chat's folder, so only a notice is shown for them. Rename and delete follow the agent through `MemoryTurns` (the folder moves or is trashed once no turn of that agent is running). Zumi Bot has no memory. Design: `docs/superpowers/specs/2026-11-02-agent-memory-design.md`.

**Agent Studio's header (`AgentEditor.tsx`).** Three groups: the Form / Raw view switch, then Revert and More (⋯, `editor-more`), then **Save changes**, the one primary action, last. Delete lives in More (`editor-more-menu`, **Delete agent**, `editor-delete`, which takes focus as the menu opens; Esc, a click outside or a blur closes it) and opens the same Move to Trash question. A red button beside Save drew the eye as much as Save did, one slip away from it.

**Isolation (Agent Studio).** The last section of Agent Studio, `AgentIsolation.tsx` (pure rules in `state/isolationForm.ts`), sets the agent Off, Sandboxed or Container, its network list, extra writable and read-only folders (mounted, for Container), web search and "Run Bash without asking", and lists what every run gets; a level this machine or agent cannot have is greyed out with the reason (`levelBlocked`; Container also while computer use is on; both levels for an engine without the `isolation` cap, Codex, ACP and remote agents, whose reason `isolation:get` sends as `refused`). It saves on its own button (`isolation:get`/`isolation:set`/`isolation:status`), into `<data>/audit/isolation.json`, never into the agent file, so Zumi Bot cannot lower it. An Agent Studio rename moves it like approvals (`agents:save`, before any await). See [Governance](governance.md) 2.3 and 2.4.
