# Desktop shell, island and tray

**Desktop shell (`zumi-bot-desktop/src/main/index.ts`).** A picker page chooses Local or VPS (`servers.ts` saves the choice to `server.json` in userData, which also holds `window-state.json`, `zoom.json`, `sync.env` and `island.json`, see Dynamic island). In Local mode it spawns the built `server.mjs` on the saved port (default 4318, passed as `ZUMIBOT_PORT`, so webhook URLs stay stable between launches) with Electron's own Node (`ELECTRON_RUN_AS_NODE=1`, see `localServer.ts`). When packaged, the file is in `resources/server`, unless Local mode's update downloaded a newer build: `serverPick.ts` then starts `<userData>/server-updates/v<version>/zumibot-server/app/server.mjs`, falls back to the bundled one when it does not start, and the server's exit code 75 (`LOCAL_RESTART_EXIT`) restarts it on the new build (see [Updates](updates.md), Local mode). A packaged shell passes `ZUMIBOT_LOCAL_UPDATES`; a dev run does not. In dev it is read from `zumi-bot-server/backend/dist`, so build the server before `electron-vite dev` (`npm run dev` does this). The preload exposes `zumibotDesktop` (`shared/src/desktop.ts`) only to the connected server's origin, and `zumibotPages` only to the shell's own `file:` pages (`src/pages/`, plain static HTML/JS). The UI checks for `window.zumibotDesktop` to turn on desktop-only features: Switch server, save-before-close, theme sync, opening attachments, the island's Settings section. Navigation is locked to the server's origin (`navigation.ts`). **No monitor.** Mutter 46 (Ubuntu 24.04, X11) aborts the whole desktop (libmutter `assertion failed: (logical_monitor)` in `meta_window_unmaximize`) when a window flagged maximized gets a `_NET_WM_STATE` remove-maximized message while Mutter has no logical monitor (one asleep or being re-detected); Chromium sends that message after a `show()`, and a main window reopened maximized is flagged within ms of it. X then reports a 32x32 stand-in display, so `screenGuard.ts` (`hasRealScreen`, `whenScreen`, bound to Electron's `screen` as `whenRealScreen` in `window.ts`) holds the main window's first show, the maximize that follows it and the tray's `showMain` until a real screen is back (a screen must stay real for 500 ms, re-checked when that time is up; `display-added`, `display-removed` and `display-metrics-changed` restart it), with at most one pending wait per window: a later call (tray Open, a second launch, the island's Open in ZumiBot, a notification click, pressed again) only replaces what runs, so it never runs N shows or collects N `screen` listeners, and the window's `closed` drops the wait; the close flow's raise of a hidden window (`onAsk`, so a quit dialog is not invisible) shows it only while a real screen is there, else the window stays hidden and the dialog is parented to it; the island is never maximized and is left alone. `Ctrl+Shift+S` or `zumibot --switch-server` reopens the picker. **Zoom (`zoom.ts`).** The app menu is removed (`Menu.setApplicationMenu(null)`), and with it the roles that bound the browser's zoom keys, so the main window handles them in `before-input-event`: Ctrl (Cmd on a Mac) with `=` or `+`, `-` or `_`, and `0` step through Chromium's own factors (`ZOOM_STEPS`, 50% to 300%; 200% is five presses) or reset to 100%. The factor is saved to `zoom.json` (`{factor}`) and set again on every `did-finish-load`, since Chromium keeps zoom per origin and the picker and the server are two. The workflow canvas zooms on the bare keys, so the two never meet. Ctrl+wheel is left alone: the canvas uses it.

**Dynamic island and tray (desktop shell; `zumi-bot-desktop/src/main/island.ts`, `islandPrefs.ts`, `tray.ts`, `autostart.ts`, `quietStart.ts`; `shared/src/island.ts`, `shared/src/islandLayout.ts`; design: `docs/superpowers/specs/2026-11-12-dynamic-island-design.md`).** The shell lives in the tray and shows a strip of the user's picked agents on the right edge of every workspace; one click opens a compact chat with that agent over whatever is on screen. **Window.** `createIslandHost` makes a second `BrowserWindow` (frameless, transparent, `type: 'toolbar'`, `alwaysOnTop` at `floating`, `setVisibleOnAllWorkspaces`; `skipTaskbar` does nothing on Linux X11, so the toolbar type is what keeps it off the taskbar and pager (Mutter marks a toolbar window skip-taskbar and skip-pager, and GNOME Shell's Super overview and Alt+Tab drop every skip-taskbar window, so the island shows in neither; Chromium logs once that the type's atom is not in its cache, which `e2e:desktop` lets through)) with its own X11 `WM_CLASS` `zumibot-island` (`ISLAND_DESKTOP_NAME`: Electron names each window's `WM_CLASS` after `CHROME_DESKTOP` as it is made, so `withDesktopName` swaps it around `new BrowserWindow` and puts it back) matched by the hidden `build/zumibot-island.desktop` (`NoDisplay`, `StartupWMClass=zumibot-island`) that the `.deb` installs through `deb.fpm` in `electron-builder.yml`, so GNOME Shell files the island under that entry, not ZumiBot's. Filed under ZumiBot's, the island was the app's only window once the main window was hidden, and Ubuntu Dock's click (with no window that is not skip-taskbar, it activates the app's first window, skip-taskbar or not) focused the island instead of launching the second instance that shows the main window; skip-taskbar alone never stopped that. An unpackaged run has no such entry, so GNOME may file its island under ZumiBot by pid and the dock click can still land on the island there. The window loads `<origin>/island` (`ISLAND_PATH`; `html.island-page` makes the page transparent) with the same navigation lock, window-open denial and permission handler as the main window (`lockToOrigin` in `window.ts`). `islandWanted` says there is no window without a connected origin, or without a picked agent unless a voice request runs or the popup is open (see Voice shortcut), and a hidden one until the page has called `ready` and reported at least one icon (or, with a voice request, until `ready`), so a newer shell on an older server (no `/island` page) shows nothing; the window is shown with `showInactive()` (it never takes focus; only a click on an icon does, in the page), and a user's close of the island window (Alt+F4, the Overview's close) is prevented (`preventsIslandClose`) so it cannot vanish until the next origin or agent change, while a quit still closes it (`before-quit` sets the shell's `exiting` flag, which a cancelled quit clears; teardown uses `destroy()`, which skips `close`), and `needsIslandLoad` sends a window stranded on a login redirect or a failed load back to its page when the main window returns to the app. The main window's `onNavigated` calls `setOrigin` only for the app page itself (not a login page or a server error), the picker and error pages and a server switch call `setOrigin(null)`, and the preload's origin is fixed at creation, so another server gets a new window with that server's picks. **X11 facts that cost time.** The every-workspace state is a client message to the window manager that Mutter takes only once the window is mapped, so `setVisibleOnAllWorkspaces(true, …)` is called again right after `showInactive()` (called only at creation it left `_NET_WM_DESKTOP` at 1 while Electron's `isVisibleOnAllWorkspaces()` already said true; the e2e reads `_NET_WM_DESKTOP` = `0xffffffff` with `xprop` for that reason). The window never moves or resizes with the strip: a resize of this transparent window freezes it blank for about a second under Mutter, and on a real desktop (GNOME 46, X11, NVIDIA, 144 Hz) Mutter applied each client-requested move of it 0.6-0.9 s late (p50 609-667 ms, against 0-2 ms on a throwaway display), falling behind at about 40 moves a second, so a drag that moved the window crawled. `islandBounds` (`shared/src/islandLayout.ts`, whole pixels) returns the work area's full-height right-hand column, `ISLAND_WIDTH` (`POPUP_WIDTH` + `POPUP_GAP` + `STRIP_WIDTH`, 430 px) wide, whatever the strip, its top or the popup, and `place()` calls `setBounds` only when that rect changes (a new work area; and once more after the first show). Where the strip and popup sit is layout only: `place()` does `setShape` (`islandShape`: `[strip]` or `[strip, popup]`), so the transparent rest takes no clicks (X11's `setIgnoreMouseEvents` cannot forward events on Linux) and is not drawn, and sends `island:layout` so the page draws the strip and popup at those window-relative rects, with `track`, the strip's full-height column. **Page and bridge.** The island window has its own preload branch (`--zumibot-island=1`, only for the island path on the connected origin) exposing `zumibotIsland` (`IslandBridge`: `ready`, `agents`/`onAgents`, `setShape(icons, open)`, `onLayout`, `drag`, `openMain`, `openAttachment`), never `zumibotDesktop`, so it gets no `setEditorDirty`, `onSaveBeforeClose`, `switchServer`, `sync` or notification call; every `island:*` handler runs `isSender` (the island window's own main frame on the connected origin) and re-validates its arguments (`parseIslandOpenTarget`, `cleanAgentList`, `ISLAND_AGENTS_MAX` 10). The React side is a lean entry in `App.tsx` (`hasIsland`, `IslandView.tsx`, pure rules in `state/island.ts`, `islandView.ts`, `net/island.ts`): the page runs `useNotifications` presence-only (no device, no tab title, no delivery), draws each picked agent's icon with its marks (a spinning ring `island-working` while a chat runs, an amber count while something waits, a blue dot for an unread reply; the class is not `working`, which is a thread rule that would push the icon out of the strip's column), and opens a popup holding the chat's own `ChatView` with `compact` (no side panel, meter, cost, picker, cold notice or Export, and a message's buttons sit under its bubble, since beside it in 360 px they left the bubble a word wide; the message box and a message's edit box stop at 160 px, since `vh` there is the island window's, the screen's full height, and the main window's 40vh cap outgrew the 520 px popup, whose clip cut off the box's bottom; every card is still answered in place). The agent's chats are its single, unarchived, non-A-to-B, non-workflow chats; a click opens its oldest chat with something waiting, else the chat the popup last showed, else its newest unread, else its newest, else a new chat (its folder is `app:lastFolder`, else home, shown dim above the box); ⋯ lists New chat, the newest 8 chats and **Open in ZumiBot**, which sends `island:openMain` and the main window's page gets `desktop:islandOpen`. The popup has no `/btw`: the `/` menu leaves it out and a typed leading `/btw` shows "Side questions open in ZumiBot" and sends nothing (`btwRefusal`, the Composer's `noBtw`), since there is no side panel to show the answer. The island page follows a theme change made in the main window live, through the `storage` event of the cached `zumibot-theme` key (`themeFromStorage`). Esc closes whatever the composer's menus, the ⋯ menu, a dialog or the reply bar took first, then the popup. Drafts and the popup's last chat live in the island page's memory only (not shared with the main window, lost at restart); the popup reports looking at its chat only while the island window has focus. A drag of the strip background slides the strip inside the window, done by the page: on `island:drag` start the shell sets the shape to the columns the strip and popup slide in (`islandShape(layout, true)`: `track`, plus the popup's column when open; while the drag lasts clicks in them do not reach the window behind), the page moves the strip and popup itself on every pointermove with `slideLayout` (the shell's own placement math, so both land on the same pixels; `clientY` is true since the window never moves) and sends nothing, and at the end sends the strip's final top in window coordinates; the shell places it there (the strip shape again), saves `top` only if it is not where the drag began, so a plain click saves nothing, and its layout replaces the page's own slid one, which the page keeps until then so nothing snaps back. The page slides the strip only when the layout has a `track`: an older shell (no `track`) still gets every move and moves its window. An older page sends moves and no final top: the shell then moves the strip in the layout by how far the X pointer (`screen.getCursorScreenPoint()`) has moved, never by the page's `screenY` (still sent, since older shells read it), which X11 Chromium works out from the window origin it asked for at `setBounds` before the window manager has moved the window, so it ran up to a move's delta past the pointer (64-96 px seen on fast drags). **`island.json`** (userData, 0600, atomic through a temp file, lenient parse in `islandPrefs.ts`): `{v: 1, startAtLogin, top, agents: {"<origin>": [names]}, voiceHotkey}`, picks kept per server origin because agents differ per server, `top` null centres the strip, `voiceHotkey` the voice shortcut (below; null is off, a missing or bad one reads as the default; the same on every server); a missing, broken or renamed-away agent is skipped silently, and an agent rename carries the pick (`desktop:islandRename`). Settings drops (`livePicks`) a pick whose agent is gone once the agent list has loaded, from the rows, the cap and every toggle or move, so the next save prunes it; while the list is empty nothing is pruned. **Settings › Island & startup** (`IslandSettings.tsx`, only where `zumibotDesktop.island` exists, so a browser tab or an older shell never shows it) reads and writes through `desktop:islandGet`/`islandSet`, which answer only the app page's main frame (`fromAppMain`) and return what the shell saved. **Tray and quit.** `createTray` (`tray.ts` holds the menu: **Open** calls `showMain`, **Sponsor ZumiBot** opens `SPONSOR_URL` (`shared/src/sponsor.ts`, the site's /sponsor page) in the default browser, **Quit** `requestQuit`; Electron's `Tray` is a StatusNotifierItem, which Ubuntu 24.04 shows through its AppIndicator extension) and closing the main window only hides it (`shouldHide` is true unless `quitRequested`), with no agent picked too, so the Local server keeps running; `showMain` (`raiseWindow.ts`) restores a minimized window, shows a hidden one on the current workspace through `showHidden` (`showHiddenWindow` in `windowState.ts`: one closed maximized is unmaximized while unmapped, which only changes the state Chromium keeps for the next map, shown at its normal size and maximized once placed, as on the first show, since mapped maximized Mutter took the maximize and dropped it about 100 ms later, leaving the window at its normal size; the close flow's raise for a quit dialog does the same, and the late maximize skips a window hidden again meanwhile, since Electron's `maximize()` shows a hidden one) and ends a quiet start; for a visible window, the dock icon's second launch (`second-instance`, unless it carries `--hidden`; Ubuntu Dock's `isolate-workspaces` launches again when the app has no window on this workspace), tray Open and a notification click (`go`) only `focus()` it, whose `_NET_ACTIVE_WINDOW` with a fresh server time makes Mutter switch to the window's workspace, as for any other app, while the island's Open in ZumiBot (`bring`) first moves it here with `setVisibleOnAllWorkspaces(false)` (Chromium sends `_NET_WM_DESKTOP` = the current one, no unmap). Never `hide()` then `show()` a visible window to move it: Mutter's withdraw clean-up deletes the `_NET_WM_STATE` Chromium wrote back for the new map, so the window came back unmaximized, at another size. A quit from the tray or `app.quit()` (`before-quit`) sets `quitRequested` and runs the main window's close flow as before (unsaved agent edits, running replies: Stop & Quit / Cancel; background processes the local server would end ask as well, on quit and on Switch server, see [Background processes](processes.md)), whose `onAsk` raises the hidden window first so the dialog is not behind nothing (Cancel hides it again if it was hidden) and whose `onQuitCancelled` clears `quitRequested`; `window-all-closed` and `will-quit` tear down the island, the tray, the notifier and the server. **Voice shortcut (`voiceHotkey.ts`).** A global shortcut (default `Ctrl+Alt+Space`, `voiceHotkey` in `island.json`, null is off, a value outside `cleanHotkey`'s grammar reads as the default) starts and stops a voice request on the island with no window of ZumiBot in front. `cleanHotkey` (`shared/src/island.ts`) allows only `Ctrl|Alt|Shift|Super` (at least one) plus one of `A-Z`, `0-9`, `F1-F12`, `Space`, at most 40 chars, and returns it in one form; it runs on the file, on `desktop:islandSet` (page input) and again inside `createVoiceHotkey`, whose `set` registers with Electron's `globalShortcut` (`index.ts`, at start, on a change, `dispose` at `will-quit`) and unregisters only what it registered, and returns `{ ok: false }` with nothing registered when the register fails (another app holds the key, or no X11 grab). A shortcut that cannot register is not saved: `desktop:islandSet` puts the old one back and answers with `ok: false`, which Settings › Island shows as "That shortcut is taken by another app."; the key is global, so a server switch changes nothing. `IslandHost.voicePress` (a press with no connected origin does nothing): with no voice request it sets `voice`, applies (`islandWanted` then makes the window even with no agent picked; `place` and `islandBounds` with `icons: 0, open: true` give the popup and a zero-height strip, and `islandShape` drops the empty strip, so a voice-only island is just the popup) and sends `island:voice true` once the page is `ready` (`onReady` sends it for a window made by the press; the page listens from mount); a press while one runs sends `island:voice false`, and a press whose page never came up ends it on the spot, so no hidden window waits. The page (`IslandBridge.onVoice`) opens `VoiceTalkView` compact in the popup in place of an agent's (`autoStart` with `noTap`: a global shortcut is no click, so `userActivation` is false and the machine would otherwise wait for a tap) and tells the shell `voiceEnded()` (`island:voiceEnded`, checked with `isSender`) when the machine reaches `ended`, on `voice false` (unmounting the view stops the talk and frees the mic), on the popup's close or Esc, on an icon click and on Open chat. Once the request is sent the voice part ends (`voiceEnded`, the shell clears `voice`) and the same popup shows the new chat, its agent's ordinary chat popup, picked or not (`popupAgentOf` in `state/island.ts`: a picked agent, or the one the voice request went to, never a gone or broken one); the reply is read there and answered in its composer. The shell keeps the window while the page reports a popup open (`islandWanted` takes `open` from `setShape`), so a voice-only island stays up as long as that chat is shown and is dropped when the popup closes (close, Esc, an icon, or the hotkey, which starts a new request in its place); a strip window stays as it was. A request with no agent known falls back to the main window (`bridge.openMain`). A reload of the page, a server change or a crashed renderer clears `voice` too. The window stays `showInactive()`: the shortcut never steals focus. The mic needs nothing new: the island window uses the default session, and `isPermissionAllowed` already allows audio-only `media` for the connected origin.
**Start at login.** `app.setLoginItemSettings` does nothing on Linux, so `syncAutostart` writes `<XDG_CONFIG_HOME or ~/.config>/autostart/zumibot.desktop` (`Exec=<APPIMAGE or execPath> --hidden`, quoted as the Desktop Entry spec says) from a packaged build only, on by default and removed when the switch is turned off; a dev run never writes it. **Quiet start.** `--hidden` (`wantsHidden`) makes the main window and loads it but never shows it; a failed connect (network or local server not up yet) is retried every `QUIET_RETRY_MS` (10 s) for `QUIET_WINDOW_MS` (2 min), after which the window shows with the error page, and a server that answers with its sign-in page (`isLoginUrl`) shows it at once since only the user can sign in; there is no island until connected. **Limits.** X11 only: Ubuntu 24.04, GNOME 46, X11 is what was built and tried; on Wayland (GNOME does not let a client keep a window on top or on every workspace, and `setShape` is X11) the island would act as a normal window, which is not handled. Notifications are unchanged and only the main window's page registers as the notification device, which stays loaded while hidden; rooms are not on the island; the island's own e2e cannot switch workspaces, so "every workspace" is checked by `_NET_WM_DESKTOP`.

## Local mode and computer use

The desktop app's Local server uses the same programs as a VPS for computer use: install the packages, the Firefox deb and cua-driver on your PC (see [Computer use](computer-use.md), "Server setup"; with your go-ahead, since the app never does it), run `npm run desktop:check` in the checkout, and the Desktop view works the same. Local desktops are separate from the VPS's and are never synced.
**Cloud builds.** `.github/workflows/electron-build.yml` packages unsigned Windows (NSIS), macOS (DMG, arm64 and x64) and Linux (`.deb`, AppImage) installers from `electron-builder.yml`'s `win`, `mac` and `linux` sections on a manual run or a `v*` tag, and keeps them as 14-day Actions artifacts; on a tag it also attaches them to the release, and the showcase site offers them for download ([Updates](updates.md)). The Linux build and a Windows dev run (`npm run dev`) have been run as apps; the packaged NSIS installer has not. **macOS** (packaged x64 build run on an Intel Mac, macOS 15): the DMG is ad-hoc signed in CI (`-c.mac.identity=-`; a bundle with no signature is "damaged" on Apple silicon) with the hardened runtime and `build/entitlements.mac.plist` (JIT, unsigned executable memory, library validation off, audio input; the Local server, Electron run as Node, inherits them), and `NSMicrophoneUsageDescription`, without which macOS ends the app at the first mic request; the job checks the signature, the entitlements and the plist key and runs the arm64 build as Node. The shell gets an app menu with the Edit roles (`appMenu.ts`; null elsewhere), `activate` (a Dock click) shows the main window, the tray image is 18 px, the switch shortcut is Cmd+Shift+S, a login start is quiet through `wasOpenedAtLogin` (login items take no args on macOS 13+), and the island has no `setShape` there, so `createIslandHost` takes `hitTest: 'cursor'`: the window ignores the mouse with `forward: true` and a 50 ms pointer poll takes it back over the strip and popup (`inShape`) or for a whole drag. Tried there: the picker, Local mode starting its server and spawning `claude`, close to hide, `activate`, the island and its click-through (pointer faked), quit by Apple Event; not tried: a signed-in reply, notifications, the voice shortcut, start at login, Apple silicon. The backend side (zsh PATH, the data lock, the vault guard's case) is in [Install](install.md), Phase 0. The NSIS installer always installs per user: `build/installer.nsh` (`customInstallMode`) skips the "Only for me / Anyone" page, because an update only replaces an install of the same kind, and a different answer left two installs with two desktop shortcuts. **Windows Local mode runs the server natively** (tested on Windows 11 with Node 26 and Claude Code 2.1.329: a chat, a Bash tool call in Git Bash, an approval card, the busy question and the stop). `startLocalServer` spawns `electron.exe` as Node with `windowsHide`, and since Windows has no SIGTERM (`child.kill` is TerminateProcess, so the server could never close cleanly) it uses the same stdin channel as WSL: `ZUMIBOT_STDIN_CONTROL=1`, `serveStdinControl` (`control.ts`) answers `busy`/`processes` lines with `CONTROL <what> <n>`, the end of stdin stops the server as SIGTERM would, and a shell that dies takes its server with it. The kill fallback is `killTree` (`taskkill /T /F`), so claude runs never outlive it. What the server does differently on Windows: [Install and first-run setup](install.md), Windows. Start at login uses `app.setLoginItemSettings` off Linux, and `app.setAppUserModelId` makes toasts show. The main and Sync windows set `icon: APP_ICON` (`window.ts`, the build icon copied next to the main bundle as `tray.png`): Windows takes the taskbar and Alt+Tab icon from the window, so without it a dev run shows Electron's. **WSL2 is still there on request:** `ZUMIBOT_LOCAL_WSL=1` makes `localRunsInWsl` (`servers.ts`) true, and then the picker asks `pages:localKind` and shows the WSL2 note, and `startLocalServer` with `wsl: true` spawns `wsl.exe --exec bash -lic 'source <(printenv ZUMIBOT_WSL_SCRIPT)'` (`wslLaunch.ts`) in the default distribution: the script travels in env, so argv holds no quotes for Windows' quoting to break, and checks `node` (≥ 22; exit 120/121) and that the entry is readable (122) before `exec node` on the bundled (or downloaded) `server.mjs`; `-i` so `~/.bashrc` puts nvm's `node` on PATH. `WSLENV` forwards only the server's variables (`/u`) and translates the entry and `ZUMIBOT_LOCAL_UPDATES` to `/mnt/<drive>` paths (`/p`), so Local updates keep working; the data folder, `claude` and `~/.claude/agents` are then the WSL user's. WSL2's localhost forwarding makes the server's `127.0.0.1:<port>` the shell's. The start timeout is 60 s there (a cold VM boots first), and `wslStartError` turns a missing `wsl.exe` or the script's exit codes into what to install. The WSL path has not been run on real Windows: its tests drive the real script through a stand-in `wsl.exe`. How to run, sign and publish: [Electron cloud build](../ELECTRON_CLOUD_BUILD.md).
