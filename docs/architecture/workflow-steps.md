# HTTP, Transform, Sub-workflow, failure path, Room step and routine parity

**HTTP request, Transform, Sub-workflow and the failure path (`shared/src/workflowHttp.ts`, `workflowTransform.ts`, `backend/src/core/workflows/httpCalls.ts`, `httpStep.ts`).** **HTTP request** (`kind: 'http'`: `method`, `url`, `headers`, `body?`, `bodyType` `json`/`text`, `key?`) makes one request with no model and no cost. Every template is filled raw (`fillTemplate`'s `encode` and `vars` options): the address's scheme and host must be literal (`fixedOrigin`: a `{{` only after the first `/ ? #` past the host, else the problem `ORIGIN_TEXT`; no credentials in it), each value filled into it is `encodeURIComponent`-ed and the filled origin is checked again, so no webhook or model value picks the host; a `json` body escapes a value inside a string literal (`jsonStringPlaceholders`) and pastes one outside as is, then must parse; header names are tokens, never `Host`, `Content-Length`, `Cookie` and the like, and a filled value with a line break fails the visit. `key` is a vault API key's item id whose **Workflow HTTP steps can use this** switch is on (`ApiKeyBody.workflows`, `VaultStore.workflowKey`, read per request): the step writes `{{key}}` where it goes (`{{key}}` without a key, or a key never used, is a problem; a key gone or not allowed is the server's problem `KEY_UNAVAILABLE`), and `scrubKey` turns its raw, URL-encoded and JSON-escaped forms into `[vault: <name>]` in the output, the error and the stored `Visit.http {method, url, status?}`. Zumi Bot's format never shows or sets `key` (an edit keeps the stored one). A filled value that makes a `.` or `..` path segment (alone, or with literal dots or `%2e` around it) fails the visit `DOT_SEGMENT`, since the URL parser would move the path (and its key) elsewhere: the template is filled a second time with every value as `x`, and a dot segment that fill does not have came from a value (the step's own literal `..` stays the user's). **Address guard.** `httpCall` (over `node:http`/`node:https`, `agent: false`) resolves the host once per hop, refuses it unless every address is public (`checkedAddresses` and `publicOrLocal` in `core/addressGuard.ts`, the guard AG-UI uses: loopback, private, link-local and cloud metadata, CGNAT, IPv4-mapped, NAT64, 6to4 and reserved ranges all refused; a mixed answer too) with the fixed sentence `HTTP_NOT_PUBLIC` (`HTTP_NOT_RESOLVED` for a name with no address), and connects through `pinnedLookup` to the checked address, so DNS cannot answer differently in between. **Allow local network** (`allowLocalNetwork: true`, stored only when on; absent, as on every older step, is public only; the inspector's checkbox, "Lets the step reach this machine and the LAN") also lets loopback and private addresses through (`HttpRequest.allowLocal`), never link-local, metadata or reserved ones. Zumi Bot's format never shows or sets it: `workflow_get` leaves it out, and a save ignores a sent one and keeps the stored step's (stripped unless already set), as the vault `key`. It sends `Accept: */*` and `User-Agent: ZumiBot` unless the step names its own, follows at most 5 same-origin redirects, each checked again (a cross-origin one is the answer, so headers never reach another host), times out at 60 s, reads at most 1 MiB, and refuses a body past `OUTPUT_MAX` or holding a NUL; 2xx and 3xx are done, anything else fails `HTTP <status>` keeping the body as the visit's `output`; JSON bodies are pretty-printed; errors are fixed sentences or a bare error code, never a message that could hold the address. The request goes out apart from the run's queue, its answer comes back through it; Stop aborts it; a running one at a restart fails `Interrupted by a restart` (cause `restart`, Retry), since it may have landed. **Transform** (`kind: 'transform'`: `fields [{name, path}]` 1 to 20, `format` `json`/`lines`) parses its input as JSON (else `The input is not JSON`) and reads each path (`parsePath`: dots, numbers index, `*`, `[n]`, `[]`/`[*]`, a leading `$`; own keys only): `json` is an object of the fields (missing ones null), `lines` one value per line (lists one line per element, text with its line breaks as spaces, objects as compact JSON, nulls left out), the shape a For each reads; missing paths go to `Visit.missing`; pure, so recover() runs it again. Both have Run step. **Sub-workflow** (`kind: 'workflow'`: `workflow` id, `input` template default `{{input}}`, filled raw) names its child run's id in the visit's opening write (`Visit.childRunId`, so a restart starts it under that id or finds it, never twice) and starts it through the runner's own `start` (`via: 'workflow'`, `WorkflowRun.parent {workflowId, runId, visitId, name, stepName, depth}`), whether or not the child is switched on, under the child's own caps and problems. The child's `{{trigger.text}}` is material (`TemplateCtx.trigger.material`), wrapped as `<input from="trigger">` for a model. While the child waits the parent visit waits (`childMoved`), and its end (`ended`, called from `advance`, `halt` and `endAs`, never awaited inside the child's queue) settles the visit on the parent's queue: done hands on `childOutput` (the end visits: done visits whose port has no edge leaving it, latest per step, by end time, joined like a multi-input step), failed is `Sub-workflow failed: <error>`, stopped is `Sub-workflow was stopped` (cause `user`); the visit's cost is the child run's. Stop on the parent stops its open children; a child's failure sends no push (the parent's does); past depth 3 (`SUBWORKFLOW_DEPTH_MAX`) the visit fails `Sub-workflows nest more than 3 deep`; a step naming its own workflow is a problem (`problemsOf` takes the workflow's `id`), a missing one the server's. The run view and Audit log link both ways (`parentLine`, **Open run**), and the sidebar tags a child's run `sub-workflow`. **The failure path.** Agent, For each, LLM, Condition, HTTP request, Transform and Sub-workflow steps (`FAILING_KINDS`) have **On failure**: Stop the run (absent) or `onFailure: 'branch'`, which adds the `error` port (`stepPorts`; `parseEdges` takes the steps and refuses an `error` edge from any other step; `setFailurePath` off drops its edges; drawn red and dashed, "Failed"). A visit that fails by itself (cause `step`, not `Ran too many times` or a missing step) on such a step with an `error` edge ends `failed` with `port: 'error'` (`handledFailure`): `failureText` (the error, then its output) goes along those edges, the run is not halted, and `outcome`, `summaryOf`'s failed list, the run's `error` and the failure push ignore it (`haltingFailure`); it can't be Retried. A For each failure carries its failed items' list; a list it can't split fails at its open and may take the path, so `progress` starts again until nothing more can. A stop, a restart or the user's own action still halts. Zumi Bot writes `error` edges and its save sets `onFailure` from them (`workflow_get` leaves it out). Design: `docs/superpowers/specs/2026-11-12-workflow-http-transform-subworkflow-failure-design.md`.

**Room step (`kind: 'room'`, `shared/src/workflows.ts`, `core/workflows/workflowRooms.ts`, `stepRules.ts`, `stepRuleSave.ts`, `state/workflowRoom.ts`; design: `docs/superpowers/specs/2026-11-12-workflow-room-step-design.md`).** A step that posts its Prompt into a fresh copy of a template group room, which then runs as any room does, and hands on the room's last reply. `room` is the template's chat id (the inspector's picker lists live rooms, with no workflow copies and no A to B chats; a gone or no-longer-room one reads "Room not found", and the server checks again when the step starts). Each visit makes the copy through `cloneRoom` with no handoff (what Clone room › Start over makes: same members, role and folder, no history), marked `ChatMeta.workflow`; the template is never changed. A Retry or a loop's next visit reuses the visit's copy. The Prompt is a template filled as an Agent step's is (`<input>` blocks, `MATERIAL_RULE`); the posted message is the user's own, so `@alpha @beta {{input}}` routes by the mentions and the moderator's pick does not matter. The visit ends done when the room goes quiet (nobody working, nobody queued), its output is the room's last reply, and the copy is archived as an Agent step's chat is (a failed one stays); the copy shows `WorkflowChatBar`. A room that stops at its turn limit (`GROUP_HOP_CAP`, a `paused` notice, `turnOutcome`'s `capped`; routines still read it as done) holds the visit `waiting` (`Visit.capped`, the run `waiting`, the copy left in the sidebar) until the user's own post in the copy, which the step then follows (`resumes` + 1) and ends on when the room goes quiet again; an Edit or Resend of the step's own message ends it "Replaced by an edit or resend". **Approval rules.** The step's `rules` (`StepRule` `{tool, command?, unsandboxed?, agent?}`, at most 100, `parseStep` drops duplicates and refuses the question, plan and `confirmOnly` tools) are standing allows saved in the workflow, copied from the run's snapshot onto each copy as `ChatMeta.workflowRules`. `ChatService` checks them after "Allow for this chat" and the agent's rules: a match (`stepRulesAllow`, the exact `Bash` command and sandbox flag, the member when the rule names one) answers the request with no card, stored as `auto-allowed-workflow`. A pending card in a copy offers **Allow for this step** (`approval-allow-step`, also on the Inbox's card), which allows the call, adds a rule naming the asking member to the copy and, through `workflowEditing.save`, to the saved step (only allowed once when the workflow or step is gone); the inspector lists the rules with Remove and an Add row. Only the user adds rules: Zumi Bot's `workflow_get` leaves `rules` out and its save keeps the stored ones, as an HTTP step's vault `key`. The step is a failing kind (On failure works), Run step is hidden for it (a room's send settles when the message is posted, not when the room goes quiet), the Audit log shows nothing for its visit while the run is open, and the node shows the room's title only. `e2e:workflow-room` covers a run that copies the room, Allow for this step saving a rule, the next run asking nothing, and the bar in the copy.

**Routine parity (Phase 1 of folding routines into workflows; `shared/src/workflowChat.ts`, `core/workflows/workflowAgentSteps.ts`, `workflowRooms.ts`, `core/chat/freshStart.ts`, `state/workflowChat.ts`, `state/workflowStepCommands.ts`; design: `docs/superpowers/specs/2026-11-13-workflow-routine-parity-design.md`).** Everything a routine can do, as optional keys and one step kind (absent means today's behaviour, and each is written only when set, so `sameDef` still finds an older saved version equal). **Chat step** (`kind: 'chat'`: `chat`, `prompt`, `session?: 'fresh'`; a failing kind, ports `out` and `error`, no Run step): posts its prompt into an existing chat or room, as a routine's `target: chat` does. It is a slot of `WorkflowAgentSteps` whose chat is given, not made (`ChatTarget`: `slotId`, `chat`, `session`, `sent`): at start, inside the run's queue, `chatStepProblem` (shared, the editor's note under the picker uses it too: `CHAT_NOT_FOUND`, `CHAT_READ_ONLY` for an A to B chat, `CHAT_OF_WORKFLOW`, Zumi Bot and a missing or broken agent) fails the visit (cause `step`, so On failure can take it); `session: 'fresh'` calls `startFresh` (`core/chat/freshStart.ts`, the routine's reseed rule moved out of `RoutineRunner` so both runners share it; skipped for a pausing or paused chat, whose session Resume needs), then the message goes through `TaskQueue.submit(..., 'routine')` and is followed as an Agent step's turn (a room as a Room step's quiet). The chat is the user's: the step never sets `ChatMeta.workflow` and never adds `workflowSystem`, so the chat's prompt-cache prefix, `WorkflowChatBar`, island listing and notifications stay as they are; a message holding an `<input>` block ends with `MATERIAL_RULE` instead (`workflowRunner.ts`), after the blocks so a leading `/command` stays first. The stored user item carries `workflowSent` (`WorkflowSent`: workflow, run, step and their names then), which draws the `wf-from` sender line and the `WorkflowPrompt` boxes in any chat and, in a room, makes `GroupService` mask the blocks (`maskInputBlocks`, as for a `ChatMeta.workflow` chat) so a webhook value never routes an `@mention`. The chat id comes only from the saved step (never filled from `{{…}}`), and `WorkflowAgentSteps.runsIn(chatId)` is how `SpendCaps` finds the run a chat with no workflow link belongs to, so the turn's cost and cap count as an Agent step's. **Room from agents** (`kind: 'room'` with `members`, `role`, `cwd` and `room: ''`, `roomFromAgents(step)` says which source a step has): `newRoom` in `workflowRooms.ts` makes the room through `createGroup` after `refuseZumiBot` and `refuseCodexMembers`, then titles and links it and copies the step's `rules`, so posting, quiet, turn limit, archive, Retry and loops are the template Room step's own. **Keep** (`keep: true`, `title?` on Agent and Room steps, `section?` on a kept room; not on For each): the chat is not archived when the step ends, takes the step's title, and `ChatMeta.workflow.keep` makes the readers that treat a workflow chat as background treat it as an ordinary one (the turn end's `workflow` flag is false so `replied` and `error` notify, the island lists it, a kept room is put first in its section by `SidebarStore.placeFirst`, a failed write logged and the step goes on); `workflowSystem` and the bar stay, since the workflow made it from its first turn. **Step commands**: the prompts of Agent, For each, Room and Chat steps take a leading `/name` under the routine's rule (`CommandResolver.forRoutine` with the step's saved prompt and its `command` pick, so a filled value never becomes a command; the editor's `/` menu comes from `stepCommandAgents`, `state/workflowStepCommands.ts`; a stale pick falls back to the name, an ambiguous one fails the visit; `todos: true` is ignored). **Run settings**: `Workflow.limitPolicy: 'skip'` ends the run `skipped` with `LIMIT_SKIP_TEXT` the first time a usage limit stops any visit (`WorkflowAgentSteps.waitForLimit` and the bare calls, then `skipRun`, which stops everything as Stop does, silently, no failure push, no Retry), `missedPolicy: 'skip'` stores a late schedule run as `skipped` with `MISSED_TEXT`, and a webhook trigger's `condition` is checked by `checkCondition` (`core/jev/webhookCondition.ts`) after the filters and only for real calls, storing `CONDITION_TEXT` and the `ConditionCheck` on a miss (`met: null` or a Jev failure runs). Zumi Bot's workflow format takes all of these (`chat` as an id or an app link, `members`/`role`/`cwd`, `keep`, `title`, the two policies, `condition`; never `command` or `section`, an edit keeps the stored ones), saved history carries them (`workflowChanges` adds "Run settings changed"), and an agent rename moves Room `members` and every step's `command.agent` (`renameWorkflowDef`, the run snapshots too). `e2e:workflows` cases 22 to 26 drive them.
