# Agent commands

**Agent commands.** An agent can offer saved prompts as `/name`, listed in its frontmatter `commands:` (`name`, `description`, `prompt`, and an optional `todos: true`; `shared/src/commands.ts`, `$ARGUMENTS` is replaced by the text after the command). The user's send, edit and resend resolve one in the RPC handlers through `CommandResolver`; a routine run resolves its own through `forRoutine`, from the agent file as it is at run time. A routine's command comes only from its saved prompt: the `/name` must lead the prompt before the webhook `{{fields}}` are filled, so a caller's text can never become a command. The routine editor's prompt field has the same `/` menu (no `/btw`), and its pick is saved as `Routine.command` while the prompt still starts with that name; at run time a stale pick falls back to the name alone, and only a name several room members share without a pick fails the run. The composer's `/` menu (only at the start of the text; in a room it groups the members' commands) sends a `CommandPick` `{agent, name}` and the server looks the prompt up itself. The resolved command is stored on the user item as `command` (agent, name and the filled prompt, so editing the agent file never changes history), while `text` stays the short form (`/check <args>`) that the bubble shows with a chip and a "Full prompt" toggle (a card comment's ask shows the toggle too, see [To-dos](todos.md)). Only the command's own agent reads the filled prompt, through `readAs`/`withCommands`; other agents and the moderator read `text`. In a room it is routed as a user mention of the command's agent. A command whose owner is gone or broken gets no notice, the same as an @mention of such an agent. An unknown `/name` is sent as typed. A card's comment box has its own `/` list of the mentioned agents' commands, anywhere in the text (see [To-dos](todos.md), Threads and `@agent` in comments). `todos: true` makes every use of the command ask for the chat's to-do list, a routine run's included, as a leading `/todo` does (see [To-dos](todos.md)); the routine editor's `/` menu shows the same ☑ mark as the composer's; the flag is stored on the user item, and `todo` is a reserved command name. A leading `/todo` is split off before the command resolves, so `/todo /check` resolves `/check`. Prompts written by Zumi Bot are YAML block scalars, since a plain scalar breaks on `: ` or `#`. A command may name a `model` (`opus`, `sonnet` or `haiku`; `shared/src/chatModel.ts`), stored on the user item's `command`. The prompt cache belongs to one model, so in a single chat `ChatService.turnModelOf` (pure rule `turnModel`) applies it only when the turn starts a session (a new chat or a reseed), saving it as `ChatMeta.model`, which every later turn of that chat runs on (`--model`, which beats the agent file's `model:`); in a running session only a stronger command's model switches up, never down, and a switch to the agent's own model clears it. Compact, side runs (`SideBase.args.model`, and `baseFor` in `app.ts`) and forks use the chat's model so they share its cache. A single chat and the new-chat screen show a model picker (`ModelPicker.tsx` over the pure `modelPicker` in `state/commandModel.ts`): it reads `Default (<agent's model>)` (plain `Default` for one that inherits), names the model the next message runs on, and previews a typed command's model as `Sonnet · /card` through the same `turnModel` rule the server runs (so in a running session only a stronger one shows). A pick (`chats:setModel`, through `patchInPlace` so the sidebar order stays; refused in an A→B chat) saves `ChatMeta.model` with `modelByHand: true`, and `turnModel`'s `byHand` then skips every command's model; picking Default clears both, so commands apply again. A pick on the new-chat screen is `NewChatDraft.model`, set on the chat right after it is made (only when it fits the agent's engine); Fork keeps both keys. The mode and effort pickers beside it, all three drawn by `ChoicePicker.tsx`: [Chat mode and effort](chat-mode-and-effort.md). A Codex agent's picker reads `Default (<its file's model>)`, offers `agents:codexInfo`'s visible models and previews no command (Codex runs none); its pick reaches the main thread, Compact and side runs as `thread.model` (`spec.model`, then the agent file's). `modelFits` (`shared/src/chatModel.ts`) makes `setModel` refuse a model the chat's engine does not run (`MODEL_REFUSED`), and `engineChatModel` makes each run read only its own engine's model (a Claude turn only Opus/Sonnet/Haiku, a Codex turn only a Codex name picked by hand), so after an engine switch the old pick is ignored, never handed to the other CLI. Switching a running Codex thread's model (`thread/resume` with another `model`) is unprobed against real codex. The picker is hidden in rooms. Rooms ignore command models. Agent Studio's commands card has a Model select (the agent's model removes the key).

**`/run-workflow`.** A built-in command beside `/btw` and `/todo` (`shared/src/runWorkflow.ts`; `run-workflow` is reserved, so an agent's command of that name never shows in the menu, `filterCommands`). The `/` menu lists it (top level only; `runWorkflow: false` hides it, as the island and the new-chat screen do, `offersRunWorkflow`); after `/run-workflow ` the composer shows a **Workflows** list of the workflows by name (`workflowQuery`, `filterWorkflowNames`: names starting with the query, then names with a word starting with it, at most `WORKFLOW_MENU_MAX` 8; `WorkflowMenu` in `CommandMenu.tsx`), and a pick inserts `<name> ` and keeps the workflow's id (`keepWorkflowPick`: only while the text still starts with `/run-workflow <its name>`; the list stays closed while the pick holds, `workflowMenuQuery`, so Enter then sends). A send whose text starts with `/run-workflow` (a word boundary after it, as `/btw`) routes through `routeSend` to `workflows:runFromChat(chatId, text, workflowId?)` (`App.tsx#runWorkflowFromChat`, the whole text, the server cutting the command) instead of the agent: a pick's id names the workflow, else the server finds it by the longest name the text starts with, so typing it by hand works the same, and the rest is the run's input; the draft clears and a "Started <workflow>" notice with **Open run** shows. The new-chat screen and the island refuse it with a notice (`workflowRefusal`, `noRunWorkflow`), edits and resends never route it, and a routine's prompt field has no such menu. Details of the run: [Workflows](workflows.md), Triggers.

**Engine commands.** Beside the agent's own saved prompts, a single chat offers the agent engine's own commands: Claude Code's for a Claude agent (Zumi Bot counts as Claude), Codex's skills for a Codex agent; ACP, AG-UI and unknown or broken agents get none. `agents:engineCommands(agent, folder)` (null folder = home) returns `{engine, commands: [{name, description, hint?}]}` from `ExtensionsService.engineCommands`, which runs a commands-only probe (`probeClaudeCommands`: `initialize`, whose `commands` list the CLI answers, and `get_skills_dialog`, whose names mark which of those rows are skills (a claude.ai skill, listed there as `anthropic-skills:pdf`, by its short name for a non-built-in row; a refused listing makes every row a command), with the least a command list needs, `commandsProbeArgs`: only the run config's `skillOverrides` and `enabledPlugins` (so a skill or plugin the agent switched off stays off), `disableAllHooks: true`, `--strict-mcp-config` and no `--mcp-config`, and the base env with no agent keys or own servers' values, since this probe starts on its own when a chat opens or a folder is picked, so a cloned repo's hooks or MCP servers never run for it; no MCP wait and no model call; `probeCodexCommands`: `mcpServerStatus/list` first (its answer unused, but the plugins' skills appear only after it; waited for at most 5 s, then `skills/list` is asked anyway), then `skills/list`, asked again until two answers hold as many skills; both 15 s) and reads the raw answer into rows at once (`engineCommandRows.ts`, pure, field by field; the raw answer, which holds the account, is never cached or passed on, and a probe that fails or finds no CLI gives no rows, is not cached and logs one fixed line naming the engine and an error's code, never output, a path or a value; a `hint` is cut at 80 characters). Claude rows keep a valid name, the first line of the description (300 characters) and `argumentHint`; they drop `__` names, the `codex:` plugin's commands (they hand the work to Codex; a chat's menu shows only its own engine's), ZumiBot's reserved `btw`, `todo`, `run-workflow`, duplicates, and any row the CLI marks `builtin: true` whose name is in `CLAUDE_DENIED` (`shared/src/engineCommands.ts`: the built-ins that open a screen or change a setting, such as `/model`, `/usage`, `/compact`, `/mcp`, since ZumiBot has its own controls; a user's own command of such a name is kept, and built-ins that act, such as `/goal`, stay). Codex rows keep an enabled skill with a name, minus a `claude:` plugin's skills (the same rule the other way), and the skill's `path` (its SKILL.md) stays on the server, never in the RPC answer or on a stored item. The cache is per folder, agent and agent-file hash (100 entries, its own, so a loadout refresh never waits on it); an entry older than `ENGINE_COMMANDS_STALE_MS` (5 minutes) is returned at once and re-probed once in the background, and the probe shares the loadout's two slots, abort and `forget()` (see [Servers, plugins, skills and hooks](extensions.md)). A pick is a `CommandPick` with `engine` (`commandPick` in `rpc/handlers.ts` checks it). In `CommandResolver.forSend` an engine pick must still lead the text and belong to the chat's agent (a room throws "Engine commands run only in a single chat"); a pick whose name no longer leads the text is dropped. A Claude command is sent as typed (`prompt` = the text; the CLI decides whether the name exists, so no probe is waited on); a Codex one needs the skill still listed (else `Codex has no $name skill any more`) and its prompt is `$name args` (`codexPrompt`). A command typed by hand works the same, but only when no agent command of that name exists (an agent's own command wins) and the engine list holds the name; for a Claude agent that list is read from the cache only (`ExtensionsService.cachedEngineCommands`), so a cold cache never holds up a send and the text goes out as typed, without the chip, while a Codex agent's is probed, since a hand-typed skill needs it; one the list lacks is sent as plain text, as an unknown `/name` always was. The name is read by `engineLeading`, wider than an agent command's (uppercase, `:` for plugin commands, `.`, `_`). The user item stores `command: {agent, name, prompt, engine}`; Edit and Resend (`forRerun`) keep the old command's `engine` in the pick when the name still leads. A Claude command runs only as the first thing in the message, so `ChatService` puts a reply's quote after the text (`withReply(…, after)`) instead of before it. A Codex turn looks the skill up again at the start (`ExtensionsService.codexSkill`) and sends its `{type: 'skill', name, path}` item after the content (`codexInput`, `spec.skills`; never on a Compact), so one removed since the menu was built is that turn's error before anything is stored. Accepted limits: a reseeded turn (the earlier session cannot be reused: after an engine switch, an expired or rebuilt session, a refused cut; a Claude Edit or Resend that can cut the session is not one) puts history before the message, so a Claude command there is read as text, not run; rooms get no engine rows, and a typed `/name` there stays text; a built-in that prints a report (`/insights`, `/doctor`) shows as a reply from a synthetic assistant message, as the CLI sends it; a routine's saved prompt that leads with an engine row's name (one an agent-command name could be, lowercase with hyphens) resolves through the engine too, since `forRoutine` ends in the typed-by-hand rule, while the routine editor's `/` menu stays agent commands only. Design: `docs/superpowers/specs/2026-11-24-engine-slash-commands-design.md`.

**Engine rows in the `/` menu (UI).** A single chat's composer and the new-chat screen (not rooms, the island or the editors) list the agent engine's own commands: Claude Code commands for a Claude agent, Codex skills for a Codex agent. `filterCommands` orders the menu as the agent's own commands, ZumiBot's built-ins (`/btw`, `/todo`, `/run-workflow`), the engine's skills (`kind: 'skill'`, every Codex row), then the engine's other commands, each group by name prefix then description word; a room draws its agent groups before the built-ins in the same order, so arrow keys follow the rows. `net/useEngineCommands.ts` asks `agents.engineCommands(agent, folder)` when the agent or folder changes, after a reconnect and on `extensions:changed` and `agents:changed` (a null new-chat folder is the scratch one, which the server maps to home); it is null while loading, on an error and for ACP/AG-UI agents, drops an answer for an older key, and keeps the shown list when a refetch fails. `Composer` takes it as `engineCommands`, passes it to `filterCommands` (`opts.engine`) and `keepPick`, and an engine row sets the pick `{agent: <the chat's agent>, name, engine}`; `keepPick` drops it when the agent was switched, the name edited, or the list no longer holds the name. `CommandMenu` draws an engine row as `/name`, a muted `command-hint` span, the description (two lines at most), and a label at the end of the name line (`skill` for a skill, else the engine's name, `claude`/`codex`; `data-testid="command-engine"`); the hint keeps to one line and gives way to the name, and the full hint and description are tooltips (`data-tip`); its key is `engine:<engine>/<name>` and it has no `data-agent-name`. A sent engine command is stored on the user item (shape in Engine commands above); `CommandBubble` shows its chip with the engine label and no "Full prompt" toggle (`MessageList` gives it no footer), and `chipBroken` judges it by the agent alone, since the name is not in the agent's own list.
