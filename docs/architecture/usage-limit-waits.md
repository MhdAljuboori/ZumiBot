# Usage limit waits

**Usage limit waits (`core/chat/limitResumes.ts`, `shared/src/limitResume.ts`).** A chat or room whose last turn the usage limit stopped continues by itself after the reset, as a routine run does. The rule is the routines' one (`limitStop`): the turn's errors are all `limit` errors with a known reset; a `/compact` the limit stopped carries `limit.compact` and counts neither way. On `onIdle` (after the task queue and the routine runner) `LimitResumes.idle` stores `ChatMeta.resume` `{at, after, waits}` through `patchInPlace` (sidebar order kept) at 60 s past the last reset (`resumeTime`), and at `at` sends `continue` (`@member continue` per stopped room member, `continueText`) through `TaskQueue.continueLimit`, which sends it at once ahead of the queued tasks, only while the wait on that turn still stands (`'gone'` otherwise) and the chat is idle (`'busy'` while a compaction runs: the wait stays, and the compaction's idle arms it again). **Queued tasks.** Messages queued behind a turn the limit stopped never go one after another into the limit: while `resume` is stored the pump sends none (also at start-up), and the tasks follow the continue's turn, oldest first. The pump reads the chat only after `TaskQueueDeps.limitChecked` (`LimitResumes.settled`, the chat's queued steps, the idle's check included) resolves, since the same `onIdle` woke both and the check must store the wait first. A turn the limit stopped (`limitHit`) that nothing continues by itself (a routine run's turn, an unknown reset, another error beside the limit, or the continues in a row past the cap) holds the tray (`held`) instead, for Send now. While a wait stands a message the user writes goes straight in, as into a held tray (`sendsAsTask`), and the tray offers Send now (`tasksHeld`); either ends the wait. It leaves alone a routine run's turn (the runner's `messagesOf`, read before `chatIdle` settles it, since the run's own `limitPolicy` decides), an A→B chat (the limit goes back to A as the ask's result) and a running chat. Any new message, edit, resend, version switch or Send now ends the wait (`TaskQueue`'s `onNewTurn`, awaited under its lock, never a compact). **Continue now** (`chats:continueNow`, `LimitResumes.continueNow`, refused in an A→B chat) sends the wait's continue at once, ahead of the tasks, as the user's own message (no `auto`); **Don't continue** (`chats:cancelResume`, `LimitResumes.dontContinue`) drops the wait and holds the tasks in the same write. Neither runs inside `LimitResumes`' per-chat steps while it waits on the task queue's lock, since the pump holds that lock while it waits on those steps. Continues the wait sent itself count in a row (in memory) and stop after 5 (`LIMIT_MAX_RESUMES`). A timer that finds the wait gone or its turn no longer last sends nothing. `recover()` re-arms stored waits at start (one already due goes at once) and `stop()` holds them at shutdown. The UI (`state/limitNotice.ts`) draws a limit error as a notice instead of the red error: "Usage limit reached · continues today at 22:21" with **Continue now** and **Don't continue** (`limit-notice`, `data-state="waiting"`, `limit-continue`, `limit-cancel`) while the wait belongs to its turn (`waitingErrors`), else "… · resets today at 22:20", or the room member's name in a room. **With Pause.** A pausing or paused chat stores no wait (`check` skips it, also inside the write), so a limit that ends a pausing turn still lands it paused and only Resume continues it; a wait stored just before a pause landed is dropped without a send when it comes due, `waitingErrors` shows none in a paused chat, and Resume's Continue ends a wait like any new message (`onNewTurn`). The wait's own `continue` goes in through `continueLimit`, which sends nothing into a paused chat; it is `auto`, a message the user did not type.
