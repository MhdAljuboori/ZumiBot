# Deploy and sync

A server is installed by `zumi-bot-server/deploy/install.sh` as a systemd **user** unit (`systemctl --user … zumibot`, no sudo) and updated from a release: push a `v<version>` tag, then use the in-app Update or `zumibot-update` on the host (see [Install and first-run setup](install.md)). There is no `npm run deploy` any more: it rsynced a local build and restarted a system unit through a passwordless sudo rule, and both are gone, so no `zumibot.service` system unit ships either. Background processes do not count as busy (a dev server may run for hours): `zumibot-server processes` (the control socket's `processes` line; an older server answers `error`, read as none) gives their count, and sync only warns that the restart stops them (see [Background processes](processes.md)). First-time proxy setup, the one root step, is in `zumi-bot-server/deploy/SETUP-VPS.md`. `sync.mjs` is not part of a container install: an image is rebuilt and recreated in place, and its data lives in volumes, so it applies only to a VPS reached over ssh.

`zumi-bot-server/deploy/config.mjs` holds what `sync.mjs` and the desktop share: the `deploy.env` parser, the host and dir allow-lists, the ssh options, `realRun` and the vault key rule. `deploy.env` (git-ignored, see `deploy.env.example`) still names the VPS (`VPS_HOST`, `VPS_USER`, `VPS_DIR`) for sync.

`npm run sync` (`zumi-bot-server/deploy/sync.mjs`, reading `deploy.env`) syncs ZumiBot data and `~/.claude` both ways between this PC and the VPS. It refuses while a reply runs on the VPS or the app runs locally, and never deletes: chats are joined (a chat with new messages on both sides keeps both, in time order; each agent's Claude session keeps only the newer side; read and archive times keep the later of each side), other files go newest-wins (`settings.json`, `sidebar.json`, `usage.json`, the run files, and `connectors.json`, the claude.ai connector switches, which keep their 0600 mode in both directions and hold no secret; see [Connectors](connectors.md)), and replaced files land in `~/zumibot-sync-backup-<time>/` on each side. That folder, and its `incoming/` upload folder on the VPS, are made 0700 (`mkdirSync` with `mode` plus a `chmod`, since the umask masks it; `umask 077; mkdir -p -m 700` over ssh): the copies keep their own 0664 modes, so the folder is what keeps chats and settings from other users. `chats/<id>.btw.json` joins side questions by entry id: finished answers win over open ones, then later `endedAt`, then this PC; copy chats keep entries anchored in their copied items (or null). `todos.json` (the task board, every chat's to-dos in one list) joins items by item id (`mergeTodos`: the later `updatedAt` wins, so a removal stays removed and nothing is deleted); a `chats/<id>.todos.json` from a machine still on a version before the board is joined the same way, and the next start of either side moves it onto the board, written 0600 and pushed with the files beside `workflow-messages.json`, so it travels both ways. A copy chat keeps no queued tasks, `held`, `pause`, `lost` or `GroupInfo.paused`/`lost`: Resume and the killed-subagents note stay with the original. Its sessions start at the stamps its items hold, each marked with the engine its stamp names, whatever it is (`sessionEngine`, or each room member's in `GroupInfo.sessionEngines`), so a Codex, ACP or AG-UI session never reaches `claude --resume`. A remote agent's `chats/<id>.agui.json` (its thread, state and open interrupts) comes from the VPS with a chat whose items do, and a copy chat gets none: it starts a new thread (the runner ignores a file whose `threadId` is not the chat's). Routines and workflows stay enabled on the VPS only (the local copies of `routines.json` and `workflows.json` are switched off, and their saved versions in `history/` are copied from the VPS over this PC's, never deleted), `workflow-runs.json` is newest-wins like `routine-runs.json`, `routine-hooks.json` and `workflow-hooks.json` (webhook secrets) stay on the machine that made them, a workflow Agent step's chat carries its `ChatMeta.workflow` link, and `auth.json` stays on the VPS. `workflow-messages.json` (the Inbox's Notify messages) is joined by message id (`mergeWorkflowMessages`): the later `updatedAt` wins per message (archive, unarchive, delete and Undo each bump it; a tie goes to this PC), a delete is a tombstone (`deletedAt`) that wins over an older archive, so a deleted message never comes back, `seenAt` keeps the later side, entries without an id or finite times are dropped, and the 500 cap and the one-year tombstone rule run after the join; it travels both ways (it is in the push list beside `usage-records.jsonl`, so the joined file reaches the VPS, 0600), since a manual run on this PC may notify too. A pulled `workflow-runs.json` holds the VPS's unfinished runs as `stopped` ("Continues on the VPS", their open visits stopped, the VPS file's time kept for newest-wins), so the local server's `recover()` never runs their steps a second time. A chat's usage limit wait (`ChatMeta.resume`) is dropped on both sides, since either server holding it would send the `continue`; so are its waiting `/later` messages (`ChatMeta.later`), for the same reason, and the sync says how many it dropped (counted once by id across both sides) so the user can type them again. `vault.json` joins by item id with no key needed (later `updatedAt` wins, a tie goes to the tombstone, then the VPS), and the vault key, which lives outside the data dir, travels over ssh stdin/stdout only: copied to a side that has none, or, when the keys differ, this PC's items are re-sealed under the VPS key (see [Vault](vault.md)). `notify-devices.json` and `notify-vapid.json` stay on the machine that made them (a push subscription only works with the VAPID keys it was made under). So does `protocol-launch.json` (the ACP launches confirmed in Agent Studio): each machine confirms its own, since the same command can be another binary on the other one. `claude-tmp/` (each chat's CLI temp root) is never copied: its paths belong to one machine and it is working state, like `desktops/`; `processes/` (background processes and their logs) is the same, and sync warns when the VPS restart at its end will stop some. `audit/` (the audit log, see [Governance](governance.md)) is never copied either, nor put in the sync's backup: each machine keeps the record of its own runs, and exports from both join by record id (`LOCAL_ONLY_EXCLUDES` in `sync.mjs`). The VPS server caches the chat index, so the pushed files are swapped and the service restarted (`systemctl --user restart zumibot`, no sudo) in one ssh call, only if the VPS index has not changed since the pull. A failed restart says to run `systemctl --user status zumibot` there. `~/.claude/agent-memory` is synced like the other agent folders, so a memory deleted on one machine comes back from the other (the Trash is the undo); `MEMORY.md` is one whole file, newest wins, and the server repairs its index afterwards. `file-snapshots/` is copied like `attachments/` (copies never change, so a union is enough), and a copy chat gets its folder under its new id. Plugins and `~/.claude/settings.json` are only reported, not copied.

**Settings › Sync & server**'s **Sync…** runs the same `sync()` from the desktop shell (`src/main/syncDesktop.ts`, lifecycle in `syncFlow.ts`): the build copies `sync.mjs`, `config.mjs` and `src/sync/runner.mjs` to `resources/sync`, run with Electron's Node, so an installed `.deb` needs no checkout. VPS settings come from `deploy.env` in dev, or from `sync.env` in userData (only `VPS_HOST`/`VPS_USER`/`VPS_DIR`, imported from a chosen `deploy.env`). It saves dirty edits, refuses while local replies run, stops the local server and reconnects afterward, even on failure. Browsers get the fixed `zumibot://sync` link (registered by the `.deb`); the shell accepts no parameters on it and always asks for native confirmation. A phone or tablet (`mobileDevice` in `state/settings.ts`) gets no link, since nothing there can open it, only a note to start Sync from the desktop app on the PC.

`channels.json` comes from the VPS with every platform's `run` off (`disableChannels`), as routines do, since one bot can be polled by one machine only; it is never pushed. `channel-state.json` and `channel-tokens.json` are per machine and excluded from the pull (`PULL_EXCLUDES`): the update offset and the sealed bot tokens (Telegram's, Slack's bot and app tokens) belong to the machine that runs each bot; Slack's Socket Mode would hand each event to one of two connected machines at random, so the same one-machine rule holds (see [Channels](channels.md)).

`workflow-mail.json` (the email trigger's place in each mailbox) is per machine: sync copies only named files and never this one, and workflows run on the VPS only, so its watchers and polls run there (see [Data folder](data.md)).
