## Built (phase 1)

Route A, as designed. Files: `shared/src/connectors.ts` (the frozen catalog, `connectorOf`, `connectorState`, `isReadTool`, `unknownTools`, `denyEntries`, the page's fixed sentences in `CONNECTOR_TEXT`), `backend/src/core/connectors/` (`connectorStore.ts`, `connectorsGuard.ts`, `migration.ts`, `connectorsService.ts`), `frontend/src/components/ConnectorsSettings.tsx` at `/settings/connectors` with its rules in `frontend/src/state/connectors.ts`, and the `connectors:*` handlers in `rpc/handlers.ts`. `sanitize.ts` sets `LoadoutServer.connector` (the catalog id, or null) from the server's URL and name; the URL itself still never leaves the sanitizer ([Servers, plugins, skills and hooks](extensions.md)).

**`connectors.json`** (data dir, 0600, `writeFileAtomic`; see [Data folder](data.md)) is `{v: 1, agents: {<agent>: [<catalog id>…]}, migration: 'kept' | 'failed', remember: {…}}`. An agent with no entry has every connector off. `migration` records how the first-start switch-over ended; `remember: {<catalog id>: true}` (phase 3, see Built (phase 3)) holds the connectors whose Remember switch is on, and the file the store writes always carries it (`remember: {}` when none is). `ConnectorStore` answers reads from memory and queues every write. A file that is not JSON, or JSON of another shape, is moved to `connectors.json.corrupt-<ms>` and the all-off state (`migration: 'failed'`) is written back, so a restart cannot read "no file" as "not migrated". A file that cannot be read at all (a permission error) reads as all off and is never overwritten: a switch then re-reads it first and fails with a fixed message if it still cannot. Renaming an agent moves its entry in memory before the first await, beside the approvals move, so a run starting in between already sees the new name; a rename or a forget (the agents-folder watcher's removal pass) while the file is unreadable waits for a successful re-read, or is dropped with one log line. Only the user's two RPCs below change a switch (`connectors:setAgent` an agent's, `connectors:setRemember` a service's Remember); besides them the file is written by the switch-over (once, at first start, carrying today's on-state) and by the rename and forget housekeeping, which move or drop entries and never turn anything on.

**RPCs.** `connectors:list(refresh)` returns `{keyVar, migration, error, agents, connectors: [{id, state, tools, unknownTools, on, remember}], at}`, built from `ExtensionsService`'s home-folder loadout (no agent), the catalog and the store; `refresh` skips the loadout cache. `connectors:setAgent(id, agent, on)` checks every argument: a catalog id, a boolean, and an agent that is a Claude agent other than Zumi Bot (Codex, ACP and remote agents never see claude.ai connectors). `connectors:changed` is pushed after a switch, after the switch-over and whenever `extensions:changed` fires, since a write on the Claude Code page can add or remove a catalog server. `connectors:setRemember(id, on)` (phase 3) is the third `connectors:*` handler besides `list` and `setAgent`, checked the same way. No agent tool, workflow step or Zumi Bot action reaches either write.

**The run's deny.** `agentRunConfig` in `app.ts` gives every agent run `connectorsOff`, the catalog connectors the agent has not switched on (even an agent with no readable file; the probe's `serversOff: false` leaves it out so a switched-off connector still shows on the page). `buildAgentRunConfig` turns it into `deniedMcpServers` entries, a `{serverUrl}` for each catalog pattern (the real guard: a claude.ai display name can change or gain a ` (N)`) and a `{serverName}` for each known name, and into the `--disallowedTools mcp__<prefix>` belt, after the agent's own `serversOff` entries and deduped as a whole. Non-catalog servers keep `serversOff` as before. **Zumi Bot** never has a connector and gets no switch: its runs deny every catalog connector. A run whose config read fails (`ChatService.runConfigOf`, and the fresh side base in `app.ts`) falls back to `CONNECTORS_ALL_OFF`, every catalog connector denied and nothing of the agent's own, not to `NO_RUN_CONFIG`: a failed read must not make every connected connector live for that run (only Claude runs reach these paths; a Codex, ACP or remote run takes `NO_RUN_CONFIG`, so its `connectorPrefixes` are empty and none of its calls is ever classed as a connector read or write). **Side runs (`/btw`) and keep-warm pings** reuse the chat's kept side base, so after a switch flip they carry the old deny until the chat's next main turn rebuilds it. That is harmless: they run no tools, since the side guard blocks every tool call.

**Guard.** `connectorsGuardSettings` (`connectorsGuard.ts`) adds deny rules for `Read`, `Edit`, `MultiEdit`, `Write`, `Grep` and `Glob` on `connectors.json` (`//c/...` on Windows, as the vault's), merged with the vault guard into each main run's one `--settings` (`vaultGuard` in `app.ts`). There is **no Bash hook**, unlike the vault's: a Bash write changes nothing until the server restarts, because the store reads the file only at start, and the next switch on the page overwrites it. It is a speed bump against the file tools, not a wall.

**Switch-over** (`connectorsService.migrate`, once per process after listen; `migration.ts` has the pure rule). Today every agent has every connected claude.ai connector, so the first start keeps that: from one home-folder probe it writes each Claude agent's current on-state (each catalog connector connected in the home loadout and not in the agent's `serversOff`, plus a catalog URL among the agent's own servers; an agent with none gets no entry) and sets `migration: 'kept'`. A connector shown as **Turned off in Claude Code** (`status: 'disabled'`) is not in use today, so it is skipped, or it would come alive later without a Connectors decision; one that needs signing in again (`needs-auth`, `failed`) is still the user's connection and is kept. If there is no Claude agent besides Zumi Bot (a fresh install) there is nothing to keep, so it skips the probe and writes `kept` with no agents. If the probe fails (or the loadout reports a servers error), nothing is kept: every connector starts off and `migration` is `failed`, which the page explains. A stop during the switch-over records nothing, so the next start tries again. Until the switch-over settles, a run waits for it for at most 10 s (`ConnectorsService.ready`, see Built (phase 3)) and past that carries **no connector deny** (as before phase 1); the page shows a short "reading your connectors" note and disables its switches.

**The page** (Settings › Connectors, after Claude Code in the nav; a palette entry with the service names as keywords). One card per catalog service: name, state, a blurb, a note on the agents it is on for, one switch per Claude agent (Zumi Bot, Codex, ACP and remote agents have none; fixed lines say why, one per engine present: `connectorEngineNote`, `engineNotes` in `state/connectors.ts`), and a button opening the service's `claude.ai/directory/<id>` page in a new tab (Connect, Reconnect or Manage). GitHub's card opens `claude.ai/customize/connectors` and shows the server URL with a Copy button, since GitHub is added there as a custom connector. States: **Connected**, **Needs attention** (`needs-auth`, `failed`, and also `pending` or `unknown`), **Not connected**, **Turned off in Claude Code** (`disabled`); with several matching servers the best state shows. A probe that failed outright shows every card as **Not checked**. A key variable that stops the CLI loading connectors (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`) gives a page-wide notice that names the variable (`keyVarInUse`), never its value. A fixed note under the intro lines (`CONNECTOR_TEXT.cacheNote`) says a flip makes the agent's next message re-read its whole context once (the deny changes the run's tool definitions, so its cached prefix no longer matches). A tool the catalog does not list shows as "Tools ZumiBot does not know yet". The page probes again when the tab gets focus or becomes visible, at most once every 5 s, because connecting happens on claude.ai. A flip shows at once and a failure reloads the server's view. Settings › Claude Code's Servers tab links here, and a catalog connector's row in Agent Studio says "Set on the Connectors page" (see [Servers, plugins, skills and hooks](extensions.md)).

**Calls made in phase 1** (beyond the proposal above): Zumi Bot never has a connector; runs carry no connector deny during the switch-over; the switch-over skips the probe when no Claude agent besides Zumi Bot exists; the guard has no Bash hook; the page probes again on focus (5 s gap); `pending` and `unknown` read as Needs attention; the e2e harness seeds an all-off `connectors.json` so no other suite runs the switch-over. Open questions 1 to 3 below are settled by the build (route A; switches in `connectors.json`; today's on-state kept). Phase 1 alone classified nothing at the permission step; phase 3 added that (below).

**Sync** carries `connectors.json` newest-wins in both directions, keeping 0600 (`NEWEST_WINS` and the copy lists in `deploy/sync.mjs`; see [Deploy and sync](deploy-and-sync.md)). It holds no secret: on route A the service's tokens stay at claude.ai. The file is synced whole, newest write wins, so a first start on the second machine (its switch-over write) can overwrite switch changes made on the other one in the meantime: sync after the first start, before changing switches.

**Tests.** `npm run e2e:connectors` (fake claude only; checks 1 to 8 are phase 1's, 9 to 13 phase 3's, see Built (phase 3)) runs the switch-over with the harness's `connectors: null`, the page in each state, the switches and a second tab following, the run's `--settings` (URL and name deny, the belt, the file guard), the focus refresh, the Agent Studio and Claude Code links, the key-variable notice (no value anywhere) and a failed switch-over. `npm run e2e:connectors-probe` is **not** part of `npm run e2e`: it uses the real CLI and the user's claude.ai account, so ask first. It lists the connectors with their host and catalog id (settling the Gmail and Calendar hosts), checks that each catalog-named server also matches a catalog URL pattern, and, for **every** connected catalog connector (one result each), checks that a `{serverUrl}` deny removes it and, where the catalog has a name (not GitHub), that a `{serverName}` deny does too. It also checks the tool-name shape (the CLI's tool names for a connector must not all be unknown to the catalog, or the bare names the page and the belt key on are wrong) and runs one `--settings` as a main run merges it, `deniedMcpServers` for every catalog connector plus a `permissions.deny` file rule in the vault guard's form, asserting that no connector is listed and the rule is still in effect (read from `get_settings`; unreadable is INCONCLUSIVE, never PASS). That last run guards against a CLI that rejects a `serverUrl` entry and silently drops the whole settings object, the vault guard with it. Phase 3 added check f, one short Haiku run (Built (phase 3)). It never prints a token, a tool payload or a URL beyond its host.

## Built (phase 3)

Connector reads run freely; a write gets a card in an attended run and is refused in an unattended one. Files: `shared/src/connectors.ts` (`connectorPrefixes`, `connectorCallOf`, `askRules`, `unattendedRefusal`, `CONNECTOR_TEXT.cardAccount`, `guardNote`, `rememberLabel`), `agentRunConfig.ts` (the prefixes and the ask rules), `chatService.ts` (the permission step), `groupService.ts` and `askService.ts` (who is attended), `connectorsService.ts` / `connectorStore.ts` (`remember`, name learning), `ApprovalCard.tsx` with `state/approvals.ts`, and `ConnectorsSettings.tsx`.

**Ask rules.** For every connector that is on for the agent, the run's one `--settings` gets `permissions.ask: ['mcp__<prefix>__*', …]` (`askRules`), merged with the guard's `permissions.deny`, so every connector call reaches ZumiBot's permission step even in auto mode (by Claude Code's documented rule order an ask match prompts even when an allow rule also matches; the probe's check f is what checks that on the real CLI, result pending). A connector that is off has no rule (it is denied outright). The prefixes are the catalog's claude.ai names plus the names the CLI gave the catalog servers the home folder lists (`connectorPrefixes`), and a run's `AgentRunConfig` carries them as `connectorPrefixes`.

**The permission step** (`ChatService`, per `can_use_tool`). `connectorCallOf` takes the LONGEST prefix `p` with the tool name starting `${p}__` (so `claude.ai Gmail (2)` never reads as `Gmail`'s tool) and gives `{id, tool}`. A **read** (`isReadTool`: listed in the catalog's read list) is answered allow with no card. A **write**, or any tool the catalog does not list, in an **attended** chat gets an approval card stamped `connector: {id, tool, remember}`; in an **unattended** turn (`auto`) it is denied with `unattendedRefusal(id, tool)` (`Gmail send_message changes data outside this machine. Runs started by a routine or workflow may only read; ask the user to do this in a chat.`) before any card, so the run goes on and reports. Side runs (`/btw`) needed no change: their guard already refuses every tool.

**The card** says the service and tool in its head (`Gmail · send_message`), "As connected on claude.ai" (ZumiBot cannot see the account), and shows the input open. With **Remember** off it offers Allow once and Deny only; with it on, also Allow for this chat and Allow always for this agent. It never offers Allow for this step, since a step's rule is not a connector's. A remembered approval (`allowed` chat set, `agentRules`) reaches a connector write only while its Remember switch is on, and the server checks the switch again when the answer comes: with it off, an allow-chat, allow-agent or allow-step answer is kept as allow-once. A step rule never allows a connector call.

**Remember** is a per-service switch on each card of Settings › Connectors (`connectors:setRemember(id, on)`, checked like `setAgent`; `remember` in `connectors.json`; no agent tool, workflow step or Zumi Bot action reaches it). A fixed note (`CONNECTOR_TEXT.guardNote`) under the intro lines says reads are free, changes ask and routines only read.

**Calls made in phase 3.**
- Own servers count as a connector only by a catalog URL match: an agent server merely NAMED like a connector is not one. A passed own server also shadows a catalog or learned name it collides with (its prefix is dropped), so its tools are never taken for the connector's and never run unasked.
- For a server outside the agent's own file (one the home folder lists), a name that normalizes to exactly a connector's tool prefix is classified as that connector (a known name-only limit; its URL is not checked at the permission step). The agent's own passed servers are not subject to it: the shadowing rule above drops the prefix of an own server whose URL is not the connector's.
- `learn()` reads the home-folder loadout for names only when some agent has a connector on, and records when it started and whether it worked (a read that reported a servers error is a failure; a skipped read is not). Names are learned from the switch-over, every Connectors page load and once at start (`startConnectors`, which registers its chain so runs can join it). A run of an agent with any connector on (or before the switch-over settled) waits in `agentRunConfig` for `ConnectorsService.ready(10_000)`: it joins a read in flight for at most 10 s, or, when no read has worked yet, starts one, but not sooner than 60 s after the last attempt began (a failed read is retried only when runs need it, at most once a minute). It never throws, and after `stop()` it returns at once. So GitHub (no catalog name) and a renamed or `(2)` connector get their ask rule and classification even for a run that starts right after the server. The probe (`serversOff: false`) never waits. The start-up reads (the switch-over's and `learn()`'s) go through `ExtensionsService.peek`, which uses a cached answer or a running probe but leaves nothing in the loadout cache: a folder's cache key holds no file text, so an answer cached at start would hide a later edit to `settings.json` from Settings › Claude Code's first read. A server the user renames on claude.ai after the last read is still not a prefix until the next read (a page load, or a retry after a failure). A failed read adds nothing and logs a fixed line.
- `AgentRunConfig.connectorsOff` carries the connectors the run denies. The permission step answers a call to one of them with `offRefusal(id)` (`<Service> is not turned on for this agent on the Connectors page.`) and no card, before the read, unattended and card branches. The CLI already denies those servers, so this is defence in depth for a name the CLI did not match.
- A failed switch or Remember save is undone in memory, as the store's other writes are.
- The card's `remember` is a snapshot taken when it was made; the server re-checks the switch on the answer.
- A room opened by a routine's or workflow's message stays unattended until the user types into it (`Room.unattended`); Resume and edit/resend are attended. An asked turn (A asks B) inherits unattended down the chain.

## What Claude Code does today

Checked against [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) and [permissions](https://code.claude.com/docs/en/permissions) on 2026-11-17, and against the CLI and files on this PC.

- **Remote server auth.** A server that answers 401/403 is flagged for sign-in. Discovery is RFC 9728 (`/.well-known/oauth-protected-resource`), then RFC 8414 (`/.well-known/oauth-authorization-server`). Client registration is Dynamic Client Registration or a Client ID Metadata Document; for a server with neither, the user registers an app and adds it with `--client-id`/`--client-secret`/`--callback-port` (the `oauth` key in config; redirect `http://localhost:<port>/callback`). The CLI appends `offline_access` when advertised. A static `Authorization` header switches OAuth off for that server, and a 401 is then a connection failure, not a re-auth prompt. `headersHelper` is a command that prints a JSON object of headers; it runs in a shell (10 s limit) on every connection and once more after a 401/403, then the call is retried once. It works for servers passed with `--mcp-config`.
- **Where the CLI keeps tokens.** macOS: the keychain. Linux: `~/.claude/.credentials.json`, key `mcpOAuth`, one entry per `<server name>|<hash>` holding `accessToken`, `clientId`, `issuer`, `redirectUri`, `serverUrl` and `discoveryState` (and refresh data when the server gives it) — seen on this PC, values not read. Tokens refresh by themselves; `claude mcp remove` deletes them locally and does not revoke at the issuer. ZumiBot's sync copies only `agents`, `skills`, `projects`, `file-history` and `agent-memory` from `~/.claude`, so these tokens never leave the machine.
- **Headless runs.** `claude -p` cannot run an OAuth flow. A server signed in earlier (`/mcp` in a terminal session, or `claude mcp login <name>`, which prints the URL when there is no browser) works in `-p` from its stored tokens. A server that turns `needs-auth` mid-run stops retrying until someone signs in again and the run restarts.
- **claude.ai connectors.** The CLI fetches the user's claude.ai connectors itself, in terminal, `-p` and Agent SDK runs (ZumiBot's probe is a `-p` run and lists them today), **only when its credential is a claude.ai subscription login**. They do not load when `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or `apiKeyHelper` is active, under Bedrock/Vertex or an Anthropic profile, or with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`. They are named `claude.ai <Name>` (tools `mcp__claude_ai_<Name>__<tool>`), their transport is `claudeai-proxy` (`mcp_status` config `{type: 'claudeai-proxy', url, id: 'mcpsrv_…'}`), and the service's tokens stay at claude.ai: nothing is stored on the machine. Sign-in and re-auth happen only at `claude.ai/customize/connectors`. A server the user added with the same URL takes precedence and hides the connector. Anthropic-hosted connectors such as Gmail, Google Calendar and Microsoft 365 **cannot be signed in from Claude Code at all**: the upstream identity provider accepts only claude.ai's redirect URL. `disableClaudeAiConnectors` or `ENABLE_CLAUDEAI_MCP_SERVERS` turn the fetch off. A "session token rejected" state needs `/login`, not a reconnect.
- **Per-run config.** `--mcp-config` takes the `mcpServers` JSON (ZumiBot already passes one per run). `${VAR}` and `${VAR:-default}` expand in `url`, `headers`, `env`, `command` and `args`; an unset variable stays literal with a warning; Claude Code's own credential names (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, …) expand to empty there. `--strict-mcp-config` loads only the passed servers.
- **Permissions.** Rules go deny, then ask, then allow; a matching ask rule prompts even when an allow rule also matches. Deny and ask rules take tool-name globs (`mcp__claude_ai_Gmail__*`); allow globs need a literal `mcp__<server>__` prefix; an `mcp__` rule with parentheses is skipped. ZumiBot already forces cards in auto mode with ask rules (`DESKTOP_ASK_SETTINGS`, checked by the desktop ask probe). An MCP tool's `readOnlyHint` only lets reads run in parallel; it is not a permission input.
- **Codex.** Codex has its own MCP config (`url`, `bearer_token_env_var`, `env_http_headers`, `http_headers_helper`, `enabled_tools`/`disabled_tools`, `codex mcp login`; [docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)) and never sees claude.ai connectors. In auto mode its MCP calls get no client review (probe check 12 in [Codex agents](codex.md)), so a card for a write tool cannot be forced on a Codex run.

## Two routes

**A. Rely on claude.ai connectors.** The page reads the probe ZumiBot already runs, matches the `claude.ai …` servers against the catalog, links to claude.ai to add or fix one, and manages only the per-agent switches.

- *Cost:* small. No OAuth code, no tokens, no callback route. New parts: the catalog module, a matcher, one page, a switch store, the run's default-off rule, two RPCs. The probe, `deniedMcpServers` and the `--disallowedTools` belt already exist ([Servers, plugins, skills and hooks](extensions.md)).
- *Both machines:* connections belong to the claude.ai account, so the PC and the VPS see the same ones when both CLIs are signed in to that account. No secret is stored in ZumiBot or `~/.claude`.
- *API-key users:* nothing works. With a key, a setup token, Bedrock or Vertex the CLI fetches no connectors; the page then says so and names the variable in use (`keyVarInUse` in `claudeStatus.ts`), never its value. **Check the VPS:** if its service runs on `CLAUDE_CODE_OAUTH_TOKEN` or a key, route A gives the VPS (and so every routine and workflow) no connectors.
- *Limits:* ZumiBot cannot see which account a connector is signed in as (claude.ai holds it), so a card can name the service but not the account. Tool names and behaviour are claude.ai's. Re-auth is a trip to claude.ai. Connector traffic goes through Anthropic's proxy.
- *Codex:* no.

**B. ZumiBot runs the OAuth itself.** Authorisation code with PKCE (S256) and `state`, DCR or CIMD where the server offers it, tokens sealed in the vault, and each run handed only its agent's connectors.

- *Cost:* large. An OAuth client (discovery, registration, PKCE, `state`, one-shot callback, expiry), a vault kind that sync must treat specially, refresh with rotation, revocation (RFC 7009 where offered), a desktop-shell relay for local mode, the per-run config and its helper, fake OAuth and MCP servers, and an e2e suite. On top of the code, per-vendor setup the user does by hand (see the catalog): own OAuth apps for GitHub and for Google, and Google's verification or weekly re-sign-in.
- *API-key users:* works, since the tokens are ZumiBot's. This is B's main gain.
- *Codex:* possible, read tools only: the run's `mcp_servers.<id>` gets the URL, the token through `bearer_token_env_var` or `http_headers_helper`, and `enabled_tools` set to the catalog's read list, because a write card cannot be forced there.
- *Per vendor:* only Notion and Linear let any client register itself (DCR/CIMD). GitHub, Slack and Google each need the user's own OAuth app first, and Google adds a preview program and weekly re-sign-in (see the catalog).

**Recommendation: route A now; no route B unless the user's setup changes.** A covers all seven services (GitHub as a custom connector), costs a fraction of B, stores no secret, and works on both machines at once. B earns its cost only if the CLI moves to an API key (or the VPS already runs on a setup token, see the check above) or if Codex agents must use connectors. Even then, B would start with Notion and Linear (self-registration, loopback and https redirects), then GitHub and Slack with the user's own apps, and Google last.

## Per-agent switches and "off until I turn it on"

`serversOff` alone cannot give "a newly connected service is off for every agent": it is an off list, so a connector the user adds on claude.ai is on for every agent the moment it appears, before ZumiBot has seen it. The page cannot write it into every agent's `serversOff` first, because on route A the connect happens on claude.ai, and a routine can run in between.

Proposal: keep `serversOff`'s **run path** and add an **on list** for catalog connectors only.

- `connectors.json` in the data dir: `{v: 1, agents: {<agent>: [<catalog id>…]}, remember: {<catalog id>: true}}`, written atomically, 0600. Absent means off.
- At spawn, `buildAgentRunConfig` gets the agent's on list and, for every catalog connector that is not on, adds `deniedMcpServers` entries by `serverUrl` (the catalog's URL patterns) and by `serverName` (its known claude.ai names), plus the `--disallowedTools mcp__<prefix>` belt that `serversOff` produces. Denying something that does not exist is harmless, so this needs no probe at spawn. Non-catalog servers keep `serversOff` exactly as today.
- Why the data dir and not a new agent-file key: Zumi Bot edits agent files with its own file tools, so a key there is guarded only by its prompt. `connectors.json` can sit behind the same deny rules as the vault (`Read`, `Edit`, `MultiEdit`, `Write`, `Grep`, `Glob` on the file in every run's merged `--settings`, Zumi Bot's included). Agents run as the same OS user, so this stays a speed bump against Bash, like the vault's.
- Rename moves the agent's entry in the agent-rename pipeline (synchronously, beside approvals); the agents-folder watcher's removal pass drops a deleted agent's entry. Sync joins it newest-wins both ways, like `settings.json`.
- Agent Studio's **What this agent loads** shows a catalog connector's row with "Set on the Connectors page" and a link, instead of a switch, so the two pages never disagree. A `serversOff` entry for a catalog name stays honoured (off wins).
- Codex agents: none on route A; the page shows them without switches and says why.
- ACP and remote (AG-UI) agents: none, on either route (see [Protocol engines](protocol-engines.md), Governance, connectors and card comments). Only Claude's CLI loads claude.ai connectors; switches stored while such an agent was a Claude agent are kept but never used. An ACP agent's own configuration may load connectors of its own (an ACP adapter of Claude Code, say): ZumiBot neither grants nor blocks them, and their calls get the ordinary ACP cards.
- **Rename risk.** A connector's name is claude.ai's display name, which can change or gain a ` (N)` suffix; a deny by name alone would then miss it and leave the connector on for every agent. The [managed-MCP docs](https://code.claude.com/docs/en/managed-mcp) say `deniedMcpServers` merges from every settings scope and that a `{serverUrl}` entry (with `*` wildcards) matches the connectors Claude Code fetches, and recommend it for exactly this. So the URL entry is the real guard and the name entry the belt; a probe check confirms both on 2.1.322, and the page flags a `claude.ai …` server whose name the catalog does not know but whose URL matches a catalog pattern.

**Existing connections.** Today every agent without a `serversOff` entry has every connected claude.ai connector. The first start of phase 1 either keeps that (writes each agent's current on-state into `connectors.json`, from one home-folder probe, before any run) or starts everything off. The proposal keeps it, so nothing the user relies on stops; turning off is one click per agent. If that probe fails, nothing is migrated, every catalog connector starts off, and the page says why.

## Unattended runs

An unattended run is a turn nobody typed: `auto` in `ChatService` (routine runs, webhook runs, workflow Agent, Room and For-each steps), and an A→B asked run whose asking turn was unattended.

**Decision: unattended runs get connector reads only.** A write or unlisted tool is refused at the permission step with a fixed tool error ("<Service> <tool> changes data outside this machine. Runs started by a routine or workflow may only read; ask the user to do this in a chat."). It is refused, not held on a waiting card, so a 3 a.m. routine finishes and reports instead of sitting `waiting` until morning. A per-routine or per-step opt-in, "may ask to write with <service>" (the card then waits, as cards do today), is a later addition, not part of the default. Remembered write approvals never apply to an unattended run. Side runs (`/btw`) get reads only and never a card.

- UI: `ConnectorsSettings.tsx` at `/settings/connectors` (pure rules in `state/connectors.ts`), one card per catalog service: name, state, one line on what it can do, the agents that have it on, a switch per Claude agent, and **Connect** / **Reconnect** / **Manage on claude.ai** opening the service's `claude.ai/directory/<id>` page in a new tab (the desktop shell already sends web links to the system browser). ## Phase 2 — route B (proposal only, not built)

Sketched so the review can judge its cost; details wait for approval.

- **Flow.** Connect opens a new tab on `/api/connectors/<id>/start`, which makes a pending flow (`state` and the PKCE verifier, 32 random bytes each, bound to the session that started it, gone after 5 minutes or first use) and redirects to the provider. The callback `GET /api/connectors/callback` sits behind the gate in `http/server.ts`: unknown, expired, replayed or other-session `state` gets a fixed error page; the code is exchanged once; a `302` back to the page follows. Redirect URI: `${ZUMIBOT_ORIGIN}/api/connectors/callback` in vps mode. A callback reached without a session lands on `/login`, which keeps no return path, so the flow is lost and Connect starts again.
- **Local mode.** The system browser has no `cb_local` cookie, so the gate would refuse the callback, and providers (Google above all) refuse embedded browsers. The desktop shell opens the sign-in with `shell.openExternal`, listens once on `http://127.0.0.1:<port>/callback` (RFC 8252 loopback), and posts `{code, state}` to the gated server route over its own authenticated session; the server does the exchange. A DCR client is registered with that exact redirect.
- **Tokens.** A `connector` vault item (sealed like the others): access token, refresh token, expiry, client registration, account label. Never in a Claude Code config, chat item, log, URL or error. **Not synced:** many providers rotate refresh tokens and treat a reused one as theft, so a copy on the other machine would break both; `vaultSync.mjs` skips the kind and each machine connects on its own (the VPS is where routines run).
- **Runs.** An agent with the connector on gets a per-run `--mcp-config` entry `{type: 'http', url, headersHelper: 'node <dist>/connectorAuth.mjs'}`; the helper asks ZumiBot over a per-run capability socket (the bridges' pattern) and prints `{"Authorization": "Bearer …"}`. ZumiBot refreshes before expiry; the CLI re-runs the helper after a 401, and ZumiBot refreshes once then. A refresh that fails marks the connector **Needs attention** and the helper prints nothing, so the tool call fails with the server's 401; the agent gets a fixed tool error naming the service. No token in argv, env or a file.
- **Disconnect** revokes at the provider where it offers RFC 7009 (or its own endpoint), then deletes the item, whether or not the revoke worked, and says which.
- **Client secrets** (GitHub, Google) come from the vault or an env var; errors name the variable or item, never the value.

## Phase 3 — guardrails for actions that leave the machine (built; the proposal as written before the build, see Built (phase 3))

- Every run with a catalog connector on gets an ask rule `mcp__<prefix>__*` in its merged `--settings`, so every connector call reaches ZumiBot's permission handler even in auto mode (probe check f confirmed the glob form on the real CLI, see Probe result).
- The handler classifies by the catalog: a read is allowed without a card; a write or unlisted tool gets a card in an attended run and is refused in an unattended one (above).
- Write cards offer Allow once and Deny only. **Remember** (Allow always for this agent) appears for a connector only when its `remember` switch in `connectors.json` is on, set on the Connectors page.
- The card shows the service, the account (route B; route A shows "as connected on claude.ai", since ZumiBot cannot see it) and the full input, unscrubbed except by the vault's own scrub.
- Codex agents: route B only, read tools only (`enabled_tools`); no write ever.
