# Workflows

**Workflows (`core/workflows/`, `shared/src/workflows.ts`, `workflowGraph.ts`, `workflowEngine.ts`, `workflowTemplate.ts`).** A fixed chain of steps drawn on a canvas, beside Routines (which are unchanged): one trigger (manual, a routines `Schedule`, or a webhook with exact-match `filters` such as `body.action` = `opened`), then Agent, For each, LLM, Condition, Approval, Wait, Notify, HTTP request, Transform and Sub-workflow steps joined by edges from ports (`out`, `yes`/`no`, `approved`/`rejected`, and `error`, a step's failure path). `workflowStore.ts` writes `workflows.json`, `workflow-runs.json` (the newest 30 runs per workflow, at most 10 of them skipped) and `workflow-hooks.json` (0600, the same `core/hooks/hookFile.ts` as `routine-hooks.json`); the trigger's config sits on the workflow, so the now generic `createScheduler` (`scheduler.ts`) runs one timer for workflows as for routines, and a missed schedule fires once late. Save always works (`workflowInput.ts` rebuilds the input key by key and refuses only what the engine could trip on, as `Invalid workflow`); `problemsOf` (one trigger and nothing into it, every step reachable, a loadable agent that is not Zumi Bot, an existing folder, prompts and a Notify body within 20 000 characters, unique and known handles) refuses Run and turning on, and a save that would turn on a workflow with problems saves it off. **Engine.** A run copies the steps and edges into `snapshot`, so editing never changes a run in flight, Retry included. A done visit hands its output to every edge from its port; a step with several inputs starts once no step that could still reach a missing input's source is running, waiting or about to fire (the one join rule, pure in `workflowEngine.ts`; it also covers a branch not taken and loops), and a step runs one visit at a time. Caps: 20 visits per step and 200 per run, past which the visit fails "Ran too many times"; a failed visit halts new starts, running ones finish and the run ends `failed`; **Retry** runs that step again with the same input (after the cap it gives 20 more visits to that step and to every other step that used up its allowance, and 200 more to the run, so one Retry pushes a whole loop on); at most 5 unfinished runs per workflow; a run is `waiting` while an Approval or a card in one of its Agent steps' chats waits. Stop stops Agent turns (a step's message still in a chat's tray is only dropped, so the turn ahead of it runs on, as does any turn during a step's usage-limit wait), kills bare calls, clears waits and closes approvals, silently. `recover()` reruns LLM and Condition visits (no side effects), re-arms Waits from their stored `until`, keeps approvals waiting, keeps following a still-queued Agent message, fails an interrupted turn (Retry offered) and marks a running Notify done without sending it again (filing its Inbox message from the visit's stored `title`/`body` if it has none, still with no push), then starts what each run's inboxes allow (a crash between a run's first write and its first start leaves them full); it runs after `usage.start()`, since the calls it asks again record their cost, so the server already listens: `holdUntilRecovered()` (called before listen) makes `run` (webhooks and the scheduler too), `approve`, `retry`, `stopRun` and `stopAllOf` wait until `recover()` ends, even by failing, or `stop()`; `stop()` clears timers and keeps state. Agent steps read whether the chat runs both before and after reading its items, so a turn that starts or ends meanwhile is never settled half-saved. **Text.** Templates (`{{input}}`, `{{steps.<handle>.output}}`, `{{trigger.text}}`, `{{trigger.body.…}}`, `{{trigger.query.…}}`) fill a field a model reads with each untrusted value inside an `<input from="…">` block (`modelPrompt`; `{{trigger.text}}` is the user's own typing, so raw), append each source of the visit's input the prompt does not name, and the fixed `MATERIAL_RULE` says `<input>` text is material, not instructions; Approval and Notify fields only the user reads are filled raw. **Bare calls** (`bareCalls.ts`): LLM and Condition steps are one `claude -p --model <m> --tools '' --setting-sources '' --strict-mcp-config --no-session-persistence --output-format json --system-prompt …` in the data dir, like the moderator, with the prompt on stdin and the material rule after any system prompt of the user's; Condition adds a yes/no `--json-schema`, stores the reason and passes its input through unchanged. At most 4 run at once server-wide (`BARE_CALLS_MAX`, the rest queue), with 5 and 2 minute timeouts; a usage limit (status 429, or the "usage limit"/"hit your limit" wording, never another limit such as a context limit; the reset from `rate_limit_info`; never seen from the real CLI yet, and a reset it cannot read fails the visit) waits for the reset and retries, at most 5 times. Their cost is recorded under `workflow:<id>` with the agent `#workflow`, shown in Usage as "Workflow: <name>". **Run cost.** Each visit also keeps the USD it cost (`Visit.costUsd`): a bare call's `total_cost_usd`, written in the same write as its end, and an Agent step's turns, which `ChatService.onRunCost` hands to `WorkflowRunner.chatCost` (before the turn ends) and which count only while that turn answers the visit's own message (not one of the user's ahead of it in the tray), a usage-limit `continue` included. `addCost` adds to a visit that already ended, in a run that already ended, without `advance()`, so a call answering after Stop still counts. `runCostUsd` sums a run (retried and stopped visits too); the summary carries it as `costUsd` (absent at 0, and in `summaryKey`, so the open run refetches when a late cost lands). The run view shows it in the header (`wf-run-cost`, "so far" while unfinished), per visit (`wf-visit-cost`) and per step with a total in the overview (`wf-run-costs`, `costByStep`), and each sidebar run row (`workflow-run-cost`); nothing shows for a run nothing reported a cost for. A turn that never reports one (a hard stop) is simply missing from it. **Agent steps** (`workflowAgentSteps.ts`) make one chat per step per run, titled `<workflow> · <step> · <date>` and carrying `ChatMeta.workflow` `{workflowId, runId, stepId, name}`, and send through `TaskQueue.submit(..., 'routine')`; the appended system prompt adds `workflowSystem` (a fixed line naming the workflow, plus the material rule, so the cache holds; first, as in a `/btw` side run's fresh base, and also for a Run step test's chat, which carries only `ChatMeta.workflowTest`, the workflow's name, since its input may come from a real run), a loop's revisit sends into the same chat, turn outcomes map as routines' do (Stopped, Interrupted by a restart, Replaced by an edit or resend; a usage limit waits and sends `continue`, at most 5 times; a turn the user paused keeps its visit open, `running` with `Visit.paused`, as a limit wait holds `until`, so joins wait on it and Stop stops no chat for it, until `WorkflowRunner.chatResumed` moves it onto Resume's Continue, counting `resumes`, or a message of the user's own fails it "Continued by hand"; the run view draws the step `paused` (`visitState`), says "Paused by you · press Resume in its chat to continue", then "Resumed after a pause" (`visitPauseText`), and stops polling while only paused visits run; a Run step test still reads "Paused by you"), and the output is the last reply (50 000 characters). The chat is archived when its step ends done (a failed one stays) and shows `WorkflowChatBar.tsx`, linking to the run. Its messages are drawn for the reader, display only (the stored text is what the agent read, and Copy and Edit keep it): each `<input from="…">` block the template wrote is a labelled box (`WorkflowPrompt.tsx`, pure parser `state/workflowMessage.ts`; folded with **Show all**, a JSON body as a code block, a For each item named `Item n of N`), and the messages the workflow sent get a sender line naming the workflow and step (`wf-from`). Items carry no sender, so those are the chat's first message (once the whole history is loaded) and any holding a block; a usage limit's `continue` still reads as the user's. Its `replied` and `error` are silent (the turn end carries `workflow: true`), but its cards notify as `waiting`. **Webhooks.** `/hooks/<id>` serves both owners through `HookTarget`s (`routineHookTarget`, `workflowHookTarget`). Besides `X-ZumiBot-Secret` (checked before any body is read, as before) it takes GitHub's `X-Hub-Signature-256: sha256=<HMAC-SHA256 of the raw body>`, for routines too, compared in constant time; until a signature checks out every answer is the same 401 an unknown id gets. A filtered-out call is a `skipped` run with "Filter did not match" (still a 202); the trigger inspector says to pick application/json in GitHub, whose default form encoding hides body fields from filters. The 60 calls a minute now count before `fire`, so authenticated test captures and calls to a disabled hook (409) count too. **Notifications.** A waiting Approval sends `waiting`, titled "<workflow> needs your approval" with the tag `workflow:<runId>:waiting`, cleared by `notify:clear` with that `tag` once the run has no approval waiting; a failed run sends `routine-failed` (reading "Workflow failed"; the toggle now reads "A routine or workflow failed"; a stop or a restart sends none); a Notify step first stores its message for the Inbox (`WorkflowMessages.add`, its id the visit's id, so a second add is a no-op; `Visit.title`/`body` keep the filled text from when the visit began, as an Approval's `question`; a failed write is logged and the push still goes), then sends the new kind `workflow` with its title (80 characters, the workflow's name when it fills empty) and `body` (the push body is the first `NOTIFY_BODY_MAX`, 200, characters; the visit's `body`, which the Inbox message and the Audit log read, keeps up to `NOTIFY_INBOX_BODY_MAX`, 20 000, and nothing longer than the 200 cut goes out in a push), always on while the device has notifications on, inside the 10-a-minute cap. The payload adds `run: {workflowId, runId}` (a click on an approval or failure opens the run) and, for Notify only, `body` (the one place a notification carries content, and only what the user wrote into the step) and `message`, the message id: its click opens the Inbox at that message (`/inbox/<id>`, `clickUrl` in `sw/clickTarget.ts`). In the desktop shell a Notify notification's click opens its Inbox message too (`DesktopNotification.open`, kept only through `safeOpenPath` in the main process and again in the preload, handed to the page by `onNotificationOpen`, `notificationTarget`); a shell without `onNotificationOpen` keeps `onNotificationClick`, where a Notify click does nothing. In the shell an approval's or a failed run's notification opens its run on a click (`desktopNotice` sets `open` to `workflowsPath` of the payload's `run`, a Notify message's Inbox path first; `notificationTarget`'s `run` kind calls `openRunFromNotification`), which every shell with `onNotificationOpen` already passes on, and a workflow notification is cleared by its tag (`DesktopBridge.closeNotificationTag?`, IPC `desktop:closeNotificationTag`, the notifier's `closeTag`); a shell older than that keeps it until dismissed by hand, and shells older than the Notify step drop the `workflow` kind. **UI.** The rail's **Workflows** (`mode-tab-workflows`, waiting dot `workflows-waiting`) between Routines and To-dos; `WorkflowsSidebar.tsx` (each workflow's switch, last run's dot and recent runs); addresses `/workflows`, `/workflows/<id>`, `/workflows/<id>/runs/<runId>` and `/workflows/<id>/runs/<runId>/audit` (`state/route.ts`); `WorkflowEditor.tsx` on React Flow (`@xyflow/react`, a lazy chunk like noVNC) with the step inspector; its connectors (`StepEdge` in `WorkflowCanvas.tsx`) are drawn like n8n's from React Flow's own helpers (`getBezierPath`, and for a loop back two `getSmoothStepPath` runs under both steps with an arrow along the bottom), grey 2px with an `ArrowClosed` marker whose colour the canvas sets per edge (accent on hover or selected, green once a run carried output along it, `edgeRuns`, with a ×N count past 1), no text on the line (each port's name sits just outside the step), a hover toolbar whose + puts a new step into the edge (`insertStep`) and whose trash removes it, and a short line with a + on every port nothing leaves yet; several items can be picked (`Selection` is `step`, `edge`, `note` or `group` (a collapsed one), or `items {steps, notes, groups}`; a plain drag box on empty canvas (Shift-drag too, even over an item), Ctrl/Cmd-click to add or take one out, Ctrl/Cmd+A for all), which move together and land as one edit (`moveItems`), show `SelectionInspector` ("N items selected", Group and Ungroup) and go with Delete, the trigger aside (`removeItems`); React Flow's own select changes drive it (`applySelect`), a plain click on a picked item narrows to it, and its frame over a box is hidden in `styles.css`, since it took every click inside it; Run step (`StepTest.tsx`: the unsaved draft, nothing stored as a run) and the unsaved-changes guard; every template field but Notify's title, Run step's input and output, and a run's input and each visit's Input and Output (`VisitText`, read-only Markdown, titled with the step and visit), has an Expand button on its label row that opens `ExpandDialog.tsx` (a portal; edits apply as typed, so no Cancel), a second editor on the same value whose `{{` menu follows the caret (`menuAtCaret`, `caretMenuPlace`), since under a tall field it would be off screen; `WorkflowRunView.tsx` draws the run's snapshot read-only with each step's state and `VisitPanel.tsx` per visit (Retry, Open chat, "Waits until" for an open visit holding `until`, and the approval box: the question as filled when the visit began, `Visit.question`, editable text plus a note, appended as `Note from the user: …`), refetching on `workflows:changed` and every 2 s while a visit runs (a tick is skipped while a fetch is out, and only an answer older than one shown is dropped, `fetchOrder`). The run header has a **Canvas | Audit log** switch (`wf-run-tabs`, `wf-tab-canvas`/`wf-tab-audit`, a `tablist` with roving focus: ←/→, Home and End pick the other tab), and the Audit log has its own address, `/workflows/<id>/runs/<runId>/audit` (a push, so Back returns to the canvas; reload and a link keep the log; an unknown run is the same unavailable page). **Audit log** (`AuditLog.tsx` over the pure model `state/auditLog.ts`, tests in `tests/auditLog.test.ts`) is a read-only timeline of an ended run, built from the run's snapshot and visits alone with nothing new stored or sent: while the run is `running` or `waiting` its tab shows only the note "The audit log shows once this run ends." (`wf-audit` `data-state="pending"`), so an Approval is still answered on the canvas. Once it ends it shows the trigger first (Manual, Schedule or Webhook with the call, the `late` tag, and the run input), then one entry per visit in start order (`wf-audit-entry`, with `data-step-id`, `data-kind` and `data-status`; a looping step shows each visit as `Visit n`), then the end line (`wf-audit-end`: done, failed, stopped or skipped, the time, the duration, the run's cost and its error). Each entry's boxes follow its kind: Notify what it sent (`wf-audit-sent`) then Input; Approval the question asked, Input and Output (an `edited` tag when the user changed the text) and the user's note; Condition Input and the model's reason, no Output; Wait Input only, with how long it waited; Agent and LLM Input and Output; For each Input, an item row per item (`wf-audit-item`: status, `from an earlier visit` for a carried one, duration, cost, Open chat, folded output, error) and the joined Output; any step its error and, when the visit's input lacked fields, a "Missing fields" line. A long box folds to a preview with **Show all** (only the preview is rendered while folded, as a still-open ```mermaid fence stays code) and every box has the Expand dialog. A run that ends on a phone shows the log in place of the visit list (the tabs are gone there), and there a failed run's log offers **Retry** on the failed visit (`wf-retry`) and on each failed For each item (`wf-item-retry`), since a phone has no canvas inspector (the desktop log stays read-only; Retry is in the inspector); a run that still runs or waits keeps the list of visits (`wf-timeline`) with the approval on top. On a phone the editor keeps only the switch and Run workflow, and a run's header is two rows: back and Stop on top (`wf-run-bar`), the title and its tags under (`wf-run-info`); the editor's header and banner never shrink (`flex: none`), since a squeezed header hid Stop under a long visit list. **Duplicate** (the editor's ⋯ menu; "Save and duplicate" while there are unsaved edits or the workflow was never saved, since `workflows:duplicate` copies the saved workflow) adds an off copy named `<name> (2)` (`copyTitle` in `shared/src/copyTitle.ts`, the next free number, within the 100-character cap; the room clone's `nextCopyTitle` uses it too) with the same steps, edges, trigger and time zone, made in one step on the store's queue (`WorkflowStore.copy`); runs are not copied, and a webhook copy gets a hook of its own (new URL and secret) holding the source's latest call as its sample. The editor opens the copy from the RPC answer, which can come before the push that lists it (`shownWorkflow`). The RPCs are `workflows:list|getRun|save|remove|duplicate|setEnabled|run|stop|retry|approve|testStep|webhook|newSecret`; `list` and `workflows:changed` carry run summaries only and `getRun` one run's visits, so outputs are never broadcast. An agent rename moves the steps and the run snapshots (after routines, caught and logged); deleting a workflow stops its unfinished runs first, and the chats it made stay. **For each step** (`kind: 'foreach'`, `shared/src/workflowForEach.ts`, the runner's item loop in `workflowRunner.ts`: `startItem`, `nextItem`, `endItem`, `goOn`; `workflowAgentSteps.ts` only follows each item's turn as a slot; design: `docs/superpowers/specs/2026-11-08-workflow-for-each-design.md`). One agent over a list: the visit's input is split on line breaks (trimmed, empty lines and exact repeats dropped, order kept), and the step's Agent, Folder, Model and Prompt run once per item, in list order, so it passes the 20-visit cap that a loop of Agent steps hits. **Run at once** (`concurrency?: 2 | 3`, absent = one at a time, `FOREACH_CONCURRENCY_MAX`; `concurrencyOf`, `concurrencyKey`, which `parseStep` uses to keep 1 to 3 and store only 2 or 3; the inspector's `wf-foreach-concurrency`) starts up to that many items at once: the visit's opening write marks them running through the pure `startPending` (list order; a paused item is open, so it keeps its slot), an ended item's write fills the freed slot, and the visit ends only once nothing is open or pending; while items are open it is `waiting` if any of them waits on a card (`openVisitStatus`), else `running`. `goOn` fills free slots (a crash between items, an empty list) and `recover()` follows or resends every open item, then fills. Each item still has its own chat, card, limit wait, cost, Stop and Retry (a Retry reruns the failed items side by side). Items share the agent's browser and desktop, which serve one turn at a time. Each item gets a fresh chat of its own (`ChatMeta.workflow.item` `{n, total}`, titled `<workflow> · <step> · <item> · <date>`), sent through `TaskQueue.submit(..., 'routine')` and ended like an Agent step's turn (cards make it `waiting`, a usage limit waits and sends `continue`); a done item's chat is archived, a failed one's stays. The prompt uses `{{item}}` (wrapped as `<input from="item">`), `{{item.number}}` and `{{item.total}}`, and must use `{{item}}` (a problem otherwise); the visit's input is not appended. A failed item does not stop the rest: once every item was tried the visit ends `failed` ("2 of 36 items failed") and the run halts. An item the user pauses follows the paused Agent step above: it stays open (`ItemRun.paused`, `resumes`), so no later item starts until Resume's Continue carries it on to done (or a message of the user's own fails it "Continued by hand" and the list goes on); the item row and the node show `paused` and the summary's progress carries `paused` (" · paused"). With several running at once a paused item holds only its own slot, so the others go on; the node reads `paused` only when every open item is paused (`pausedVisit`), and the progress carries `running` (open items, when more than one) and `pausedItems`, read as `4 / 36 · 3 running · 1 paused` (`progressText`; one open item still reads `2 / 3 · beta`). **Retry** (`workflows:retry`, `runId`, `visitId`, optional `itemId`) runs only the failed items again, or just the one named, in their own chats where those still exist; done items are carried over (`ItemRun.carried`) so the output covers the whole list. The output is every reply under a `## <item>` heading, 20 000 characters per reply and 100 000 joined with an equal share per item (`FOREACH_ITEM_OUTPUT_MAX`, `FOREACH_OUTPUT_MAX`); at most 100 items (`FOREACH_ITEMS_MAX`) of 1 000 characters (`FOREACH_ITEM_MAX`). Progress is `WorkflowRunSummary.progress` (`{stepId, done, failed, total, current}` per open For each visit, `current` cut to 80 characters, part of `summaryKey`): the run header (`wf-run-progress`), the sidebar run row (`workflow-run-progress`), the canvas node (`wf-node-progress`) and the visit panel's counter and item list (`wf-items-count`, `wf-item`, per-item Open chat, output and Retry; on a phone behind `wf-timeline-progress`). Run step tests the first item only. Design: `docs/superpowers/specs/2026-11-07-workflows-design.md`.

**Triggers (`shared/src/workflowEvents.ts`, `runWorkflow.ts`, `core/workflows/workflowEvents.ts`, `workflowEventSources.ts`, `fileWatchers.ts`, `mailWatchers.ts`, `mailClient.ts`; design: `docs/superpowers/specs/2026-11-13-workflow-event-triggers-design.md`).** Besides manual, schedule and webhook, the **Starts** select offers five event kinds (`EVENT_KINDS`): `reply` (an agent's turn in a chat or room ended, replied or failed), `todo` (to-dos were added to a chat's list), `inbox` (a workflow's Notify step filed an Inbox message), `file` (a file in a folder or its subfolders was added, changed or removed) and `email` (a new message in an IMAP mailbox). Routines get none of them. **Event shape.** An event becomes a run the way a webhook call does: the run stores `call` (`method: 'EVENT'`, empty `query`, the event's JSON `body`; `eventCall`), so `{{trigger.body.…}}` and the `filters` work unchanged, and `input`, the event's text (`eventText`), which the trigger step hands on as its output and `{{trigger.text}}` names. That text comes from a reply, a mail or a file name, so `contextOf` marks it `material` for `via: 'event'` and a model reads it inside an `<input from="trigger">` block; a `/run-workflow` run's text is the user's own typing and stays raw. `WorkflowRun.via` gains `'event'` (with `run.event: {kind, depth?}`) and `'chat'` (with `run.chat: {chatId, title}`); both run through `WorkflowRunner.run`'s `o.event`/`o.chat`. Bodies (`EventBodies`; `EVENT_SAMPLES` are the static examples the inspector's field list and the editor's `{{` menu read, as a webhook's latest call): `reply` `{chat: {id, title, folder}, agent, outcome: 'ok' | 'error', room, reply}` (text = the reply, cut to `REPLY_TEXT_MAX`, 20 000), `todo` `{chat, by, count, todos: [{text, group}]}` (one to-do per line), `inbox` `{message: {id, title, body}, workflow: {id, name}, step, runId}` (title, a blank line, the body), `file` `{folder, count, truncated, files: [{path, name, change}]}` (one path per line; `count` is every matching file of the burst, `files` the first `FILE_BURST_MAX` of them, `truncated` true when that cut some) and `email` `{from: {name, address}, to, subject, date, messageId, text}` (`From:`, `Subject:`, a blank line, the text, cut to `MAIL_TEXT_MAX`, 20 000). A filter row has an equals/contains select: `TriggerFilter.op?: 'contains'` (absent = equals, as stored before; `filtersMatch`), shared by webhook and event triggers (`TriggerFilters.tsx`, pure `setFilterOp` in `state/workflowTriggers.ts`). **Dispatcher.** `WorkflowEventDispatcher.emit(event, {only?})` takes each enabled workflow whose trigger is that kind, checks the filters, then a cap of `EVENT_RUNS_PER_MINUTE` (30) starts per workflow in a sliding minute (past it the event is dropped with a log line), then `runner.run(w, 'event', …)`. A filtered-out or dropped event writes nothing, unlike a webhook's `skipped` run, since every reply in the app would write one; an error is caught and logged, and a run that cannot start never changes the turn, to-do or message that caused it (`fireEvent` in `app.ts`, fire and forget through the `eventDispatcher` that is undefined until the runner exists). Loop guards: `reply` and `todo` skip chats a workflow made (`ChatMeta.workflow`, `workflowTest`, a Room step's copy) and A→B ask chats (`workflowChat`), and a deleted chat, and any chat a run's step is waiting on at that moment (`WorkflowRunner.runsIn`, read synchronously in `app.ts`'s `fireChatEvent`), since a Chat step posts into the user's own chat and a reply workflow posting back into it would otherwise start itself on every reply; `inbox` skips the message's own workflow; `file` drops a change at the moment the watch reports it (not at the flush, `FILE_BURST_MS` later) while that workflow is busy (`fileBusy`: a run of it is unfinished, `WorkflowRunner.busy`, or one ended less than `FILE_BURST_MS` ago, `endedRecently`, from the in-memory time of each workflow's last run end), since its own agent writes into the folder and a write made just before the run ends reaches the watch after it; the dispatcher checks `busy` again at the flush. Chains across workflows are bounded by a depth that inbox and file runs store in `run.event.depth` (reply, todo and email runs store none, read as 1; their sources skip workflow chats): an Inbox run gets 1 more than the root of the message's run (its sub-workflow chain walked up, `PARENT_HOPS_MAX` 10 hops) when that root was started by any event (no depth stored = 1), else 1; a file run gets 1 more than the deepest unfinished run of any other workflow at the flush (`WorkflowRunner.activeDepths(except)`, 0 for a run no event started; none = 1), since any of them may have written the file. Past `INBOX_CHAIN_MAX` (3) neither fires, so an Inbox workflow writing into a folder another workflow watches, which notifies back, stops after three hops. An event run at the active-run cap (5) ends `skipped` ("Too many runs in progress", `EVENT_SKIPPED_BUSY`), not `failed`, so it sends no failure push. An event run of a workflow with problems ends `failed` (`PROBLEMS_TEXT`) and pushes only when the workflow's newest run did not also fail on its problems, so a broken workflow on a chatty source pushes once per streak, not on every event. **Sources.** `reply`: `ChatService.onTurnEnd` and `GroupService.onTurnEnd` carry the reply text, and `replyEvent` returns nothing for a stopped turn, an Agent step's reply (`e.workflow`), an asked chat, or a passed room turn, and reports a room's turn once, by the room's own hook. `todo`: `TodoService.onAdded(chatId, items, by)` after a user or agent add that added something. `inbox`: `WorkflowMessages.add`'s `onAdded`, for a message stored the first time only. `file` (`FileWatchers`): one recursive `fs.watch` per enabled file workflow, resynced on every workflows change, ignoring any path with a `.git` or `node_modules` segment, debounced `FILE_BURST_MS` (2 s), then each path is statted: gone = `removed`, a path with a rename in the burst (how `fs.watch` reports a create, and what a write through a temp file and a rename looks like) = `added`, else `changed`; the trigger's `path` (absolute folder), `pattern` (optional `*`/`?` glob on the file name, case-insensitive, `nameMatches`, no regex) and `changes` pick what counts; one run per burst, listing at most `FILE_BURST_MAX` (100) files. A missing folder is a problem (`FOLDER_MISSING`: Run and turning on refuse), and so is a path that is not absolute (`FOLDER_RELATIVE`, "Use the full folder path, like /home/you/invoices": `~/x` would be read against the server's own folder); a watch that fails is logged and reopens on the next sync, each distinct error once per workflow (a dead folder fails at every workflows change) until the watch has reported a change, or the workflow is turned off and on. `email` (`MailWatchers`, `mailClient.ts`): `imapflow` 2.10.0 and `postal-mime` 4.2.0, both pinned and bundled into `dist/server.mjs`; every `MAIL_POLL_MS` (2 minutes) each enabled email workflow signs in over TLS (`logger: false`, so nothing of the mailbox or the server's lines is logged) and opens the folder read-only (EXAMINE), so nothing is marked read. The first check after the trigger is set, or after its host, user or folder changed or the mailbox's UIDVALIDITY did, records the next UID and fires nothing; later checks fire one run per new message, oldest first, at most `MAIL_PER_CHECK` (10) and no more than the workflow's free run slots (`MailDeps.freeRuns`, `WorkflowRunner.freeRuns`: the active-run cap less its unfinished runs), so a burst of mail waits in the mailbox for a later check rather than being passed as skipped runs (the stored UID moves only past what was fetched; with no free slot the check does not connect), each source read up to 2 000 000 bytes and parsed to the body above. State is `<data>/workflow-mail.json` (see [Data folder](data.md)), written before the events fire, so a crash loses mail rather than running it twice; turning the workflow off or deleting it forgets its place. A check ends at `MAIL_CHECK_DEADLINE_MS` (110 s) and one runs at a time per workflow; an unreadable message is skipped with a log line, and a failing mailbox logs once per distinct error. The trigger's `account` is a Vault login shared with workflows (see [Vault](vault.md)), read server-side per check (`vault.workflowLogin`; a switch turned off or a deleted login is `ACCOUNT_MISSING` at once, as is an empty `host`, `MAIL_HOST_MISSING`), `host` (trimmed), `port` (`MAIL_PORT_DEFAULT` 993) and `folder` (`INBOX`); every error text passes `scrubPassword` and the password never reaches the client, a run or a log. **Check mailbox** in the inspector is `workflows:checkMail(trigger)`, which parses the trigger as a save does and signs in once (30 s limit) to answer the message count or the error. **/run-workflow.** A built-in composer command beside `/btw` (`shared/src/runWorkflow.ts`, see [Agent commands](agent-commands.md)): `workflows:runFromChat(chatId, text, workflowId?)` takes the composer's whole text (`/run-workflow <name> <input>`; the server cuts the command, `runWorkflowRest`, and a bare rest works too). A pick from the `/` menu's Workflows list carries the workflow's id (`WorkflowPick`, kept by `keepWorkflowPick` only while the text still starts with `/run-workflow <its name>`, and the list stays closed while it holds, `workflowMenuQuery`, so Enter after picking "Report" sends rather than picking "Report weekly"); with an id the server runs that workflow (`Workflow not found` when it is gone), the input being the rest past its name (`afterWorkflowName`, case-insensitive, ending at whitespace) or the whole rest when it does not start with it, so two workflows of one name still run. Typed by hand, the server resolves the longest workflow name the text starts with (case-insensitive, ending at whitespace; `resolveRunWorkflow`, errors `No workflow has that name` and `Several workflows are named "…"`). Either way it starts a `via: 'chat'` run with input = the text after the name and body `{chat: {id, title, folder}, text, lastReply}` (the chat's last agent reply). It runs any workflow the Run workflow button would, and a workflow with problems refuses it as a manual run does (`PROBLEMS_TEXT`); a workflow of any trigger kind works, and nothing is posted back into the chat (a Notify step reaches the Inbox; adding items from outside the turn would race its own item writes). **UI.** `TriggerInspector.tsx` (pure `state/workflowTriggers.ts`): each kind has a hint and, for events, the field list from the static sample with Filter buttons (`eventFieldRows`) and the filters, whose hints speak of events for event kinds and of calls and skipped runs for a webhook (`filterHints`); an equals row with an empty value (what a field's Filter button adds) shows "An empty value matches only an empty field." (`emptyValueHint`); `file` has a folder picker, pattern and three change toggles (`toggleChange` keeps one on); `email` has the account select (only logins with the switch on, `mailAccounts`), host, port (`portDraft`, 1 to 65 535), folder and Check mailbox (`mailCheckText`). A Zumi Bot save keeps an email trigger's account only while host and port are unchanged (`workflowTrigger` in `authoring.ts`); a new email workflow is saved off until the user picks an account, and one already on stays on with `ACCOUNT_MISSING` in the save's problems (a save never turns a workflow off). The sidebar shows each kind's summary and icon, and run rows are tagged by `runTag` (`manual`, the event's label, `from chat`); the Audit log's trigger entry reads the event's label (`eventLabel`) or `From chat <title>` with the body as JSON and the text. Run workflow by hand on an event workflow is a manual run: only the typed text reaches the trigger, body fields stay empty (the hint says so); Run step on an event workflow fills `{{trigger.body.…}}` from the kind's static sample (`eventCall(EVENT_SAMPLES[kind])`), as material, the way a run's event would.
