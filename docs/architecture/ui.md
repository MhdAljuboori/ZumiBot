# App shell UI

**Approval actions.** Approval buttons center their labels and scope hints vertically and horizontally, with a 40 px minimum height and extra space above the action row. Buttons wrap onto additional rows in narrow panels; long tool names in scope hints stay within their button. **Allow once** is the primary (accent) button and **Deny** is outlined in red.

**Approval input (`ApprovalCard.tsx`, pure `state/approvalFields.ts`).** The card's Input panel lists a plain-object input as labelled fields (`approval-fields`): each top-level key in words (`channel_id` → `Channel ID`, `humanizeName`), short scalars beside their label, and long or multi-line text and nested values in their own box below it. Text keeps its line breaks (`visibleLines` in `shared/src/visibleText.ts`); every other hidden character still shows as an escape, as in the JSON. Field names and a connector's tool name are escaped the same way (`humanizeName` ends in `visibleText`, and a field's tooltip is its escaped key), so a key cannot hide or reorder what the card says. **Show JSON** (`approval-raw`) switches to the exact JSON (`visibleJson`); any other input (empty, an array, a scalar) shows only the JSON. A connector card's head reads `Service · Action`, the tool in words without the service's own prefix (`slack_send_message` → `Slack · Send message`, `connectorAction`), in the regular font; the Jev risk pill and the claude.ai account line share one row.

**Settings (`components/Settings.tsx`).** The rail's gear (also `Ctrl+,`) opens Settings, and the Usage popover's **Usage details** opens **Settings › Usage**; the account menu is gone (see Rail). Settings take the whole window: `SettingsNav` takes the sidebar's place (the drawer on a small screen, opened on its list) and `SettingsPage` the main area's, over the view underneath, which is still there when Back, Esc or a Usage row leaves them. Each section has its own address, `/settings/<section>` (`state/route.ts`), so reload, Back and Forward work as they do for chats. Sections: General (theme, color, Easy-to-read replies), Notifications, Vault (see [Vault](vault.md)), Claude Code (see [Servers, plugins, skills and hooks](extensions.md)), Connectors (`ConnectorsSettings.tsx`, `/settings/connectors` right after Claude Code; see [Connectors](connectors.md)), Voice input, Jev decisions, Usage, Sync (Sync & server in the shell, with Switch server), Account (sign-out, VPS only) and About (version, and for an install made by `install.sh` the self-update controls: Check, Install update with the release notes (no token: releases come from the showcase site), the last result with Roll back; see [Updates](updates.md)). The new-version toast, the "replies are running" confirm and the full-screen updating overlay (`UpdateHost.tsx`, not in the island page) share one store, `useUpdate.ts`, over `api.update`; while an install runs the store polls status: a changed version reloads the page, and an install that ends at the same version (failed download or run, busy after download) drops the overlay and shows the reason in the toast and About (`runOutcome` in `state/update.ts`). Opening them goes through the unsaved-changes guard; they close only by an explicit way out, never because the view under them changed.

**Side panel.** The panel icon at the top right of a chat (in the mobile bar on a small screen, `useNarrow`, so the row over the chat shows there only for the archived note; see Chat title row) opens the right side panel on a short list: **Open Browser** (in a room, with a member picker), **Open Desktop** (agents with computer use only, with its own member picker), **Open Files**, **Open Changes** (only in a git repo, with the uncommitted count; also the git chip's click, see [worktrees](worktrees.md#changes-panel)), **Open Side questions** and **Open To-dos** (each with its count). On a phone the list starts with the chat's agent (not in a room, whose members are in the bar) and its folder with the whole path and a worktree's own (`side-chat-about`, none for the built-in agent), since the row under the composer leaves both out to keep to one line (see [Chat mode and effort](chat-mode-and-effort.md)). The views have a Back arrow to the list and ✕; Esc closes Files, Side questions or the list, and the list gets a ✕ of its own on a phone, where the sheet covers the icon. One view at a time: a browser stays open behind a chat view and comes back when it closes; closing the panel with its icon closes that browser too, so no hidden view keeps capturing. A desktop behind a chat view stops streaming and comes back live when it shows again; browser and desktop views close each other. A browser opened anywhere else (Agent Studio, the agent intro) takes the panel; one opened from a handoff card stays inline in the card. Expanded, `BrowserPanel` draws from the body through a portal: the thread's edge fade (`.messages`) is a mask, which clips and stacks even a fixed descendant inside it, so the panel would sit under the sidebar, chat head and composer. The pure rules are `frontend/src/state/sidePanel.ts`.

**Command palette (`components/CommandPalette.tsx`, `state/commandPalette.ts`).** **Ctrl+K** (**Cmd+K** on a Mac; `App.tsx` listens on the window, from every mode, Settings and page included) or the rail's search button (`rail-palette`, also in the phone's drawer) opens one box to go anywhere: each view (Agents, Routines, Workflows, To-dos, Inbox, Archived), each Settings section the nav lists (`visibleSections`, so Account only on a server with a sign-in, and Sync reads "Sync & server" in the shell), every chat and room (archived ones tagged; a single chat whose agent is gone left out, as the sidebar does), every agent (a Codex one tagged), routine and workflow (an off one tagged), and five creates (New chat, New group chat, New agent, New routine, New workflow). A blank query lists the newest live chats, the places and the creates. A query is folded as message search folds it (`fold`, so case and accents don't count) and every word must match: a label start scores over a word start over a substring over the hidden detail and keywords (a section's words, such as "theme" or "passwords"; inside a word only from three letters) over letters in order in the label; sections are capped (`GROUP_LIMITS`), sorted inside by score, then recency, then label length, and the section with the best match comes first. Under them, from two characters (`messageQuery`), the message search's first six hits (`useMessageSearch`, `PALETTE_HITS`) with their count. The box keeps focus (a row's mousedown is prevented; Tab stays): ↑/↓ move and wrap (`moveActive`), PageUp/PageDown move five, Enter opens, Esc or Ctrl+K again closes and gives focus back to where it was; `aria-activedescendant` names the active row of the `listbox`. A pick closes the palette and goes through `pickPalette`: To-dos, Inbox, Archived and Settings through their own open functions, everything else through the unsaved-changes guard (`navigate`) after `toMode` closes the views laid over the modes (an agent opens as its sidebar row does, `openAgentChat`, or Agent Studio when its file has an error; New routine and New workflow get fresh editor keys, as their New buttons do), and a message hit through `openMessage`. Ctrl+K does nothing while another dialog shows (`.modal-backdrop` that is not the palette's), so it never opens over the unsaved-changes question. Nothing is stored or sent: the rows come from the lists the page already holds. The sidebar's search keeps its button and no longer takes Ctrl+K.

**Rail (`components/Rail.tsx`).** A 52 px icon column at the window's left edge, the first child of `.shell`, replaces the sidebar footer (`SidebarFoot.tsx` is gone). Top to bottom: the logo (`rail-home`, Zumi Bot's Z drawn by `BotIcon`, so it follows the theme; a button named Home that goes to the root, Agents' new-chat screen, from any view through the unsaved-changes guard, `openHome`, and closes the phone's drawer; it never shows as the current page), the palette's search button (`rail-palette`, see Command palette), **Inbox** (`rail-inbox`, a bell, with the waiting count `rail-inbox-count` or, when nothing waits, the new-message dot `rail-inbox-new`; named `Inbox, N waiting` or `Inbox, new messages`), **Agents** (`mode-tab-agents`, carrying the unread dot `mode-unread` or, winning the slot, the approval badge `rail-agents-approval`), **Routines** (`mode-tab-routines`, with the waiting dot `mode-waiting`), **Workflows** (`mode-tab-workflows`, with the waiting dot `workflows-waiting`), **To-dos** (`rail-todos`, with the count `rail-todos-count`), **Archived** (`archived-open`), then at the bottom the Usage ring (`sidebar-user`) and **Settings** (`settings-open`). Each button has an `aria-label`, and `aria-current="page"` marks the one whose view shows (`active` is settings, else inbox, else to-dos, else archived, else the remembered mode); Usage is a popover and never stays lit. `AccountMenu.tsx` is that popover (`usage-popover`): a ring filled to the session limit's percent used around the avatar, a red dot when `claude` is not found, name, email, the plan usage limits, Codex's own limits once a Codex run here reported them (`usage-codex`; the ring stays Claude's, see [Codex agents](codex.md)), **Usage details** (`usage-details`, opens `/settings/usage`) and **See all**; it no longer holds Archived… or Settings…. `RailMode` is `agents | routines | workflows` (the remembered mode); To-dos, Inbox, Archived and Settings are route-driven views over it, and `switchMode` closes all four and runs the unsaved-changes guard once. On a phone the sidebar is a drawer and the rail sits inside it at the left edge, so one toggle slides rail and column in together (the mobile bar's toggle keeps its approval-badge-else-unread roll-up and gets no To-dos or Inbox count). The column's layer sits under the rail's, so while it holds a dialog (Delete chat, Delete agent, Archived's Delete) it moves above the rail (`.sidebar:has(.modal-backdrop)`); otherwise the rail covers the dialog's left side. The Inbox has no column, so while it shows the drawer holds only the rail, and picking it closes the drawer. The Esc handler of Settings leaves the Usage popover to close first.

**Chat title row (`ChatView.tsx`).** On a wide screen the row over a chat (`chat-top`) names it: the agent's icon, or a room's member stack, then the title as the sidebar shows it (`chatTitle`, `chat-title`, an `h1` that ellipsizes with the whole title as its tooltip), with the process mark and the side panel's icon at its end. With the sidebar hidden or scrolled away it is the only place that says which chat is open. An archived chat's note gets a row of its own under it. On a small screen the mobile bar names the chat instead, and the row shows only for the archived note; the island's popup has no row (its page head names the chat).

**Phone tab bar (`components/TabBar.tsx`, pure `state/tabBar.ts`).** Below `NARROW_QUERY` the main area ends in a tab bar (`tab-bar`, `nav` named Sections) with five labelled tabs: Agents, Inbox, To-dos, Routines, Workflows (`tab-<name>`), each with the rail's own marks (the approval badge or unread dot on Agents, the Inbox count `tab-inbox-count` or new dot, the To-dos count `tab-todos-count`, the waiting dots on Routines and Workflows), named for a screen reader as the rail's buttons are, and `aria-current="page"` on the open one (`activeTab`: Archived and Settings are no tab). A tap goes where the rail's entry goes (`switchMode`, `openInbox`, `openTodos`); the open section tapped again opens its list in the drawer (`tabTap`: Agents, Routines and Workflows have one; Inbox and To-dos do nothing). The drawer and its rail stay for each section's list and for Go to, Archived, Usage and Settings. It is the main area's last row, so the message box sits above it; it steps aside while a typing field in the main area has focus (a text input, textarea or contenteditable: `TYPING_FIELD` in `typingHold.ts`, which `phone.css` repeats; a checkbox, button or slider gets no keyboard, so it leaves the bar alone) and under `kb-cover`. It comes back only once the tap that ended the typing is over: `holdTypingLayout` (started in `main.tsx`) puts `typing-hold` on `<html>` when such a field loses focus and drops it a task later, or after the pointerup when a mouse button is still down. Back at once, the bar pushed Send up by its height between the tap's mousedown (the blur) and its mouseup, so the click went to the box around them: the keyboard closed and nothing was sent, and every control above the bar missed the same way. The message box's own buttons never take focus (`keepFocus` in `media.ts`, on their mousedown): Send and Stop, Pause, the mic and its language, and the side panel's Ask. So an open keyboard stays open after Send, as in chat apps, and a closed one stays closed. Each tab is a fifth of the width by 54 px.

**Touch text size.** Under `pointer: coarse` messages (both bubbles) and the message box, its edit box included, are 16px (24-25px lines), near the 17 pt phone default; iOS Safari also zooms the page into a focused field under 16px.

**File viewer (`components/FileViewer.tsx`, pure `state/viewer.ts`).** A click on a composer file (thumbnail, or a chip once staged), a sent message's file or a loaded image in Markdown opens one in-app viewer over the page instead of a tab or the default app: images fitted, and full size around the click when larger (click again to fit); text attachments (`isTextAttachment`, which also knows text files by name, since the server stages everything but images as `application/octet-stream`; NUL bytes show as a file) as escaped text, so html or svg shows its source and never runs; anything else as a card. ← → step through the message's (or the draft's) files, Esc, ✕ or a click beside the file closes, and focus goes back to what opened it. A sent file keeps **Open in default app** (shell) or **Open in new tab** (browser) through `attachments.open`, and every file **Download** (`?download=1`; a reply image only when same-origin, `data:image/` or `blob:`). One store per page (`viewer`) and one `ViewerHost` (App's main tree, portalled to `body`; the island's popup holds its own `contained` one, since the island window shows nothing outside the popup). It is a `.modal-backdrop`, so Ctrl+K and the island's Esc leave it alone, and it takes Esc and the arrows on the window's capture phase. Its dark look sets the dark token values on the viewer itself: the build resolves `light-dark()` once at `:root`, so a `color-scheme` on an element flips nothing. PDFs get the card: every response carries `frame-ancestors 'none'`, so none is framed.

**Tool rows.** Every `ToolCallRow` (the chat's tool runs and a dispatched agent's steps) has a two-line head from `state/toolLabel.ts`: what the call did, then the exact command, path or URL dimmed on one line. A Bash call shows its own `description` over its command, a file tool its file name (a partial Read its line range) over the path, an Agent call `Agent: <description>` over its type, an MCP tool its name in words over its server, a desktop action `desktopActionSummary`; other tools the plain `toolSummary`. A run also holds the agent's thinking as `ThoughtRow`s, and its head shows the live thought while it spins (see [Thinking](thinking.md)). Agent text in the head shows hidden characters as escapes (`visibleText`). Approval cards and agent prompts still use `toolSummary`, since a card must show the exact command to judge; a routine or workflow delete reads `Delete routine “<name>”` in the card and in its row (`automationSummary`). A Bash row Auto mode refused (`blockedBy: 'classifier'`) keeps its `⛔ blocked:` title; the way to allow it is not on the row but an inline `AllowCard.tsx` in the message flow, like the question card (`approval question`, same frame and icon tile), drawn by `AgentGroup` right after the tool run's `ToolRun`, outside its fold, so it shows without opening the run. `state/allowBlocked.ts` decides its state: pending, running (the chat is running: inputs and button disabled), collapsed (an older refusal, one line with **Allow…** that expands it in place) or done (one muted line with `allowed-as`). Test ids: `allow-card` (`data-status`), `allow-blocked`, `allow-blocked-part`, `allow-blocked-scope`, `allow-blocked-submit`, `allow-blocked-error`, `allowed-as`. See [Allow a refused call](chat-mode-and-effort.md#allow-a-refused-call).

**Processes in the side panel.** `SidePanelMenu`'s **Open Processes** row, the Processes view (`ProcessesPanel.tsx`) and the chat header's `ProcessMark` are described in [Background processes](processes.md).

**A room's running turns (`state/groupChat.ts`, `MessageList.tsx`).** A room draws its members' work in the thread as it happens, as a single chat does; there is no tray for it over the composer. The backend stamps every item of a running turn with `turn` and, when the turn ends, appends the turn to the thread in one piece (`GroupService.endTurn`), so items of members working side by side interleave in the store. The thread therefore draws only the items without `turn` as its rows (`threadItems`), and under them, in `room-live`, one block per running turn (`liveTurns`: the members in `group.active` order, then any turn still stamped whose end has not been pushed yet), drawn by `AgentGroup` with the member's own streamed text (`streamingBy`, a reply that so far reads as the pass marker hidden), its tool runs, and its approval, question, plan, browser and vault cards. Its finished messages get their hover buttons (`liveActions`: Copy, Reply, react, Mark unread, Export keep the item's id when the turn moves into the thread), less Fork, which the server refuses on an item still stamped with `turn`, and Resend; the text still streaming in has none. `liveTail` picks the tail the way a single chat's does (streamed text, else a spinning tool run, else "Working…" or "Compacting…"; nothing while the member waits on the user). A turn's notices, errors and a pass reply show only once it ends. When the turn ends its items land where its block was, under the finished rows, so a block moves above another member's only when it finishes first. While the room runs with no member at work (the moderator picking), a "Thinking…" line holds the place (`room-thinking`), and queued members are listed under the blocks (`queuedMembers`: "up next", or "waits for" the members they follow); both lines start where a turn's name does, and the placeholder is laid out as a member's working line, so its spinner stays put when a member takes over (`.room-status`, its indent sized again in `studio.css` for the bigger tile). The New line is looked for among the finished items only. DOM hooks: `live-turn` (`data-agent-name`, `data-state` = `working`, `approval` or `asked`), `queued-member`.

**Bubble colors (`tokens.css`, `AgentGroup` in `MessageList.tsx`).** The user's bubble is a plain gray in every color theme (`--user-bubble`: light gray in light, dark gray in dark). Every agent's reply bubble (the streaming one too) takes the color theme's own wash (`--reply-bubble`, with a border of 24% `--accent` over `--border`), whatever the agent's color: a soft fill, not a solid one, because replies carry long markdown, code and tables. Graphite has no hue to wash with, so its reply bubble is `--bg-raised`. The agent's own color (`agentColor`, set as `--agent-tint` on the turn) stays on its avatar tile, and `agentInk` on its name. Since the reply no longer says who wrote it by its color, the avatar tile is sticky (`studio.css`, `top: 8px` inside the thread's padding, past its fade): while any of the turn shows, the tile stays in view beside it, so the bottom of a long reply still shows its agent; the tile's tooltip is the agent's name.

**Tooltips (`components/TooltipLayer.tsx`, pure `state/tooltip.ts`, `styles/tooltip.css`).** The UI never uses a native `title` (the browser's popup takes no theme, font or width); any element gets a tip with `data-tip`, and one `TooltipLayer`, mounted beside the app in `main.tsx`, draws it (`app-tip`, `role="tooltip"`): a small raised card, 12 px, at most 320 px wide and wrapping, keeping line breaks. It follows pointer hover (mouse and pen, not touch; disabled buttons too, so a button can say why it is off) and keyboard focus, only while the keyboard drives (`:focus-visible` after a key press; a click or tap into a field, or a dialog focusing its first control after a click, shows none). The first tip waits 500 ms; while one is open, or within 300 ms after, the next shows at once. It sits centered above its target, below when above would leave the window, 8 px inside the edges, and follows the target each frame: a changed `data-tip` updates it, a target that left the page hides it, as do leaving, a press (until the pointer leaves that element), any key but a modifier, Esc, a scroll that moves the target, a resize and the window losing focus. A tip that only repeats text the element already shows (a file name, an agent's description in its row) shows only while that text is cut off. The target gets `aria-describedby="app-tip"` while it shows unless the tip equals its name; an icon-only control keeps its own `aria-label`, since a tip is not a name. A `title` that other code still sets (React Flow's zoom buttons, a markdown link's title) is moved to `data-tip` on hover, before the browser's popup can show. `frontend/tests/noTitleAttribute.test.ts` fails on a `title` attribute, an attribute spread with `title:`, an SVG `<title>` or `.title =` in `frontend/src`; a component's own `title` prop (a dialog's heading) is fine. The one exception is an element marked `data-native-title`, whose `title` the layer leaves to the browser: the island's agent icons (`IslandView.tsx`), since the strip sits at the island window's right edge and the app's tip, drawn inside that window, was cut off there, while the browser's popup is drawn outside it.

**Stylesheets (`frontend/src/styles/`).** One global stylesheet split by area (`tokens.css`, `chat.css`, `composer.css`, `board.css`, `workflow-canvas.css`, `island.css` and so on), each file opening with a line that says what it holds. `main.tsx` imports `styles/index.css`, which `@import`s them in a fixed order. The files were cut from what was one 18 800-line `styles.css` as contiguous slices in its own order, so the built CSS stayed byte for byte the same; later rules still win ties across files, so a file's place in `index.css` is part of the cascade, and a file never moves in that list without checking what it overrides. A new rule goes in its area's file; a new area gets a file and an `@import` line. The one exception is `studio.css`, imported last: the Zumi Studio look laid over the area files (see Look). Phone and touch overrides that predate the split stay in `phone.css` (small screens and touch) rather than beside their base rules. Tests read the sheet through `frontend/tests/stylesheet.ts` (`stylesheet()` is every file in order, `styleFile` one file), and `stylesheet.test.ts` fails when a file in the folder is not imported or is imported twice.

**Look (`styles/studio.css`).** On a wide window (800 px and up) the rail and sidebar sit on a canvas (`--bg-sidebar`) and the main pane floats over it as a rounded card (`--bg`, `--shadow-pane`, `overflow: clip` so its side panels keep the corners); the page you are on in the rail, a picked sidebar row and the side panel's launcher rows are raised tiles in the same lift, and an agent's sidebar icon sits bare in its row (no tile), its unread dot on the icon's corner. Both sides talk in bubbles with one tucked corner toward the speaker: the user's top right, an agent's top left beside its avatar tile, a reply washed in the color theme's hue and the user's in gray; with a mouse a reply's buttons float in a small card over its bottom right edge while it is hovered (no row of hidden buttons spacing out the thread), and on a touch screen or in the island they sit under it. A one-agent chat's title icon sits on the same small tile. Replying shows a soft card in the agent's color on the message box (`reply-strip`), and the sent message's quote (`reply-quote`) is the same card, smaller; files waiting to send sit in a row lined up with it. A GFM task list drops its bullets, the checkbox being the marker. Tool calls are small cards with a thin status edge (green, or red when failed or blocked; the title keeps its `▸`), a thought a dashed card, waiting approval, question and plan cards glow in the accent (the Inbox's frame replaces theirs), the thread fades under the head and into the message box (`mask-image` on `.messages`), and the message box and its pickers are one card (`.composer-box` + `.pickers`), whose chips drop their outline in a narrow pane (a container query on `.composer`) and which goes compact when its full layout does not fit (see [Chat mode and effort](chat-mode-and-effort.md)). The new-chat screen shows Zumi and a question over the box (`new-chat-hello`); the input starts at one line there too, and an empty chat's intro puts its agent on the same raised tile. A primary button that cannot act yet (a Save with problems left) is a muted solid button, not a faded accent. The workflow inspector's no-problems line (`wf-ready`) is a green check, the answer to its red problem list. The Ctrl+K palette is a floating sheet whose picked row takes the selection wash; its icon cell grows for a room's member stack instead of running under the title. A phone keeps its drawer and full-bleed pane (`phone.css`); only the thread's spacing and the avatar tile shrink there, and the tab bar's open tab puts its icon in a pill of the accent's wash, the phone's version of the rail's raised tile.

**Color themes (`settings.accent`, `theme.ts`).** Settings › General › Color (`AccentControl.tsx`) picks one of `ACCENTS` (`shared/src/types.ts`): Blue (the default), Teal, Coral or Graphite. It is saved in `settings.json` (`accent`, anything unknown reads as blue; `app:getAccent`/`app:setAccent`), so every device shows the same one. `applyAccent` sets `data-accent` on `<html>` (none for blue, whose palette is `tokens.css`'s `:root`); each other theme's block restates the accent and the neutrals tinted to it, Graphite also `--accent-fg`, since its fill is near-white in dark. Like the theme, the last one is cached in `localStorage` (`zumibot-accent`) and applied in `main.tsx` before the first paint, and it reaches the island window through that key's `storage` event. The system bars' `theme-color` follows both (`ACCENT_BG`, each theme's `--bg`). The app icons, the login and setup pages, the desktop picker and the desktop window's first paint stay in Blue: they show before the setting is known. The Zumi Z in the app (`--bot-zumi`) takes each theme's own hue.

**Palette and contrast (`styles/tokens.css`).** Every token is checked against WCAG AA in both themes and every color theme (`palette.test.ts` reads each `data-accent` block over `:root`): text 4.5:1 on each surface it sits on (up to `--bg-selected` and both bubbles, `--user-bubble` and `--reply-bubble`), dots and edges 3:1. Two pairs need a split. **Accent:** white on the accent and the accent as text on the dark background cannot both reach 4.5:1 with one blue, so `--accent` is the fill (buttons, send, badges, spinners; white text on it) and `--accent-text` is the same blue for text; `--accent-hover` darkens the fill on hover instead of fading it, which paled white text below 4:1. **Agent colors:** `agentColor` (`state/bot.ts`) gives the fill (`--agent-<c>`: icons, dots, avatar tiles, mention washes) and `agentInk` the text variant (`--agent-<c>-ink`: the name over a reply, mentions, the composer's mention marks, command chips, reply quotes and strips, a room's queued and from names, board avatars). Most fills are too pale for text in light (yellow is 1.8:1 on white), so each ink is its hue moved in OKLCH lightness until it keeps 4.5:1 on the worst surface it meets, its own mention wash inside a bubble: darker in light, and in dark lighter for red, blue, purple and pink, the rest equal to their fills. A board avatar's initials are white in light and dark in dark, on the ink. `prefers-contrast: more` raises `--fg-muted`, `--border` and `--sel-border` (to the theme's `--ring`), for every color theme. The login page (`login.css`), the desktop picker (`picker.css`), the desktop window's background (`window.ts`), the file viewer's dark blocks (one per color theme) and the showcase site copy some of these values: change them together.

**Agent names in the UI (`state/agentNames.ts`).** The UI names an agent by `displayName` (`workiom5-assistance` reads "Workiom5 Assistance"); the handle stays in everything stored and sent. Chat titles go through `chatTitle(chat, agents)` (`friendlyText`: a known agent's `@handle` reads `@Display Name`, code spans left alone; a search matches either spelling, `titleMatches`), as do the Inbox header, the asked bar, search hits, the island and the phone bar; `mentionLabel` names an agent in the Inbox, the vault card and the ask cards. In agent text a code span that is exactly an agent's handle with a hyphen becomes its mention chip (`codeHandle` in `remarkMentions`; a one-word handle such as `claude` stays code, since it usually names a program). The composer keeps `@handle` as the draft's text: `MentionHighlight` hides it and draws `@Display Name` in its place, and shows the handle again while the caret or a selection touches it (`revealsMention`), so it is edited as typed and the caret never sits in hidden text. Notifications still show the stored title.

**Phone system bars (`theme.ts`, `index.html`).** An installed app's status bar (and, where Chrome colors it, the navigation bar) takes `theme-color`, not the page. `index.html` has one `theme-color` per OS scheme (`media="(prefers-color-scheme: …)"`), each in that scheme's `--bg` (`THEME_BG`); `applyTheme` points both at a theme forced in Settings and gives each its own back for System (`themeColor`), so a dark theme on a light phone no longer gets white bars. The viewport also has `viewport-fit=cover`: where the browser draws under the bars, they show the page's background. `body` pads by the four `env(safe-area-inset-*)`, and each fixed layer that covers the window pads itself (the phone drawer's rail and column, `.modal-backdrop` top and sides, the bottom sheets' bottom, the palette, `.voice-page`, the expanded browser). A new full-window fixed layer needs the same. Drawing edge to edge, Chrome on Android ignores `interactive-widget=resizes-content`: the keyboard covers the page's bottom, and the browser pans to the caret, so the top bar and the composer's bottom go off screen. `keyboardCover.ts` (started in `main.tsx`) watches `visualViewport`, and while it is at least 80 px shorter than the window at zoom 1, it puts `kb-cover` on `<html>` with `--vv-top`/`--vv-height`. `#root` then becomes a fixed box over the part left on screen, following every pan, with no bottom inset, since the keyboard sits over the navigation bar. Where the keyboard does shrink the page, both heights shrink together and nothing changes. The manifest's `theme_color` and `background_color` stay white: one manifest serves both themes, and an installed app picks up manifest changes only on a later update. The sign-in page has the two scheme tags too.

**Error boundaries (`components/ErrorBoundary.tsx`).** A render error no longer blanks the app. `AppBoundary` wraps `<App />` in `main.tsx` and shows the error, its stack, **Go home** (`/`, which leaves a chat whose items broke the page) and **Reload**. That matters most in the installed app, which reopens on the same chat, so a crash there would come back on every launch. `ItemBoundary` wraps each agent block in `MessageList` (a message, a card or a tool run): a block that throws shows "This message could not be shown: <error>" (`item-error`), and the rest of the chat still renders. Both log the error and component stack to the console.

**Markdown rendering (`remarkMathGuard.ts`, `Diagram.tsx`).** Replies render with react-markdown, KaTeX math and Mermaid diagrams. Mermaid draws with its `base` theme fed the app's own tokens (`themeVariables`: each token resolved to hex through a probe, since Mermaid's color math cannot read `light-dark()`), so a diagram follows the theme and the color theme and redraws when either changes. A single-`$` pair follows Pandoc's rule (`remarkMathGuard.ts`), so "$5 and $10" stays text. Mermaid (`Diagram.tsx`) loads lazily, renders with `securityLevel: 'strict'`, and a reply still streaming shows its diagrams as code. A single-line shell block of a finished agent reply also gets a **Run** button and a status chip beside Copy (`CodeBlock.tsx`): see [Run button](run-blocks.md).

**No folder (`shared/src/scratch.ts`).** Picking a folder is optional. The new-chat screen (single and group) starts with none, its chip reads **No folder**, and the folder menu gets a **No folder** row (`new-chat-no-folder`) once one is picked; a group is no longer pre-filled with the last group folder. Send with none calls `chats:create`/`chats:createGroup` with a null `cwd`, and the server makes the chat a folder of its own, `<server home>/zumibot/cache/<yyyy-mm-dd>-<8 hex>` (`newScratchFolder` in `rpc/handlers.ts`): never shared, never isolated in a worktree, and never saved as the agent's last folder or the last group folder, so a real pick stays the island's default and where the folder dialog starts. Clicking an agent (its sidebar row, or its name in the palette) opens its start screen with no folder picked, chats or not, since a chat's folder is locked once it is made (`openAgentChat` in `App.tsx`); only the built-in agent, whose folder is fixed, opens a chat straight away. A `cwd` equal to the scratch root itself (the sidebar group's **+**) is read the same way. In the sidebar `sidebarFolder` files every scratch chat under the root, so they share one group, and `folderName` shows **No folder** for the root and each scratch folder (chat chip, room row, palette, side panel). `recentFolders` leaves scratch folders out, and `reusableChat(…, null, …)` reuses an empty scratch chat of the agent. Nothing cleans the folders up.

**One folder, no folder header (`Sidebar.tsx`).** An agent's chats are listed under a header per folder (name and a + for a new chat there) only when they sit in two or more folders. When they all share one, the header would be a third sidebar level for nothing: the chats sit straight under the agent, as the built-in agent's always do, and the chat's folder chip still names the folder. The `folder` wrapper (`data-cwd`, Show more) stays either way, with `single` on it.

**Dropdown search (`components/MenuSearch.tsx`, `components/SearchSelect.tsx`, pure `state/menuSearch.ts`, `state/menuPlace.ts`).** Every dropdown opens with a search box that has the focus, except on a touch screen (`coarsePointer()`): there the box waits for a tap, since focusing it brings up the phone keyboard, which covers the list and shifts the page under the menu on every open. `MenuSearch` sits at the top of a custom menu (`ChoicePicker`, `RunPicker`, the assignee and status menus, the new-chat agent/folder/members menu, the room-step and routine member pickers) and stays put while the list scrolls. It filters the menu's own DOM: rows (`role` `menuitem*` or `option`) whose text lacks any word of the query get `hidden`, a `role="group"` with none left is hidden too, a MutationObserver filters rows that render later, and **No matches** shows when nothing is left; a row with `data-menu-search="keep"` (Choose folder…, No folder, the worktree toggle) always shows. ArrowDown/ArrowUp move between the box and the shown rows, Enter in the box picks the first, and typing on a row goes back to the box. The menus no longer `autoFocus` their current row; it is scrolled into view inside the menu instead (never `scrollIntoView`, which would scroll the page). Context and action menus (a chat's ⋯, a board card's ⋯, the vault's Add, Sidebar's hover-opened Move to) and type-to-filter lists (`@`, `/`, the palette, folder picker) have none. Native `<select>`s cannot hold a search box, so none are left: each is a `SearchSelect`, which takes the same `<option>`/`<optgroup>` children and the select's `className`, `data-testid` and `aria-label`, but `onChange(value: string)`. Its button carries `data-value` (the current value) and shows the picked option's label (else the first's, as a select does); its menu (`.search-select-menu`, `role="listbox"`) is portalled to `<body>`, so a drawer's `overflow` cannot clip it, opens upward only when there is clearly more room above, measures that room in the part of the page on screen (`visibleView`: the visual viewport, so a phone keyboard that covers the page without resizing it is left out; a pinch zoom is ignored), follows its button when anything under it scrolls, the window resizes or the keyboard opens, pans or closes (`visualViewport` resize and scroll; closing there raced a click on an option, and would drop the list while typing in its box), stays on screen when the keyboard covers its button (anchored at the keyboard's edge), and closes on a pick, Esc (heard first, so the panel or dialog under it stays open), a click outside, a scroll taking the button out of what is shown, or the window blurring. Options are `data-testid="select-option"` with `data-value`. Classes that draw their own chevron (`.rt-select`, `.todo-card-status-select`, the side menu's row) hide the button's `Caret`.

## Connection liveness

A half-open socket (a phone waking from sleep, Wi-Fi handing over to mobile data) fires no `close`, so the page would show connected while every call hangs. When the page becomes visible again or the browser reports `online`, `rpc.checkAlive()` (`net/rpc.ts`, wired in `api.ts`) sends `rpc:ping` (`PING_METHOD`), which the hub answers itself, before any handler and even while draining. With no answer in 5 s the socket is dropped as a close would drop it: pending calls reject with `NOT_CONNECTED` (a `chats:send` whose message is stored stays quiet, see `state/sendFailure.ts`) and the client reconnects. One probe runs at a time.

A call made before the socket has ever opened waits for that open and is sent then, in the order made and ahead of the calls the first connect starts; a sign-out close before it fails them. A page loaded at its own address (a refresh on Settings › Notifications, an editor, Usage) asks for its data on mount, before the socket is up, and a rejection then left it on "Not connected. Reconnecting…" until the user left the page and came back. Once the socket has opened, a call made while it is down still fails at once with `NOT_CONNECTED`: a send or a click must not run late, after a reconnect.

So a page opened while the socket is down (a phone waking up, a reconnect after a server restart) waits for it in the page, not in the client. `useConnected()` (`useConnected.ts`, one watcher on `api.connection.onStatus` behind `useSyncExternalStore`) is true while the socket is up; a load effect keyed on it asks nothing while the socket is down and asks once it is back. Status-like data (Settings › General, Notifications, Vault, Audit's side panel, Channels, Voice, Jev, Usage, spend caps, the cost chip, gh's state, attempt changes, the vault lists of Agent Studio's cards and the workflow inspectors, the Jev check in the routine and workflow editors) is asked again on every connect, which also picks up a change broadcast while the socket was down. What feeds a form or a scrolled list is read only until it lands and never over it: the agent file in Agent Studio, its isolation settings and loadout folder, Voice's alias phrases being typed, a routine's webhook, Audit's rows for the current filters. A loader that runs in an effect of its own and clears its own error (`useLoadout`, Agent memory, remembered approvals) calls `useOnReconnect(fn)`, which runs it each time the socket comes back while the component is mounted, never on mount. A load the socket cut off mid-call rejects with `NOT_CONNECTED`; pages with a shared note (Notifications, Jev, Voice, Channels, Agent Studio) do not show that one, since the reconnect asks again. Loads started by typing or a picker (the new-chat agent suggestion, a card's folder) stay as they were.

**Ack line (`core/chat/acknowledge.ts`, `withAcks` in `state/messageGroups.ts`).** Every single-chat turn the user typed (a send, an edit or a resend, any agent, no setting) opens with one short line on what the agent is about to do. `ChatService.runTurn` starts the `acknowledge` dep right after it stores the user's message, without awaiting it: `app.ts` runs a separate `claude -p --model haiku` call with no tools, settings or session (`runJsonCall`, as the moderator), given the agent's name and description, what the agent reads for the message (`ackMessage`: a command's filled prompt, else the text) and whether the turn asks for to-dos (`asksTodos`, so the line then adds that tasks follow). Its cost is recorded as a moderator call. The answer is stored on the user item as `ack`, through the turn's `items` (the ref agentTurn writes), so the turn's own saves keep it; a line that arrives after the turn ended, a failure or a 15 s timeout stores nothing, and the turn's end aborts the call. A routine's or workflow's message (`auto`), another agent's ask (`from`) and group rooms get none. No agent ever reads `ack` (`readAs` and the seed read `text`), and an edit or resend writes its own. The list draws it as the first bubble of the agent group after the message, with no buttons (it is no item); before the reply's first item lands, `withAcks` gives it an empty group under the key that reply's group will have (`agentKeyAfter`), so the live tail joins it.

**Enter while a reply runs (`state/sendKeys.ts`).** Enter sends into the running reply, Ctrl/Cmd+Enter or holding Send queues a task; unread mid-turn messages show above the task rows (`steer-row`). See [Mid-turn messages](mid-turn-messages.md).

**Suggested replies (`core/chat/replyOptions.ts`, `replyOptionsService.ts`, `state/replyOptions.ts`, `ReplyOptions.tsx`).** After a reply that asks the user something, the chat offers the user's next message: 2 or 3 options are a card in the thread, under the reply that asked (`ReplyOptions.tsx`, passed to `MessageList` as `afterItems`, so it scrolls with the messages and starts where a turn's body does; pinned over the composer it hid the reply on a phone): the reader's `summary` of what the reply did, then the `question` the options answer, then the options as buttons, and a click sends that exact text alone (`onPickReply`, like `onAllowed`: the draft, its files and its reply quote stay in the box, since the card shows while the user types); 1 option is the composer's placeholder (`suggestion` prop), and Tab in an empty box, with no menu open and no modifier, or the hint button beside the mic ("Tab", or "Use" on a coarse pointer) writes it into the box through `onDraftChange`, sending nothing; only a box holding a lone empty paragraph takes it (`isBlankBox`, read live), so Tab in an empty code block still indents. **Server.** `ReplyOptions` (built in `app.ts`) runs last in ChatService's `onIdle` hook, so for single chats and rooms alike, after the task queue, routines and wake-ups had their chance to start a run. Each idle first aborts the chat's earlier read, whatever it then finds. It stops unless the Suggested replies switch is on, the chat is neither running nor paused nor held by a run that has not yet stored `inFlight` (the `running` dep, `chatService.isRunning`), no unheld queued message is about to start (its run would refuse the write), it is not a chat answered away from the composer (`skipsChat`: `asked`, `task`, `cardComments`, `attempt`, `workflow`, `workflowTest`, `channel`, `voice`), its last item is not already `suggested.after` (so a Compact, or any idle that added nothing, never pays twice), and `replyInput` finds something to read: the last item must be an `assistant` item with text (a room first steps back past its own trailing `held` and `moderator` notices, such as "Bob waits for your answer.", which follow the reply that asked); a single chat reads it, a room reads each member's last reply after the last `user` item (members finish in any order, so the one that asked may not be last), each headed by its display name; and `asksUser` (a `?`, `؟` or fullwidth `？` in the last paragraph, or a last paragraph that is a list of choices right after one that asks) must pass on one of them. The message is `ackMessage` of the last `user` item (capped at 2 000 characters), the reply its last 4 000 characters. `runReplyOptions` is a separate `claude -p --model haiku` call through `runJsonCall` (no tools, settings, MCP or session; `--json-schema` `{summary, question, options}`, at most 3 options; the prompt tells it that a room's reply has one section per member and that a question one member asks another gets `[]`; 20 s timeout), its cost recorded as a moderator call. `parseReplyOptions` collapses whitespace and drops blank options, ones over 80 characters, ones starting with `/` or `@` (they would run as a command or a mention) and case-insensitive repeats; more than 3 is none. `question` (at most 140 characters) and `summary` (at most 300) are collapsed to one line, and one past its cap or not text is left out, so the card shows without it rather than cut mid-sentence; both are stored only with options to frame. `close()` aborts every read at shutdown and refuses any later one, also one whose gates were being read. The result, `[]` included, is stored as `ChatMeta.suggested {after, options, question?, summary?}` (`after` the last item's id when the read began) through `patchInPlace`, which writes nothing while the chat is running (stored or claimed) or paused, and the meta is pushed to every tab. Meta, not items: nothing is written into the item list after the turn released the chat, so no write can race a new send. **Client.** `replyOptionsOf` shows nothing unless the switch is on, the chat runs nothing (a room's pending send counts), `suggested.after` is the last loaded item's id (a send from another tab, an edit, a resend or a version switch makes it stale) and, for the placeholder only, the draft is empty (no text, file or reply quote): the card stays while the user types, so its question can be read while answering, and goes only when a message is sent. **Setting.** `AppSettings.suggestedReplies`, on unless `false`; `app:setSuggestedReplies` broadcasts `app:suggestedReplies {on}`, and `useSuggestedRepliesOn` (one watcher per page, asked again on every connect) shows nothing until the server has said it is on, so switching it off hides every tab's buttons and placeholder at once; Settings reads the same watcher (`useSuggestedReplies`), so its switch follows a change made in another tab. The agent never sees any of it: no prompt, tool or cache change.
