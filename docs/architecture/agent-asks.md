# Agent asks

**Agent asks (`core/asks/`, `shared/src/agentAsk.ts`).** In a single chat agent A can run agent B mid-turn with `mcp__zumibot_agents__ask` (`agent`: a handle, a leading `@` dropped and matched without case; `message`: at most 20 000 characters; exact keys only, `askTools.ts`), and gets B's last reply back as the tool result. **Bridge.** `zumibot_agents` is a stdio MCP server built like `zumibot_todos`: `askBridge.mjs` (its own `input` in `backend/vite.config.ts`, `askBridgeEntry` in `browserRuntime.ts`) talks over a Unix socket in a 0700 `/tmp/cb-a-*` dir (`askIpc.ts`: socket 0600, auth line first, byte limits before JSON parsing, at most 4 calls in flight per connection) with a capability token per CLI attempt, bound to the owner `{chatId, agent, chain, turn}` and revoked when the attempt ends; the bridge names only the target and the message. Its `--mcp-config` entry has `timeout: 86400000` and the run's env `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0`, so a long ask is never backgrounded or timed out by the CLI; the token stays out of argv (a `${…}` placeholder). Every attempt of every single-chat turn gets it (routine runs too), never a room member's turn, Zumi Bot's or a `/compact`, so the prompt-cache prefix holds; a `/btw` side run joins one (empty chain, blocked by its deny hook) only when the main run had it. `ChatService` answers the ask's permission request itself (no card, no rule, no Jev hint), and the appended system prompt ends with `askSystem` (`askPrompt.ts`): a fixed paragraph and a roster of the loadable agents (Zumi Bot and A left out, sorted by name, first line of each description). **Service.** `AgentAsks` (`askService.ts`, built in `app.ts` with `run` reaching `chatService.runAsked` by closure) checks the target and the limits and refuses with a fixed sentence the agent can act on (`REFUSAL`; the IPC lets through only text matching `SAFE_ASK_MESSAGE`, so no path or CLI output ever reaches A): unknown name (with the handles that exist), Zumi Bot, A itself, an agent already waiting in the chain, a chain past 3 hops (`ASK_MAX_HOPS`), 10 asks per turn of A (counted on the turn key across attempts, forgotten by `askEnd`), 3 at once, a broken agent file, B still answering an earlier ask from the same chat (`busy`, the claim failed), the usage limit (with its UTC time), a failed or stopped turn, and the server stopping (`asks.close()` before `stopAll`). B's reply is capped at 50 000 characters with a note, or reads "finished without writing a reply". **The A→B chat.** One per `(source chat id, B)`, found by `ChatMeta.asked` `{by, from, fromTitle, chain}` and `agentName` (concurrent asks share one `making` promise); a deleted one is made anew, an archived one reused (the run's `inFlight` unarchives it). It is B's chat in the source chat's cwd, so it sits under B in the sidebar, titled `@A · <source title>` once (`askedTitle`). `ChatService.runAsked` claims it directly (no `TaskQueue`, nothing else sends there) and runs one turn: A's message is a `user` item with `from: A` (readers that build prompts still treat it as user text), B's appended prompt adds `askedSystem` (it is asked by @A for the user, who does not read this chat; questions go at the end of the reply), and B's `AskUserQuestion` is denied with `QUESTIONS_DENIED` so the question reaches A; tool approvals and `ExitPlanMode` are not denied. Its turn end carries `asked: true`: `ReadMarks` stamps `seenAt` with `replyAt` (never unread) and `NotifyService` sends no `replied`/`error`. It is read-only: `writable()` in `rpc/handlers.ts` refuses send, edit, resend, version switch, fork, compact and mark unread (`This chat is read-only`). Side questions are still taken there, from the Side questions panel: B answers from the A→B chat like any single chat, and A (an `@A` mention, stored with `mention: true`) answers from `asked.from`, that chat's session, tools and fork point, with the A→B chat's messages so far (`askedThread`: A's ask, B's text, one line per tool step, capped at 20 000 characters keeping the first and the newest) in its message; the entry stays in the A→B chat, and once the source chat is gone it fails with `sourceGoneText` ("The chat @A asked from was deleted") and no run. The UI shows `AskedBar.tsx` (who talks, a link to the source chat or "(deleted chat)") in place of the composer, Copy as the only message action, no selection menu and no version switcher. **Roll-up and Stop.** `ChatService.askParents` links each running A→B chat to its asker: `pendingCount(A)` adds every live ask's below it, and `pushPending` pushes the count up the whole chain, the asked chat's own push marked `asked: true` so it notifies nobody; A's `approvals` push, sidebar badge, routine `waiting` state and `waiting` notification therefore include B's cards. `stop(A)` stops every chat it asked, down the chain, and an aborted MCP call (A's CLI ended, the attempt disposed) stops B through the signal. **In A's chat.** `foldTools` lets an ask call stand alone and `MessageList` draws it as `AskCard.tsx` (`state/agentAsk.ts` `askCardState`): who was asked, A's message, a status (working, waiting for you, done, failed; stopped once the source chat stops running without a result), B's reply behind a toggle and **Open conversation**. The card finds the A→B chat by `askedChatOf` (source id plus B), loads its items while it has cards waiting (`App.tsx` `askEnv`) and shows them live, answered through `chats:answer`/`answerPlan` with B's chat id (Allow for this chat applies there, Allow always to B); deeper chains show a hint to open the conversation. A single chat's composer `@` menu, and the message edit box's, lists `askableAgents` (loadable, not the chat's own agent nor Zumi Bot nor a remote agent, no `everyone`; the roster in A's prompt, `askRoster`, and `targetOf`, which refuses one with `REFUSAL.remote`, leave remote agents out too: the message and chat would leave this machine) and colors the mentions; the text is sent as typed. Sent messages, replies and side answers there draw every other agent's `@handle` (Zumi Bot aside, broken ones greyed) as a chip, as a room does its members' (`mentionHandles`); `@everyone` stays text. Rename moves `asked.by`, `asked.chain` and each `from` with the agent (`ChatStore.renameAgent`). **Side asks.** The bridge's second tool, `mcp__zumibot_agents__side_question` (`ASK_SIDE_TOOL`; `agent`, `question` of at most 4 000 characters), asks B a quick question about a conversation A already opened with `ask` from this chat (the A→B chat by `asked.from` plus B, never made: otherwise `REFUSAL.noConversation`). `AgentAsks.sideAsk` checks the target as `ask` does (no hops, no chain), shares its per-turn and parallel counts, and runs `SideQuestions.askFrom`: a plain `/btw` entry in the A→B chat (clean point or seed, three open, its own three minutes, cost there, no unread or notification) with `from: A`, B's note naming the asker and the plain guard, so B can ask nothing on. The end is B's answer (capped like a reply) or a fixed sentence (stopped, timeout, limit, failed). The main run's call gets no card (`ownAsk` covers both tools) and is drawn as `SideAskCard.tsx`, whose **Open in conversation** opens B's entry (found by `from` and the exact question). A's own side run gets the one exception to the no-tools guard, only for the user's side question in a chat whose run has the bridge (`SideBase.asks`, set by `baseFor` too): `SIDE_GUARD_ASKING`, whose lookahead matcher lets exactly that tool through (proven against the real CLI by `e2e/sideAskProbe.mjs`), and an allow for exactly its permission request; every other side run keeps the plain guard byte for byte, and the server refuses a plain `ask` from a side run (`REFUSAL.sideRunAsk`). Its note names whom A asked from this chat. A user's side question to A from an A→B chat's panel gets the same exception through the source chat's base: the ask owner is the source chat (whose A→B chats A may ask), while the link and the paused clock stay on the entry in the A→B chat (`sideBrowser`'s `side` place). A's side entry records each call in `asks` (`{agent, chatId, entryId, state}`, a chip that opens B's entry; a running one becomes `error` at a restart, Ask again clears them), and its clock pauses while it waits on B, capped at `SIDE_ASKING_CAP_MS`. The A→B chat's Side questions view shows "from @A" on B's entry and offers Stop (A gets `REFUSAL.sideStopped`) but not Ask again (`again()` refuses an entry with `from`). A chat Stop never stops side answers: only a cancelled call (A's run or A's side entry ended) or a stop of B's entry ends a side ask. Rename moves `from` and each `asks[].agent`. `e2e:ask` drives both paths with the fake. **Unattended.** An asked turn whose asker is unattended (its `TurnSpec.auto`: a routine's or workflow's message, or a room opened by one until the user types into it) is unattended too, down the whole ask chain: `AskOwner.auto` carries the flag to `AgentAsks.run`, `runAsked` puts `auto` on B's turn, and B's own asks inherit it, so connector writes are refused there (see connectors.md).
