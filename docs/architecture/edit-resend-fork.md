# Edit, Resend, Fork

**Edit, Resend, Fork.** Hovering a message offers these; Edit and Resend make a new *version* of a user message, shown as `‹ n / m ›`. The server refuses a switch while the chat runs, so the arrows are off then, and `switchBlocked` (`messageEdit.ts`) gives them and the group a tooltip saying why (wait for the reply, sending unavailable, a switch on its way). The visible `chats/<id>.json` holds one version of each edited message (its `versions` marker); the others sit in the hidden `chats/<id>.versions.json` (`versions.ts`), away from every reader of the items, so a seed or a fork never includes them. To rewind the agent, the runner records the CLI's entry uuids (`streamParser` `entry` events; a Codex turn's id, see [Codex agents](codex.md)): the last item of a turn gets an `end` stamp (session id and last entry, plus `agent`/`seen` in rooms) and each assistant message of a Claude turn a `cut` stamp. `sessionPoints.ts` turns the stamps into where a session starts, stored as `next` on the chat (or per member in `GroupInfo.next`): `{at}` runs `--resume <session> --resume-session-at <at> --fork-session`, so the old version's session stays untouched, and `{seed: true}` starts a fresh session seeded from the visible items (with the `expired` notice), which is also the fallback for messages sent before the stamps existed or a session file that is gone. Every run reads a stored point through one function, `turnStart(sessionId, at?, drops?)` (`core/engines/engine.ts`): a session with a point is forked, one without is resumed, and no session is a fresh one. The main run and a side run both call it, and each engine's adapter spells its own form of the three — those two flag names appear only in `claudeResume`, and `thread/fork` only in `codexStartOf`; behind the `ZUMIBOT_CLAUDE_SDK` hook a third, `sdkResume`, asks the Claude Agent SDK for the same rewind through its documented `resume`, `resumeSessionAt` and `forkSession` options (see [Engines](engines.md)). Those two flags are hidden in the CLI and could change in any update, so a failing cut run is a visible error and never retried as a plain `--resume` (that would write into the version being kept; a Codex fork that fails reseeds instead, see [Codex agents](codex.md)), and after a cut run's `init` a session id equal to the resumed one means `--fork-session` was ignored: the run is stopped with the `FORK_IGNORED` error naming the CLI version. `TaskQueue.rerun` on a running chat holds the tray (`held` on the chat) first, then stops the reply, so nothing starts by itself, not even after a restart, until the user presses **Send now** or removes each task (a Run result's hidden task is never held, and its user item is never edited or resent, see [Run button](run-blocks.md)); on an idle chat the tray is left as it is. Rooms rewind every member in `GroupService.rerun`, each on its own engine (a Codex member forks its thread at its own end stamp, and `GroupInfo.sessionEngines` follows the stamps); Fork (`fork.ts`) copies the visible items into a new chat and cuts the sessions the same way. `sync.mjs` compares each chat's versions file: when they differ it keeps the newer side and turns the older one into a separate copy chat if it holds any item the newer lacks, so nothing is lost.

**The declared turn (`--resume-drops-turn`).** A cut can tell the CLI which turn it means to discard, and the CLI then refuses one that would discard anything else — a queued message or a task notification the session took in mid-turn that ZumiBot had not seen — instead of cutting on trust. Every Claude prompt therefore goes out under an id ZumiBot gives it (`encodeUserMessage`'s `uuid`, the SDK adapter's `SDKUserMessage.uuid`), and the item that records where a turn's session ended records that id beside it, as `sent: {session, at}` next to `end`, in the same items write: one rule for a single chat and for a room member alike, since a member's turn may answer another member rather than a message of the user's, and several members answer the same one. A turn that recorded no end records no `sent` either, since it is no cut point to begin with. `droppedTurn(stored, userId)` reads the stamp back for a rewind, and `startBefore`'s third argument carries it into `NextStart.drops` — but **only when that turn is the only one the cut discards**, because the CLI validates the whole discarded range against the one declared turn: a range holding a later turn as well is refused (probed against Claude Code 2.1.325), and so is a cut that starts inside a turn, since the range must begin with the declared turn's own prompt. So Edit and Resend of the latest message declare their turn; editing an earlier message, switching versions, and Fork from a reply (`startAfterMessage`) declare nothing and cut unvalidated, exactly as every cut did before. A room rewind declares per member (`droppedMembers`, read off each member's own items into `memberStartsBefore`'s fourth argument): a member that loses exactly one turn declares it, while one that spoke twice in the discarded pass (a hop, a mention), left work it never ended, or lost nothing at all declares nothing — so in the same rewind one member can declare and another cannot. A refusal arrives as `error_during_execution` with no turns and `Resume rejected by --resume-drops-turn:` on stderr (`isCutRefused`): it is deterministic, so the cut is never sent again — the turn reseeds from the visible items with the `expired` notice, the same recovery as a session that is gone. On the CLI path the flag rides only on a binary that takes it, asked once per binary by `dropsTurnProbe.ts` (`-p --resume-drops-turn <uuid>`: a CLI that has it answers that it `requires --resume-session-at`, one that does not says `unknown option`), so an older `claude` keeps cutting as it always did; the SDK adapter needs no probe, its `resumeDropsTurn` being a typed option of a version-pinned SDK.

**The edit box (`MessageEditor.tsx`).** The composer's Tiptap editor (same extensions, markdown in and out through `composerMarkdown.ts`), so mentions read by display name and lists and code show styled; the `@` and `/` queries come from `composerExtensions.ts`, shared with the composer. A leading `/` opens the command menu (`CommandMenu.tsx`) and an `@` the mention list (`MentionMenu.tsx`, shared with the composer; options from `mentionOptions` in `state/mentionInput.ts`): a room's loadable members with `@everyone` first, or in a single chat the agents it can ask (`askableAgents`). Both stay closed until the first change, so a message ending in `/name` or `@name` opens without a list; the `/` menu wins when both could open; Esc closes a list first and only then cancels the edit. The lists float over the chat (`.msg-edit-menu`, `position: fixed`, so the chat's scroll box never clips them), above the box or below it when it sits near the window's top (`editMenuPlace` in `state/editMenu.ts`). The box takes focus synchronously on open (Tiptap's own focus waits a frame, and an Esc pressed at once would be lost). The edited text goes to the server as typed, so its mentions route a room's turn (or ask an agent from a single chat) the same as a new message's. E2E reads its text and sets its caret through `el.editor` (Tiptap's editor on its element).

**Engines without the caps.** Edit, Resend, version switching and Fork read `EngineCaps.resend` and `fork` (ACP has neither: no rewind at a point in stable v1): `MessageList` takes `chatCaps` and leaves out the buttons and the `VersionSwitcher`, and `chats:edit`, `chats:resend`, `chats:switchVersion` and `chats:fork` go through `refuseWithout` with `capRefusal`'s fixed sentence. A room needs them in every member, like Pause. An "i" beside the agent (`EngineInfo`, `missingFeaturesTitle`) lists what the engine can't do.
