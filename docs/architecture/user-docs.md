# User docs

**What it is.** `zumi-bot-docs/` (package `@zumibot/docs`) is the end-user documentation for `https://docs.zumibot.run`: an Astro Starlight site that teaches ZumiBot from install to the most advanced feature. It is for people who use ZumiBot, not people who change its code; developer detail stays in `docs/architecture/`. Design: `docs/superpowers/specs/2026-11-20-docs-site-design.md`; plan: `docs/superpowers/plans/2026-11-20-docs-site.md`.

**Build.** `npm run dev -w @zumibot/docs` serves it on port 4321 (`.claude/launch.json` has a `docs` entry); `npm run build -w @zumibot/docs` writes static HTML and the Pagefind search index to `zumi-bot-docs/dist/`. Astro 7 needs Node 22.23.4 or newer. The package lists `cookie` itself: the root hoists cookie 0.7 (express, through the MCP SDK), and Astro's prerender bundle in `dist/` resolves `cookie` from the nearest `node_modules`, which would find the old one and fail with a missing `parseCookie` export. Nothing third-party loads at view time: the font is self-hosted (`@fontsource-variable/bricolage-grotesque`), search is Pagefind's own files, and there is no analytics. Checks around the build: `prebuild` (and `dev`) run `scripts/writeChangelog.mjs`, which writes the git-ignored `src/content/docs/server/changelog.md` from the root `CHANGELOG.md` without its title and intro; `starlight-links-validator` makes a broken internal link fail `astro build`; and `scripts/checkDist.mjs` then fails the build when a built page has no CSP meta tag, has unhashed inline code, or loads a script or stylesheet from another host.

**Where things are.**
- `src/content/docs/<group>/<page>.md(x)`: one folder per sidebar group. A page's frontmatter has `title`, a one-line `description` (search and link previews) and `sidebar.order` (its place in the group).
- `src/sidebar.ts`: `SIDEBAR`, the groups in the approved order (the spec's sidebar). `astro.config.mjs` turns each entry into a labeled group that autogenerates from its folder. A group joins `SIDEBAR` when its first page is written; `tests/sidebar.test.ts` checks every group has a page, every folder is listed and the order is the approved one.
- `src/styles/brand.css`: Starlight's `--sl-color-*` variables set from `zumi-bot-site/src/styles.css` (light and dark), and the font. Keep it in step with the site when the app's palette changes. `src/assets/zumi-z.svg` is the Zumi Z from `botShapes.ts`, drawn as the site draws it; `public/` holds the same three icons as the site's. It also holds `og-image.png`, the link-preview card every page names (`src/lib/socialCard.ts` adds `og:image`, its size and alt, and `twitter:image` through Starlight's `head`; Starlight writes the title, description, URL and `twitter:card` itself but no image, so a pasted link unfurled in Slack with an empty picture). `npm run og-image` draws it with the site's card (see Link preview in [updates.md](updates.md)); never edit it by hand.
- `social` in `astro.config.mjs` puts three icons in the header: GitHub (the repo's home page, `https://github.com/MhdAljuboori/ZumiBot`), a heart to the site's sponsor page (`https://zumibot.run/sponsor`) and email (`mailto:contact@zumibot.run`). The site's header carries the GitHub mark, as a button after the theme button, and its footer the email. No `editLink`: pages never send readers into the source.
- **License and sponsoring.** The FAQ's "License and sponsoring" section says what the license allows (everything but selling) and points at the sponsor page; What is ZumiBot has one line on both. The page itself lives on the showcase site, never here, so there is one place that names the wallet.
- **Contact.** The FAQ's Contact section and Troubleshooting's last tip give `contact@zumibot.run` and the GitHub repo, asking for the version from **Settings**, **About** and the log.

**Deploy.** Hosting is Vercel, a second project next to the site's, Root Directory `zumi-bot-docs` (`vercel.json` steps up to the repo root for the workspace install and build, as the site's does), deploying every push to `main`. Old deploys are deleted hourly by the site's prune workflow, which keeps the one `docs.zumibot.run` serves and its rollback target (see "Keeping deploys few" in [updates.md](updates.md)). The owner adds the domain and DNS. `vercel.json` sets the site's security headers and a header CSP with `'unsafe-inline'` for scripts and styles. That is safe because a page is held to both policies: Astro's `security.csp` puts a hash-only CSP meta in every page, so the meta's hashes are what actually apply, and `checkDist.mjs` fails the build when a page has no meta or has inline code the meta does not hash. Astro hashes only what it bundles, so `src/lib/cspHashes.ts` (run by `src/lib/cspIntegration.ts` after the build) adds the hashes of Starlight's inline scripts and `style="..."` attributes to each meta, with `'unsafe-hashes'` for the attributes. `'wasm-unsafe-eval'` is for Pagefind's WebAssembly. Astro does not enforce the CSP in `dev`; test it with `npm run preview -w @zumibot/docs` after a build.

**Writing rules.** Plain, second person, short sentences, US spelling, the tone of `CHANGELOG.md`. A feature page runs: what it is for (one or two sentences), how to use it (numbered steps, screenshots), tips and limits, related. Each page is written fresh from its area doc here and checked against the app: nothing is copied over, and a page has no file names, module names, internal paths, development-only environment variables or test hooks. Only released behavior is documented; a part this repo's docs mark as a later phase or "to verify" is left out or named as not available yet. UI labels are quoted exactly as the app shows them. Examples use `zumibot.example.com`, never a real server. Server install commands use the public installer, `https://zumibot.run/releases/latest/install.sh`, as the site's "On a server" section does. On Windows, Local mode runs the server inside WSL2 (Node.js 22 and Claude Code installed there); the steps are `get-started/run-locally.mdx`. Slugs are the file paths and never change once the site is live, so later in-app links can rely on them.

**Comments.** A `.md` page cannot hold a JSX comment (`{/* */}` shows as text), and an HTML comment (`<!-- -->`) ships in the built page. Use `.mdx` for a page that needs a note to its writers: MDX drops `{/* */}` when it builds. `checkDist.mjs` fails the build on any HTML comment in a built page, and on anything loaded from another host (a `src`, `href`, `srcset` or `poster` that is `http:`, `https:` or `//`, except on `<a>` and on a `<link>` that is only `canonical`, `alternate` or `sitemap`, plus `@import` and `url()` with a host in a style); the checks are in `src/lib/distChecks.ts`, with tests. A note in a page's source does not name a task number: `Task 12` is a leak too.

**Leak list.** Pages are the instructions, not a way into the source, and the owner's servers stay unnamed. The one GitHub address a page may name is the repo's home page, `https://github.com/MhdAljuboori/ZumiBot` (a trailing `/` is fine); `findLeaks` sets it aside before matching. Past that, a page must never contain `github.com/MhdAljuboori` (so no link to a file, a release or `.git` under the repo), `raw.githubusercontent.com`, `mhdaljuboori.me`, `zumi-bot-server/`, `docs/architecture`, a source path such as `src/<name>.ts` or `.tsx`, a bare `MhdAljuboori`, or a plan's `Task <n>`. `zumi-bot-docs/tests/leaks.test.ts` enforces this on every page and on `CHANGELOG.md` (`src/lib/leaks.ts`), and also fails a `bash`, `sh` or `shell` code block with a `$ ` prompt or a curly quote.

**Screenshots.** Real screenshots of the app, in light and dark, made by a script from demo agents and made-up chats, never by hand. `shots/list.mjs` is the list (`SHOTS`, each entry documented by its JSDoc `Shot` type); `shots/run.mjs` makes them. For each shot and each theme the runner starts a fresh server through the e2e harness (Local mode, fake claude, the four demo agents in `shots/agents/`: Code Reviewer, Docs Writer, Researcher and Release Helper, so readers never see the backend test fixtures' odd names or duplicate-name warning), writes `{ theme }` into `settings.json`, copies the shot's `seed` folder (`shots/seed/<seed>/`, copied into the data dir) first, sets the viewport (default 1280x800), runs the shot's `go(h, theme)`, waits 1.5 s and saves `src/assets/shots/<name>-<theme>.png`. A console or server error fails the shot, naming it, and the browser and server are always stopped. `list.mjs` imports nothing at top level, so the vitest test can read it fast.
- **Server screens and scripted replies.** A shot's `start` option (an object, or a function of `{ tmp, dataDir, agentsDir }` for an option that names a path inside the shot's folders, such as the extensions shots' state file for the fake extensions CLI) is merged into the harness `start()` call: `{ mode: 'vps', setup: false }` serves the first-run wizard (`h.setupCode` holds its code; the wizard follows the browser's color scheme, so `go` calls `h.page.emulateMedia({ colorScheme: theme })`). A reply that waits on an approval card comes from a script file in `shots/scripts/` copied over `h.script` before the message is sent. The runner ignores the server's `setup:` progress lines on stderr; any other stderr line fails the shot. A shot that needs its own story builds the script on the spot with `replyScript` and plays it with `writeScript` (in `list.mjs`): steps of thinking, a tool call, text or a pause, a context size, a usage-limit end, and `uuid: true` so Edit can rewind the session (the second script of an edit needs its own session id). `demoChats` makes three finished chats for the sidebar shots. A room shot starts with `roomStart()` (`shots/fakeRoomClaude.mjs` as the fake claude: member turns play one script per agent, `finishedRoom` and `newRoom` make the story, the moderator picks the members named in its `FAKE_ROOM_PICKS` when you speak, and the handoff summary is fixed); the agent-ask shots script an ask with a `#MCP_CALL` line (`askScripts`) and the dispatch shots a reply with two subagents (`dispatchScript`). The projects shots add `detail` on a script's tool step (the CLI's own `tool_use_result`, which the Files panel reads), `makeRepo`/`worktreeChat` (a real repo with a bare `origin` in the shot's folder, and a chat on its own worktree), `ghStart` (the backend's fake `gh` first on the server's PATH, answers from a state file the shot rewrites), `appCall` (the board's cards are set up through the app's own calls) and `runningProcess` (the backend's fake process CLI; its scenario rides in the first message, so those shots use a narrow window where the side panel is a sheet and the chat is not visible). The to-do panel inside a chat is not shown as a picture, since every group there carries the time of its reply. A shot may set `clip`: a CSS selector (the picture is that element only) or a function of the harness that returns a rectangle in window pixels (the picture is that part of the window). The automation shots clip to the editor's right-hand panel, a dialog or the Inbox page by selector, and to the canvas by rectangle (`canvasCrop`: around the steps and the toolbar, ending before the small "React Flow" credit at the canvas's lower right), so the sidebar and a header with the time of a run stay out. A clip only crops the screen. The automation shots save routines and workflows through the app's own calls (`routines:save`, `workflows:save`, `workflows:run`; `saveWorkflow`, `releaseNotes`, `startRun`), use the backend's fake workflow claude, and open a screen by its address. Times that would differ between the light and dark picture are avoided: the routine has no runs yet and its zone is set to UTC, and the History and Inbox shots rewrite the stored `savedAt` and message `at` to fixed dates before the screen opens.
- **Voice and computer shots.** The voice shots copy `shots/seed/voice/voice.json` (voice on, a made-up key the page never shows) and the dictation and phone shots pass Chrome's fake microphone through the `start` option's `chromeArgs` (the e2e's tone file; the recording is never sent anywhere before a second tap), so the listening line and the talk screen are the app's own. The browser panel shot sets `ZUMIBOT_BROWSER_EXECUTABLE_PATH` to the machine's Chrome and shows the real, blank, view-only panel. The runner reads that Chrome's path from `ZUMIBOT_DOCS_CHROME` and falls back to `/usr/bin/google-chrome`; with neither present, the shot stops with a message that says so. The desktop approval card is a scripted reply asking to use `desktop_click`, cropped (`clip` function) from the card's top to Allow once, since the rows under it name the tool the way the server knows it. The Desktop view itself has no shot: a real agent desktop shows the host account's name and a clock in its panel, so that page is text only, as are the island shortcut and the phone's top-bar mic (the Electron shell and the phone's own chrome are not reachable).
- **Connect shots.** The notifications shot uses VPS mode and enables the page's own device through the app's own `notify:enable` call with made-up keys and a push address that is never contacted (Chrome grants the permission), so the page reads "On" with nothing sent. The Telegram shot starts the e2e suite's fake Telegram service from an async `start` function, which returns `cleanup` (the runner stops it when the shot ends), then saves the fake token, turns the bot on and switches one agent on through the page. The Slack shot is the page before any setup, and the Connectors shot answers the connector list from the extensions fake CLI's state file and flips one switch through the page. Pairing codes are random and are never shown; the real Telegram and Slack sides, and claude.ai's sign-in, are not reachable, so the page's steps there are text.
- **Safety shots.** The Vault shots save three made-up items (`vaultDemo`: a login, a card with a published test number, an API key; every secret an obvious fake) through the app's own `vault:save` and show only the list and a form whose secret boxes are empty. The spend cap shots set a cap in Agent Studio's own field and run one short chat per agent (the fake claude's reply costs $0.0213, so a $0.02 cap is passed and a $5 cap is not: `spendCapChats`). The Usage shots (`usageChats`) are cropped to the total and to the token boxes and breakdown, never the daily chart, whose date axis would age; the cost chip shot is clipped to its window. The audit shots (`auditDemo`) run three chats (two calls with no card, one allowed once, one denied) and then rewrite the one audit file to fixed made-up times, durations and machine name with the hash chain worked out again, so Verify chain would still say intact; the footer (machine name, size) and the record's JSON (ids) are cropped out. There is no Isolation shot: the section's text depends on the machine (Sandboxed is greyed out where `bwrap` is missing, Container says to build the agent image with an npm script, and the folder lines carry a temporary path), so that page is text only, as is the vault card that asks to use a saved card (it needs a real page in the agent's browser).
- **Engines shots.** The Codex shots start the fake Codex app-server (`codexAgentStart` writes a demo Codex agent and turns on `fakeCodex`; `codexScript` plays one turn), so no login or quota is used. The ACP and Remote card shots only fill the card's boxes with examples (`gemini`, `--acp`, `https://agents.example.com/run`) and save nothing. The Jev shot seeds `shots/seed/jev/jev.json` with an obvious fake key, which the page never shows. Jev's own calls (risk hint, agent chip) have no shot: the OpenRouter address is fixed, so the app cannot be pointed at a fake.
- **The on-screen edits.** Two presentation-only edits are allowed, and no shot may change any other text, state or element. First, the harness's home folder has a random temporary name, and three screens print a folder as a full path (the extensions loadout card and Settings page, and a process's log). For those shots, `go()` calls `tidyFolderPath` (in `shots/list.mjs`), which replaces only that path's text and tooltip with the fixed demo path `~/projects/shop`. Second, the slash menu shots (`chatting-slash-menu` and `agents-zumi-bot-commands`) add a style to `.mention-menu` that lifts its maximum height (`max-height: none`), so every row shows instead of a scrolled part. The Zumi Bot one also sets `.chat-intro-desc` to `visibility: hidden`, since the tall menu covers the start screen except the end of the agent's description, which showed beside it. A shot passes `go: (h) => helper(h)`, never a helper itself: the runner's second argument is the theme.
- **Make them.** The runner needs the built server: `npm run docs:shots` (repo root) runs `build:server` and then the runner; `npm run docs:shots -- <name> [name...]` makes only those shots. If the server is already built, `npm run shots -w @zumibot/docs -- <name>` skips the build.
- **Add one.** Add a `SHOTS` entry (`name` is kebab-case and starts with its page's group, like `chatting-composer`), run the runner for it, look at both PNGs (light is light, dark is dark, the app rendered), then put `<Shot name="chatting-composer" alt="..." />` in the page. A page that uses `<Shot>` is `.mdx` and imports it: `import Shot from '../../../components/Shot.astro'` (the depth follows the folder). The alt text says what the screen shows. `src/components/Shot.astro` renders both PNGs through `astro:assets`; `brand.css` shows only the one that matches `:root[data-theme]`, so the shot follows the theme picker, not the system theme. An unknown name fails the build. `tests/shots.test.ts` checks every used name is listed and made, every listed name is used, and names are unique and kebab-case. The PNGs are committed.
- **Keep them current.** A change that alters a screen means rerunning the shots of every page that shows it.
- **Not reachable.** The runner drives the web UI only. Screens that live in the Electron shell (the island, the tray, the server picker) cannot be captured, so their pages describe them in text.

**Keeping it current.** A change that alters what users see updates its page under `zumi-bot-docs` in the same change, and redoes the page's screenshots when the screen changed. The index line in the root `CLAUDE.md` says the same.
