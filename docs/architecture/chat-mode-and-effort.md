# Chat mode and effort

**Chat mode and effort (`shared/src/chatRun.ts`, `state/runPickers.ts`, `ChoicePicker.tsx`).** A single chat keeps its own permission mode (`ChatMeta.permissionMode`) and effort (`ChatMeta.effort`); absent means the defaults (the server's mode, Medium effort). Rooms have neither: their members run on the server's mode and their agents' own effort, and `chats:setPermissionMode` / `chats:setEffort` leave a room alone (as `setModel` does).

**Modes.** `CHAT_MODES` is `manual | acceptEdits | plan`, shown as **Ask permissions**, **Accept edits** and **Plan mode**; absent is **Auto**, the server's own mode (`auto`, or `manual` under the `ZUMIBOT_PERMISSION_MODE` dev hook). A chat never stores `auto`, so the dev hook stays the default, and never a mode that skips approvals (`bypassPermissions`, `dontAsk`); the handler refuses anything else (`isChatMode`). Each turn spawns its own `claude`, so a mode applies from the next message (`runMode` in the spawn). Side runs (`/btw`) keep the server's mode under their own guard, and Compact runs no tools, so it gets the server's mode too.

**Plan mode.** A process started with `--permission-mode plan` has no earlier mode to go back to: when its `ExitPlanMode` is allowed plainly the CLI goes on in `default` and asks before every edit (the plan probe found this; Claude Code 2.1.322). So approving the plan card of a turn that started in Plan sends `updatedPermissions: [{ type: 'setMode', mode: <server mode>, destination: 'session' }]` with the allow (`allowResponse`'s third argument), and the chat goes back to Auto (`leavePlan`, only while it still reads `plan`, so a mode picked meanwhile stays). Keep planning leaves it in Plan. An agent that enters plan mode by itself (`EnterPlanMode`) in another mode is untouched: the CLI restores that mode itself.

**Effort.** `EFFORTS` is the CLI's `low | medium | high | xhigh | max` (**Low** … **Extra high**, **Max**), passed as `--effort` after `--model`. There is no Default option: a chat with no effort of its own runs at `DEFAULT_EFFORT` (`medium`), and picking Medium (or `null`) stores none, so absent and Medium read the same. Rooms and Codex chats pass no `--effort`, so there the agent's or the CLI's own applies. The chat's effort also goes to Compact, the side base (`SideBase.args.effort`, and `baseFor` in `app.ts`) and a fork, as the model does, since another effort may write the cache again. The CLI warns and ignores an unknown level; Haiku takes `max` without an error.

**Codex.** A Codex chat's mode picker offers Auto and Ask permissions only (`modeFits`): Ask runs its thread on the `manual` policy pair in `codexParams.ts`. It has no effort picker (`effortFits`): `turn/start`'s `effort` stays on the thread for later turns, so picking Default again could not undo it. A setting left from when the agent ran on the other engine is ignored (`engineChatMode`, `engineChatEffort`) and the picker shows the default, as `engineChatModel` does for the model; the service refuses a new one (`MODE_REFUSED`, `EFFORT_REFUSED`).

**ACP.** An ACP chat's mode picker offers Ask permissions only (`modePicker`: `AUTO_OFFERED` is false for `acp`, and `modeFits` leaves only `manual`), checked whatever the chat stored, with no "Applies from the next message" since there is nothing to change; no effort or model picker. ZumiBot has no classifier for it, so every turn runs as Ask permissions: before each prompt it puts the session in the agent's own `default` mode when the agent offers one (its mode config option, else `session/set_mode`; the Claude adapter's Manual), every call the agent asks about gets a card (`MODE_HINT` says so), and only remembered rules allow a call by themselves. Which calls ask is still the agent's own (its allow rules, or its whole config when it has no `default` mode). A session or config mode that would let the agent act without asking ends the turn instead. See [Protocol engines](protocol-engines.md).

**UI.** The open chat's picker row (`ChatView.tsx`) and the new-chat screen (`NewChatView.tsx`) show the mode and effort pickers after the model picker, all three through `ChoicePicker` (the model picker keeps its own test ids and `data-model`). On a small screen (`useNarrow`) the open chat's row keeps to one line (`.pickers.one-line`): the locked agent and folder chips move to the side panel (see [App shell UI](ui.md)), and the model, mode and effort share one chip, `RunPicker.tsx`, whose menu holds the three lists under their headings with the separate pickers' option test ids. Its label is `runSummary`: the model (an agent's default by the model's own name), the mode in a word (Ask, Plan) and the effort's level once it is not the default, such as `Opus · Plan · High`. That chip and the git chip shrink to an ellipsis, and a room's row too full for the screen scrolls sideways. The new-chat screen uses the same chip on a small screen and keeps to one line too (`.pickers.compact`): each chip gets an equal share of the row capped at its own width (`flex: 1 1 0; max-width: max-content`), so a short label stays whole and only the longest are cut to an ellipsis; the Role chip keeps its size. On an agent's start screen (its intro above, "Message <agent>…" in the box) the agent chip is its icon alone (`.icon-only`; the name stays in the DOM, hidden, and is the chip's `aria-label` and tooltip).

**Compact row on a wide window (`useFitRow.ts`, pure `state/pickerRow.ts`).** The row also goes compact when its own width cannot hold the full layout (a small window, the sidebar or side panel open), not only on a phone. `useFitRow` measures the full row's natural width in a layout effect (class `fit-measure` sets every chip to `flex: none` for the read; the menus the chips open, `.menu`, are not counted) and watches the row with a ResizeObserver; `nextCompact` switches to compact when that width is over the room and back only once the room reaches it again, so the two never flip at one width. A change in what the compact row shows (a model picked, a new branch, the cost) forgets the measured width, so the full row is tried and measured again before anything paints. Compact there means: the one `RunPicker` chip, no agent chip (the title row and the "Message <agent>…" placeholder name it), the folder as an icon (its name and path in its title; a room's too), the run and git chips shrinking first, and a row still too long scrolling sideways (`.pickers.one-line.compact`). The new-chat screen merges the run chip the same way and keeps to one line as on a phone (`.pickers.compact`), its agent and folder labels cut to fit. In every layout the context meter and cost sit at the row's right end (`.pickers-end`). A phone keeps its own layout, unmeasured. The new-chat screen keeps the picks on `NewChatDraft` and sets them on the new chat before its first message (`startChat` in `App.tsx`), so a chat can start in Plan mode. DOM hooks: `new-chat-mode`, `new-chat-effort`, `chat-mode`, `chat-effort`, `chat-mode-option` and `chat-effort-option` (+ `data-value`; the mode's default is `''`); on a small screen or a compact row `chat-run` and `new-chat-run`, with menus `chat-run-menu` and `new-chat-run-menu`. `e2e:commands` check 11 covers the start screen picks reaching the first run's argv and Auto/Medium putting the chat back.

## Allow a refused call

In Auto, the CLI's classifier may refuse a Bash command (`system`/`permission_denied` with `decision_reason_type: "classifier"`); no approval card comes, so the user can neither answer nor remember it. A blocked row can instead be allowed from the chat, and the agent then continues by itself. Design: `docs/superpowers/specs/2026-11-22-blocked-call-allow-design.md`.

**`blockedBy`.** `streamParser` turns that message into `{kind: 'denied', toolUseId, reasonType}`; `chatService` sets `blocked: true, blockedBy: 'classifier'` on the tool item only when `reasonType === 'classifier'`. Every other block (the user's Deny, an `APPROVAL_REQUIRED` result, a deny rule, a hook, the sandbox, a pause) leaves `blockedBy` unset and gets no button: an allow rule cannot beat a deny rule, and a Deny must never turn into an Allow.

**Card.** `AgentGroup` draws an inline `AllowCard` (like the question card, not a dialog) after a tool run's `ToolRun`, outside its fold, for each `Bash` tool item in the block with `blockedBy: 'classifier'`. `state/allowBlocked.ts#allowCardState(item, chat, running, latest)` gives its state. **hidden**: the row can never be allowed (agent `zumi-bot` or empty, a workflow or workflow-test chat, no string command, a turn that has not ended). **done**: `item.allowedAs` is set, one muted line with the command and `Allowed for this chat` / `Allowed for <agent>` (`allowed-as`). **running**: the chat is running, so the full card shows with its inputs and button disabled (`Wait for the reply to finish`). **pending**: allowable and in the latest turn (`inLatestTurn`: no user message after the row), full and actionable. **collapsed**: allowable but in an older turn, one line `⛔ Auto mode refused a command` with **Allow…** that expands the card in place. A chat that cannot be talked to (agent-to-agent, offline, no CLI) shows only a done card. The full card holds the command, the parts (`commandParts` in `shared/src/allowRules.ts`), each with a tick and an editable prefix (`suggestPrefix`), the rule texts and the scope (**This chat** by default, or **Always for <agent>**), and one button, **Allow and continue**. Parts starting with a `SAFE_HEADS` word start unticked; a part an existing rule already covers reads "already allowed"; a part led by a shell, interpreter or wrapper (`programError`) is unticked and disabled with its reason and no prefix to edit (the wrapped command is not suggested: how the CLI matches `timeout 30 git …` against `Bash(git …:*)` is unverified); when every part that would be ticked is already held, the card has no button and says why: when a part is one no rule can allow (`unallowableParts`: led by a shell, interpreter or wrapper, or a folder `checkFolder` refuses), it names that part with its reason (`allow-unallowable`; a program's is `PROGRAM_REASON`, without "Allow a narrower command instead", since nothing can be allowed there), since the CLI hands a command with such a part to the classifier however many other parts are held, asks the user to have the agent do it without that part, and lists the held rules as already allowed (a `python3 - <<'EOF' > /tmp/x.json` heredoc ahead of a held `workiom records update` read as if the held rule did not work); otherwise it says Claude Code still refused it although these rules are allowed. That calls `chats:allowBlocked(chatId, toolUseId, prefixes, scope)` → `{rules, text}`; the client then sends `text` through its own `sendMessage` (not the composer), so the optimistic bubble, queueing and error handling are the usual ones. The text is ``I allowed `Bash(git branch -D:*)` for this chat. Continue.`` (`for <agent>` with agent scope); in a room it starts with `@<member> `, the row's agent. The handler refuses with `NOT_ALLOWABLE` (not a classifier-blocked Bash row, Zumi Bot, a workflow chat), `CHAT_BUSY` (a turn is running), `ALREADY_ALLOWED` (the row has `allowedAs`, so two tabs or a double click add nothing twice) or `checkPrefix`'s reason. A rule is exactly `Bash(<prefix>:*)`; a prefix is 1 to 300 characters with no newline or NUL and no `*`, its first word is not a shell, interpreter or wrapper (`INTERPRETERS`: Auto drops rules for the shells, and a rule for a wrapper such as `timeout`, `nohup` or `su` would run any command; the word is compared lowercased, without path, `.exe`/`.cmd`/`.bat`/`.com` and version, and a first word that starts with a quote or contains `$` or a backtick is refused), a git prefix must name the subcommand after git's global options (`git`, `git -C /repo` or `git --work-tree=/x` alone would allow every git command, and `git -c` can run any program; `suggestPrefix` keeps every global option with its value, then the subcommand, as `git -C /repo branch -D` or `git --git-dir /x/.git push`), and it equals one of the command's parts or a word-boundary prefix of one, so a click can only grant a trimmed form of what was refused; 1 to 10 per call, all checked before any is stored. Afterwards the row is marked `allowedAs: 'chat' | 'agent'` (re-reading the items after the rule writes, and left unmarked if a turn started meanwhile) and the card turns to its done line (`allowed-as`). A fork copies the rows but not `ChatMeta.allowRules`, so `fork.ts` clears `allowedAs: 'chat'` on the copied rows (the user grants again in the fresh context); `'agent'` stays, since that rule is the agent's. A redirection alone after a keyword (`done > out`, `fi 2>&1`) is not a part.

**Folders.** The CLI checks a `cd` into a folder outside the run's working folders before any Bash rule (`Bash(cd:*)` does not help) and, in Auto, hands the whole command to the classifier, so `cd /other/repo && gh pr merge 1` was refused although `Bash(gh pr view:*)` and `Bash(gh pr merge:*)` were held, and the card, which counted `cd` as safe, showed only "still refused". A `Read(//<folder>/**)` allow rule lets that cd through (as `--add-dir` or `additionalDirectories` would, which also grant edits). So `sheetRows(command, held, chat.cwd)` makes a part `cd <path>` a **folder row** when `cdTarget` (`shared/src/allowRules.ts`) reads an absolute target (one argument, no `~`, expansion, option or partial quoting; normalised, `..` resolved) outside `chat.cwd`: no prefix to edit, ticked, "Folder <path> read its files and cd into it", held when a held folder rule's folder is it or holds it (`folderCoveredBy`), and unticked with its reason when `checkFolder` refuses it. `checkFolder(folder, command, home?)` wants an absolute, already normalised path of 2+ segments (not `/` or `/etc`), at most 300 characters, without control characters or `*?!()[]{}\` (which would widen the glob or break out of `Read(…)`), that is the `cd` target of one of the command's parts; the server also passes its `homedir()`, so the home folder and every folder above it are refused (a rule there would let the agent read `~/.ssh`). A Windows home is compared as a rule names it (`homeAsFolder`: `C:\Users\me` is `/c/Users/me`, the form Git Bash's `cd` and the CLI's rule matching use) and without case; a UNC home is not read, so nothing is refused for it. `chosenFolders` gives the ticked, unheld ones; the click sends them as `chats:allowBlocked`'s fifth argument `folders` (absent from an older page = none), counted with the prefixes (1 to 10 together), all checked before any rule is stored, and the rules are the prefixes' then the folders'. `cd <outside folder> && git …` stays asked whatever is allowed (the CLI's own check that the folder's hooks or config could run, which a Read rule, `--add-dir` and `additionalDirectories` do not pass), so when a folder row is followed by a git part (`gitAfterFolder`) the card adds a note (`allow-git-note`) to ask the agent for `git -C <folder>`.

**Storage.** This chat: `ChatMeta.allowRules`, merged in the write so a second tab's rules survive; in a room it reaches every member's runs. Always for this agent: an `approvals.json` rule `{key: JSON.stringify(['cli', rule]), toolName: 'Bash', command: null, cli: rule}` (`toolName: 'Read'` for a folder rule) through `ApprovalStore.addCli`, so renaming and deleting the agent move and drop it like any approval; the key never equals an `agentAllowKey`, so `has()` never matches a `can_use_tool` by it, and an older server loads it as an inert rule. Agent Studio's Remembered approvals lists it as `Bash: commands starting with <prefix>` or `Read: files in <folder>`, removable. Agent Studio's Remembered approvals can also add one by hand (`RememberedApprovals.tsx`, `addRuleCheck` in `state/approvals.ts`): **Bash commands starting with** or **Folder it may read and cd into**, sent as `approvals:addCli(agent, 'prefix' | 'folder', value)`, which trims the value, refuses Zumi Bot and an empty name, checks it with `prefixRuleError` or `folderRuleError(value, homedir())` (the card's checks without the refused command to match), and stores the same `cli` rule (`toolName` `Bash` or `Read`). Nothing but the user's click through those two RPCs makes a rule: no agent tool, bridge or Zumi Bot automation can.

**Applying.** `allowSettingsArgs` (`core/chat/allowRules.ts`) gives each Claude turn one more `--settings` piece `{"permissions":{"allow":[...chat rules, ...agent cli rules]}}`, merged with the others by `oneSettings`, in Auto, Ask permissions and Accept edits. **Plan** turns never get it (a plan stays read-only), nor do Compact, `/btw` side runs or the moderator. Claude Code checks deny and ask rules before allow rules, so the user's own ask/deny rules in their Claude settings (for example `Bash(git *push*--delete*)`), ZumiBot's isolation and connector deny rules and the file guard still win; a card then shows as it would have. Calls these rules let through arrive as `allowedByMode` ([Governance](governance.md)).

**Checks.** `npm run probe:allow` runs the real CLI to confirm the classifier refusal, that prefix rules let a multi-line script run (an exact whole-command rule does not match one), that `Bash(sh:*)` is ignored, and that a `Read(//<folder>/**)` rule lets a `cd` outside the cwd through (case e; e0 and e1 report that it is asked without the rule, and that `cd <folder> && git …` is asked even with it); run it after every Claude Code update ([E2E](e2e.md)). `npm run e2e:allow` covers the UI flow against a fake CLI.
