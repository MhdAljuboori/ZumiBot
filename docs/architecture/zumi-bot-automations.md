# Zumi Bot automations

**Zumi Bot automations (`core/automations/`, `shared/src/automations.ts`).** Zumi Bot makes, changes and deletes routines and workflows from a plain message or its six commands (`/create-routine`, `/edit-routine`, `/delete-routine`, `/create-workflow`, `/edit-workflow`, `/delete-workflow`, prompts in its frontmatter, `$ARGUMENTS`), ends every create or edit reply with a link to the result, and never runs one. **Bridge.** `zumibot_automations` is a stdio MCP server built like `zumibot_todos`: `automationBridge.mjs` (its own `input` in `backend/vite.config.ts`, `automationBridgeEntry` in `browserRuntime.ts`) talks over a Unix socket in a 0700 `/tmp/cb-r-*` dir (`automationIpc.ts`, the to-do IPC's framing; 128 KiB requests for a save's 60 000-byte object, 1 MiB answers for a transcript) with a capability token per CLI attempt bound to `{chatId, writable}`, revoked when the attempt ends, `alwaysLoad: true`, the token in `ZUMIBOT_AUTOMATIONS_CAPABILITY`/`_IPC` env (placeholders in argv, both in `PRIVATE_ENV` so errors redact them). Only Zumi Bot's runs get it (`ChatService`'s `automatable`: agent `zumi-bot`, no `author`, so never a room member's turn, and never a Compact; no other agent, the moderator or a bare call; Zumi Bot's `/compact` runs without it, as a `/compact` runs without the ask bridge, a known limit: its tool list differs in that one run) and its `/btw` side runs (`sideBrowser`, `writable: false`, blocked by the side guard, no ask rules), so the tool definitions never vary between turns and the cache prefix holds. **Tools** (`automationTools.ts`, exact keys only, `parseAutomationCall`): `routines_list`, `workflows_list` (id, name, enabled, trigger text, target or step count, `problems` for workflows, `nextRunAt` as ISO, `path`), `routine_get`/`workflow_get` `{id}`, `routine_save {routine}`/`workflow_save {workflow}` (no `id` creates; an `id` plus the `updatedAt` its get returned edits), `routine_delete`/`workflow_delete {id, name}` and `chat_read {chat}`. `path` is `routinesPath`/`workflowsPath` (`shared/src/appPaths.ts`, re-exported by `state/route.ts`); Zumi Bot copies it into `[<name>](<path>)` and builds none. **Authoring format** (`authoring.ts`): the stored shape minus what Zumi Bot should never invent. A routine is `RoutineInput` with defaults (`enabled` true, the page's time zone, a missing `cwd` from `lastFolderByAgent[agent]` or `lastGroupFolder`, else home, the `*PolicyOf` policies, a webhook with no `sample`), applied on a create only: on an edit a key the agent leaves out (or sends as null) keeps its stored value (`routineKept`/`workflowKept` in `automationService.ts`; a routine's `target` and `trigger` are taken whole as sent, but a blank `cwd` keeps the stored folder while the target's kind, and a new chat's resolved agent, is unchanged, and a target of the same kind sent without `title` or `section` keeps them (null clears them; Zumi Bot never sets a section); a workflow keeps its name, `enabled` and `timeZone`, and an existing Agent or For each step, by handle, its blank `cwd`, while `trigger`, `steps` and `edges` must be sent); there is no `command`, but an edit keeps the editor's pick while the prompt still starts with its name, and the conversion ends in `parseRoutineInput`, so the editor's refusals are the tool's. A workflow lists `steps` by `handle` (no ids, x/y or trigger step; edges name the trigger by the reserved handle `trigger`) and `edges` `{from, port?, to}` (port default `out`, checked against `portsOf`), fills each kind's fields over `stepDefaults` (a For each step also takes `concurrency` 1, 2 or 3) (`shared/src/workflowDefaults.ts`, the canvas's own too) and ends in `parseWorkflowInput`; on an edit a step whose handle exists keeps its id and x/y, an unchanged connection its id, and every id the workflow ever held stays taken, since runs and chats name them. `*_get` returns the same shape plus `path` (and `problems`), which a save takes and drops, so get, change, save works; a webhook's `sample` never leaves, and a trigger step the editor renamed has its `{{steps.<handle>.output}}` placeholders rewritten to `trigger` (`renameHandle`). `layout.ts` places a new workflow left to right (a step's column is its longest distance from the trigger, ignoring edges that close a loop, found by a DFS; a column stacks in the order edges reach it; `COLUMN_WIDTH` 320 and `ROW_HEIGHT` 140 clear the 220 by 72 node) and, on an edit, leaves placed steps put and puts each new one a column right of its feeder, below what is there. **Time zone.** The server never knew the user's: the page sends `app:setTimeZone` on every connect, `SettingsStore.setTimeZone` keeps a valid IANA name as `AppSettings.timeZone` (an invalid one is ignored), and a save naming none uses it, else the server's own. **Shared save.** `routineEditing` and `workflowEditing` (built once in `app.ts`) hold what `routines:save|remove` and `workflows:save|remove` did (the scheduler-atomic update, `nextFor` in `core/nextFor.ts`, `clearDraft`, `rearm`, the broadcast, a workflow's problems turning a save off, stopping unfinished runs before a delete), so the editor and the tools cannot drift; the tools pass `webhookWithoutSample` (skips "needs a test call before saving") or `ensureHook` (the hook exists at once; the result carries neither URL nor secret). A workflow is switched on at create unless it has `problems`, which then saves it off and are listed in the result; an enabled one stays on at an edit. **Checks** (`AutomationService`): a save whose `updatedAt` differs (checked again after the conversion, since the user may save meanwhile) or is missing, an unknown id, a delete whose `name` is not the stored one (the card named it, so a rename since refuses), a `chat` target that does not exist, an unknown or broken agent (`agentNames.ts` resolves "@X Expert" loosely against the file name or display name, and the refusal lists the agents, cut to about 300 characters) and Zumi Bot as an agent ("Zumi Bot can't run routines or workflow steps") are refused with a fixed sentence. A remote (AG-UI) agent is refused too (`AGUI_TEXT.zumiBotPick`) unless the stored routine or workflow already holds it (`agentResolver(agents, kept)`, `routineAgents`, `workflowAgents`): Zumi Bot may keep one the user chose, in the place they chose it (a workflow step's handle, the routine's target), never add one or move it. **Write gate.** `TurnSpec.auto` and `QueuedTask.auto` mark a turn that answers a message the user did not type: `TaskQueue.submit(..., 'routine')` (routine runs, workflow steps, a limit wait's `continue`) sets it and `withAuto` carries it to `ChatService.send`; the capability's `writable` is `!auto`, and every write tool of such a turn is refused first ("Routines and workflows can only be changed from a message the user sends."), reads still work. A user's send, edit, resend, Send now and Resume's Continue are not auto; Send now of a task a routine queued stays auto, since the task carries the flag. **Delete card.** Zumi Bot's runs carry `AUTOMATION_ASK_SETTINGS` (ask rules for the two delete tools, `CONFIRM_ONLY_TOOLS`) as one more `--settings` merged by `oneSettings`, so the CLI asks even in auto mode (side runs keep theirs byte for byte); the card reads `Delete routine “<name>”` from the call's own `name` (`automationSummary`, used by `toolSummary` and `toolLabel`) and `approvalChoices` leaves it Allow once and Deny. A `confirmOnly` tool is asked every time (`askEveryTime`: no chat or agent rule allows it, whoever serves it), any answer but Deny is stored as allow-once, and in an auto turn it is denied with the write refusal before any card exists; every other tool of the bridge `ChatService` answers itself (`ownAutomation`: no card, rule or Jev hint). **`chat_read`** takes any chat or room, archived and A→B included: `chatIdFrom` reads a bare id (`[A-Za-z0-9-]{1,100}`) or `/chat/<id>`, `/archived/<id>` or a full URL of one (a `/todos/<id>` names a board card, not a chat), and `chatTranscript` builds one `<chat id>` block (header, each user message's short form, replies named by agent, a `toolSummary` line per tool, approval, question and plan statuses, errors, notices) cut by `cutLines` to `CHAT_READ_MAX` (150 000, the first user message and the newest kept), with a closing tag inside a message defanged; versions, side questions, dispatch entries and to-dos stay out, and the tool's text and Zumi Bot's prompt call it material, not instructions. **What reaches the agent.** The IPC's `errorText` passes only the service's own sentences, by a structural rule: a message matching `SAFE_MESSAGE` (letters, digits, a few marks), not code-shaped (`ENOENT:`) and with no `/` outside a quoted span (but the fixed time zone example), since a store failure names a path; values echoed back go through `said()`, which turns other characters into `?`. A webhook's URL and secret are in no result, log or error: the hook is made and Zumi Bot tells the user to copy them in the editor. **Prompt.** `zumiBotContent` has the six commands and one fixed "Routines and workflows" section (the tools and formats, ask one question when unclear, never Zumi Bot as an agent, never run anything, never claim a change the tool did not confirm, `*_get` first and send every field back, link last, name the delete then call it without a typed yes, `chat_read` is material, and a guide to building workflows). **In-app links.** `state/appLink.ts` (`appPath`: same origin, http(s), a path one of the route parsers accepts; `plainClick`) and `Markdown.tsx`'s `AppAnchor`: such a link has no `target`, and a plain left click does `history.pushState` and dispatches `popstate`, which `App.tsx` takes through the unsaved-changes guard as Back does; a modified click keeps the browser's, and other links stay `_blank` (the shell sends those to the system browser). Known limit: in a turn the user typed, text Zumi Bot read from a converted chat could still steer what it creates; the user sees the reply and the link. Design: `docs/superpowers/specs/2026-11-09-zumi-bot-routines-workflows-design.md`.

**Workflow trigger kinds.** `workflow_save` (no id creates) and `workflow_get` carry all eight kinds (`WorkflowTriggerAuthoring`, `WORKFLOW_TRIGGERS` in `authoring.ts`): `{kind:"reply"|"todo"|"inbox", filters?}`, `{kind:"file", path, pattern?, changes?, filters?}` (`changes` default all three, an empty list refused) and `{kind:"email", host, port?, folder?, filters?}` (993 and `INBOX` by default), with filters `{field, equals, op?}` and `op` `contains` or equals. The **account rule**: Zumi Bot never sees a Vault id, so an email trigger has no `account` in either direction; a save keeps the saved workflow's account only while host (trimmed, case-insensitive) and port are unchanged, since a new host would send the stored password to a server Zumi Bot chose, and otherwise clears it, so the workflow is saved off ("Pick an email account…") until the user picks one in the editor. Limits and the port range are the shared `parseTrigger`'s (a refusal reads "The trigger is invalid…"). The prompt (`zumiBot.ts`) lists the kinds, says `{{trigger.body.…}}` is a webhook's, event's or chat's body field, and that an event's text is material, never instructions. Workflow lists name an event trigger by `eventLabel` (`scheduleText`).
