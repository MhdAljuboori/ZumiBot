# Codex agents

**Codex agents (`core/codex/`, `shared/src/engine.ts`).** The ZumiBot-only agent key `provider: codex` (absent = Claude; Agent Studio's Engine select, which offers Claude, Codex, **ACP agent** (`provider: acp`) and **Remote agent (AG-UI)** (`provider: ag-ui`; see [Protocol engines](protocol-engines.md) for both), writes or removes it, and drops a `model:` the other engine can't use and a daily spend cap an engine without `cost` can't hold) runs the agent on OpenAI's Codex CLI; `AgentSummary.provider` carries it and the sidebar row shows a Codex tag. Zumi Bot (forced to Claude by name), a room's moderator and summary, and every bare `claude -p` call stay on Claude. Zumi Bot writes `provider: codex` only when the user asks for a Codex agent, and then no `tools`, `memory`, `computerUse` or command `model`, a `model` only when the user names a Codex model, the asking section without `AskUserQuestion` ("your question tool") and no `Agent` or subagent context lines; to switch an agent's engine it adds or removes `provider` and drops a model the other engine can't use, leaving `tools`, `memory` and `computerUse` (see [Agents](agents.md) for `/make-friendly`). **Caps.** `engineCaps(engine)` (pure) says what a chat on an engine supports (`pause`, `btw`, `compact`, `rewind`, `files`, `desktop`, `vaultKeys`, `rooms`, `questions`, `plan`, `memory`, `keepWarm`, `dispatch`); Codex has all but `desktop`, `plan`, `memory` and `keepWarm`. `ChatService`, `GroupService`, the handlers (`refuseWithout`, which judges a room by the member named, else by every member, and leaves a room's side question to `SideQuestions`, which judges the member it picks), `SideQuestions`, `AgentAsks` and `groupMembers.ts` take an injectable `caps?(engine)` (default `engineCaps`) and read the nine at each gate, so a flag turned off (a later probe failed) brings back the earlier behaviour: without `rewind` a cut point reseeds, without `compact` Compact is refused with `CODEX_REFUSALS.compact` and hidden in `ContextMeter`, no auto-compact limit is sent and Agent Studio hides Compact at (`showsCompactAt`), without `btw` `btw:ask`, `btw:follow`, a side ask and a side answer are refused with `CODEX_REFUSALS.btw` and no Codex side base is kept, without `files` no change is recorded, without `questions` the question flag is not passed and a `requestUserInput` is refused at once with no card, without `pause` Pause is refused with `CODEX_REFUSALS.pause` and no pause hook rides, without `vaultKeys` a Codex run gets no vault hooks and no keys (and the Vault editor marks the agent, `vaultGrantNote`), without `rooms` a Codex agent is refused from rooms with `CODEX_REFUSALS.room` (`refuseCodexMembers` at `createGroup`, member edits, Clone room and a routine's new room; `GroupService.refuseCodex` for a member whose agent moved to Codex after it joined, its turn, Compact and side answers), and without `dispatch` the run keeps `--disable multi_agent`. The UI reads the caps too (`ChatView`, `SidePanelMenu`, `ContextMeter`, `NewChatView`, `AgentForm`, and in a room `chatCaps`, which shows a side panel row while any member has it and Pause only while every member does, `memberCaps` per member, `joinsRooms` and `memberOptions(caps)` for the member pickers, an engine-aware `hasComputerUse`, and `coldContexts`, which skips Codex members). `desktop`, `plan`, `memory` and `keepWarm` are read in `ChatService` like the rest: its desktop turn, `memory.begin` (so no memory index is repaired and no memory note read), the plan card's `setMode` back out of Plan and the contexts that arm keep warm each test the cap, so a phase that flips one changes what runs with it. Two gates still judge by engine, because they are not cap questions: `SideQuestions.warm` and `isCodexChat` in `app.ts` drop a chat on any engine but Claude, or one that *holds* another engine's session (a Codex thread), which has no Claude session to ping whatever the cap says (see [Engines](engines.md), Phase 4). A Codex single chat's composer is blocked only by a missing `codex` (`cliMissing`: `codexInfo.found === false`, an unanswered lookup counting as found), every other chat's by a missing `claude` (the Composer prop is `cliFound`), a room's included whatever its members run on, since its moderator needs `claude` (a missing `codex` then fails that member's turn with `CODEX_REFUSALS.notFound` as its error item); `App` asks `agents:codexInfo` on each connect while some agent is a Codex agent, and `NewChatView` applies the same rule to the picked agent. **Runner.** `ChatService` reaches it through the Codex adapter (`core/engines/codexEngine.ts`, see [Engines](engines.md)), which turns a turn's engine-neutral start and action into codex's own (`thread/start`, `thread/resume`, `thread/fork`; `turn/start` or `thread/compact/start`) and passes the rest of the run's Codex-only configuration — the thread, the hooks, the request tag, subagents, questions — straight through. `codexRunner.ts` spawns one `codex app-server --listen stdio://` per attempt in the chat's folder with the run's env (no shared daemon: each run gets its own capabilities and dies with its turn; `codexLocator.ts` mirrors `claudeLocator.ts`, with `ZUMIBOT_CODEX_BIN` as the override), then `--enable multi_agent` for a run with `subagents` (a main run while `dispatch` is on, never a side run or a Compact; the thread then names no `features.multi_agent` switch, as probe check 13 ran it), else `--disable multi_agent`, then `--enable default_mode_request_user_input` while `questions` is on (without it a model's question becomes a plain message and the turn sleeps for good, probe check 15; the `enable` option never names it or `multi_agent`), then the hook arguments (see Hooks). It speaks JSON-RPC lines (`codexRpc.ts`): `initialize` (the version is the `userAgent` text after the first `/`), the hooks' trusted check, then by its `CodexStart` `thread/start`, `thread/resume` or `thread/fork {threadId, lastTurnId}` (an ephemeral fork adds `ephemeral`; a resume and every fork send `excludeTurns: true`, so the answer leaves out the turns, which nothing reads, while the model still remembers them, probe check 16, and codex requires it with `ephemeral`, check 8), each with `threadParams` (`codexParams.ts`: `cwd`, the agent's `model:`, `baseInstructions`, the policy, sandbox `workspace-write` (a side run's `read-only`) with network on, `features.multi_agent: false` unless the run has subagents, the agent's Compact at as `model_auto_compact_token_limit` (only below the model's window, `codexCompactLimit`: the window the chat's `ContextUse` last saved, or while none is known, on a first turn or a reseed, only below `CODEX_COMPACT_FLOOR`, 200 000; a limit at or past the window would never fire, and codex takes one above the window silently, probe check 17, so none is sent and codex compacts by itself near its window), `model_reasoning_summary: 'auto'` (the thought rows, see [Thinking](thinking.md)), and each bridge as `mcp_servers.<name>` whose capability and socket pass by name in `env_vars`), then by its `CodexAction` `turn/start` or `thread/compact/start`. The turn ends at `turn/completed` (stdin closed, then the kill ladder); Stop sends `turn/interrupt` and starts the ladder one grace later. Codex numbers its requests from 0 in every process and a card's item id is its request id, so the runner prefixes every id of an attempt with its `requestTag` (`<tag>:<id>`) and `send` answers only ids carrying it; without it a later turn's first card was dropped as a repeat and the turn hung. The instructions are the agent file's body, then the same appended system text a Claude run gets, sent as `baseInstructions` on every start, resume and fork, because Codex ignores `developerInstructions` given on resume (probe check 2). Manual mode is `approvalPolicy: untrusted` with reviewer `user`; auto mode is `on-request` with Codex's own `auto_review` reviewer, which ZumiBot trusts as it trusts Claude's auto-mode classifier; never `never`, `danger-full-access`, a bypass flag or `--dangerously-bypass-hook-trust`. A chat's own **Ask permissions** mode runs its thread on the manual pair whatever the server's mode; a Codex chat has no Plan, Accept edits or effort ([Chat mode and effort](chat-mode-and-effort.md)). **Hooks** (`codexHooks.ts`, `codexHookTrust.ts`, probe check 11). Codex takes a `PreToolUse` hook only from the app-server's argv, `-c hooks.PreToolUse=[…]` (TOML inline from `hookConfig`: no `matcher` key for a hook on every tool, the handler's `timeout` in seconds; a `thread/start` config's hooks are ignored), and runs one only once `-c hooks.state={"<key>"={trusted_hash="sha256:…"}}` trusts it by the hash codex itself computes (an untrusted hook is skipped silently; the key is `/<session-flags>/config.toml:pre_tool_use:<group>:<handler>`, and the hash is no plain sha256 of the command). So `hookTrustFor` reads the hashes from `hooks/list` of a model-free pre-flight (`app-server --disable multi_agent` with the same `-c hooks.PreToolUse`, `initialize` then `hooks/list {cwds}`, killed at its end or after `HOOKS_TIMEOUT_MS`, 15 s), run with `hookTrustEnv`, the base env without the run's keys or capabilities, and caches the table in memory per codex binary and exact hook arguments (calls made together share one process; a failure is not kept). The run then calls `hooks/list` after `initialize` and before any `thread/*`, and goes on only if `hooksTrusted` finds every hook listed under source `sessionFlags` with its exact command, enabled and `trusted`; otherwise it drops the cached table and ends with `outcome.hooksUntrusted` before any thread, so no model ever runs with the agent's keys and no guard (a codex version other than the table's also drops it, for the next run). `ChatService` (and `sideRun.ts` for a side answer) then tries once more with the trust asked afresh (`freshHookTrust`), then once with no hooks: no keys, no pause hook, one fixed log line (`codex hooks not confirmed: running without the vault guard, the pause hook or API keys`, or `codex side hook not confirmed: …` for a side run), and, for a main run, an `unguarded` notice in the chat ahead of that reply, once a turn (`unguardedNoticeText` in `shared/src/engine.ts`, fixed text naming only what the run lost: the vault guard, the agent's API keys when it has any, and that Pause lands only when the reply ends; a room member's names the member). A side run's fallback stays log-only, since a side answer adds no chat items. The notice is drawn in the warning colour (`unguarded-notice`) and, like every notice, never reaches an agent's prompt or seed. Codex lets a call run when a hook exits 1 or times out (it fails open), so every ZumiBot hook exits only 0 or 2, with `timeoutSec` 30, far above its own work: the vault guard (`codexVaultHooks`, one hook on every tool: shell, MCP, patch, the reads `untrusted` runs without asking and the subagent tools) is `vaultGuardCommand(o, true)`, the same `grep -qF` as Claude's Bash hook passing only on grep's "no match" (`grep …; [ $? -eq 1 ] && exit 0; printf <VAULT_GUARD_TEXT> >&2; exit 2`, so a grep error blocks too); the pause hook (`codexPauseHook`, built in `app.ts` as a pair with Claude's from the same entry) is `[ -e "$ZUMIBOT_PAUSE_FILE" ] || exit 0; <node> <entry>; [ $? -eq 0 ] && exit 0; exit 2` (never `exec`, so a node that dies blocks; `runPauseHook`'s own input deadline is 10 s); a side run's `CODEX_SIDE_DENY_HOOK` is `echo 'No tools in a side answer' >&2; exit 2`. A main run (single chat, room member, routine, A→B asked run; never a Compact) carries the vault hooks while `vaultKeys` is on, then the pause hook while `pause` is on, one set trusted and checked together, so a run has both or neither. A blocked call has no item at all: its text comes only in `hook/completed {status: 'blocked'}`, so the mapper builds a `Blocked` row (`CODEX_BLOCKED_TOOL`, input `{}`, an error result holding the hook's stderr, one row for a call several hooks blocked) keyed by the `tool_use_id` inside `run.id`, the only link to the call; failed and timed-out hook runs are dropped. **Mapping.** `codexEvents.ts` (pure) turns notifications and server requests into `RunEvent`s: agent message deltas and items, `commandExecution` as `Bash`, `fileChange` as `ApplyPatch` (its completed result carries every change in `detail.codexChanges`, in memory only, each diff whole up to 1 MiB or marked `cut`), `mcpToolCall` as `mcp__<server>__<tool>` (the name the model sees, so the prompt texts need no second form), `webSearch`, `thread/tokenUsage/updated` as `context` (input plus output: cached input is inside input), a `contextCompaction` item (or the older `thread/compacted`, never both) as `compacted`, an `error` with `usageLimitExceeded` (or a snapshot's `rateLimitReachedType`) as `limited` from the last `account/rateLimits/updated`, which is also passed on as a `rateLimit` tagged `provider: 'codex'`, and `turn/completed` as an `entry` named by the turn's id (Codex's only cut point: `thread/fork` keeps whole turns), then a `result` with a cost priced from the Codex table in `shared/src/pricing.ts` (`codexCost.ts`; the main thread's and each subagent's tokens summed per model by `codexTurnCost`; an unlisted model records tokens with no cost). Each main-thread `toolUse` (a `Blocked` row included) carries a per-response `message` id, `<thread>:response-<n>`, which advances at a main-thread `agentMessage` or `reasoning` item, a new turn, or the main thread's `thread/tokenUsage/updated` once a call came since the last advance (codex sends one per model request), so the pause's safety cap counts rounds as it does on Claude. Approval requests (`item/commandExecution|fileChange|permissions/requestApproval`, and an `mcpServer/elicitation/request` that is a tool-call approval, which comes only in manual mode) become `permissionRequest`s, and an `item/tool/requestUserInput` an `AskUserQuestion` card (each question keyed by its text, with its Codex id as `codexId`; one with no options is a free-text question, and `isOther` is the card's own Other). An elicitation names its tool by the quoted name in its `message` (a running `mcpToolCall` of that server and tool, of the asking thread, gives the item only when it is the only one), else by the one running call of that server; with none or several it shows no card and is declined, since calls of one server run in parallel and a card or rule for another tool would allow a call the user never saw. An `ApplyPatch` card carries each change's `diff` (4 000 characters each, 20 000 a card, `…[cut]` and a `sha256` of the whole diff past that) and a move's `movePath`, so the user reads what will be written and where, and "Allow for this chat" keys on the content; tool rows keep paths only. `ChatService` decides on them as it does for Claude (rules, own bridges, Jev, cards); `codexAnswers.ts` turns its `control_response` into `accept`/`decline` (never `acceptForSession`: ZumiBot keeps the rules), an elicitation's `action`, a question's `{answers: {<id>: {answers: [...]}}}` (Skip sends `{answers: {}}`) or a JSON-RPC error. A request with no card (a question with no usable question, an elicitation that is no tool approval or names no sure tool, a patch with no known changes or one asking for a `grantRoot`, an unknown method) is refused at once: a decline, an empty answer, or an error. Accepting a patch's non-empty `grantRoot` would allow writes under that root for the rest of the session, which neither the card nor an `ApplyPatch` rule shows, so it is always declined. **Subagents** (probe check 13). A spawn shows only as a main-thread `subAgentActivity` item (no `spawnAgent` call item, and its message is sealed): `started` becomes an `Agent` dispatch (`toolUse` with `description` the last segment of its `agentPath`, `subagent_type: 'codex'`, plus `taskStarted` keyed by the child's thread id), so the Dispatched agents panel, the Files panel and the pause read it as they read Claude's. The child's own notices come on the same connection under its thread id: its items become `subText`/`subToolUse`/`subToolResult` under that dispatch (a child's patch through `FileTracker` labelled with the subagent, a child's blocked call a `Blocked` sub row), its token usage a `taskProgress` and part of the turn's cost (never the main thread's context or a response boundary), and `completed` or `interrupted` the `taskUpdated` (an interrupted child carries `cut`, so it ends `interrupted`, not `failed`) and the `Agent` result, whose report is the child's last message. A child's approval request is a normal card whose description says `From subagent <name>` (`subagentLabel`), answered by its id. `collabAgentToolCall`s (the model's `wait`, `sendInput`, `closeAgent`, `resumeAgent`) are `Subagents` rows. Once the main thread is known, a notice naming a thread no `started` activity announced is dropped and a request from one is declined at once with no card, fail closed (a resolved notice still passes, since request ids are the process's). `turn/interrupt` of the main turn does not stop a child: Stop ends children through the app-server's exit (the kill ladder), and the recorder ends their open entries `stopped` or `interrupted`, as codex sends nothing for a child it killed. **Sessions and rewinds.** The thread id is `ChatMeta.sessionId`, with `sessionEngine: 'codex'` beside it (per room member, `GroupInfo.sessionEngines`); a turn whose agent's engine differs from that mark drops the session and reseeds from the visible items with the `expired` notice (in a room, that member alone), so a thread id never reaches `claude --resume` (nor the other way round), and a resume that codex answers with `no rollout found` (`isMissingThread`), or a main turn's fork that it answers with any JSON-RPC error, reseeds once too (a fork never writes into its source, and the rewind point would otherwise fail the same way on every send; a side run's ephemeral fork and a compaction's keep the `no rollout found` rule). A Codex turn's `end` stamp is its turn id with `engine: 'codex'` (start points carry the engine, and `fork.ts` sets the fork's `sessionEngine` from it, or each member's `sessionEngines` in a room), so Edit, Resend, version switches and Fork from a user message run `thread/fork {lastTurnId}` at the turn before into a new thread (inclusive: codex keeps that turn, probe check 7, an interrupted one included, check 18), leaving the old thread as it was; a fork answered with the source's own id stops the run with `CODEX_REFUSALS.forkIgnored` (Claude's `FORK_IGNORED`, naming the Codex version). A Codex reply carries no `cut` stamp, since a turn's id comes only as it ends: Fork from the reply that ends its turn forks at that turn's `end` stamp (`startAfterMessage`, `memberStartsAfterMessage` per member in a room), and Fork from a reply mid-turn reseeds. `sync.mjs`'s copy chat takes `sessionEngine` from the stamp it starts at, as a fork does (`copyMeta` does it per member in `sessionEngines`). **Compact** resumes the thread and sends `thread/compact/start`, which answers at once and then runs a real turn holding a `contextCompaction` item (no `thread/compacted` comes, probe check 9); the runner holds `compacted` to that turn's end, in the order Claude reports a compaction. A Compact runs no hooks, keys or subagents. The typed note has nowhere to go, so its field is hidden (`compactNoteShown`), and the meter reads "Compacted" with no sizes, since Codex reports none. **Side questions.** A Codex agent's main run keeps a side base with `codex: {threadId, at, baseInstructions, model}` (`at` is the last completed turn, also while a turn runs), and `baseFor` builds one when none was kept (`codexSideBase` in `app.ts`, with the room briefing for a room member); a kept base of the engine the agent has left is dropped for a fresh one, and `warm` never pings a Codex agent. A side run (`sideRun.ts`) is `thread/fork {ephemeral: true, excludeTurns: true, lastTurnId}` of that turn (no rollout is written; with no completed turn, or a thread codex no longer has, a new thread seeded from the items, so `CODEX_REFUSALS.threadGone` never shows today; a point of the other engine is never forked, the run ends `missing` and the caller seeds, a belt since every caller passes a matching one) under `untrusted`, reviewer `user` and sandbox `read-only`, with `CODEX_SIDE_DENY_HOOK` (cached, fresh, then none, as a main run's hooks), which blocks every call, the reads `untrusted` runs without asking included, and it declines every request with no card (an unknown one at once), which still holds when the hook falls back. A side run gets no keys, no pause hook and no subagents. A Codex agent's own side answer asks no other agent (`NO_ASK_SIDE_NOTE` tells it so; its hook cannot single out the ask tool as Claude's lookahead matcher does), while a Codex B can still be side-asked. **Pause.** As on Claude (see [Pause and Resume](pause-resume.md)), through the pause hook above: `ZUMIBOT_PAUSE_FILE` is in a Codex main run's env (a Compact's none), `blocks()` reads Codex's hook input unchanged (a top-level `agent_id` marks a subagent's call, exactly as on Claude), and a blocked main call is a `Blocked` row carrying `PAUSE_BLOCK_TEXT`. `ChatService.canPause(chatId)` reads the chat's engines (every member of a room): Codex needs `codexPauseHook` and the `pause` cap. A pause asked while the run fell back to no hooks blocks nothing and lands when that turn ends. **Vault.** The agent's API keys go into a Codex run's env only beside its trusted vault hooks (a `hooksUntrusted` attempt ended before any thread, so no model saw them unguarded), never into the pre-flight's, a side run's or a Compact's; a key whose env name codex reads for itself (`CODEX_*`, `OPENAI_*`: `isCodexOwnEnv`, which could switch codex's own login or home) is left out of a Codex run, logged by code only, and its value is still scrubbed from the output like every key's. **Rooms.** While `rooms` is on a room takes Codex members: each member's turn runs on its own agent's engine (`GroupService` reads `engineOf` per turn and passes it in the turn's spec), with the room briefing in its `baseInstructions` after the body, the vault hooks and keys, the pause hook and subagents as in a single chat, and no ask bridge (members never get one). The moderator, the room summary and the side question's member picker stay Claude. Rewinds fork Codex members and cut Claude ones (`enginesAfter`/`withSessionEngines` in `sessionPoints.ts`), version switches and Fork carry the engines, and Clone room copies none (it copies no sessions). A room `/btw` to a Codex member forks that member's thread, and a room Compact on one runs `thread/compact/start`. **Questions.** A question card is answered on the page, in the Inbox or in an ask card as a Claude one is; in an A→B chat a Codex B's question is denied with an empty answer, since a `requestUserInput` answer has no field for the `QUESTIONS_DENIED` sentence. **Files.** `FileTracker.ownPatch` turns an `ApplyPatch` result into one `FileChange` per change (ids `<toolId>:<n>`, every disk read started before anything is awaited): an update reads the new file from disk (at its `movePath` when moved) and rebuilds the old one with `reversePatch` over `parseUnifiedDiff` (`shared/src/unifiedDiff.ts`; codex sends hunks with no headers, and a diff that does not apply exactly, such as one touching a file without a final newline, gives a null old file with `unrebuilt`); an add's diff is the whole new text and a delete's the whole old text (its new side null with the `deleted` miss, "File was deleted by this change"); a cut diff is `too-big` and a NUL `binary`. **Usage.** `codexReadingsOnly` (on both Codex run paths in `app.ts`) takes the tagged `rateLimit`s into `CodexUsage` (`codexAccount.ts`) and never hands them to the chat or to Claude's reading (`claudeUsageOf` skips them); `app:account` adds the latest as `ClaudeAccount.codex` (`withCodexUsage`), which the Usage popover shows as "Codex usage limits" (`codexRows`), while its ring keeps Claude's session. Codex sessions are not estimated in Usage. **Off for Codex** (hidden, or refused with a `CODEX_REFUSALS` sentence): computer use (Codex has no setting that forces a client approval for an MCP tool in auto mode: `approval_mode = "prompt"` goes to Codex's own auto reviewer, which approved the call itself, probe check 12, so the desktop's forced cards could not hold; the agent's run gets no desktop server, prompt or capability whatever its file says), agent memory, keep warm and the cold notice (`coldNoticeShown`; `isCodexChat` drops a keep-warm slot), and plan cards. A Codex agent gets the browser, to-do, vault and ask bridges (it can ask and be asked) and runs in routines, rooms and workflow Agent and For each steps like any agent. `agents:codexInfo` (`codexInfo.ts`) says whether `codex` is found and lists `model/list`'s visible models for Agent Studio (cached once listed). A missing CLI disables Codex in Agent Studio's Engine select (with `CODEX_REFUSALS.notFound` as the reason) and fails a send with that sentence, and a signed-out one with `signedOut`, fixed text, never CLI output. **Honest limits.** The vault guard is a speed bump, as on Claude: other spellings (`"$HOME"/…`, a `cd` first, a glob, a script) and garbled hook input pass its grep, and Codex has no deny rules for its file tools, only the hook (see [Vault](vault.md)). A run whose hooks codex never confirms goes on with no guard, no pause hook and no keys; the chat's `unguarded` notice and a server log line say so (Agent Studio's `CODEX_VAULT_NOTE` says it may happen), while a side run's says so only in the log. Whether `-c hooks.state` replaces the user's own `hooks.state` for that run is untested (the probe found no user hooks). In auto mode Codex's MCP tool calls get no client review (probe check 12). The hook pre-flight runs with `--disable multi_agent` while a run with subagents enables it (the hash follows only a hook's content, and the run's own check catches a table that does not hold). Only `collaborationwait_agent`'s and `collaborationspawn_agent`'s hook names were recorded; the pause lets `collaborationlist_agents` through by the same pattern. A child already announced in this process returns to running when reactivated, with a fresh report; child tokens reported after the main `turn/completed` would be missed. With `btw` off, a room's `btw:ask` to a Codex member fails in `prepare` with the fixed sentence, not at the RPC. In manual mode Codex's `untrusted` policy still runs commands it deems known safe (`cat`, `ls`) without asking (probe check 14 judged only writes, MCP calls and edits); the hooks see them first, but a side run whose deny hook fell back runs them and keeps no tool rows, so such a read there leaves no trace. A printed value stays in Codex's own rollout under `$CODEX_HOME/sessions`, which nothing scrubs. A side fork running while the main turn's app-server works on the same thread is unprobed, and so is `model_auto_compact_token_limit` on resume and fork (only on `thread/start`); a secret question (`isSecret`) is shown and stored as plain text; the Codex limits reading lives in memory, so after a restart the popover has none until the next Codex turn; a machine still on Phase 1 that syncs Phase 2 Codex stamps can, at worst, hand a thread id to `claude --resume`, which fails to find it and reseeds. Design: `docs/superpowers/specs/2026-11-09-codex-provider-design.md`; plans and probe results: `docs/superpowers/plans/2026-11-09-codex-provider-phase-2.md` and `docs/superpowers/plans/2026-11-10-codex-provider-phase-3.md`.

**Isolation.** Sandboxed and Container isolation (see [Governance](governance.md) 2.3, 2.4) are refused for a Codex agent: `isolation:set` refuses them, Agent Studio's Isolation section says why (`CODEX_ISOLATION_REFUSED`), and an agent saved as either that is later switched to `provider: codex` has its runs refused with that line (`CODEX_SANDBOX_REFUSED`, `CODEX_CONTAINER_REFUSED`), never run as Off. Codex's own `workspace-write` sandbox is unchanged. The test is the `isolation` engine cap, off for Codex (and for ACP and remote agents), and the sentences come from `isolationRefusal('codex', …)`, word for word as before.

## Server setup (optional)

Only for agents whose file says `provider: codex` (Agent Studio's **Engine** select). Without `codex` on the VPS nothing else changes: Agent Studio's Engine select offers Codex disabled, with "Codex CLI not found" as the reason, and a send to an agent already on Codex fails with that sentence.

1. **(you)** Install the Codex CLI as the server user (the account that ran `install.sh`), with an npm prefix of your own (`npm config set prefix ~/.npm-global`, and `~/.npm-global/bin` on the PATH in `~/.profile`, the same as for the `claude` CLI):
   ```sh
   npm i -g @openai/codex
   codex --version
   ```
   The server finds `codex` as it finds `claude`: `ZUMIBOT_CODEX_BIN` in the service environment, then the PATH, `~/.local/bin/codex`, then a login shell. Check with `bash -lc 'command -v codex'` as that user. Put `ZUMIBOT_CODEX_BIN` in a drop-in (`systemctl --user edit zumibot`, then `systemctl --user restart zumibot`; see [Install](install.md), Service environment).
2. **(you)** Sign in, as the server user. The VPS has no browser, so use the device code:
   ```sh
   codex login --device-auth   # open the printed address on any device and enter the code
   codex login status          # must say you are logged in
   ```
   The login lives in the server user's `~/.codex` (`auth.json`). ZumiBot never reads or copies it, and `npm run sync` never touches `~/.codex`, so the PC and the VPS each sign in on their own. A Codex chat continued on the other machine starts a new thread from its visible messages.
3. Routines and workflows run on the VPS only (sync switches the local copies off), so a routine, or a workflow Agent or For each step, that uses a Codex agent needs `codex` installed and signed in here. Otherwise the run fails with "Codex CLI not found. Install it and run `codex login` on this machine." or "Codex is not signed in on this machine. Run `codex login` in a terminal."
