# Agent commands

**Agent commands.** An agent can offer saved prompts as `/name`, listed in its frontmatter `commands:` (`name`, `description`, `prompt`, and an optional `todos: true`; `shared/src/commands.ts`, `$ARGUMENTS` is replaced by the text after the command). The user's send, edit and resend resolve one in the RPC handlers through `CommandResolver`; a routine run resolves its own through `forRoutine`, from the agent file as it is at run time. A routine's command comes only from its saved prompt: the `/name` must lead the prompt before the webhook `{{fields}}` are filled, so a caller's text can never become a command. The routine editor's prompt field has the same `/` menu (no `/btw`), and its pick is saved as `Routine.command` while the prompt still starts with that name; at run time a stale pick falls back to the name alone, and only a name several room members share without a pick fails the run. The composer's `/` menu (only at the start of the text; in a room it groups the members' commands) sends a `CommandPick` `{agent, name}` and the server looks the prompt up itself. The resolved command is stored on the user item as `command` (agent, name and the filled prompt, so editing the agent file never changes history), while `text` stays the short form (`/check <args>`) that the bubble shows with a chip and a "Full prompt" toggle. Only the command's own agent reads the filled prompt, through `readAs`/`withCommands`; other agents and the moderator read `text`. In a room it is routed as a user mention of the command's agent. A command whose owner is gone or broken gets no notice, the same as an @mention of such an agent. An unknown `/name` is sent as typed. A card's comment box has its own `/` list of the mentioned agents' commands, anywhere in the text (see [To-dos](todos.md), Threads and `@agent` in comments). `todos: true` makes every use of the command ask for the chat's to-do list, a routine run's included, as a leading `/todo` does (see [To-dos](todos.md)); the routine editor's `/` menu shows the same ☑ mark as the composer's; the flag is stored on the user item, and `todo` is a reserved command name. A leading `/todo` is split off before the command resolves, so `/todo /check` resolves `/check`. Prompts written by Zumi Bot are YAML block scalars, since a plain scalar breaks on `: ` or `#`. A command may name a `model` (`opus`, `sonnet` or `haiku`; `shared/src/chatModel.ts`), stored on the user item's `command`. The prompt cache belongs to one model, so in a single chat `ChatService.turnModelOf` (pure rule `turnModel`) applies it only when the turn starts a session (a new chat or a reseed), saving it as `ChatMeta.model`, which every later turn of that chat runs on (`--model`, which beats the agent file's `model:`); in a running session only a stronger command's model switches up, never down, and a switch to the agent's own model clears it. Compact, side runs (`SideBase.args.model`, and `baseFor` in `app.ts`) and forks use the chat's model so they share its cache. A single chat and the new-chat screen show a model picker (`ModelPicker.tsx` over the pure `modelPicker` in `state/commandModel.ts`): it reads `Default (<agent's model>)` (plain `Default` for one that inherits), names the model the next message runs on, and previews a typed command's model as `Sonnet · /card` through the same `turnModel` rule the server runs (so in a running session only a stronger one shows). A pick (`chats:setModel`, through `patchInPlace` so the sidebar order stays; refused in an A→B chat) saves `ChatMeta.model` with `modelByHand: true`, and `turnModel`'s `byHand` then skips every command's model; picking Default clears both, so commands apply again. A pick on the new-chat screen is `NewChatDraft.model`, set on the chat right after it is made (only when it fits the agent's engine); Fork keeps both keys. The mode and effort pickers beside it, all three drawn by `ChoicePicker.tsx`: [Chat mode and effort](chat-mode-and-effort.md). A Codex agent's picker reads `Default (<its file's model>)`, offers `agents:codexInfo`'s visible models and previews no command (Codex runs none); its pick reaches the main thread, Compact and side runs as `thread.model` (`spec.model`, then the agent file's). `modelFits` (`shared/src/chatModel.ts`) makes `setModel` refuse a model the chat's engine does not run (`MODEL_REFUSED`), and `engineChatModel` makes each run read only its own engine's model (a Claude turn only Opus/Sonnet/Haiku, a Codex turn only a Codex name picked by hand), so after an engine switch the old pick is ignored, never handed to the other CLI. Switching a running Codex thread's model (`thread/resume` with another `model`) is unprobed against real codex. The picker is hidden in rooms. Rooms ignore command models. Agent Studio's commands card has a Model select (the agent's model removes the key).

**`/run-workflow`.** A built-in command beside `/btw` and `/todo` (`shared/src/runWorkflow.ts`; `run-workflow` is reserved, so an agent's command of that name never shows in the menu, `filterCommands`). The `/` menu lists it (top level only; `runWorkflow: false` hides it, as the island and the new-chat screen do, `offersRunWorkflow`); after `/run-workflow ` the composer shows a **Workflows** list of the workflows by name (`workflowQuery`, `filterWorkflowNames`: names starting with the query, then names with a word starting with it, at most `WORKFLOW_MENU_MAX` 8; `WorkflowMenu` in `CommandMenu.tsx`), and a pick inserts `<name> ` and keeps the workflow's id (`keepWorkflowPick`: only while the text still starts with `/run-workflow <its name>`; the list stays closed while the pick holds, `workflowMenuQuery`, so Enter then sends). A send whose text starts with `/run-workflow` (a word boundary after it, as `/btw`) routes through `routeSend` to `workflows:runFromChat(chatId, text, workflowId?)` (`App.tsx#runWorkflowFromChat`, the whole text, the server cutting the command) instead of the agent: a pick's id names the workflow, else the server finds it by the longest name the text starts with, so typing it by hand works the same, and the rest is the run's input; the draft clears and a "Started <workflow>" notice with **Open run** shows. The new-chat screen and the island refuse it with a notice (`workflowRefusal`, `noRunWorkflow`), edits and resends never route it, and a routine's prompt field has no such menu. Details of the run: [Workflows](workflows.md), Triggers.
