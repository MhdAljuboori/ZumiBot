# Inbox

**Inbox (`InboxPage.tsx`, `InboxWaiting.tsx`, `InboxCard.tsx`, `InboxMessages.tsx`, `state/inbox.ts`, `useInboxHolds.ts`, `net/useInboxMessages.ts`, `net/useWorkflowApprovals.ts`, `shared/src/inbox.ts`, `core/workflows/workflowMessages.ts`).** The rail's Inbox puts everything that waits on the user, and the workflow Notify messages, in one stream with no column beside it: `/inbox`, or `/inbox/<messageId>` for a push click (`inboxFromPath`/`inboxPath`), a route-driven view like To-dos and Archived that the same ways out close. A header with the chips All · Waiting N · Messages (· N new) (All each time the page opens from closed and whenever a message is named, `filterOnOpen`; each section is hidden, not removed, under the other chip, so a card keeps its draft, a delete its Undo and the archived list its fold), then **Waiting for you**, then **Messages**. **Waiting** is built in the client and stored nowhere (`waitingEntries`): for each listed chat whose pending count (the `approvals` push) is above 0, the pending `approval` items (tool approvals, `AskUserQuestion`, `ExitPlanMode`) and pending `browser-action` handoffs among its loaded items, plus `workflows:approvals` (the waiting Approval step visits of every run, `WorkflowStore.waitingApprovals`, with the run snapshot's step; refetched on each `workflows:changed` while a run waits), plus the task board's open cards whose agent waits on an answer (`askingOf` over the board `useBoard` already holds: one `todo` entry per card, keyed `todo:<item id>`, `since` its oldest open question; see [To-dos](todos.md)); oldest first by the item's `ts`, the visit's `startedAt` or the question's `at`. `App.tsx` loads the items of each waiting chat through `loadAsked`, again when its count moves (`loadKey`, sorted ids), so only running chats are read. Only the newest page loads, and a card can sit above it (a room member waits while the others work on): while a chat's own count (`ownPending`: the server rolls an A→B chat's cards into the asker's count, so those are taken out) is above the cards its loaded items hold, older pages load one at a time through `loadOlder` (`needsOlder`) until they are found, the history starts, or `OLDER_PAGES_MAX` (10) pages were tried for that count. After a page load or a reconnect `resyncApprovals` asks the server for the counts (`chats:pending`, `ChatService.pendingCounts`: what each running chat's approvals push would carry, asked chats included), never each chat's newest page, so a card above that page still counts and the older-page loading finds it; a push that arrived after the request was sent wins for its chat, even a 0 (`mergeApprovalCounts`, since the socket carries pushes and the answer in order). An A→B card shows once, under the A→B chat (the asker's count includes it, its items do not), and a run waiting on an Agent step's card shows that card as a chat card. The rail number is that list's length (`countText`, `99+`), so the two always agree; the Agents badge, the Routines and Workflows dots and the row badges stay. `resyncApprovals` runs on the first page load as well as after a reconnect (the server pushes counts only when they change, so a fresh page showed no card), and `pendingFromItems` (what the older-page loading compares against) counts pending handoffs too. Each card is today's `ApprovalCard`, `QuestionCard`, `PlanCard` (folded, **Show full plan**) or `ApprovalBox`, a handoff's reason with I'm done and Cancel, or a to-do card's open questions (`CardQuestions` from `TodoCard.tsx`: choices, an answer box each, **Send answer**, answered through `todos:answer`; its line reads `✓ Answered · <first question> · @agent`, and its header `@agent asks about “<title>”` with **Open to-do →**, which opens the board with that card in its drawer, `/todos/<id>`), under a header (the agent's icon and `@name in <title>`, a room's member, `@B, asked by @A in <source title>` for an A→B chat, `<workflow> › <step>`; how long it has waited; **Open chat →** or **Open run →**, which leaves the Inbox as a sidebar click does). It answers through today's paths with the card's own chat id (`chats:answer`, `chats:answerQuestions`, `chats:answerPlan`, `workflows:approve`, the desktop or browser socket's `answer`); Show on desktop, Open Desktop and Open Browser open the chat and the view there (no live view in the Inbox). Pressing an answer swaps the card for an answered line at once (`useInboxHolds`, above the page so it survives a chip switch or leaving): held while the send is out, the card still mounted but hidden with what was typed in it, then 4 s from the settle (`ANSWERED_MS`); a failed send shows the same card again with the error (`inbox-error`; the Messages section's own failures are `inbox-messages-error`). A card answered anywhere else, or that stops being pending, just leaves. **Messages** (`workflow-messages.json`, `WorkflowMessages`, 0600 through `writeFileAtomic`): `{v, seenAt, messages}`, each `{id, workflowId, workflowName, runId, stepName, title, body?, at, archivedAt?, deletedAt?, updatedAt}`, its id the Notify visit's and its names as they were then; `body` keeps up to `NOTIFY_INBOX_BODY_MAX` (20 000) characters, and the Messages section renders it as Markdown (`MessageBody` in `InboxMessages.tsx`, the in-app link rule included), folded to a preview past a few lines until **Show all**. Every write prunes (`pruneMessages`): the newest 500 live ones are kept (`INBOX_KEPT`, archived included); a delete is a tombstone, its title and body dropped 60 s later (`STRIP_AFTER_MS`, past the 6 s Undo, `UNDO_MS`), kept a year (`TOMBSTONE_KEEP_MS`) so a sync never brings it back, and not counted. Newest first, each with **Open run →** (hidden once the run is pruned or the workflow deleted), **Archive** (into **Show archived (N)**, with Unarchive and Delete) and **Delete** with a 6 s **Undo** toast. RPCs: `inbox:messages` (live and archived, never tombstones, plus `seenAt`), `inbox:archive {id, on}`, `inbox:remove`, `inbox:restore` (`Too late to undo` past the window), `inbox:seen {at}` (clamped to the server's now); every change broadcasts `inbox:changed` with an empty payload, so no message text goes out in an event, and the page refetches (300 ms trailing debounce, an older answer never replaces a newer one). **Seen.** One `seenAt` on the server, shared by every device: a message is new while `at > seenAt` and it is neither archived nor deleted (`isNewMessage`), which the rail dot and "N new" read. The page sends `inbox:seen` only while its Messages section shows (not under the Waiting chip) on a visible tab, with the newest message's own `at` (the server's clock, not the tab's; the server still clamps it to its now), each value once a visit (`seenToSend`: seen broadcasts a change that refetches, so a clamped value can never loop), and keeps the `seenAt` it opened with (`heldSeenAt`) until it is left, so the new marks (`data-new`, a blue edge) do not change under the reader. A message named by the address is scrolled to and lit once, then `/inbox/<id>` becomes `/inbox` in place (`focusStep`: it waits, keeping the id, while the section is hidden or the message is not in the list yet, and the same address opened again lights it again). **Unchanged by design:** the Inbox counts as looking at no chat, so presence, read marks and every push (waiting cards, workflow approvals, Notify messages) behave as before. Design: `docs/superpowers/specs/2026-11-07-inbox-design.md`.

**Inbox messages as a trigger.** A message a Notify step files starts the workflows whose trigger is **When an Inbox message arrives** (`WorkflowMessages.add`'s `onAdded`, once per new message, never for a repeat id): its body is `{message: {id, title, body}, workflow, step, runId}` and its text the title, a blank line, the body. A workflow never starts from its own messages, and a chain of Inbox-started runs ends after `INBOX_CHAIN_MAX` (3); see [Workflows](workflows.md), Triggers.
