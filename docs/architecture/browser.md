# Browser audit tools

**Browser audit tools (`core/browser/browserShots.ts`, `shared/src/browser.ts`).** Four more `zumibot_browser` tools, for every agent, let one audit a web UI signed in through the Vault: `browser_save_screenshot {name, ref?, stamp?, fullPage?}`, `browser_computed_style {stamp, ref}`, `browser_hover {stamp, ref}` and `browser_set_viewport {width, height}`; the inline `browser_screenshot` JPEG is unchanged. **Save.** The worker hands the PNG (CSS pixels, over 5 MiB fails `image_too_large`) to the manager, which writes it through `BrowserShots` to `<data>/browser-shots/<chatId>/<name>.png` (`name` is `[a-z0-9][a-z0-9_-]{0,63}`, the same name overwrites, 200 files a chat, then `too_many_shots`) and answers `{path, name, bytes, width, height}`: the bytes never leave the manager, so no tool result, log or chat item holds image data, and the agent reads or attaches the file by its path. That answer, built by the manager itself, is the one result the vault scrub leaves alone (nothing in it comes from the page); every other result of the four, `computed_style` included, is scrubbed and cut like page text. `chats:remove` deletes the chat's folder; Fork, Clone room and `sync.mjs` never carry `browser-shots/`. **Style.** `computed_style` returns `{style, rect}` for a fixed property list; the worker cuts each value at 200 plus `SCRUB_MARGIN` characters and the server cuts it to 200 after the scrub; what the page-side read returns is never trusted: Node rebuilds the object (`cleanStyle`: only the fixed names, string values, finite numbers), since the page can replace `getComputedStyle`. **Hover.** `browser_hover` moves the pointer onto the element, so hover styles can be measured or shot. **Viewport.** `set_viewport` goes through the manager, which owns the size: the agent's size is an override held on the entry while the agent holds the lease, winning over a viewer's size and the default, dropped on release and at a relaunch; the parser refuses sizes outside 240x200..1920x1080, and layout changes, so the agent observes again. Nothing answers a page dialog by itself: a save or hover a dialog interrupts returns `dialogPending`, the agent answers it with `browser_dialog`, and that answer's result is `dialog_interrupted` (run it again) only when the save's or hover's Playwright wait ran out first; computed style and viewport never produce it. A screenshot a dialog suspended is never saved or handed back: the dialog's answer gets a fixed note to shoot again (the manager turns any PNG outside `keepShot` into that note). The browser prompt gains a short paragraph naming the tools. `e2e:vault` covers them against the fixture site's `/style` page. Design: `docs/superpowers/specs/2026-11-08-browser-audit-tools-design.md`.

**Leftover IPC and container run folders (`core/ipc/staleIpcDirs.ts`).** The browser bridge talks to the server over a socket `s` (0600) in a private `mkdtemp('/tmp/cb-b-')` folder (0700), and the desktop, to-do, process, vault, ask and automation bridges each make one the same way (`cb-d-`, `cb-t-`, `cb-p-`, `cb-v-`, `cb-a-`, `cb-r-`). A contained turn's run folder, `mkdtemp('/tmp/cb-c-')` in `ContainerRunner.open` ([Governance](governance.md) 2.4), holds the auth and network proxies' sockets `api.sock` and `net.sock`. `close()` and a turn's `dispose()` remove them, but a server that is SIGKILLed or crashes never runs either, so `startServer` first calls `sweepStaleIpcDirs`. It removes a `/tmp/cb-?-XXXXXX` folder only when the folder is this uid's and 0700, holds nothing but its kind's sockets (`IPC_DIR_NAME`: `s`, which must be 0600, since our bridges chmod only after `listen`; `RUN_DIR_NAME`: `api.sock` and `net.sock`, or `api.sock` alone for a server killed between the two listens, never chmodded), each a socket of this uid, and a connection to each is refused (`ECONNREFUSED`: nothing listens) twice, 200 ms apart, all checks again the second time (a server between `bind` and `listen` refuses too, for the microseconds Node takes to do both in one call). A socket that answers belongs to another live server on the machine (the user's own, another test run) and is never touched; nor is one that times out or reports a full backlog (`EAGAIN`, a stopped server), an empty folder (a server between `mkdtemp` and `listen`), or a run folder holding anything else (it is mounted read-write into the container, so an agent may have written there). It unlinks `s` and then `rmdir`s, so anything that appeared meanwhile keeps the folder; it never throws and prints one stdout line with the count. `staleIpcDirs.test.ts` covers each check with real sockets in a temp root (dead ones left by a SIGKILLed child, a stopped one with a full backlog, one that answers on the second probe, run folders with one live and one dead socket in either order) and fails if a new `mkdtemp('/tmp/cb-?-')` in `src` matches neither name or `ContainerRunner.open` listens on other socket names than `RUN_SOCKETS`; `e2e:browser` and `e2e:btw` check it against a really killed server ([E2E](e2e.md)).

## Server setup (optional managed agent browser)

After installing, run these **as the non-root server user** (the account that ran `install.sh`), with the same data directory as the systemd user service. No website credentials or app password/2FA are involved in these checks.

```sh
~/zumibot/bin/zumibot-server browser-install
~/zumibot/bin/zumibot-server browser-check
```

`browser-install` explicitly invokes the shipped Playwright Core 1.64.1 CLI to download its pinned Chromium into `~/.local/share/zumibot/browser-runtime/` (or the launcher's `ZUMIBOT_DATA_DIR`). Budget hundreds of megabytes of download and at least 1 GB of free disk for installation/extraction, plus growing profiles/site caches. It uses no sudo, installs no OS packages, and never starts the app server. Ordinary install, update and startup never download a browser. A missing browser leaves text chats usable.

OS libraries and sandbox support are the operator's prerequisite. Inspect the pinned dependency list without installing it:

```sh
node ~/zumibot/app/node_modules/playwright-core/cli.js install-deps --dry-run chromium
```

Review the command and have the operator install appropriate packages for the VPS OS, then rerun `browser-check`. Run under the service account with Chromium sandbox support (working user namespaces or a correctly configured sandbox helper); keep sandboxing enabled. Check failures never trigger automatic downloads or dependency installation. The check uses a temporary synthetic profile and validates assets, executable, sandboxed launch/observation and owned-process cleanup without opening app auth or real agent profiles.

To use an already installed supported Chrome/Chromium instead, set `ZUMIBOT_BROWSER_EXECUTABLE_PATH=/absolute/path/to/chromium` in the service environment (a drop-in: `systemctl --user edit zumibot`, then `systemctl --user restart zumibot`) and in the environment used for `browser-check`. A missing explicit override does not fall back. Otherwise the pinned managed binary is preferred, followed by known system locations. Linux x64/arm64 is the supported managed process lifecycle.

Profiles live under `<dataDir>/browsers/<opaqueProfileId>/`; sign into websites through the in-app viewer on the VPS. Local and VPS browser sign-ins remain separate. Exclude both `browsers/` and `browser-runtime/` from transfers and whole-data backups: never copy live profile SQLite files or ownership records. The repository sync script enforces this for pull and backups; its push names only chats/settings/attachments. A deliberate offline profile backup requires a clean server stop and separate handling.

Defaults are two browser slots, four tabs each, two-minute idle shutdown/ownership inactivity, ten-minute unattended handoffs, 30-second commands, two-minute queue waits and at most 10 viewed frames/sec at 1280×800. Two explicit viewers can fill both slots; closing a viewer stops streaming. Idle shutdown retains cookies/site storage but loses tabs and unsaved forms. Website RAM usage varies; monitor the actual process tree rather than assuming a fixed memory cost. All resource variables and bounds are listed in [README: Agent browsers](../../README.md#agent-browsers).
