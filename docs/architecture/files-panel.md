# Files panel and Restore

**Files panel.** **Open Files** in the side panel (a full-screen sheet on a phone) lists what the chat's agents changed with `Edit` or `Write` (a Codex agent with `ApplyPatch`, see [Codex agents](codex.md); an ACP agent with an `AcpEdit` whose `diff` content carries the whole old and new text or a hunk of it, `FileTracker.ownAcp`, see [Protocol engines](protocol-engines.md)), their subagents included, and what the user attached. Per file it shows a Diff (default), the whole Old or New file, a step picker, Copy, Download, Show in chat, and the Quote / Explain menu over a selected line range (`path:2-3`, then a fenced block). `streamParser` keeps the CLI's `tool_use_result` as `detail` on a tool result, and a subagent's `Edit`/`Write` calls and results as `subToolUse`/`subToolResult` (its text and other tools are still dropped). `FileTracker` (`core/files/fileChanges.ts`) turns them into a `FileChange` on the tool item (`changes`): an own `Edit` takes `originalFile` and the CLI's replacement, a subagent `Write` its `content`. A copy it cannot make exactly is null with a `why`, and the panel says so, never guesses. The one disk read: right after a subagent's `Edit` or a Codex `ApplyPatch` update (or a Codex add whose diff was cut) succeeds, the server reads that path, resolved against the chat's cwd (one regular file, at most 1 MiB, no NUL), because the stream carries no new contents for it. The old file is rebuilt from that exactly or not at all. An ACP edit's file is read too: a diff that is the whole file keeps its own texts (its last newline put back when the agent cut it), and a hunk of a longer file (claude-agent-acp) takes the disk as the after copy and rebuilds the before as a subagent's `Edit` does, exactly or not at all. Whole copies go to `SnapshotStore` (`core/files/snapshotStore.ts`, `<data>/file-snapshots/<chatId>/<sha256>`, same text stored once) and never into the chat JSON or the items feed. Fork copies the copies its items use, and deleting the chat removes the folder. `chatFiles.ts` in `shared` builds the list (one entry per path, newest change first; memory and plan files and agent memory left out, under `CLAUDE_CONFIG_DIR` when set); the `files:list` RPC serves it, and `GET /api/files/<chatId>/<id>` (`http/files.ts`, behind the gate, `text/plain` with `nosniff`, `?download=<name>` for a download) serves a copy. The pure logic (views, steps, overall diff, line numbers, Quote text) is `frontend/src/state/filesPanel.ts`; rows are drawn in syntax colours (see [Syntax colours](worktrees.md#syntax-colours)); `useChatFiles.ts` refetches the list on item pushes. **Restore.** Under a changed file's path, **Restore to before this change** (one step picked) or **Restore to before all changes** (All picked) puts the file on disk back, after a confirm (`files:restore {chatId, path, fromId, toId}`, `core/files/restoreFile.ts`). The plan is the shared pure `restorePlan` (`shared/src/fileRestore.ts`): the first step's kept before copy against the last step's kept after copy; a step whose before is a create sends the file to the Trash (`trashPath`), and a Codex delete (after `deleted`) needs the file still absent. The server takes the path and both copies only from the chat's own stored changes (`listChatFiles`), refuses while the chat runs, and writes only when the file on disk hashes to the after copy's id exactly (a content check, so an edit made since, by hand or by another chat, is never lost), through `writeFileAtomic` (mode kept, a symlink followed). Refusals are fixed sentences (`RESTORE_REFUSALS`), the panel greys the button out by the same rule with the reason as a tooltip (`restoreButton`), and a failure logs its code only. Nothing is added to the chat and the agent is not told: its next Edit of that file finds it changed and reads it again. Known limits: a Codex move restores the old text at the moved path, and the check and the write are not one atomic step. Design: `docs/superpowers/specs/2026-11-02-files-panel-design.md`.
