# Updates and showcase

**Self-update (`core/update/`, `shared/src/update.ts`).** A ZumiBot installed with `install.sh` finds new versions on the public showcase site, shows them, and installs one when the user clicks. No laptop, SSH or deploy script is involved: `npm run deploy` is gone. The repository `MhdAljuboori/ZumiBot` and its releases are public, but a server never reads GitHub and holds no token: the site's build re-publishes the latest release as static files (a manifest and the tarball), and the server reads those. The desktop app's Local mode updates the same way (see Local mode below): its server downloads the same signed package and the shell restarts it on the new build. The Electron shell itself (window, tray, island) is not updated in place: it loads its UI from the server, so a server update updates that, and the shell changes with a new desktop install. The `claude` CLI has its own updater.

Parts, one doc: the release flow and `CHANGELOG.md` (what a release is made of), where the server reads releases, the server's check and install, rollback, the UI, and the public showcase site (`zumi-bot-site/`) that reads the same releases.

## Release flow

1. `npm run bump:patch` (or `:minor`, `:major`, or `npm run bump:set -- X.Y.Z`). `deploy/bump.mjs` runs `npm version` in every workspace, refreshes the lockfile (`bump:lock`) and adds an empty `## v<version> — <date>` section at the top of `CHANGELOG.md`. Only a level or a plain `X.Y.Z` is accepted. It runs npm through `npm_execpath` with this node, since Windows has only an `npm.cmd` that cannot be spawned without a shell; when it changes the lockfile on a machine with a newer npm than the repo uses, keep only the workspace version lines (a newer npm rewrites unrelated `dev` flags). Every workspace shares one version, the site's too.
2. Write the notes under that heading.
3. Commit and push.
4. Tag and push the tag: `git tag v<version> && git push origin v<version>`.
5. `.github/workflows/release.yml` runs on the `v*` tag, in three jobs. Its default permissions are none. `build` stops if the tag and the backend's version differ (every workspace shares it), runs `npm run typecheck` and `npm run build:server`, packs with `deploy/package.sh release`, takes the notes with `node deploy/changelog.mjs notes <version> release/NOTES.md` (a tag with no notes fails the job before anything is published, and there is no `--generate-notes`), and uploads the tarball, `SHA256SUMS` and the notes as the run's artifact. It holds only a read-only token (`contents: read`, checkout with `persist-credentials: false`) and is the only job that runs npm. `image` downloads the artifact, builds the Docker image from the tarball's `app/` for amd64 and arm64 and pushes it by digest with no tag, using the `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` secrets (see [Install](install.md), The release artifacts); a release without them fails there, before anything is published. `publish` runs no npm code and installs nothing: it checks the tag out again (for `deploy/docker-bundle.mjs`, `deploy/release-sign.mjs` and the shared modules they read), downloads the artifact with `actions/download-artifact` (pinned by commit), packs the Docker bundle with the image's digest in its compose file, signs the tarball and the bundle (see Release signing) with the `RELEASE_SIGNING_KEY` secret, and only then tags the pushed digest `<version>` and `latest`, so a tag never names an image no signed bundle points at. It creates the release with `zumibot-server.tar.gz`, `zumibot-server.tar.gz.sig`, `zumibot-docker.tar.gz`, `zumibot-docker.tar.gz.sig` and `SHA256SUMS` (`contents: write`). A missing signing secret, or one that is not the pair of the pinned public key, fails the job before anything is tagged or published. A manual workflow, `docker-image-check.yml`, proves the image and the bundle build and start without releasing anything; run it before the first tag after a change to the Dockerfile, the compose file, `docker/` or a workflow.
6. If the `VERCEL_DEPLOY_HOOK` secret is set, a last step posts to it (the secret is in that step's env only), so the showcase site rebuilds: the page shows the new version and the site re-publishes its files, which is what servers update from. Unset, the step is skipped and servers keep seeing the previous release. The push in step 3 also triggers a site build, which runs before the release exists and so republishes the previous one; the hook's later build supersedes it.

The version the server reports is the backend's `package.json` version, baked into `server.mjs` at build (`__SERVER_VERSION__`, `backend/vite.config.ts`).

**The version restart.** The first release is `v0.1.0`: every workspace restarts at 0.1.0 (`bump:set -- 0.1.0`), which is also what the updater compares from then on. The reset breaks no stored data. A server still on 10.x does not see 0.1.0 as newer, so the first move onto it is by hand (`install.sh --version v0.1.0`). The desktop `.deb` also goes from 10.x to 0.1.0, which `dpkg` reads as a downgrade, so it is installed once with `sudo apt install --allow-downgrades ./ZumiBot_0.1.0_amd64.deb` (or removed and installed again).

### Release signing

Every release is signed with the publisher's ed25519 key, so the showcase site, its DNS or Vercel can serve files but cannot change what a server runs.

- **Signed text** (`releaseSignedText` in `shared/src/update.ts`): `zumibot-server\n<version>\n<sha256>\n`, the bare version and the tarball's SHA-256 in lowercase hex. The signature is base64 of the 64 raw bytes, in `zumibot-server.tar.gz.sig` and in the manifest's `signature`.
- **The Docker bundle** has its own label (`dockerBundleSignedText`): `zumibot-docker\n<version>\n<sha256>\n`, with the bundle's SHA-256, in `zumibot-docker.tar.gz.sig`. Different labels, so a server tarball's signature can never pass for a bundle or the reverse. The bundle's compose file names the image by digest, so its signature covers that digest, and the Docker installer (which checks it) installs only what the publisher signed. The manifest carries no bundle signature: only `docker/install.sh` reads it.
- **Public key** (`RELEASE_PUBLIC_KEY` in `shared/src/update.ts`, and the same string in `deploy/install.sh`): the raw 32 bytes in base64. A test checks the two agree.
- **Private key**: GitHub secret `RELEASE_SIGNING_KEY`, a PKCS8 PEM. Made once with `node zumi-bot-server/deploy/release-key.mjs <path>`, which writes the PEM with mode 0600 (it refuses an existing file and any path inside the repository) and prints only the public key. The publisher keeps the PEM outside the repo (`~/.config/zumibot-release-key/`, folder 0700); it is never printed or logged.
- **Signing**: `deploy/release-sign.mjs <version> <release-dir>` reads the key from the env (never argv), checks both the tarball and the bundle against `SHA256SUMS` before signing either, refuses a key whose public half is not `RELEASE_PUBLIC_KEY`, and writes a `.sig` next to each.
- **Rotating the key**: make a new pair, pin the new public key in both places, ship a release signed with the old key that carries the new key, then change the secret. A server only trusts the key it was built with, so a lost private key means installing a new release by hand (`install.sh --tarball`).

### CHANGELOG.md rules

- The reader is public: the notes also show on the showcase site. Say what ZumiBot does and what changed for a user. No internal paths, hostnames, secrets, ticket numbers or deploy detail.
- One section per release, headed exactly `## v<version> — <date>`, newest first. The heading's version must end at a space or the line end, so `0.1` never matches `v0.1.0`.
- A section ends at the next line that starts with `## `. Notes must not contain a `##` heading of their own; use `###` or lists.
- An empty section counts as missing and fails the release job. `bump.mjs` leaves the new section empty on purpose, so a forgotten one stops the tag.
- `deploy/changelog.mjs` holds the two functions (`changelogSection`, `addSection`), tested in `shared/tests/changelog.test.ts`.

## Where the server reads releases

The release job still makes a GitHub release. The showcase site's build (see Showcase site) re-publishes the latest one as static files, so a server never reads GitHub and needs no credentials. The contract, fixed (`ReleaseManifest` in `shared/src/update.ts`):

`GET <site>/releases/latest.json` answers 200 with `{ "version", "publishedAt", "notes", "tarball", "sha256", "signature" }`: the bare version (`0.1.2`), an ISO time, the release notes as Markdown, the tarball's path on the same site (`/releases/0.1.2/zumibot-server.tar.gz`), its SHA-256 as 64 lowercase hex characters, and the publisher's signature (see Release signing). `parseManifest` lets `signature` be absent (the updater then refuses the release with its own message) but refuses one that is not 64 bytes of base64. A 404 means nothing is published yet: not an error, `latest` stays empty.

The site is `UPDATE_SITE` (`https://zumibot.run`). The server uses `devEnv('ZUMIBOT_UPDATE_URL') ?? UPDATE_SITE`, so a test can point it at a fake site, and `devEnv('ZUMIBOT_TEST_RELEASE_KEY')` (a raw ed25519 public key in base64) so that site's releases can be signed by a key of the test's own; both hooks are ignored under `NODE_ENV=production`. `releaseSite.ts` does the two requests (`User-Agent: ZumiBot`, no credentials of any kind). `parseManifest` (shared) checks the shape and the hash; `parseVersion` still decides whether the version is one we offer.

**The old domain.** The site moved from `zumibot.mhdaljuboori.me` to `zumibot.run`. A server or `install.sh` copy from a release before the move still asks the old domain, and `releaseSite.ts` follows a redirect only on the site's own origin, so a redirect to `zumibot.run` would read as a failed check (`redirect`) and strand it. Keep `zumibot.mhdaljuboori.me` on the Vercel project as a second domain that serves the site, not one that redirects, until every server has updated past the move; each picks up the new `UPDATE_SITE` with that update.

**The apex domain serves.** For the same reason, `zumibot.run` itself (the bare domain in `UPDATE_SITE` and `install.sh`) must serve the Production deployment, never redirect: a redirect to `www.zumibot.run` is another origin, so every server's check fails with `redirect`. On the Vercel project, `zumibot.run` is connected to Production and `www.zumibot.run` redirects to it (308), never the other way round. Vercel suggests the www-first setup when a domain is added, so check this after any change to the project's domains.

The tarball's full URL must have the site's own origin (`tarballUrl`), checked when the manifest is read, so a manifest can never send a server to another host. An `http:` site is accepted for the tests' loopback server, and any other scheme is refused. Redirects are followed by hand (`redirect: 'manual'`, at most 3) and only on the site's own origin; any other is "The update site redirected to another site". Bodies are capped: the manifest at `MAX_MANIFEST_BYTES` (1 MiB), the tarball at `MAX_DOWNLOAD_BYTES` (200 MiB), checked against `Content-Length` first and then while streaming; an overflow deletes the partial file and says "The update site sent more than an update can be". All error text is fixed (`SiteError`): "Could not reach the update site", "The update site answered <status>", "The site sent a release it cannot use", "The update site pointed to a download on another site", and the two above.

An earlier version kept a sealed GitHub token in `<data>/update-token.json`. Nothing reads it now, and `start()` deletes a leftover one.

## Availability

`detectAvailability` (`updateService.ts`) decides per install, and `UpdateStatus.availability` says why when it is not `ok`:

| Value | When | What the user sees |
|---|---|---|
| `local` | Local mode with no `ZUMIBOT_LOCAL_UPDATES` (a development run of the desktop app, which always serves its fresh build) | "Updates are off in a development run of the desktop app" |
| `container` | `/.dockerenv` exists or `ZUMIBOT_CONTAINER` is set | "run the Docker installer again" |
| `notInstaller` | no `ZUMIBOT_INSTALL_DIR`, or no `<dir>/bin/zumibot-update` there | "Updates need the installer install" |
| `ok` | the installer's user unit, which sets `ZUMIBOT_INSTALL_DIR=<dir>`; or Local mode in a packaged desktop app, whose shell sets `ZUMIBOT_LOCAL_UPDATES` (`LOCAL_UPDATES_ENV`) to an absolute folder | check, install; roll back on an installer install only |

Only `ok` checks, installs or rolls back; the other three never reach the site. The toast shows only for `ok`. `UpdateStatus.local` says the server runs in Local mode, which changes what the UI suggests when an update is slow. `ZUMIBOT_LOCAL_UPDATES` means nothing outside Local mode.

## Checking

`UpdateService.start()` (called from `app.ts` after the control socket is up; `stop()` runs in the unwind) settles what the last run left (see Boot settle), deletes `<dir>/updates/` and a leftover `update-token.json`, then checks 10 seconds after boot and every hour (`UPDATE_CHECK_MS`). Nobody has to press Check to hear of a release: `update:status`, which every tab calls when it connects and again whenever it comes back into view (`visibilitychange` in `useUpdate.ts`, which covers the desktop window coming out of the tray), answers through `seen()`, and when the last answer is older than `UPDATE_STALE_MS` (15 minutes) that starts a check in the background; its result reaches every tab as `update:changed`, so the toast appears by itself. Before the first check has run, the boot timer is on its way and `seen()` leaves it alone. **Check for updates** in About calls `update:check` and checks at once. Checks that overlap share one request. A check does nothing unless availability is `ok`, and a failed one sets `error` (fixed text, never the response) and `checkedAt` anyway.

One request: `GET <site>/releases/latest.json` (see Where the server reads releases; 30 s timeout). A 404 is no release yet: `latest` is empty and `error` stays null. The manifest's version minus a leading `v` is the version; `parseVersion` accepts only plain `x.y.z`, and `isNewer` compares numbers, so a pre-release, `latest` or an equal or older version is "not newer" and gives no toast (`latest` is then empty and `error` says "The latest release has no usable version"). A manifest the site sent in the wrong shape gives "The site sent a release it cannot use". A release whose signature is missing or does not verify for its version and `sha256` is never offered: `latest` stays empty and `error` is "The release is not signed by the ZumiBot publisher". The release notes are the manifest's `notes`. A failed check keeps the release seen before.

`UpdateStatus` goes to every tab as the event `update:changed` (and `update:status` reads it). The RPC set: `update:status`, `update:check`, `update:install` and `update:rollBack` (both `{force: boolean}`, checked in `forceOf`). There is no call that takes a credential.

## Installing

`update:install` (`UpdateService.install`), in order:

1. Refuse unless availability is `ok` ("This install cannot update itself"), no install runs (`ALREADY_UPDATING`, which the UI matches on), and the latest release is newer.
2. **Busy.** `busy()` is running replies, `chatService.runningCount() + side.runningCount()` (the same count the control socket gives; background processes do not count). With replies running and no `force`, the call returns `{busy: n}` and nothing starts; the UI asks "Update anyway?" and calls again with `force: true`. The count is read again after the download, since replies may have started meanwhile.
3. Check the signature again (`signature.ts#verifyReleaseSignature`, against `RELEASE_PUBLIC_KEY`): an unsigned or badly signed release stops here with "The release is not signed by the ZumiBot publisher", before any byte is downloaded. Then download the tarball from the manifest's URL (same origin as the site) into `<dir>/updates/v<version>/` (`releaseSite.ts#downloadFile`: a temp file renamed into place, so a partial file is never the tarball; 10 minute limit).
4. Compare the tarball's SHA-256 with the manifest's `sha256`, which the signature covers. A mismatch stops the update ("The download did not match its checksum"), and nothing else has happened yet.
5. Extract only `zumibot-server/install.sh` from the tarball: the release's own installer, which unpacks everything else itself and so always matches the build.
6. Write `pending {from, to, at}` to `update.json`.
7. Start the installer in its own transient unit so the restart of this service cannot take it along: `systemd-run --user --collect --unit=zumibot-updater-<stamp> --setenv=ZUMIBOT_DATA_DIR=<data> -p StandardOutput=truncate:<data>/update-log.txt -p StandardError=inherit sh <updates>/…/install.sh --dir <dir> --tarball <file> --snapshot-data [--force]`. The unit does not inherit the server's environment, so only the data dir (a path) is passed. Stderr inherits stdout's file: a second `append:` would have its own offset and overwrite the output. The log is truncated each run.
8. `install.sh --snapshot-data` checks again that no reply runs (unless `--force`), stages the new app, copies the data to `<dir>/data.prev` (see [Install](install.md), Updating), swaps `app` for `app.prev`, and restarts the service. This process ends with the restart.

**While it runs.** `installing` is true and `begin()` has broadcast it. The server asks `systemctl --user is-active zumibot-updater-<stamp>` every 5 seconds. A unit that still runs is never given up on (a big data copy is only slow). A unit that has ended while this process is still here means the updater failed before the restart: the result is `failed` with the last 20 lines of `update-log.txt`, `pending` and the download are removed, and the install may be tried again. A probe that gets no answer (no `systemctl`, no user bus, a timeout) is "unknown", never "ended"; after 24 unanswered probes in a row the wait stops with the error "Could not tell whether the updater is running". `pending` and the download stay then, so the next boot settles it, and the user can try again meanwhile.

**Failures before the unit started** (download, checksum, unpack, a busy server after the download, `systemd-run` itself) throw a fixed message, remove the download and any `pending`, and leave `installing` off. A disk that would not take the download says so. Any other error shows "The update failed", never its own text.

### Local mode (the desktop app)

In a packaged desktop app the shell starts its server with `ZUMIBOT_LOCAL_UPDATES=<userData>/server-updates` (a development run passes nothing, so it always runs the fresh `backend/dist`). There, `update:install` (`installLocal`) skips systemd and the installer script:

1. The same refusals, busy rule, signature check, download (`<builds>/downloads/v<version>/`) and checksum as above. The update log is emptied first.
2. Unpack the whole tarball into `<builds>/v<version>.staging/`, and refuse a package whose `zumibot-server/VERSION` is not the release's version or that has no `app/server.mjs` ("The update package is incomplete").
3. Look at the busy count again, then rename the staging folder to `<builds>/v<version>/` and drop the downloads.
4. Write `pending`, then `<builds>/current.json` (`{"version"}`, last: until it names the build, the shell keeps starting the one it has).
5. Ask for a restart, 300 ms later so the `update:install` answer reaches the tab first: `cli.ts` stops the server as a signal would and exits with `LOCAL_RESTART_EXIT` (75), the watchdog included. `installing` stays set until then, so every tab shows the updating overlay.

The shell (`zumi-bot-desktop/src/main/serverPick.ts`, used by `launchLocal` in `index.ts`) decides at every launch which build to start: the one `current.json` names, when it is a plain x.y.z newer than the app's own version (`app.getVersion()`) and its `server.mjs` exists, else the bundled `resources/server`. So a newer desktop install wins over an older download, and an equal one runs what it shipped with. It then prunes every other `v<x.y.z>` folder (and `current.json` when the bundled build runs); the server's `start()` removes a killed install's `downloads/` and `*.staging` folders. On exit code 75 the shell forgets the old server and starts again on the same fixed port, so the window keeps its origin and its overlay reloads once the new version answers. If the downloaded build does not start (`startLocalServer` rejects: an exit before `LISTENING`, or the 15 s timeout), the shell deletes it and `current.json`, appends why to `<data>/update-log.txt`, and starts the bundled build; that server's boot settle reads the pending update as failed, with that text as the log tail, and the overlay clears with "Update to X failed". If the bundled build fails too, the shell shows its error page, as before.

There is no data snapshot and no Roll back in Local mode (`canRollBack` needs an install dir). A build that starts but misbehaves stays until a newer release or a newer desktop install replaces it.

### Boot settle

`settle()` runs at every start and writes `lastResult` (`updated`, `failed` or `rolledBack`, with `from`, `to`, `at`):

- A `pending` whose `to` equals the running version: `updated`. A `pending` whose `to` does not: `failed`, with the log tail (the updater died, or the restart came back on the old build).
- `<data>/update-rolled-back` (written by `zumibot-rollback` as `{"from","to"}`): `rolledBack`, the file's mtime is `at`, and the file is removed. It wins over the first rule.
- `update.json` is read back as untyped JSON: a part of the wrong shape is dropped.

## Rolling back

`update:rollBack` runs `<dir>/bin/zumibot-rollback` in the same kind of transient unit. It needs `canRollBack` (availability `ok`, both `<dir>/app.prev` and `<dir>/data.prev`, and the last result is `updated`: after a failed update that never swapped, an old pair belongs to an earlier update and is not offered; the server refuses it too), and it follows the busy rule: `{busy: n}` without `force`, then a confirm. The UI always confirms first ("Go back to v<from>? Chats and settings changed since <date> are set aside (kept in a .failed folder on the server)."), and asks again when replies run. A roll back that fails to start or whose unit dies is stored as `failed` with `to` the older version, so the UI reads from > to as "Roll back to vX failed". It puts the previous app and the data from the snapshot back, keeps what the failed update left as `app.failed` and `<data>.failed`, and restarts; the boot settle then reports `rolledBack`. The script's own steps, and the commands it prints if a move fails, are in [Install](install.md), Rolling back. A rollback that fails to start clears `installing` and shows its error. After a rollback `data.prev` is gone, so Roll back is offered once. Without `--snapshot-data` there is no `data.prev` and no rollback: old code alone could read data the new code changed.

## UI

Settings › About and the app-level pieces share one store, `frontend/src/useUpdate.ts` (rules in `state/update.ts`), over `api.update`:

- **Toast** (`UpdateToast.tsx`): "ZumiBot v<version> is available", with Update, What's new (opens About) and a dismiss. The dismissed version is kept in `localStorage` (`zumibot.update.dismissed`), so a newer release shows it again. No toast when availability is not `ok`, nothing is newer, an install runs, or that version was dismissed. An error from Update is its own line in the toast, and shows even with no version to offer (after Local mode's restart the new server has not checked yet, but why the update failed shows at once); dismiss closes that line first.
- **About** (`Settings.tsx`): version, one status line, Check for updates, Install update (when newer), Latest, Last checked, the error, the release notes (Markdown), and the last result with its log tail, plus Roll back when `canRollBack` and the last result is `updated`. Below them, always: the License row (`LICENSE_NAME`) and a Sponsor ZumiBot button that opens `SPONSOR_URL` (both in `shared/src/sponsor.ts`; the site's /sponsor page) in a new tab, which the desktop shell hands to the default browser. When availability is not `ok`, only the reason shows. Before the first check has answered (`checkedAt` is null) the status line says "Not checked yet" instead of "Up to date". Check for updates is off while a check or an install runs (`canCheck` in `state/update.ts`). A check does nothing, and never reaches the site, unless availability is `ok`.
- **Updating overlay** (`UpdatingOverlay.tsx`): covers the app while an install runs and makes the rest of the page inert. After 90 seconds it offers Reload and says what to do if it does not come back (`slowHint`): run `~/zumibot/bin/zumibot-rollback` on the server, or in Local mode quit the app and open it again. A second tab sees `installing` from the broadcast and waits too. While it runs the store also polls `update:status` every 2 seconds, since the socket drops across the restart. When the status says another version, the page reloads (`runOutcome`); when an install ends at the same version (a failed download or run, busy after the download, a failed rollback) the overlay goes and the reason shows in the toast and About.
- **Reload notice** (`UpdateToast.tsx`): when no run is active and the server's version differs from the build this tab loaded, the toast says "ZumiBot was updated. Reload to use v<current>." with a Reload button. It never reloads by itself.
- **Confirm** (`UpdateHost.tsx`): "N replies are running. Updating stops them. Update anyway?".

## Known limits

- If the server does not come back after an update, run `~/zumibot/bin/zumibot-rollback` on the server (the overlay says so after 90 seconds). In Local mode, quit and reopen the app: a build that does not start is set aside for the bundled one.
- Local mode has no Roll back and no data snapshot, and it never updates the Electron shell itself: a change to the shell (main process, preload, its own pages) reaches a user only through a new desktop install. A new server meets an older shell there, as it does when a desktop app connects to an updated VPS.
- Roll back is offered only right after an in-app update succeeded. A failed rollback is not retried from the app: rerun `~/zumibot/bin/zumibot-rollback` over SSH (it prints the steps left).
- A server only sees a release once the site has re-published it. An expired Vercel `GITHUB_TOKEN` fails the site build, and Vercel keeps the previous deploy (servers then keep seeing the old release). The Vercel setting "Include source files outside of the Root Directory" must stay on, since the site's build steps up to the repo root.
- A tab that cleared its overlay after "Could not tell whether the updater is running" does not reload by itself if the update succeeds later. Reload by hand.
- That failure message shows in About, and in the toast only while the toast for that version is not dismissed.
- The checksum comes from the manifest, but the publisher's signature covers it and the version, so whoever can publish the site can withhold or delay a release (or serve an older signed one, which `isNewer` never offers), not forge one. The signing key is the trust root; see Release signing.
- A data snapshot is a copy of a running data folder; a file that changes under `tar` fails the update (nothing was swapped), and it is tried again.
- Running replies are stopped by an update with `force`; background processes are not counted, and the restart stops them.

## Files

Data dir (see [Data folder](data.md)): `update.json` (`pending` and `lastResult`), `update-log.txt` (the last run's output) and, only between a rollback and the next start, `update-rolled-back`. Install dir `<dir>` (`~/zumibot`): `updates/v<version>/` (the download, removed on failure and at every boot), `app.prev`, `data.prev` (with `.zumibot-from`), and after a rollback `app.failed`; `<data>.failed` sits beside the data folder. Local mode, in the desktop app's userData: `server-updates/` with `current.json`, the running downloaded build `v<version>/zumibot-server/`, and while an install runs `downloads/` and `v<version>.staging/`.

## Security notes

- No token or credential exists on the server: the site is public, and no request carries an `Authorization` header. Site errors are mapped to fixed text (`SiteError`), so nothing from the request or response is shown.
- Downloads come only from the site's own origin: `tarballUrl` refuses a manifest whose tarball points anywhere else, and a redirect off the origin is refused too. A body past its cap is cut off.
- Nothing is downloaded, unpacked or run without the publisher's signature over the version and hash.
- The tarball is hashed before anything is extracted, only `install.sh` is extracted by the server, and the installer unpacks the rest. The updater unit gets one environment variable, the data dir.
- Local mode runs only a build that passed the same signature and checksum checks and names its own version; the shell starts a downloaded build only from its own userData folder and only when `current.json` names a complete, newer one.
- Every update is a click. Checking is automatic; nothing installs on its own.

## Showcase site (`zumi-bot-site/`)

A static Vite and React page for `https://zumibot.run`: what ZumiBot is, the latest version with its release notes, its desktop installers, and how to install the server. It is public and read-only. Everything it offers is served from the site itself: it never links to a file or release in the repo or anything that needs the token. The one GitHub link is the repo's home page, in the header nav and the footer. It also hosts the update channel (below): those files are public but unlisted. The domain of the live install is `zumibot-server.mhdaljuboori.me`.

**Build-time fetch.** `npm run build -w @zumibot/site` runs `prebuild` first: `scripts/fetchRelease.mjs` calls the releases API (`src/latestRelease.ts`) with `GITHUB_TOKEN` and writes `src/release.json` (git-ignored). `releaseInfo.ts` keeps only the version, the date and the notes, and nothing else of the release (no assets, no URLs) reaches the page.

**Update channel.** The same script downloads the release's `zumibot-server.tar.gz`, `SHA256SUMS` and `zumibot-server.tar.gz.sig` through the API (`downloadAsset`: only `api.github.com/repos/…` URLs get the token; fetch drops it on the redirect to the CDN), checks the hash (`sumOf`), and writes `public/releases/` (git-ignored), which Vite copies into the deploy:
- `latest.json`: the manifest above (`manifestFor` in `src/publishRelease.ts`, which refuses a version that is not a plain x.y.z, since it names a folder);
- `<x.y.z>/zumibot-server.tar.gz`, `SHA256SUMS` and `zumibot-server.tar.gz.sig`: what the manifest points at, and what `install.sh` downloads;
- `latest/zumibot-server.tar.gz`, `latest/SHA256SUMS`, `latest/zumibot-server.tar.gz.sig` and `latest/install.sh` (taken out of the package): stable names for a first install by URL.
- `<x.y.z>/zumibot-docker.tar.gz` and `zumibot-docker.tar.gz.sig`: the Docker bundle that `docker/install.sh` downloads (hash checked against `SHA256SUMS`, which lists it; a signature that is not 64 bytes of base64 fails the build).
- `latest/docker/install.sh` (taken out of the bundle): the Docker installer's URL, `https://zumibot.run/releases/latest/docker/install.sh`. The bundle is optional like the desktop installers: a release from before it existed is published without it, with a warning, and the installer then says that release has no Docker bundle.

The signature is carried into `latest.json` (`manifestFor`, `signatureOf` in `src/publishRelease.ts`), not checked: the site holds no key that matters. A `.sig` that is not 64 bytes of base64 fails the build; a release with none (older than signing) is still published with a warning, and every server refuses it.

Only the latest release is published. The files are built in `public/releases.next/` and swapped in at the end. `vercel.json` gives `latest.json` and `latest/*` `Cache-Control: public, max-age=0, must-revalidate`, since their content changes under the same name; versioned paths keep the default.

**Desktop installers.** On a `v*` tag, `electron-build.yml` builds the installers (see [Electron cloud build](../ELECTRON_CLOUD_BUILD.md)) and its `publish` job attaches them to the release `release.yml` created (it waits up to 20 minutes for that release to exist and never makes one), then uploads `SHA256SUMS-desktop` last and posts the deploy hook again. It runs when a platform fails too (`!cancelled()`), so the builds that worked still ship. The prebuild then downloads `SHA256SUMS-desktop`, and for each installer it lists (`installersIn` in `src/downloads.ts`, which takes only names matching electron-builder's `artifactName` patterns, so a name can never become a path outside the folder) downloads it, checks its hash (streamed: they are large) and writes it to `<x.y.z>/` beside the server package, with no `latest/` copy. `release.json` gets `downloads: [{ file, size }]`; nothing else about the assets reaches the page. Installers never hold back the update channel: no `SHA256SUMS-desktop` yet (the first rebuild, from `release.yml`, runs before they are attached) publishes the release without them, and a listed file the release lacks is skipped with a warning. A hash mismatch fails the build. They are unsigned and not ed25519-signed: the hash check guards the copy, not the publisher. Each is around 100 to 150 MB, so every deploy carries several hundred MB and each download counts against the Vercel plan's bandwidth.

With no `GITHUB_TOKEN` the script writes `null`, publishes nothing and exits 0, so a local build works. With a token, a failure (a non-200 other than 404, the network, bad JSON, a missing asset, a checksum mismatch) exits non-zero, so Vercel keeps the previous good deploy; 404 means no release yet and gives `null`. The token is never printed and never in the bundle or the published files.

**Vercel.** Root Directory `zumi-bot-site` (so its `vercel.json` applies; its commands step up to the repo root for the workspace install and build). Environment variable `GITHUB_TOKEN`, the fine-grained token above. Node 22.x (`engines.node`: the prebuild script runs `.ts` through Node's type stripping, which needs 22.6+). A deploy hook URL goes in the repository secret `VERCEL_DEPLOY_HOOK` so each release rebuilds the page. The headers in `vercel.json` set a strict CSP (`default-src 'none'`, no connections).

**Keeping deploys few.** Every deploy carries the whole release, installers included, and Vercel stores each one. Two parts keep that small:
- *Skipped builds.* `vercel.json`'s `ignoreCommand` runs `scripts/shouldBuild.mjs` (exit 1 builds, 0 skips). It builds when a file the site is made from changed since the last deploy (`SITE_INPUTS` in `src/buildCheck.ts`: this folder, `frontend/src/botShapes.ts`, the root `package.json` and lock file; shared is left out because the site imports only types from it, so a new value import from outside the folder must be added there). With no file changed, a preview is skipped and production compares the latest GitHub release with the one the live site holds: the prebuild publishes `releases/fingerprint.txt`, a SHA-256 of the version and each asset's name and API URL (which holds its id), so a deploy hook for a new release or for installers just attached still builds. Anything unknown builds: no previous SHA, one outside Vercel's shallow clone, no `GITHUB_TOKEN`, a failed request. The log line `shouldBuild: building (…)` or `skipped (…)` says why.
- *Pruned deploys.* `.github/workflows/prune-site-deployments.yml` runs `scripts/pruneDeployments.mjs`, which keeps the deploy `zumibot.run` serves (asked of Vercel by host, since the project's production target is the newest production build, even one still building) and the newest ready production deploy before it (the rollback target), and deletes every other one older than production (previews, errored, canceled), plus errored and canceled ones of any age (a build the ignoreCommand skipped shows as canceled). Newer ready deploys and in-flight ones are left for the next run; the live deploy is found from the domain's alias record (`/v4/aliases/<host>`), with a lookup by host as the fallback; an unknown production deploy deletes nothing (`src/pruneDeployments.ts`). It runs hourly (Vercel does not report this project's deploys to GitHub, so there is no `deployment_status` event to start it) and by hand with an optional dry run. The same job prunes the docs project (`docs.zumibot.run`): each project is a matrix entry with its ID and live domain (`LIVE_HOST`). It needs the repository secret `VERCEL_TOKEN`, a Vercel token for the team; the project and team IDs are in the workflow. Vercel keeps a deleted deploy restorable for 30 days.

**The page.** One scroll through thirteen scenes (hero, chat, Agent Studio, group room, control, automation, computer use, work board, voice and island, everywhere, latest release, download, on a server), with two unnumbered bands: one between the hero and the chat scene (`scenes/BuiltOn.tsx`, "Built on Claude Code": agents keep the tools, skills, MCP servers, plugins and hooks of the user's Claude Code, and ZumiBot adds rooms, agent asks, the shared board and one place to manage them; the docs' What is ZumiBot page says the same under "What ZumiBot adds"), and one after the server scene (`scenes/SponsorBand.tsx`, `#sponsor`: the ask, with a big plain button to /sponsor, so the two download buttons stay the prominent ones). Neither band has a `data-scene`, so the cast keeps following the scene before it. The first eleven are each a drawn app window in HTML and CSS, not a screenshot; the last two hold real controls. The windows use the app's own palette (`styles.css` copies the default Blue theme of `frontend/src/styles/tokens.css`) and its own icon set: `Bot.tsx` imports `frontend/src/botShapes.ts`, so the Zumi Z logo and the agent shapes always match the app (a site test checks the demo cast only uses shapes and colors the app offers). The demo cast, its agents and folders are made up (`showcase.ts`); never put a real chat, agent or path in a scene. A scene's animation runs only while it is on screen (`useScenes.ts` adds `.in`), the header's cast follows the scene in the middle of the screen, and reduced motion shows every scene in its finished state. The theme button overrides the system theme for the visit only. The display face (Bricolage Grotesque) is bundled from `@fontsource-variable/bricolage-grotesque`, not linked from Google Fonts, since the CSP allows fonts from the site only. React `style` props are fine under `style-src 'self'` (they go through the CSSOM); a `style` attribute in `index.html` is not.

**Download and server scenes.** The hero's Download button jumps to the download scene, which features the visitor's own system (`useVisitor.ts`: `detectVisitor` from the user agent, then Chromium's `getHighEntropyValues` for the CPU, so an Intel Mac gets the Intel build; elsewhere a Mac gets Apple silicon) as one card with the app's icon, one prominent button and that system's other build as a link (Intel, AppImage), and lists the other systems below, one group each, with their first-open notes (`firstOpen`: the builds are unsigned, and the Linux packages need a command). The macOS builds carry a Preview tag (`isPreview`) until they have had real use. They are ad-hoc signed, not notarized, so their first-open note is the `xattr -cr` line (the v0.1.3 DMGs had no signature at all and were not offered; the site only offers the latest release's installers). The header and footer are one pair for every page (`Chrome.tsx`; links in `siteLinks.ts`, whose `linkFor` sends the section anchors through `/` from any page but the home one). The header nav links to the user docs at `https://docs.zumibot.run`, and the footer links to the docs, the sponsor page and `mailto:contact@zumibot.run`. Three icon buttons end the header, styled the same (`.icon-btn`) so they show at every width, phones included: a pink heart to /sponsor (outlined pink on that page, `aria-current`), the theme button, and the GitHub repo's home page (`GitHubMark` in `Glyph.tsx`, labelled for screen readers); the footer has no GitHub link, by choice (`DOCS_URL`, `GITHUB_URL`, `CONTACT_EMAIL`, `SPONSOR_PATH`; GitHub and the contact address are the same two as the docs site's header icons). A labelled "Sponsor" pill was tried and dropped: with the cast label it needs ~1180px, more than the 1136px the wrap leaves. To keep the header on one line, the cast label hides at 1199px and below, and the cast itself between 901px and 1020px, just above where the nav hides (900px); on a phone the header's gaps shrink so the brand and the three buttons fit at 320px. A phone, a Chromebook or an unknown system gets no featured card, and a phone is pointed at the server scene. The featured card is a different element from the list, not a bigger button beside smaller ones: the preferred choice stands out by style, as Apple's button guidance asks. The server scene builds install.md's Phase 3 commands (`serverInstall.ts`: download, read, run with `--origin`, proxy, `/setup` and the journal line, `zumibot-update`) from an address the reader types (`originFrom` refuses what `install.sh` refuses, and an invalid one keeps the example), with a Copy button per step that selects the commands instead when the browser refuses the clipboard. Change those commands with install.md and `install.sh`. With no release, both scenes say so; with a release and no installers yet, the download scene points at the server one.

**Sponsor page.** `/sponsor` is a second Vite entry: `sponsor.html` (its own title, description, canonical URL and link preview tags, on the same `og-image.png`) loads `sponsorMain.tsx`, which renders `SponsorPage.tsx` between the shared header and footer; `vite.config.ts` lists both pages and `vercel.json`'s `cleanUrls` serves `sponsor.html` at `/sponsor` (and redirects the `.html` form there). The one way to give for now is USDT on TRON (TRC20) to the owner's Binance deposit address (`sponsor.ts`: coin, network, address and the address's QR code as one SVG path, the one Binance shows). `tests/sponsor.test.ts` checks the address's base58check checksum and that the QR path encodes exactly that address (it rebuilds the code with `qrcode`, a site dev dependency, at every level and mask), so changing one without the other fails. The code is drawn black on white in both themes with a 4-module quiet zone, since a dark or inverted code fails some scanners. The card has a Copy button (`CopyButton.tsx`, shared with the server scene) and a warning that another coin or network is lost for good. The page says a sponsorship is a gift that buys no license, support or feature, which keeps it clear of the license's no-selling clause. Everything that links here: the site's header, footer and last band, the docs header (a heart icon) and FAQ, the README, `.github/FUNDING.yml` (GitHub's Sponsor button), the root `package.json` `funding`, the app's Settings › About and the desktop tray. To add a way to give (GitHub Sponsors, another coin), add it to `sponsor.ts` and the page; every other link points at the page, not at a wallet.

**Icons.** `public/` holds `favicon.png` (64, the app's own), `favicon.ico` (16, 32 and 48 PNG frames, for crawlers and bookmarks that only ask for that path) and `apple-touch-icon.png` (180, a full square with no rounded corners, since iOS rounds it itself and would turn clear corners black). `npm run icons` (`design/zumibot-icon/make-icons.mjs`) renders all three from `zumi-z.svg` with the app's icons; never edit them by hand.

**Link preview.** `index.html` carries Open Graph and `twitter:` tags, so a zumibot.run link pasted in Slack, X, iMessage or LinkedIn unfurls with a picture: crawlers read the served HTML only, never the page's script. `og:image` must be an absolute URL (`https://zumibot.run/og-image.png`), and `og:description` repeats the page's `description` (a site test checks both, and the image's 1200x630 size; `sponsor.html` has its own tags, checked in `sponsor.test.ts`). `public/og-image.png` is drawn by `npm run og-image` (`design/zumibot-og/make-og.mjs`, which also draws the docs site's card, `zumi-bot-docs/public/og-image.png`, with its own name and host): the Z on its tile between the demo cast's six shapes, the name and the slogan ("Your agents. Your workspace. Your rules."), in the dark palette. It renders in headless Chrome through `playwright-core`, since it has text; the layout is centred so a square crop still shows the Z and the name. Re-run it when the Z, the cast, the palette or the slogan changes; never edit the PNG by hand. Slack caches an unfurl per URL for a while, so a changed card shows only on links it has not seen lately.
