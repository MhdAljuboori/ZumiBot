# Servers, plugins, skills and hooks

**Servers, plugins, skills and hooks (`core/extensions/`, `shared/src/extensions.ts`).** **Settings › Claude Code** (`ExtensionsSettings.tsx`, `/settings/claude-code`, after Vault; pure rules in `state/extensions.ts`, `extensionsPage.ts`, `extensionForms.ts`) shows what Claude Code loads from a folder (home by default, a Change… picker) in four tabs and edits the user's own Claude Code config; Agent Studio's **What this agent loads** card (`AgentLoadout.tsx`, `AgentOwnExtensions.tsx`, `state/agentLoadout.ts`) shows the same for one agent, with switches. A catalog connector's row (`connector` not null) shows "Set on the Connectors page" and a link to **Settings › Connectors** instead of a switch, so the two pages never disagree (see [Connectors](connectors.md)); it keeps its `serversOff` switch only while the agent's `serversOff` still lists that name (an old off entry still wins, and can be cleared there). The Servers tab has a note and an **Open Connectors** link for the same reason; it still reads and edits servers as before, and its `oauth` refusal stays. The palette lists the section by its keywords (mcp, plugins, skills, hooks). Beside the folder picker a sentence says that looking at a folder starts its MCP servers and runs its hooks, as a chat there would (a probe is a real `claude` start there, no confirm). **What loads** is asked of the CLI: every row comes from its answers, and the user's files are read only to place an edit on a row the CLI listed (a hook's position, its file's stamp and its timeout; a skill's folder; which folder's `.mcp.json` holds a project server), never to add a row: `probe.ts` starts `claude -p --input-format stream-json … --permission-prompt-tool stdio [--agent <name>] --no-session-persistence` in the folder, sends the control requests `initialize`, `mcp_status` (asked again every 500 ms until no server is `pending`, at most 15 s), `get_skills_dialog` and `get_hooks_listing`, sends no user message (no model call, no quota) and ends the process group. The whole probe has a 30 s deadline; a section still missing then carries a fixed sentence and the others still show. A Codex agent's probe is `codex app-server` (`mcpServerStatus/list`, `skills/list`, hooks) and its card is view only, like Zumi Bot's; its fixed sentences name Codex (`codexMissing`, `codexTimeout`, `codexUnsupported`). An ACP agent gets no probe: ZumiBot does not read its own configuration and gives its runs none of these parts, so every section of its card shows `EXT_TEXT.acpUnsupported` and no ZumiBot rows (its runs have no bridges or hooks). The requests are no documented API, so `sanitize.ts` (`toLoadout`) reads each answer defensively and builds every row from an allow-list; an MCP server's raw `config` (env, headers, expanded args) is never passed on, logged or cached. The one thing derived from a server's URL is `LoadoutServer.connector`, the catalog id of a claude.ai connector (or null), set from the URL and then the name by `connectorOf` in `shared/src/connectors.ts`; the URL itself is dropped as before. `ExtensionsService` runs at most two probes server-wide (the rest queue in order), lets a caller (a refresh too) join the probe already running for its key, and caches only the sanitized `Loadout` (100 entries) under folder, agent and a hash of the agent file's text, so a Save never gets an older answer; every write, Vault change and agents-folder change calls `forget()`, whose generation counter keeps a probe that began before it out of the cache. The `/` menu's commands-only probe (`probeClaudeCommands`, `probeCodexCommands`) and its own cache of rows share the same two slots, abort and `forget()` (see [Agent commands](agent-commands.md), Engine commands); unlike the loadout probe it runs with hooks off, no MCP servers and no agent keys, since nobody opened a card for it. `stop()`, in app.ts's shutdown beside the runs, aborts every probe and CLI write in flight and waits for the write queues, refusing later calls with `ESHUTDOWN`; an edit's restore of the old server runs without the abort, so a stop between `mcp remove` and `mcp add` never loses the server, and a CLI run ends after its kill grace even while a grandchild that left its group holds its stdout. ZumiBot's own rows (the `zumibot_*` bridges, the pause hook, the vault guard, the desktop ask rule) come from the facts the runner uses (`zumiBotAdds`) and have no switch; a folder with no agent (the Settings page) gets none, since it is no run. **The Hooks list is the CLI's** (Ruling 24): a user, project or local row of `get_hooks_listing` takes its place, its file's stamp and its timeout (the listing has none) from the settings-file row with the same source, event, matcher and command (each file row once), which makes it editable; a row no file row matches (the repo root's `settings.local.json`, which the CLI also loads for a subfolder) stays read-only, and a file row the CLI did not list (its whole file rejected, such as one holding a `PreToolUse` hook timed 0, or one that does not parse, which the hooks section still names) is not shown. A project server only a parent folder's `.mcp.json` holds (the CLI walks up) is read-only and says "From <folder>'s .mcp.json"; an own server the CLI lists unscoped (its `--mcp-config` replaces a configured server of the same name) is relabelled `agent`, and says "Same name as a server this agent already loads" when the user's or the folder's config has that name. Every error that leaves is an `EXT_TEXT` sentence or a bare error code (`pageError`), never CLI output, a path or a value. **Agent file keys.** `serversOff` (server names exactly as the CLI lists them, such as `claude.ai Google Drive` or `plugin:x:y`), `skillsOff` and `plugins` (id to boolean) are ZumiBot-only; `mcpServers` (a bare name, or `{name: {command|url, args, env, headers, type}}`) and `hooks` (settings.json format) are the CLI's own subagent keys, which the CLI ignores when it runs an agent with `--agent` (checked by the probe's `--model-check`) and ZumiBot now applies to the agent's own runs. `AgentFields.mcpServers` and `hooks` carry an `editable` flag: a shape the parser does not understand (the map form of `mcpServers`, always, even with valid definitions; a list item whose definition has keys outside the CLI's six; a `type: prompt` hook; an extra key; a hook `timeout` that is not a number above 0, Ruling 23) stays in the file and is applied by no run (`serversEditable`/`hooksEditable` false; the card says it is kept and not applied), and `serializeAgent` never rewrites or deletes it on a caller's value (the file's own flag guards it, only an explicit null removes it); a Save that changed another field keeps its value and comments but may re-indent it. Zumi Bot never adds, changes or removes any of the five (its prompt says so in "Editing an agent" and in `/make-friendly`). **What a run gets.** `buildAgentRunConfig` (`agentRunConfig.ts`, pure; `agentRunConfig` in `app.ts` supplies the Vault's grants, or `locked` when its status is `keyMissing` or `keyMismatch`) returns `{disallowedTools, extraArgs, env, dropped}`: one `--settings` holding only `deniedMcpServers` (`{serverName}` per off server, the CLI's own name, then, for its `connectorsOff` option, the catalog connectors the agent has not switched on in **Settings › Connectors**: a `{serverUrl}` per catalog pattern and a `{serverName}` per known claude.ai name, with the `--disallowedTools mcp__<prefix>` belt deduped with the agent's own; `serversOff: false` leaves them out too, so the probe still lists a switched-off connector; Zumi Bot's runs deny every catalog connector; see [Connectors](connectors.md)), `enabledPlugins`, `skillOverrides` (each exactly `"off"`) and `hooks` (nothing else from the agent file is copied, so no agent can set `disableAllHooks` or permissions; as a belt for Ruling 23 every hook timed 0 or below is left out, since claude 2.1.322 silently drops a run's whole merged `--settings`, guards included, for one such `PreToolUse` hook and drops another event's alone), one `--mcp-config` of the agent's own servers, and as a belt `--disallowedTools mcp__<name>` (`toolPrefix`: every character outside `[A-Za-z0-9_-]` becomes `_`, no collapsing, as the real CLI does) for each off server in case a CLI stops honouring `deniedMcpServers`; a `serversOff` name reserved for ZumiBot's bridges is ignored, since those are always on. `ChatService.agentTurn` puts these right after `spec.extraArgs`, before ZumiBot's bridges, and `buildArgs` merges every `--settings` into the run's one; they are read per attempt, so a Save applies from the next run, and are in the side base too (`baseFor` builds them for a fresh one), so a main run, room member, routine, A→B run, Compact, `/btw` side run and keep-warm ping see the same tools, skills and plugins and the cache prefix holds. Codex agents, Zumi Bot and bare `claude -p` calls (moderator, room summary, workflow LLM and Condition) get none. Duplicate server names resolve first (one winner per name, the last definition at the first one's place), and a name whose `toolPrefix` starts `mcp__zumibot_` is reserved (`isReservedServerName`, the one rule the RPCs, the forms and the run share) and dropped from the run. An env or header value may hold `${vault:<ENV_NAME>}`, the env name of an API key granted to the agent: it is rewritten to `${ZUMIBOT_MCP_VAULT_<n>}` (n from 0 by first appearance) and the value goes only in the run's env, which the CLI expands when it starts the server, so no argv, file, log or page holds it (the values join the run's scrub map). A reference with no granted key, or a Vault that cannot be opened, leaves out that one server in every run alike (`dropped`, logged by server name and reason; the card gives a fixed sentence; the agent file is never changed). A side base kept from the last main run keeps its own parts and `SideBase.env`/`ownParts`, but `refreshSideBase` rebuilds just those when an env value is no longer in the agent's current grants, so a side question or keep-warm ping never starts a server with a value the agent lost. The probe for an agent applies the same config with `serversOff: false, skillsOff: false` (a server or skill it turned off still shows and can be switched back on) but keeps `enabledPlugins` (an off plugin's rows are gone; its plugin row comes from `claude plugin list --json`, overlaid with the agent file's `plugins`), and gets the agent's own servers' Vault values and its granted API keys (as a main run's env holds them; a folder's probe gets none) in its env, so its own servers, and a global one whose config names a key, show the status a run would see. The card warns that a change to the off lists, plugins or own servers (they change the tool list; own hooks do not) makes the next message re-read the whole context once, and an open own-server or own-hook sub-form counts in the editor's unsaved-changes guard (Save puts its draft into the file). **Writes** change the user's real Claude Code config. User and local MCP servers go through the CLI (`claude mcp add-json`, `claude mcp remove`; an edit is a remove then an add, and a failed add puts the old definition back; `~/.claude.json` is only read, since the CLI rewrites it all the time), plugins through `claude plugin enable|disable`; project servers (`<folder>/.mcp.json`), hooks and the skill switch are atomic edits (`settingsFile.ts`: `JSON.stringify(obj, null, 2) + '\n'`, key order and file mode kept, a missing file created holding only the edited key, a file that does not parse refused and left byte for byte). Project-scope writes (`.mcp.json`, `<folder>/.claude/settings*.json`, `<folder>/.claude/skills`) refuse (`notEditable`) a target that is a link, a dangling one too, or whose folder resolves outside the chosen folder (Ruling 25, `assertProjectPath`: a cloned repo cannot point a save at `~/.claude.json`), and the page shows those rows read-only (`EXT_TEXT.linkedFile`); user files keep following links (dotfile setups). The user's `settings.json`, skills and `.claude.json` are found by `CLAUDE_CONFIG_DIR` of the env every CLI run gets, not this process's, and local scope reads "This project, only for you" (the key is the repo root). A save that went stale or lost its server offers Reload, which reopens the form fresh; a form's heading takes focus when it opens and its opener gets it back when it closes. A skill is a `SKILL.md` folder under `~/.claude/skills` or `<folder>/.claude/skills` (`skillFiles.ts`: only a direct child of its root; a create never overwrites a name; a delete moves the folder to the Trash); off writes `skillOverrides.<name> = "off"` in the user's settings.json and on deletes the key. One in-process queue per file orders writes, and each write carries the stamp of what the page read (the SHA-256 of the file's text, or `absent`; for a user or local server the hash of that server's own stored definition, not of `~/.claude.json`; a plugin or skill switch carries none), a mismatch failing with `EXT_TEXT.stale`. Local servers live under `projects[<key>]` of `~/.claude.json`, and the CLI keys a folder by the real path of the nearest ancestor holding a `.git` entry, else the folder's own real path (`localProjectKey`, checked against the real CLI by the probe), so the service reads them under that key. Global servers' env and header values never reach the page (`serverView` blanks them and lists their names, and a null value in a save keeps the stored one); an agent's own servers show theirs, since they live in the agent file. A `.mcp.json` entry the page does not read whole (`oauth`, `headersHelper`) is refused for an edit, never rewritten. A name being written must pass `isServerName` (never `__proto__`, `constructor` or `prototype`) and not be reserved, an env or header name must be non-empty with no `=`, line break or NUL and at most 200 characters, as the form checks, and only a skill named by the skill RPCs' pattern shows as editable; one already stored can still be viewed, removed or renamed away from. The RPCs are `extensions:loadout|server|saveServer|removeServer|setPlugin|skill|saveSkill|removeSkill|setSkill|saveHook|removeHook` (every folder an existing absolute directory, names, scopes and stamps checked by the handler) and `extensions:changed` (no payload; open pages refetch). **Sync** carries agent files and `~/.claude/skills`, so the agent keys and user skills follow; `~/.claude/settings.json`, `~/.claude.json` and plugins do not (sync only reports that settings.json differs), and the page says changes there apply to this machine only. **Honest limits:** `claude mcp add-json` takes a server's env and header values in argv (the CLI has no stdin form), so a process list shows them for the moment the command runs, and the log holds only the subcommand and exit code; an agent's own hooks have exactly the power of global hooks (a `PreToolUse` hook that prints an allow decision, or a `PermissionRequest` hook, can approve a call before ZumiBot's card, though the side guard's block still wins in a side run, which the model probe checks); the project-path check and the write are two steps; a read-only (0444) settings file is replaced by the atomic rename; a plain value typed into an own server is stored as plain text in the agent file, and its plain env or header value is in the run's `--mcp-config` argv, so the process list, while the run lives (Ruling 26; only a Vault reference keeps it out of both); the desktop shell's save-before-close counts only the agent file, not an open own sub-form's draft (the in-app guard asks about both).
