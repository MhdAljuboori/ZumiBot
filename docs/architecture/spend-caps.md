# Spend caps

**Spend caps (`core/caps/`, `shared/src/spendCaps.ts`).** Three optional caps in USD at API list prices (`parseSpendCap`: above 0, at most `SPEND_CAP_MAX` 10 000, cents): `Workflow.spendCap` and `Routine.spendCap` (per run; the workflow trigger inspector's and the routine PolicyCard's **Spend cap per run**, `SpendCapInput.tsx`) and an agent's `dailySpendCap:` frontmatter key (Agent Studio's **Daily spend cap**; the day is `AppSettings.timeZone`'s, else the server's, `dayOf`). **Measuring.** `streamParser` prices every `assistant` line with a message id and usage, the agent's and a subagent's (`spend` events, `usageTokens` plus `priceMessage`; `codexEvents` prices each `thread/tokenUsage/updated` `last`, main and child, with `priceCodex`); ChatService keeps the highest price per message id per attempt (the CLI repeats a message's usage on each content block line) and hands only the growth to `SpendCaps.liveSpend` with the attempt's key (`<chatId>:<n>`, never `newId`, so item ids stay) and the user message the turn answers (the newest at its start, `LiveSpend.message`), and drops the attempt's estimate as its result's exact cost arrives (and again in its `finally`, `spend.ended`); once Usage stored that cost, `SpendCaps.settled` judges the agent's day again, since the crossing request may have been the turn's last. Totals: a workflow run's `runCostUsd` plus the live estimates of turns answering its own messages (`CapContext.liveBy`, matched against `runMessages`), a routine run's new `RoutineRun.costUsd` (`RoutineRunner.chatCost`, from `onRunCost`, counted only while the turn answers the run's message, like an Agent step's visit) plus the live estimate of that turn, an agent's `UsageService.agentSpend` (its exact v2 records and log estimates since the day's start, leaving out the log estimates of chats it has a turn running in) plus its live estimates; so the user's own turn in a routine's or step's chat is never the run's. Side runs, keep warm, the moderator and room handoffs are never live-priced (a side run and keep warm still count in the agent's day through Usage). **At a cap.** A workflow run's own cap is judged by `WorkflowRunner` inside its writes (`capCheck` in `progress` and `nextItem`, with the `CapContext` read before each `advance`; `checkCap` asks again when a turn's spend grows): `WorkflowRun.capHold {kind: 'run', at, spentUsd, limitUsd, capUsd}` stops every new start and For each item, the run reads `waiting`, an ended run drops it, and the hold's first write calls `caps.held`, which pauses the run's running chats (`TaskQueue.pause(chatId, cap)`) and notifies. An Agent or For each step about to start on an agent past its day holds the run the same way (`kind: 'agent'`). A routine run's cap pauses its chat and marks the run `capped` (Recent runs: "Paused at its spend cap"). A turn answering a held run's message (a usage limit's `continue`, a step sent as the hold began) pauses on its first request, as does an automated turn of an agent whose day is tripped. A step or item a cap paused is marked `capPaused` ("Paused at a spend cap" in the run view). A routine run is marked `capped` only once its chat really paused. An agent's day pauses every running turn of it (single chats and rooms where it is active, never an A→B chat), trips the day in `spend-caps.json` (`CapStore`, per machine, never synced, so a restart neither forgets nor pauses again), skips a routine run that would start it (`skipReason: 'cap'`, `capSkipText`) and holds workflow steps on it. **Pause.** A cap's Pause stores `ChatMeta.pauseCap` (`CapPause {scope, label, spentUsd, limitUsd, capUsd}`) beside `pause`, writes `cap` into the flag file, so `pauseHook.ts` blocks with `CAP_BLOCK_TEXT` (it carries `PAUSE_MARKER`, so the block cap counts it), and the landed notice (single chat, room, restart recovery) reads `capPausedText` instead of "Paused." (`pausedText`). Sync's copy chat drops `pauseCap` with `pause`. **Going on** is always the user's act and allows one more cap's worth from what was spent (`raisedLimit`; the limit is `effectiveLimit(cap, raised)`, so a cap raised by hand wins): Resume, or the user taking over a capped chat (`TaskQueueDeps.capOverride`, awaited under the chat's lock before the turn starts; a workflow scope's Continue is not awaited, since the run's queue may wait on that chat), the run view's **Continue** (`workflows:continueCap`, banner `wf-cap-hold`/`wf-cap-continue`, `capHoldBanner`; it resumes the run's chats that hold paused, its own cap's or the held agent's, one still wrapping up once its pause lands (`SpendCaps.chatIdle`, from `onIdle`), and fills For each slots; `WorkflowRun.capLimitUsd`; an agent hold whose cap was removed or renamed away still lifts), or **Settings › Usage › Spend caps**' **Allow more today** (`SpendCapsCard.tsx`, `usage:caps`/`usage:allowMore`, `capRow`). A reached cap sends one `spend-cap` notification (payload kind, under the devices' `waiting` toggle, its `body` the amounts, its click the chat or the run; not while someone looks at the chat). The user's own typed messages are never refused. Zumi Bot's routine and workflow formats take `spendCap` (left out keeps it, `null` clears it), and it writes `dailySpendCap` only when asked. Saved history keeps a cap only when set, so older versions compare equal. Design: `docs/superpowers/specs/2026-11-12-spend-caps-design.md`. **Engines without `cost` (ACP).** A cap holds only where every turn reports a USD cost (`EngineCaps.cost`, ACP's may be in credits): Agent Studio hides the daily cap (an engine switch drops it, a cap the file already holds shows the fixed sentence with **Remove the cap**, and Usage's row shows the sentence instead of a live cap, `capBlockedOf`), and `agents:save` refuses one (`spendCapRefusal`). `routineEditing.save` and `workflowEditing.save` (so Zumi Bot's tools too) refuse a `spendCap` when a target or step agent lacks `cost` (`core/caps/capEngines.ts` over the pure `shared/src/capAgents.ts`), the editors show the sentence in the cap's place, and `RoutineRunner.run` and `WorkflowRunner.start` check again where a run starts, since the agent may have changed engine: the run fails with the sentence (a manual workflow run throws, an event workflow's streak pushes once), and a lookup that throws fails it with `SPEND_CAP_UNCHECKED`, never runs it uncapped. See [protocol engines](protocol-engines.md).
