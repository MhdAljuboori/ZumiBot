# Vault

**Vault (`core/vault/`, `shared/src/vault.ts`).** **Settings › Vault** keeps logins (sites, username, password, an optional 2FA secret), cards, contact details and API keys that chosen agents use without ZumiBot ever sending them a password, 2FA secret or code, card number, expiry, CVC or key value. **Store.** `VaultStore` keeps `<data>/vault.json` (0600, `{v: 1, keyId, items: [{id, updatedAt, deleted, sealed}]}`): each item is sealed alone with AES-256-GCM (`vaultCrypto.ts`, a fresh 12-byte nonce, additional data `claudebot-vault:v1:<id>:<updatedAt>`, so an item can't be moved to another id or time), its name, grants and approved sites included; a delete is a tombstone, never pruned, since sync never deletes. One queue does every read and seal, and a stale save is refused with `VAULT_CHANGED`. The key is 32 random bytes, base64 in `vault.key` (0600, folder 0700), at `ZUMIBOT_VAULT_KEY_FILE`, else `$XDG_CONFIG_HOME/zumibot-vault/vault.key`, else `~/.config/zumibot-vault/vault.key`, made at the first save only (two machines that never used the vault make no keys to clash); `keyId` is the first 16 hex of SHA-256 of `claudebot-vault-key-id` plus the key. `resolveVaultKeyFile` (`config.ts`, mirrored by `vaultKeyFileOf` in `deploy/config.mjs`) refuses a path inside the data folder, and a folder that is not one only for the key (`/`, `/etc`, a temp folder, a home or anything above it, one holding the data folder, or a name without `vault` or `zumibot`), because the guard denies agents that whole folder. Status (`vault:status`) is `empty`, `ready`, `keyMissing` (live items, no key file) or `keyMismatch` (another key, or a file that won't parse or open): in the last two saves fail with `VAULT_UNAVAILABLE`, the file is never overwritten, agents list nothing, fills fail `vault_unavailable`, and **Start a new vault** (`vault:reset`, refused on a healthy vault) moves it aside as `vault.json.unreadable-<time>`. Grants name agents, never Zumi Bot (the editor leaves it out, `vault:save` and the store refuse it, a rename onto its name, as the old built-in's migration runs, drops the grant, and `grantedTo` reads none for it even from disk). A rename moves them in memory before the first await, like approvals, and re-seals as a step of the agent-rename pipeline; the agents-folder watcher's `removed` pass drops a deleted agent's grants by `approvals.forgetAgents`' rule. **What the agent gets.** `zumibot_vault` is a stdio MCP bridge built like `zumibot_todos` (`vaultBridge.mjs`, its own `input` in `backend/vite.config.ts`, `vaultIpc.ts` with a 0700 `/tmp/cb-v-*` socket dir, a capability per CLI attempt bound to `{chatId, agent, turn}`, `alwaysLoad: true`). It goes in every run of every agent with ZumiBot's bridges (an ACP agent's runs get none; Zumi Bot's lists nothing) and every side run (blocked there by the side guard), so tool definitions never depend on grants, and `ChatService` answers its permission itself (no card, no rule, no Jev hint). Its one tool, `vault_items`, lists that agent's items with only the fields `agentView` keeps, by kind (login, card, contact, apiKey), then name (`VaultStore.agentItems`); its row is stored as "Checked the vault (N items): <names>" (`vaultRowResult`, also for a subagent's call in `dispatch.json`). The fixed `VAULT_SYSTEM` paragraph (`vaultPrompt.ts`) is appended after `TODO_SYSTEM` for every agent and must never vary with the vault or the agent (prompt-cache prefix), and `browserPrompt`'s sign-in sentence says to try the vault before `browser_request_user_action`. `AgentStore.save` adds `vault_items` to every non-empty `tools:` list (`withVaultTools`), and Zumi Bot does in the lists it writes. **Fill.** `browser_fill_from_vault {stamp, ref, item, field}` is a `zumibot_browser` tool. The manager plans it (`vaultFill.ts`: the grant, the field, the value, a TOTP code through `auth/totp.ts`, the expiry parts, and `loose` read-back for every field but the password) and the worker fills it (`chromiumAdapter.ts` `fillElement`), re-reading the page's and the frame's URLs at fill time, never the observation's label: both must be `https:` or loopback (else `insecure_site`), and a login needs both hosts among its sites (else `wrong_site`, naming them). The element must fit (`wrong_field_type`): a password only into `input[type=password]`, other secrets only into a visible, enabled text-like `<input>`, expiry parts also into a `<select>`, and every iframe up the chain visible. The value is then written inside the element's own frame in one evaluate (`vaultElement`): mask (`-webkit-text-security: disc !important`, for every field whose `BrowserFill.mask` is set: each card part, the expiry parts included, the password and the 2FA code; an expiry part is not `secret`, so a `<select>` may still take it, unmasked), focus, check again, the prototype's native value setter, `input` and `change`, a read-back (exact for a password; for any other field case, spaces, dashes, dots, slashes and parentheses a page's formatter changes are not a different value), mask again. It never goes through the keyboard, so a focus thief (an ad frame, a page's focus handler) gets nothing, and a value the page undid or moved is `fill_failed`. Worker answers carry codes only, and `workerEnv` drops `DEBUG*`/`PWDEBUG*`/`NODE_DEBUG`, since Playwright's protocol log would hold the value. Observation also reads child frames (each element labelled with its `frame` host), which card iframes need: while the main frame is read, up to 32 elements and 4 096 characters are kept back for them (only as many elements as they hold), frames holding an `input` or `select` go first, the main frame then gets what they left, and on a page with child frames an observation that left anything out says `truncated: true`. The result's bound (`boundBrowserResult`, 24 000 characters of element JSON) likewise takes framed elements first, up to 32 of them and about 8 KiB (8 192 characters) of their JSON, then the main frame's in order, then every framed one not yet kept, keeping the observation's order. A page without child frames reads, and is bounded, exactly as before. Every browser result an agent gets is scrubbed before it is cut (`scrubBrowserResult`, then `cutBrowserResult`; the worker hands strings over `SCRUB_MARGIN` longer than their limits, `browserLimits.ts`): passwords of 6 characters or more, card numbers as digit runs with single spaces or dashes, and API key values, of every item whoever holds it, become `[hidden by vault]`, and so does every Luhn-valid 12–19 digit run ending in a saved card's last 4 (any such run for a saved number that fails Luhn), so a page can't tell which of its guesses is the card. The server's own ids (a stamp's parts, `ref`, tab and download ids, `activeTabId`, in UUID shape only) are never scrubbed, since a match inside one would corrupt it and a changed `generation` voids every stamp. Only whole secrets are replaced, never a prefix, since blanking a prefix told a page how much of a secret it had guessed. The scrub reports how much its replacements shortened each string, and a string the worker itself cut shows nothing within `SECRET_MAX - 1` characters of that cut, counted after the replacements, whose shortening moves the cut in steps of 256 so its length never tells how long a hidden secret was (`cutBrowserResult`). An observation carries at most `MARGIN_PAYLOAD` characters of margins (`BROWSER_PAYLOAD`, 1 000 000 in all); past that a string longer than its limit is dropped, never sent without its margin. **Card approval.** A card fills on a (page host, frame host) pair only once the pair is among its `approved`. Otherwise the manager suspends the lease's idle timer (`leases.protect`), releases its active grant (so the user may take control) and waits on `VaultApprovals` (`vaultApprovals.ts`, one pending per profile; a second gets `approval_pending`, and a turn with no card to show it on `approval_unavailable`, neither read as a Deny), which adds a `vault-approval` chat item (`VaultApprovalCard.tsx`: "@agent wants to use Work Visa (Visa •4242) on shop.example.com", plus the card form's host when it differs). It counts in `pendingCount` like an approval card (the badge, the `approvals` push, the `waiting` notification, a routine's `waiting`, the A→B roll-up, a room's running turn), Jev never sees it, and `vault:answer` takes only a request pending for that chat (`VaultApprovals` checks the chat and the id; not the stored items, since a card is pushed before its save lands). **Allow** plans again (a grant removed or an item deleted meanwhile ends `not_allowed` and remembers nothing), adds the pair and fills after the worker checks the hosts again (a page that moved asks again); **Deny** types and remembers nothing. Stop, the turn's end, a server stop or a restart make a pending card `interrupted`, and a fork copies it so. A fill row is stored as `{item: <name>, field}` ("Filled from vault · Work Visa · card number") with the fixed browser result line. **API keys.** Values are trimmed on save (a stray space would keep the bare token from being scrubbed). An API key's **Workflow HTTP steps can use this** switch (`workflows: true`) lets a workflow's HTTP request step send it (see [Workflows](workflows.md)); that path has no agent and no env. Env names pass `envNameError` (reserved prefixes and names in `shared/src/vault.ts`; two keys with one name for one agent are refused). Every main run of a granted agent (single-chat turns, room members, routines, A→B asked runs; never a side run, Compact, the moderator or the room summary) gets them as env, read per attempt (`vaultEnv.ts`), so a grant change applies from the next attempt and the prompt never changes; they go first in the run's env, so no key's name can stand in for a value the server sets. A Codex run gets them only beside its trusted vault hook, and never one named `CODEX_*` or `OPENAI_*` (see [Codex agents](codex.md)). An ACP agent's run (no guard stands beside it: `vaultKeys` off) gets only the keys its own sign-in names in `acp.authEnv`, under their own names; a named key not granted to it, or a Vault that cannot be opened, fails the send naming the env name, and every granted value is still scrubbed (see [Protocol engines](protocol-engines.md)). Agent Studio's ACP card picks those names (Sign-in keys) from the API keys granted to the agent, env names only (`vault:list`), and `acp.authEnv` is part of the launch Save confirms; the Vault editor marks an ACP agent's grant checkbox on an API key with `ACP_API_KEY_NOTE` (`vaultGrantNote`), since a grant alone gives it nothing. A remote (AG-UI) agent's run gets no key as env at all (`vaultKeys` off): only the one key its `agui.authKey` names, read from the Vault per attempt and sent in its auth header alone (`Authorization: Bearer <value>`, or the bare value in `agui.authHeader`), never in the agent file, a log, a URL, a body or an error, which name `authKey` instead; a named key not granted to the agent, or one with a character a header cannot carry (a control character other than tab, or one past U+00FF), fails the send naming the env name, and the value is in the run's scrub map like any granted key. Agent Studio's remote card picks it (Auth key) from the API keys granted to the agent, env names only, and the grant checkbox for such an agent carries `AGUI_API_KEY_NOTE` (see [Protocol engines](protocol-engines.md), AG-UI). Each parsed event of such a run passes `scrubEvent` before `ChatService`, the dispatch recorder or anything else stores, pushes or logs it, each value becoming `[vault: <name>]`; text deltas go through `DeltaScrubber`, which holds back a tail so a value split across deltas is caught, and errors and stderr are scrubbed too. Side runs are scrubbed with their base agent's grants, and to-do adds, `ask` messages, `side_question` questions and the reason of a browser or desktop handoff card with the owner agent's (`scrubBridges.ts`). A permission reply sends the raw input back (`allowResponse`, or the approved command would run with the tag), and only the stored and shown copies are scrubbed. **Guard.** Every main run's one merged `--settings` (`oneSettings`, with the desktop ask rules and the pause hook) carries `vaultGuardSettings` (`vaultGuard.ts`): deny rules for `Read`, `Edit`, `MultiEdit`, `Write`, `Grep` and `Glob` on the key's folder and on `vault.json`, and a `PreToolUse` hook on Bash, a plain `sh` `grep -qF` over its stdin for those paths in absolute, `~/` and `$HOME/` forms, which blocks with exit 2 and `VAULT_GUARD_TEXT`. On a Mac it is `grep -qiF`, since its disk ignores letter case (`~/.config/Zumibot-Vault` is the same folder). On Windows (where Claude Code runs hooks in Git Bash) the patterns also cover the JSON-escaped, forward-slash and `/c/...` spellings, `tr` first lowercases the call and turns every `\` into `/`, since Git for Windows' grep 3.0 aborts on `-iF` and mismatches backslashes, and the deny rules take the `//c/...` form Claude Code matches Windows paths in (see [Install](install.md), Windows). The same guard keeps agents off the audit log (`GuardPaths.auditDir`, `<data>/audit/`): deny rules on that folder too, and a second grep with its own `AUDIT_GUARD_TEXT`, the hook then reading the call's JSON once (`i=$(cat)`) for both; without an audit folder the settings stay byte for byte as before (see [Governance](governance.md)). The folder also holds `isolation.json`, so the guard keeps agents off each agent's isolation setting too. A sandboxed agent's Bash cannot see the key folder or the data dir at all (the sandbox's `denyRead`), so for it the guard is a second wall, not the only one. A Codex main run carries the same grep as one `-c` PreToolUse hook on every tool instead (`codexVaultHooks`; it also blocks when grep itself fails, since Codex lets a call run on any exit but 2), with no deny rules, which Codex's tools do not take (see [Codex agents](codex.md)). It matches resolved paths only, so work on ZumiBot's own source is not blocked. The same merged `--settings` also carries `connectorsGuardSettings` (`core/connectors/connectorsGuard.ts`): the same six deny rules on `connectors.json` in the data dir, with no Bash hook (see [Connectors](connectors.md)). Side runs and Compact keep their settings byte for byte, apart from the agent's own extension parts (see [Servers, plugins, skills and hooks](extensions.md)). `vaultGuardProbe.mjs` checks it against the real CLI (see [Commands](e2e.md)). **Settings › Vault** (`VaultSettings.tsx`, pure rules in `state/vaultSettings.ts`, `/settings/vault` after Notifications): search, Add, items grouped by kind, forms whose secret fields are empty on open (blank keeps the stored value; Show and Copy fetch one value through `vault:reveal`, 30 a minute, never logged), **Agents that can use this**, a card's **Approved sites** with remove (`vault:removeApproval`), Delete with a confirm, the unsaved-changes guard, and for `keyMissing`/`keyMismatch` the explanation, the key path the server looks at (`vault:keyFile`, a path, never the key) and Start a new vault. `vault:list` carries no secret (`listView`), and `vault:changed` (no payload) makes it refetch. **Sync** joins `vault.json` by item id (`deploy/vaultSync.mjs`, which the shell's build copies to `resources/sync`): the later `updatedAt` wins, tombstones included, and a tie goes to the tombstone, then the VPS. Key bytes travel only over ssh stdin and stdout, never argv, a log or a backup: a key only one side has is copied to the other (a push never replaces a key that appeared on the VPS meanwhile, and links it in only once its byte count and shape show it arrived whole), equal keys merge, different keys re-seal this PC's items under the VPS key and keep the old one as `vault.key.replaced-<time>`, and a side whose `vault.json` does not match its own key leaves both vaults as they were and says so (a missing key names the path checked and the setting that moves it). Every vault and key file is written whole: a short write fails, a vault cut short is never renamed in, and a key pulled from the VPS (written in place, exclusively) is removed when its write fails. A reseal flushes both key files and the joined vault to disk before the new key is renamed in; a rename a crash left undone (a plain-file `vault.key.sync-tmp` whose key opens this PC's `vault.json`) is finished by the next sync, and one that fails puts the old vault back. A key folder the sync writes in is made 0700 and the log says so (on the VPS only a folder whose name has `vault` or `zumibot`, never the home or one above it, and a symlinked folder by where it points), and `/vault.key*` at the top of the data folder is left out of the pull and the VPS backup even if one sat there. The VPS's `vault.json` is replaced only if it has not changed since the pull, through `vault.json.sync-in` and an `mv`, so a full VPS disk leaves it as it was (and the sync says so). `VPS_VAULT_KEY_FILE` (`deploy.env`/`sync.env`, default `~/.config/zumibot-vault/vault.key`) must match the VPS service's `ZUMIBOT_VAULT_KEY_FILE` when that is set. Logs carry item ids and codes only, never values, names or hosts. **Honest limits** (accepted by the user): a Codex agent's run is guarded by its one hook alone (no deny rules), which has the limits of Claude's Bash hook below on every tool, the reads Codex runs outside the project without asking included; a run whose hook codex never confirms goes on without it and without the agent's keys, after an `unguarded` notice in the chat; in auto mode its MCP tool calls get no client review (probe check 12); and a printed value also stays in Codex's own rollout under `$CODEX_HOME/sessions` (see [Codex agents](codex.md)). Agents run as the same OS user as the server, so the vault files are guarded only by a speed bump: a determined agent can read the key and open the vault, as it could `~/.ssh` or a `gh` token. The hook lets a call through when its stdin is garbled, and other spellings pass it (`"$HOME"/.config/…`, `cd ~/.config && cat zumibot-vault/vault.key`, `$XDG_CONFIG_HOME` forms, a script). Commands that use an API key get no approval card: only the auto-mode classifier and the `VAULT_SYSTEM` rule stop one from sending the key elsewhere without printing it, so routines never wait. A printed value reaches the model, and the CLI's own session log under `~/.claude/projects` keeps it; neither that log nor Files-panel snapshots are scrubbed. Only literal values are scrubbed, so an echo in another form (a base64 Basic auth header, a JSON-escaped or percent-encoded value) passes, and once a grant is revoked its value is no longer scrubbed in later runs, though the session log holds it. Whole-secret scrubbing is an equality oracle: a page or an agent can test guesses at a weak password or key by whether the text comes back `[hidden by vault]` (not a card's number: for a Luhn-valid saved card, every Luhn-valid 12–19 digit run ending in its last 4 is replaced, and a card that fails Luhn blanks every such run, so all such guesses come back identical). The approved frame shares the page's world (no isolated world), so it can tamper with its own prototypes, fake the read-back or undo the mask; it receives the value by design. CVC, expiry, 2FA codes and passwords under 6 characters are masked in their field but not scrubbed from browser output, and screenshots can't be scrubbed. An agent whose saved `tools:` list is not empty gets `vault_items` only when it is saved again in Agent Studio. A wildcard site on a shared suffix (`*.github.io`, `*.azurewebsites.net`) is accepted, since there is no public-suffix list, and would hand the login to any site under it: don't save one. Only up to 32 child-frame elements (and, in the bound, about 8 KiB of their JSON) are kept ahead of the main frame, so a hostile iframe can take no more of the page than that, in the observation and in its bound: on a page whose iframes hold more, or whose main frame is huge, a card field past them can still be left out, and the result then says `truncated: true`. The approval card is not shown inside an asking agent's ask card (Open conversation shows it), as with browser handoffs. Sync carries the CLI session logs (`~/.claude/projects`), and any value an agent printed in them, to the other machine; `vault.json` copies in sync backup folders and `vault.json.unreadable-*` files are outside the guard's deny rules, which rest on the key's folder. A sync join can leave two API keys with one env name granted to one agent (the editor refuses that on save, `mergeVault` re-checks nothing); the env then takes the last in name order. Design: `docs/superpowers/specs/2026-11-07-encrypted-vault-design.md`.

**Server-only secrets.** `sealExtra(id, updatedAt, body)` seals a body under the vault key (made at first use, refused with `VAULT_UNAVAILABLE` while the vault can't be opened) and `openExtra` opens it, or answers null for no key or another key; the key never leaves the store. Channel bot tokens use it, kept in `channel-tokens.json` rather than as a `vault.json` item kind, which an older server would read as an unreadable vault after a sync. `setExtraSecrets` adds their values to `secrets()`, so they are scrubbed wherever vault values are (see [Channels](channels.md)).

**Logins for workflows.** A login's **Workflows may use it (email trigger)** switch (`workflows: true`, `VaultListItem.workflows`; an API key's own is above) lets a workflow's email trigger sign in to its mail server with it (see [Workflows](workflows.md), Triggers). `VaultStore.workflowLogin(id)` returns `{username, password}` only for a login with the switch on and both fields set, read per check by the mail watchers and the runner's `problems` (`mailAccount`), so turning it off or deleting the login stops the next check and marks the workflow as having a problem; no agent, env or card is involved. The password is read on the server only: the inspector lists logins by id and name, Check mailbox and the run say only the count or an error that `scrubPassword` has cleaned, and the mail client's logging is off. A save without `workflows` clears the switch (`vaultInput` reads `o['workflows'] === true`).

## Server setup: the vault key (back it up)

**Settings › Vault** seals every item with one key, kept outside the data folder: `~/.config/zumibot-vault/vault.key` of the server user (or `$XDG_CONFIG_HOME/zumibot-vault/vault.key`, or the service's `ZUMIBOT_VAULT_KEY_FILE`, set in a drop-in with `systemctl --user edit zumibot`). The server makes it at the first vault save.

- **Back it up yourself**, apart from the data backups (a password manager or an offline copy). Without it the vault can't be opened: the Vault page can only start a new, empty one, and keeps the old `vault.json` aside as `vault.json.unreadable-<time>`. Copies and backups of the data folder, `npm run sync`'s backup folders and installer updates never hold the key, by design. When you restore onto a new server, put the key back at the same path (0600, in a 0700 folder) before the first start. The key is outside the install folder (`~/zumibot`), so an update or rollback leaves it alone.
- Keep it in a folder of its own. The server refuses a key in a shared folder (your home, `~/.config`, `/tmp`, the data folder, or a folder without `vault` or `zumibot` in its name), because agents are denied the key's whole folder.
- If the service sets `ZUMIBOT_VAULT_KEY_FILE`, set `VPS_VAULT_KEY_FILE` to the same path in `deploy.env` (and import it again into the desktop's Sync settings). Otherwise sync reads and writes the default path: a key it pushes there is never read by the VPS server, so the VPS's Vault page shows an unreadable vault while sync reports success.
- Agents run as the same user as the server. The deny rules and Bash hook that keep them off the key are a speed bump, not a wall; see the rest of this doc.
- A full sync (`npm run sync -- --with-chats`) also copies the CLI's session logs (`~/.claude/projects`) both ways, so any value an agent printed reaches the other machine too. The sealed `vault.json` copies in the sync's backup folders, and `vault.json.unreadable-<time>` files, are outside the agents' deny rules, which cover only the key's folder and the live `vault.json`: sealed, they are no use without the key.
