# Git worktrees and the git chip

A chat or room can run in its own git worktree on its own branch, so two chats in one repo don't edit the same files. Every chat inside a git repo also shows its branch and dirty state in the header, and a click on that chip lists the uncommitted files with their diffs in the side panel (Changes). Design and reasons: `docs/superpowers/specs/2026-11-14-git-worktree-per-chat-design.md` ([design](../superpowers/specs/2026-11-14-git-worktree-per-chat-design.md)).

ZumiBot makes the worktree itself (`git worktree add`, through `execFile` with no shell). The chat's `cwd` becomes the worktree path, so the runner, `--resume`, the Files panel, Codex agents and side questions see an ordinary folder. Never `--force`, never a branch delete, and never a write inside the source checkout (no `.gitignore` or `info/exclude` edits).

## Data

- `ChatMeta.worktree?: ChatWorktree`: `root` (worktree top; `cwd` is it or a subfolder), `branch`, `source` (top of the checkout it came from: re-adding runs there, links point into it), `folder` (what the user picked; sidebar grouping and `reusableChat` use it), `links` (relative `node_modules` links ZumiBot made), `removed?: true` (folder removed by cleanup), `kept?: WorktreeKeep` (why the last release skipped it), `base?: string` (the full sha `create` started the branch at, read with `git rev-parse HEAD` in the picked folder; optional, so a chat made before base diffs simply has none, and `ensure`'s remake leaves it alone — it is still where the work started).
- `AppSettings.worktreeFolders: string[]`: the remembered toggle, keyed by the repo's top folder, so `WebFrontend` and `WebFrontend/angular` read the same setting. It lives in `settings.json`, which sync carries whole, newest wins. No new file in the data dir. `setLastFolder` still stores the picked folder, never the worktree path.

## Create

`chats:create` / `chats:createGroup` ask `topOf(dir)` (only when some toggle is on, so a machine without git still chats); when the repo is in `worktreeFolders` they call `create(dir, handle)` (`room` for a room). The built-in agent never isolates. A non-repo pick fails with `Not a git repository: <folder name>`. A git failure reaches the client as the first line of git's stderr, with no chat made and the half-made folder removed.

- Folder `<parent of repo top>/<repo basename>-<slug>`, slug `<handle>-<6 hex>` or `room-<6 hex>`; branch `zumibot/<slug>` from the picked folder's `HEAD` (`worktree add -b`, run in the picked folder, so a linked worktree as the pick starts from its own `HEAD`). A taken folder or branch draws a new suffix, five tries.
- A subfolder pick keeps the subfolder: `cwd` is the same relative path inside the worktree (the root when that path isn't in the checkout).
- **Links.** After the add, every `node_modules` up to 3 levels below the source top (never inside another) is symlinked at the same relative path, only when: its parent exists in the worktree and nothing is at that path; `git check-ignore -q -- <path>` says the path is ignored once linked (a symlink doesn't match a `node_modules/` pattern, and `git add -A` must never commit one; the link is removed again when not ignored); and the `package.json` beside it has no `workspaces` field (a workspace's `node_modules` holds relative links that would resolve into the source). So WebFrontend's `/node_modules` is linked, ZumiBot's own `node_modules/` and any workspaces package are not. A skipped link is logged and never fails the create.

## Ensure

Archive can remove a folder that a later turn needs (any turn starting unarchives the chat), so every spawn in a chat's `cwd` first awaits `ensure`. With no `worktree`, or a folder that exists and isn't `removed`, it does nothing. Otherwise it `worktree prune`s, then adds the folder from `source`:

- the branch exists: `worktree add <root> <branch>`;
- only `origin/<branch>` exists: `--track -b <branch>` (a chat moved to the other machine after a push);
- neither: the branch is made again from `source`'s `HEAD`, and the turn gets the notice `Branch <branch> was gone, so it was made again from <source folder>'s current HEAD.`;
- the branch is checked out elsewhere: `Branch <branch> is checked out in <path>. Switch that checkout to another branch, then send again.` Nothing is forced.

A folder that exists while the chat is flagged `removed` (the flag synced from a machine that cleaned up) is not added over: when `git worktree list --porcelain` in `source` lists it, `ensure` only relinks what is missing, clears `removed` and `kept` on every chat with that root and adds nothing; a folder git does not know still fails with git's line. Otherwise, after the add, it relinks, and clears `removed` and `kept` on every chat with that root. Another failure is `Can't rebuild the worktree for branch <branch>: <git line>`, and a `source` that isn't a repo on this machine says so. `ensure` and `release` share a per-root serial lock, so two room members add once and a release never removes a folder a turn is just starting in (git calls stay out of `ChatStore`'s lock).

**The notice.** Only a turn takes it (`forTurn`, used by `ChatService.ensureFolder`; shown as a `worktree` notice item before the turn). Any other caller (moderator, side picker, side base, summary) rebuilds but leaves the remake notice pending in the service (in memory, per root, lost on restart), and the first turn after takes it once. Chats sharing a root share one notice. A release that removes the folder again drops a notice no turn took.

**Spawn-site audit** (searched `meta.cwd` / `.cwd`):

- Behind ensure: the single chat turn, routines (`chats.send`), asked-agent chats, the tasks queue and resend/edit/fork reruns all go through `ChatService.agentTurn` (`ensureFolder`, `forTurn`); Compact goes through `agentTurn` (`spec.compact`); room member turns go `GroupService` -> `chats.agentTurn`; the moderator (`moderate` dep in `app.ts`); the side-question picker (`pick` dep, spawns `runJsonCall` in `meta.cwd`); `SideQuestions.baseOf` (`deps.ensure`), the one place every side run takes its base from: ask, follow, again, askFrom (the asker's `from` chat too) and keep-warm pings, kept bases included, so a /btw or a ping on an archived chat never spawns in a removed folder; `baseFor`, for fresh Claude and Codex bases; `RoomSummaries.run` (a failing ensure shows as the generic "Couldn't write the summary").
- Left out, no spawn in a chat's worktree `cwd`: `sideRun.ts`, `claudeRunner`, `codexRunner`, `codexHookTrust`, `moderator.ts` (spawners only; their callers ensure first); `restoreFile.ts`, `fileChanges.ts`, `listChatFiles`, `chatTranscript.ts` (read paths, a removed folder lists nothing); `jev.approvalRisk`, `roomBriefing` / `buildBriefing`, `workflowEventSources` (`cwd` as text); workflow steps, `bareCalls.ts` and the workflow Room step (workflow-made chats get no worktree); extensions' `claudeCli.ts` (its own cwd).

## Release

After `chats:archive(id, true)` succeeds and after `chats:remove`, the handler runs `release(chat, { deleted })` in the background. It logs, never throws, and never fails the archive or delete. Under the per-root lock it re-reads the store (a send after archiving means the chat needs its folder: touch nothing), then:

1. skips when there is no `worktree` or it is `removed`;
2. `shared`: another live chat has the same `root`. Archived chats and asked chats (`asked` set) don't count, since asked chats are never archived with their asker;
3. a root that's already gone only gets `worktree prune` and `removed`;
4. one `git status --porcelain=v2 --branch --untracked-files=normal --ignored=matching` (always with `--no-optional-locks -c core.quotePath=false`: a status must not take `index.lock` from under the agent's own `git add` or `commit`) gives the rest, checked in this order (`releaseBlock`): `dirty` (any uncommitted entry except ZumiBot's links), `ignored` (an ignored entry that is not a link and not a rebuildable cache: a path segment `node_modules`, `.angular`, `dist`, `out`, `build`, `coverage`, `.cache`, `.turbo`, `.next`, `.vite`, `tmp`, or a `*.log`; `git worktree remove` deletes ignored files silently and agents keep real work in ignored paths such as `.superpowers/`), `detached` (commits on a detached HEAD would be left on no branch);
5. if `HEAD` is on another branch than `worktree.branch` (the agent ran `git switch -c`), updates `branch` on every chat with that root, so `ensure` brings back the branch that holds the work;
6. removes ZumiBot's links (right before the remove: they are untracked files and would make the folder dirty), then `git worktree remove <root>`, never `--force`, and marks `removed: true` on every chat with that root, asked chats included (on delete the chat is gone, so only the others). The branch is kept.

A skip sets `worktree.kept` (`dirty`, `ignored`, `detached`, `shared`) and pushes the meta; it is not retried. The folder stays until the chat is used and archived again while clean, or the user removes it by hand. `'failed'` is set when `git worktree remove` failed and the folder is still there (maybe partly deleted): the links are put back and the archive line says `removing its folder failed`. `kept` is never written on delete; a skip on delete logs `worktree kept after delete: <root> (<reason>)`, the only record of the folder left behind.

## The chip

`chats:gitStatus` runs `git --no-optional-locks status` in the chat's `cwd`, or in the agent's own worktree (see above), (5 s timeout) and returns `{ branch (null = detached), head, changed, removed?, agentTree? }`, or `null` outside a repo or without git. A removed worktree answers from the meta (`removed: true`, branch, no git call). `changed` counts staged, unstaged and untracked entries, ZumiBot's links left out. `GitChip.tsx` sits after the folder chip, hidden on `null`: branch (or short sha), `●` when dirty (`chat-git-dirty`), greyed and locked when removed. Tooltip: `<n> uncommitted changes` / `1 uncommitted change` / `No uncommitted changes`, plus `Worktree: <root>` (or `In the agent's worktree: <folder>`), plus `Click to see the changes`. A click opens the side panel on Changes (`toggleChanges` in `state/sidePanel.ts`), the chip reads pressed while it shows, and a second click closes it (a browser or desktop waiting behind comes back, as with ✕). The folder chip of a worktree chat shows the picked folder's name with the worktree path in its tooltip.

Refetch moments (`useGitStatus.ts`, `shouldRefetchGit`): a chat opens, `inFlight` goes true to false, the meta's `worktree.removed` flips (release or the next turn), window focus, and each answer the Changes panel gets (so the chip's count follows its Refresh). Not while a turn runs.

Archived note (`ChatView`, `archived-worktree`, from the pushed meta, `worktreeArchiveLine`): `Its worktree folder was removed. Branch <branch> is kept.` or `Its worktree was kept: <reason>.`, with reason `uncommitted changes`, `ignored files that would be lost`, `detached HEAD`, `another chat uses it` or `removing its folder failed`.

## The agent's own worktree

An agent can make a worktree itself (`git worktree add /tmp/wt-x -b feature/x` in Bash, or Claude Code's own worktree tool) and work there with `cd` and absolute paths while the chat's `cwd` stays the checkout it was opened in. The chip and the Changes panel then follow the agent, so they show its work rather than the user's own edits or caches in that checkout.

`chats:gitStatus`, `chats:gitChanges` and `chats:gitDiff` hand the services a loader for the chat's items (`feed.peek(id)`, the open chat's held list with the running turn's calls, else `loadItems`). `agentTreeOf` runs `git worktree list --porcelain` in `cwd` (not bare, not prunable); with only one worktree it stops there and never loads the items. Otherwise it walks the tool calls newest first and takes each call's places (`toolPlaces`): the folder of an `Edit`/`Write`/`MultiEdit` `file_path` or a `NotebookEdit` `notebook_path`; for any tool with a shell `command` (Bash, a background process) each `cd`/`pushd` at a command's start and each `git -C`, the last first, then its `cwd`. Only absolute paths count (`~` and `$HOME` expanded): a relative one depends on a shell folder the item does not record. Reads don't count, since agents review other folders too. Paths are compared as real paths (macOS lists `/private/tmp` for `/tmp`), and the deepest worktree holding a place wins, since one can sit inside another (`.claude/worktrees/x`). The first place inside any of the repo's worktrees decides: the chat's own one means null (read `cwd` as before), another means that folder. Places outside the repo (scratch files in `/tmp`) are passed over, and a worktree removed since is no longer listed, so it is never followed. Only the git list is trusted: the client never names a folder.

Read there, the answer carries `agentTree` (the folder): `GitStatus.agentTree` and `GitChanges.agentTree`. ZumiBot's links are left out of the count only in the chat's own worktree. Both scopes follow the agent. **Since start** there measures from where the agent's branch was made (`branchStart`): the oldest entry of `git reflog show refs/heads/<branch>` ("branch: Created from ..."), so the work shows once the agent has committed it, as it usually has by the end. None for the repo's main checkout (its branch reaches back to the clone), a detached HEAD or a reflog that is gone. The chip's tooltip says `In the agent's worktree: <folder>` in place of the `Worktree:` line, and the panel shows the same under the branch line (`changes-agent-tree`).

## Changes panel

A side panel view (`'changes'`, a chat view like Files: Back to the list, ✕ and Esc close it, a full-screen sheet on a phone). It opens from the git chip or from **Open Changes** in the panel's list, which shows only while the chip's status is known and not removed, with the uncommitted count beside it.

- **Scope** (`changes-scope`, a `seg` under the branch line, on a worktree chat or while the list reads the agent's own worktree; `sinceStart` in `state/gitChanges.ts`): **Uncommitted** (the default) or **Since start**. Since start is disabled with a tooltip when there is no commit to measure from: the worktree has no `base` (made before base diffs), or the agent's worktree has no branch start. `GitChanges.base` carries that commit; when the switch can no longer offer Since start (the agent left its worktree), the panel goes back to Uncommitted. The choice is the component's, so it starts at Uncommitted each time the panel opens, and switching refetches the list and the shown file's diff.
- **List** (`chats:gitChanges`): `git rev-parse --show-toplevel` in the chat's `cwd` (or the agent's own worktree, see above), then one `git --no-optional-locks status --porcelain=v2 --branch -z --untracked-files=all` in the top. `-z` so no path is quoted; `-uall` so an untracked folder lists each file (the chip still counts with `normal`, so a new folder of three files counts 1 there and 3 here). Paths are relative to the repo top, sorted by path, ZumiBot's links left out, capped at `GIT_CHANGES_MAX` (500, the rest is `more`). Line counts come from one `git diff --numstat -z -M HEAD --` (a repo with no commit yet has none); an untracked file's lines are counted by reading it (regular file, at most 1 MiB, no NUL, 8 MiB read in all). `null` outside a repo, without git, or once the worktree folder was removed (the panel says which); any other git failure is git's line. A header line shows the branch (or short sha), `N files changed` and the `+added −removed` total; each row a status letter (`M A D R C T U !`, `KIND` in `state/gitChanges.ts`), the file name, its folder and its counts.
- **Since start** (`scope: 'base'`) answers the same shape against `worktree.base` (or the agent's branch start, above), so work the agent already **committed** shows too: `git diff --name-status -z -M <base>` for the kinds, `git diff --numstat -z -M <base>` for the counts, plus the status's untracked entries (`baseEntries`: a file the agent made and never committed is part of the work since the base, and a diff never lists it), and each file's before side read from `<base>:<path>`. It is base → working tree, so one list covers committed and uncommitted work. `null` when there is no base; a base commit no longer in the repo surfaces git's own line, as any other git error does. The header still shows where the worktree is **now**, not the base.
- **Diff** (`chats:gitDiff`): runs the status again and serves only a path it lists now, so a made-up path never reaches the disk (`This file has no uncommitted changes now.` otherwise). Before = `git cat-file blob HEAD:<path>` (a rename's or copy's old path; `cat-file -s` first, absent on exit 128); after = the file in the folder: a symlink is its target text (as git stores it, never followed), a regular file is read only when its real path stays inside the repo. Each side is `{ text }` or a miss: `absent`, `binary` (a NUL in the first 8000 bytes, git's test), `too-big` (over 1 MiB), `unreadable`, `submodule`. Nothing is written, nothing is staged.
- **Preview**: the first file shows until another is picked (a picked file that gets committed falls back to the first). Diff / Old / New as in the Files panel (`changeRows`: the frontend diffs the two texts with `rowsFromTexts`), Copy, and the Files panel's `Lines`, so Quote and Explain work on a selection. The list is read when the panel opens, when a turn ends, when `worktree.removed` flips, on window focus and on Refresh; every answer bumps `version`, and the picked file's diff is read again with it. The last list and diff stay shown while new ones load.

## Pull requests

A worktree chat's panel ends with its pull request: **Open PR…** while it has none, else its number, state and checks with **Refresh** and, per failing check, **Send to agent**. A chip beside the git chip shows the same (`chat-pr`: the number, the state and a dot coloured by the checks; a click opens it on GitHub). Both are `PullRequest.tsx` over `state/pullRequest.ts`; everything else — the gh CLI, the push, the watcher and the card's copy — is in [Review loop](review-loop.md).

## Review comments

Selecting lines in a diff and writing on them collects a **draft review** for the chat, sent as one ordinary user turn. Design and the rest of the loop: [Review loop](review-loop.md).

- **Making one.** The diff's selection menu (`SelectionMenu`, which already gives Quote and Explain) adds **Comment** wherever the rows carry line numbers; `Lines`' `onComment` hands the panel the range `selectedLines` found, whether it is an old-side range, and the selected text. A form at the panel's foot (`review-form`) shows the range and the lines, takes the text (Enter adds, Shift+Enter is a new line, Esc drops it) and **Add comment** puts it in the draft. The quote is kept as the user saw it and is never re-read, so it still points at the right place after the file has moved on.
- **The draft** (`review-bar`): the count, **Send review**, and a chevron listing each comment with its range, its first line, **Edit** and **Delete**; a file's row carries a badge (`review-dot`) with how many of them sit in it. It lives in `localStorage` under `zumibot:review:<chatId>` (`state/reviewDraft.ts`: every access guarded, a value that is not a list of comments reads as no draft, and an empty draft removes the key). So it survives a reload **per device** and never reaches the server, `chats.json` or sync. Caps: 4 000 characters a comment, 4 000 for a quote (a longer selection is cut with a line saying how much went), 50 comments a draft.
- **Sending** builds the text with `reviewMessage` (pure) — a line saying how many places, then each comment's range, its quoted lines in a fence longer than any backtick run inside them, and the text, in path order and then up the file. A range marks ` (old)` and ` (since start)` where they apply. It goes through the chat's ordinary send, so Edit, Resend, versions, the queue, spend caps and notifications all work on it. The draft is cleared at once rather than held: a send settles only when the turn ends, and a failure shows as a failed message carrying the whole review, with its own Retry.

## Syntax colours

The Files and Changes panels draw code rows in colour (`state/syntax.ts`, pure and tested). `languageOf(path)` picks a highlight.js language by name or extension (none: plain). The highlighter is lowlight (`syntaxEngine.ts`, highlight.js's common grammars plus Dockerfile), loaded with a dynamic import by `useHighlighter`, so its chunk stays out of the main bundle and rows draw plain until it arrives. lowlight returns a tree, never HTML: `hastLines` turns it into tokens per line (a token across a newline, such as a block comment, keeps its tone on both lines) and rows render them as React text. `toneOf` maps highlight.js scopes to a few tones (`.tk-kw`, `.tk-str`, ...; an unknown scope keeps its parent's, `subst` goes back to plain); the colours are `--syn-*` tokens in `:root`, GitHub-like, readable on the diff's green and red rows in both themes. `rowTokens` gives each row its tokens: with the whole old and new texts (the Changes panel) by line number, so a hunk that starts inside a comment is right; otherwise (Files panel patches) each run of code rows between headers is highlighted as one block per side. Tokens that don't spell the row's text exactly are dropped, and past `HIGHLIGHT_MAX` (300 000 characters) rows stay plain.

## New chat UI

The folder menu of `NewChatView` ends with a checkbox row (`new-chat-worktree`): "Isolate in worktree — runs on its own branch next to the repo". It is disabled while the folder's state is unknown (loading, offline, a failed lookup) and, with the tooltip "Not a git repository", only when the server said it is not a repo. Its state is `app:gitFolder` for the picked folder, read on each folder change; ticking saves at once with `app:setWorktreeFolder`, so it isn't draft state. The folder chip shows a branch mark while it is on (`new-chat-folder-worktree`). The same toggle shows for a new room, not for the built-in agent. The sidebar shortcut that skips the screen ("New chat in <folder>") follows the remembered setting because the server decides; an agent row opens the screen. Sidebar chats group by `sidebarFolder`, and a worktree chat row has a branch mark (`chat-row-branch`). When the folder's git lookup fails, the shortcuts reuse no empty chat and create a new one, since the kind to match is unknown. `reusableChat` matches on `worktree?.folder ?? cwd` and only the same kind (a plain empty chat is never reused when the toggle is on, nor a worktree one when it's off).

## Copy rules

- **Attempts** get one worktree each, all from one base commit, and are never shared: see [Review loop](review-loop.md).
- **Fork** copies `worktree`: it shares the folder, as it shares `cwd`.
- **Clone room** keeps the worktree (`cloneRoom(..., { keepWorktree: true })` from `chats:cloneRoom`). A **workflow Room step** copy calls `cloneRoom` without it and gets a plain room in the template's `worktree.folder`: unattended runs must not share a folder cleanup can remove.
- **Asked chats** copy `worktree` so `ensure` can bring the folder back for them, but they don't keep it alive (release ignores them when counting sharers) and are marked `removed` with the rest.
- Routines, workflows, voice requests and the built-in agent never isolate.
