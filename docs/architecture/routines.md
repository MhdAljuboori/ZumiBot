# Routines

**Routines.** The rail's Agents and Routines buttons (`mode-tab-agents`, `mode-tab-routines`, see [Rail](ui.md)) switch the UI between the two. Routines has its own address (`routinesFromPath`/`routinesPath` in `state/route.ts`): `/routines`, `/routines/new` and `/routines/<id>` (ids are UUIDs, so `new` never names one); an id not in the list holds the address back until the list loads, then falls back to `/routines` in place, and Back to `/` from Routines keeps the Agents view left there. `core/routines/` holds `routineStore.ts` (`routines.json`, `routine-runs.json`, `routine-hooks.json`; the hooks file holds secrets and is written 0600; the last 50 runs per routine are kept, at most 10 of them skipped), `routineRunner.ts` (starts a run in a new or existing chat or group room, with at most 5 unfinished runs per routine) and `scheduler.ts` (one timer for the next due routine; a missed run is marked late). A run that needs a tool approval stays `waiting`, and the Routines tab shows a dot. `http/hooks.ts` serves `/hooks/<id>` before the gate, because callers have no session: it takes only the routine's own secret in the `X-ZumiBot-Secret` header, or a GitHub signature made with it (see [Workflows](workflows.md)) (a missing or wrong one is a plain 401, never a login redirect), caps the body at 1 MiB and allows 60 valid calls a minute per routine. A webhook draft that is never saved is swept at server start once it is older than 24 h. A `new-chat` or `new-group` target may carry `title` (at most `ROUTINE_CHAT_TITLE_MAX`, 100; each run's chat or room is named that, else `<routine name> · <date>`, `defaultRunTitle`), and a `new-group` one `section`, a sidebar section id: the runner puts each run's room first in that section (`SidebarStore.placeFirst`, broadcast as `sidebar:changed`; a failed write is logged and the run goes on), a section deleted since leaves it outside them, and the editor then shows **Outside sections** (`shownSection`). A single chat has no section to pick, since it always shows under its agent. The editor's header matches the workflow editor's: the name, an **Unsaved** pill while there are unsaved edits, On/Off, Run now, **Cancel** (shown only where it does something: leaving a routine never saved, or putting back the saved one) and **Save** (also Ctrl+S; off while the draft has problems, and, as in the workflow editor, off for a saved routine with no unsaved edits). What still stops a save is listed in the side column's first card, **Before you save** (`ProblemsCard` in `HowItWorks.tsx`), above How it works or Recent runs; a failed save and the restore note show in a banner under the header. On a phone (one column) that card comes first, over the form, and the name shares its row with the ⋯ menu. Its ⋯ menu matches the workflow editor's too: **Duplicate** ("Save and duplicate" while there are unsaved edits or the routine was never saved; `routines:duplicate`, `RoutineStore.copy`) adds an off copy named `<name> (2)` (`copyTitle`) with the same trigger, target, prompt, command and policies, no runs, and for a webhook routine a hook of its own (new URL and secret) holding the source's latest call, or its saved sample, so the copy saves again; **Discard changes** puts the saved routine back; **Delete**. Prompts can hold `{{body.field}}` placeholders filled from the call (`shared/src/routineFields.ts`). Two per-routine settings (the editor's `PolicyCard.tsx`; absent in older routines, read through `limitPolicyOf`/`missedPolicyOf`): `limitPolicy` and `missedPolicy`. `limitPolicy` is `wait` (default) or `skip`. A rejected `rate_limit_event` (`streamParser` `limited`, with its `resetsAt`) makes `agentTurn` stamp the turn's error item with `limit` (plus `agent` in rooms). The runner then skips the run, or makes it `limited` until 60 s past the reset and sends `continue` in the same chat (`@member continue` in a room), at most 5 waits per run. A user message meanwhile ends it as "Continued by hand". The wait is stored on the run (`resumeAt`), so `recover()` re-arms it after a restart (except for a routine that is off: that is a synced copy, and any write would overwrite the VPS's newer-wins runs file), and `runner.stop()` holds it at shutdown. `missedPolicy` is `run-once` (default) or `skip`: a late schedule run becomes a `skipped` run with `skipReason: 'missed'`. A routine that posts into an existing chat or room also has `sessionPolicy` (read through `sessionPolicyOf`; shown in `PolicyCard.tsx` only for an existing chat): `continue` (default) resumes each agent's session, while `fresh` makes `RoutineRunner.startFresh` set `next` to `{seed: true, fresh: true}` for the chat, or for every room member that has a session, and drop their old meters, before the run's message goes in. Each of those agents then starts a new session seeded from the chat's recent messages (the reseed path, capped like any seed) instead of reloading a big context whose cache expired overnight, and the chat shows the `fresh` divider instead of `expired`. A room member that does not speak in the run starts fresh at its next turn. Design: `docs/superpowers/specs/2026-11-02-routine-policies-design.md`.
