# Routines and Remembered Approvals Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let agents work unattended. Part 1 adds "Allow always for this agent", remembered on the server. Part 2 adds
Routines: a schedule, manual or webhook trigger that sends a prompt to an agent or group, in an existing chat or a new
chat per run. Part 2 also fixes the Local-mode port so webhook URLs survive restarts.

**Architecture:**
- **Shared code:** schedule math and webhook-field helpers live in `@zumibot/shared`, so the UI preview and the
  server use one implementation.
- **Server:**
  - `ApprovalStore` (agent rules, `approvals.json`) is consulted by `ChatService`.
  - `RoutineStore` (three data-dir files) feeds a `RoutineRunner`, which sends through the existing `TaskQueue.submit`.
  - A scheduler with one timer.
  - A `/hooks/<id>` HTTP route that is handled before the session gate.
- **UI:** a rail switches between today's Agents views and a Routines sidebar plus editor (layout B in the mockups).

**Tech Stack:** TypeScript, Node ≥ 22 (`Intl` time zones), `ws`, React 19, Tiptap (already a dependency), vitest,
Electron shell, playwright-core e2e. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-27-routines-design.md`. Mockups and the user's reference screenshots are in
`docs/superpowers/specs/2026-10-27-routines/`.

## Global Constraints

- **Never commit.** The user's global rule: do not run `git commit` unless the user explicitly says so. Each task ends
  by leaving the work uncommitted and reporting what changed.
- No new dependencies. The cron/schedule calculator is in-house. Dependencies stay pinned to exact versions.
- A new API method touches three places: `ZumiBotApi` in `zumi-bot-server/shared/src/types.ts`, its handler in
  `backend/src/rpc/handlers.ts` (checks every argument with `str()`, `strings()`, …), and its mapping in
  `frontend/src/net/api.ts`. New server events go in `RpcEvent` (`shared/src/rpc.ts`).
- Never add `--dangerously-skip-permissions` or `bypassPermissions`. Routine runs wait on approval cards like any chat.
- Secrets (the webhook secret) never go into logs, URLs, error messages or broadcast pushes. Compare in constant time.
- The server stays bound to `127.0.0.1`.
- Comments are short and say *why*. Match the surrounding code's naming and idiom.
- Exact values:
  - Card button copy: `Allow always for this agent`.
  - Webhook URL: `<origin>/hooks/<id>`. Secret header: `X-ZumiBot-Secret`.
  - Webhook body limit: `1_048_576` bytes. Valid calls: at most `60` per minute per routine.
  - At most `5` unfinished runs per routine. Runs kept per routine: `50`.
  - Webhook drafts are dropped after `24h`.
  - Local-mode default port: `4318`.
  - New-chat title: `<routine name> · <Mon D>` (e.g. `Daily AI digest · Oct 27`), formatted in the routine's time
    zone.
- Test commands: `npx vitest run <file>`, `npx vitest run --project <shared|frontend|backend|zumibot> -t "<name>"`.
  Before calling any task done, run `npm run typecheck` at the repo root.

## Review Focus

1. **Server time zone ≠ user time zone, across DST.** A routine saved from a browser in `America/New_York` fires at
   07:00 New York wall time on the VPS (UTC) before and after the March and November switches. Test in Task 5.
2. **Huge or odd webhook bodies.** A top-level JSON array, deep nesting, or thousands of keys must still give a bounded
   field list: at most 500 fields and depth 10, with the extras dropped. A plain-text body becomes `body`. Test in
   Task 6.
3. **`{{…}}` in non-webhook prompts.** A scheduled prompt that contains literal `{{x}}` is sent unchanged, and
   rendering only applies to webhook runs. Test in Task 8.
4. **A save or Run now racing a scheduled tick.** One tick gives exactly one run, even when `rearm()` is called while a
   fire is in progress, or when two tabs save at once. Test in Task 9.
5. **An agent renamed while its routine has a run waiting.** The waiting run keeps tracking its chat, and the routine's
   target follows the new name through both rename paths. Test in Task 11.
