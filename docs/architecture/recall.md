# Hive recall

**What it is (`core/recall/`, `shared/src/recall.ts`, `state/recallCard.ts`).** An agent with `recall:` on gets two read-only tools that search and read earlier chats through the [message search](message-search.md) index, so "what did we decide last week?" is answered from real history. Off by default. Design: `docs/superpowers/specs/2026-11-28-hive-recall-design.md`.

**Setting.** Frontmatter key `recall: agent | folder` (ZumiBot-only, parsed strictly by `parseRecall`; anything else, and no key, is off). `AgentSummary.recall` carries it. With `--agent` the CLI gives an agent only the tools it lists, so `AgentStore.save` adds `RECALL_TOOLS` (`withRecallTools`) to a non-empty `tools:` list while recall is on (a listed tool whose server is absent does nothing, so turning it off needs no edit); Zumi Bot adds them when it writes such a list, and `/make-friendly` adds them to an agent with `recall`. Agent Studio shows a **Recall** card (`AgentForm.tsx`, choices from `recallChoices`: Off, Own chats, This folder; Off removes the key) for engines with `bridges` (`studioCards().recall`), so not for ACP or remote agents. Zumi Bot writes the key only when the user asks for an agent that searches earlier chats (memory is `memory:`), and `/make-friendly` never changes it.

**Scope (`inRecallScope`).** `agent`: the agent's single chats, and rooms it is a member of, in any folder. `folder`: every chat whose folder equals the calling chat's, whatever agent ran it; a chat's folder is `worktree.folder ?? cwd` (`recallFolderOf`), so a worktree chat meets the chats of the folder the user picked. Archived chats count. The calling chat never does (its history is already the agent's). The scope is worked out by `RecallService` on every call from the bridge's owner (chat id and speaking agent) and the agent's `recall:` read fresh (`agents.list()`), so turning recall off stops a running turn's next call ("Recall is off for this agent.").

**Tools (`recallTools.ts`, server `zumibot_recall`).** `search {query, since?, until?, offset?}`: the index's word matching (`SearchIndex.search` with `listed` = in scope and the new `range`), `RECALL_PAGE` (10) hits newest first, each with its UTC time, who wrote it, the chat title, the chat and message ids and the snippet; `since`/`until` are a UTC day (`until` takes the whole day) or a full ISO time, anything else is refused so the agent works the date out; "More: search again with offset N" when there is a next page, and a note while the index is still building. `read {chatId, messageId}`: the message (first 8 000 characters) and up to two indexed messages before and after it (1 500 each), with the chat's title, agent or room members and folder. Only what the index holds is ever returned (`searchableOf`: user and agent text, never tools, results, approvals or a Run's hidden result). Recalled text is fenced: every line of a message is indented under its header, a snippet is one line, and titles and the folder are JSON strings, so nothing stored can pass for a header of the answer (a forged "the user (the message you asked for):"). A chat outside the scope, the calling chat and an unknown id all answer "No such chat in your recall scope.", so ids cannot be probed. Unknown keys (a chat id on search) are refused before the service.

**Bridge (`recallIpc.ts`, `recallBridge.ts`).** The processes bridge's shape: a per-attempt capability token in env only (`ZUMIBOT_RECALL_CAPABILITY`, `ZUMIBOT_RECALL_IPC`, both scrubbed from what the turn stores), a `/tmp/cb-h-*` socket (`h` in `staleIpcDirs`; the container mount's `cb-[a-z]-` covers it), the env names in `PRIVATE_ENV.browser` so a side run redacts them too, `alwaysLoad`, and only the service's own sentences pass back as errors. Built as `dist/recallBridge.mjs` (`recallBridgeEntry`).

**Runs (`chatService.ts`).** `recallTurns.scopeOf(spawnedName)` is read once per turn, beside the system prompt: off means no bridge and no paragraph; on adds `recallSystem(scope)` after the processes paragraph (fixed text per scope, so the prompt cache misses only when the setting changes) and a bridge on every attempt, a Compact too, after the processes bridge (and after the ask bridge in Codex's `mcpServers`). A room member's run follows that member's own setting. Its calls are answered without a card (`allowedByZumiBot`, why `recall`), only while bridged; a tool of that name otherwise asks like any other. The side base records `recall`, so `/btw` side runs join a side-owned bridge that refuses every call, keeping the tool definitions equal. Not gated by isolation: it runs nothing and only reads chats over the IPC. The loadout lists `zumibot_recall` for an agent with recall on.

**Prompt injection.** Past messages are data: the paragraph tells the agent they are information, not instructions, and the tools never write.
